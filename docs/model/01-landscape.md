## 开始前：先认识几个最基本的词

| 大模型术语 | 基本解释 |
| --- | --- |
| 模型（Model） | 一个由大量数学运算组成的函数，接收输入并产生预测结果 |
| 参数（Parameter） | 模型通过训练学习到的数值，例如线性层中的权重和偏置 |
| 前向传播（Forward） | 输入依次经过模型中的各层运算，最终得到预测结果和 Loss |
| Loss | 衡量模型预测结果与正确答案之间差距的标量，训练目标通常是让它尽量减小 |
| 梯度（Gradient） | Loss 对某个参数变化的敏感程度，用于确定参数的调整方向和幅度 |
| 反向传播（Backward） | 从 Loss 出发，沿计算图反向计算每个可训练参数的梯度 |
| 设备（Device） | 实际存储张量并执行计算的硬件，例如 GPU 或 NPU |
| Rank | 分布式任务中一个参与进程的编号，通常负责控制一张设备 |
| World Size | 当前通信组中参与计算和通信的 Rank 总数 |

这里最容易混淆的是**参数**和**梯度**：参数是模型当前保存的知识，梯度是当前这批数据对“参数应该怎么改”的建议。优化器读取梯度后才会真正修改参数。

### 为什么训练需要反复执行

模型一开始的参数通常不能很好地完成任务。一次训练迭代只根据一小批数据做一次调整，因此要不断重复：

```text
拿一批数据 → 产生预测 → 计算错误 → 计算梯度 → 更新参数
```

每次迭代都利用当前数据产生的梯度更新参数。随着大量数据被反复用于训练，模型的 Loss 通常逐渐下降，预测能力逐步改善。

### 1. 一家餐厅变成连锁店之后

你训练模型，就像经营一家餐厅：

- **菜谱**（模型参数）= 怎么做菜的全部知识；
- **做生意**（训练）= 每天按顾客反馈调整菜谱：做一批菜（前向）→ 顾客打分（Loss）→ 分析哪道菜该改（梯度）→ 改菜谱（更新参数）。

只有一家店时，一切在店内解决。**单卡训练不需要集合通信**——所有材料、账本、修改意见都在这一家店里。

店做大了要开分店（多张卡），麻烦立刻出现：每家店都在改自己的菜谱，改完之后**各家的菜谱就不一样了**。连锁品牌不允许这种事——必须有人负责"对账"。这个对账系统，就是**集合通信**。

::: details 小测 1：为什么单卡训练不需要集合通信？
因为参数、数据、梯度都在同一张卡内，本地显存读写就能完成一切数据流动。集合通信解决的是"多个 Rank 之间的数据交换与聚合"——没有第二个参与者，就没有这个问题。
:::

### 2. 分店有三种开法，对账方式各不相同

| 开法 | 怎么切 | 产生的对账 |
| --- | --- | --- |
| **数据并行 DP** | 每家店用**同一本菜谱**，接待**不同的顾客** | 各店改菜谱的意见不同 → 意见**汇总求平均**（AllReduce） |
| **张量并行 TP** | **一道菜由多家店合炒**（把一个大矩阵拆开） | 每家只炒出半成品 → 要**拼成完整的一道菜**（AllReduce / ReduceScatter） |
| **流水线并行 PP** | 按工序分店：洗菜店→切菜店→炒菜店 | 半成品**按顺序传给下一家**（点对点发送） |

还有两种变体：**FSDP** 像把菜谱**撕开分家保存**，用之前先拼回完整（AllGather），改完再撕开分回去（ReduceScatter）；**MoE** 像专科分诊，病人要在分店之间转来转去（AlltoAll）。

::: warning 关键
**模型定义计算，并行策略把计算切开，集合通信把切开的数据重新连起来。** 想知道一次通信"为什么存在"，先问"切的是什么"。
:::

::: details 小测 2：数据并行为什么通常需要 AllReduce？
因为每家店（Rank）用不同数据（顾客）算出了不同的修改意见（本地梯度）。如果各改各的，菜谱（参数）会越来越不一样。AllReduce 把所有梯度汇总求平均，让每家拿到同一份意见，改出同一本菜谱。
:::

### 3. 从你敲下一行代码，到对账车出发

在 PyTorch 里你只写了一句 `loss.backward()`，背后是一条完整的物流链：

```text
loss.backward()
→ Autograd 算出梯度（分店整理好意见）
→ DDP 把意见装箱（Bucket）
→ ProcessGroup 发起对账（AllReduce）
→ 昇腾适配层调用 HCCL（物流公司接单）
→ HCCL 选路线和车队（算法、拓扑）
→ Runtime/驱动发车（任务下发）
→ NPU 和互联链路真正运货
```

**HCCL 就是那条物流线**：它住在框架和硬件之间，把"对账"这个抽象要求变成真实的传输任务。

::: details 小测 3：优化一个 AllReduce 算子时，为什么必须知道它来自 DP 还是 TP？
因为来源决定了它的"快递属性"：DP 的梯度对账可以攒大箱、走夜路（不着急、可与计算重叠）；TP 的对账卡在下一道工序前（关键路径、延迟敏感）。同样是 AllReduce，快递的急缓和路线完全不同，优化手法也不同。
:::

### 3 句话带走

1. 单店不需要对账，**多店才需要**——并行为什么产生通信；
2. **切法决定对账方式**：DP 汇总意见、TP 拼半成品、PP 传半成品；
3. `loss.backward()` 到真实传输隔着一条链，**HCCL 是框架和硬件之间的物流公司**。

### 黑话小词典

| 术语 | 人话 |
| --- | --- |
| 参数 / 梯度 | 菜谱 / 这批顾客对"菜谱怎么改"的意见 |
| 前向 / 反向 | 做菜 / 复盘哪道菜该改 |
| Rank / World Size | 一家分店的编号 / 一共几家店 |

## 01-1｜模型训练的主线与系统分层

::: info 本单元目标
围绕 **模型训练的主线与系统分层** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

大模型本质上是一个参数很多、计算量很大的函数。训练时，它会反复执行：

1. 从数据集中取出一批 Token；
2. 前向计算得到预测结果；
3. 用预测与目标计算 Loss；
4. 反向传播计算每个参数的梯度；
5. 优化器使用梯度更新参数。

当模型和数据规模小，一台设备可以完成全部工作。当单卡显存、计算能力或训练时间无法满足要求，就需要把工作拆给多个设备。**一旦拆分，不同设备就必须交换参数、梯度、激活值或 Token，集合通信由此进入大模型系统。**

可以先把整个系统理解为：模型定义计算，并行策略切分计算，通信库负责重新连接被切开的数据。下面以数据并行为例，追踪一个梯度张量怎样从模型中的数学概念，变成设备链路上真正传输的数据块。

### 大模型系统的分层

从上到下可以先建立如下心智模型：

![大模型训练系统分层](/images/llm/llm-system-stack.svg)

| 层次 | 关注对象 | 典型内容 |
| --- | --- | --- |
| 模型与算法 | 模型要算什么 | Transformer、Loss、Optimizer |
| 并行策略 | 计算和数据如何切分 | DP、TP、PP、FSDP、EP |
| 深度学习框架 | 如何表达和调度计算 | PyTorch、Autograd、ProcessGroup |
| 编译与算子 | 如何变成设备任务 | 计算图、Kernel、算子融合 |
| 通信库 | 多设备如何交换数据 | HCCL、NCCL、Collective、P2P |
| Runtime 与驱动 | 如何管理设备资源 | Stream、Event、Memory、Task |
| 硬件与网络 | 任务实际在哪里执行 | NPU/GPU、HBM、片间/节点间互联 |

阅读源码时不要孤立地看某一层。上层决定“为什么通信、通信什么”，下层决定“怎样把通信执行得更快”。

#### 为什么会有这么多层

每一层都在屏蔽下一层的复杂性：

- 模型开发者只想表达“计算什么”，不想管理网卡和链路；
- PyTorch 把模型运算组织成计算图，并负责自动求梯度；
- 分布式框架决定一个张量由哪些 Rank 共同处理；
- HCCL 接收“对这段设备内存做 AllReduce”这样的请求，选择具体通信算法；
- Runtime、驱动和硬件最终把任务提交到 NPU 与链路执行。

因此，同一个操作在不同层有不同说法：

```text
模型视角：同步梯度
框架视角：对梯度张量调用 AllReduce
HCCL 视角：对若干设备内存地址执行归约与传输
硬件视角：DMA 搬运、链路收发、片上计算与同步
```

## 01-2｜并行策略为什么产生通信

::: info 本单元目标
围绕 **并行策略为什么产生通信** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

下面这张图画出了五种并行策略中，模型、数据或 Token 究竟被怎样放在不同设备上。重点观察红色箭头：只有理解“切开的是什么”，才能理解为什么要选择对应的通信原语。

![并行策略与集合通信的关系](/images/llm/parallelism-collectives.svg)

#### 先区分“并发”和“并行策略”

使用多张卡并不自动等于完成了分布式训练。还必须回答：

1. 每张卡保存完整模型，还是只保存一部分？
2. 每张卡处理相同数据，还是不同数据？
3. 某个中间张量是完整的，还是分片的？
4. 下一步计算需要本地分片，还是需要先收集完整数据？

这四个问题决定了需要通信的张量、通信时机和通信原语。

#### Collective 到底是什么

Collective（集合通信）是**通信组内多个 Rank 共同参与的一次操作**。它和普通点对点通信的区别是：

- `Send/Recv`：明确指定发送方和接收方；
- `Collective`：描述整个组最终要达到的数据状态，由通信库安排具体传输步骤。

例如 AllReduce 的语义只是“把所有 Rank 的输入归约，并让所有 Rank 都得到结果”。至于是组成 Ring 还是 Tree、分多少块、走哪条链路，是通信库的实现问题。

#### 常见 Collective 的最小例子

假设有两个 Rank：

```text
Rank 0: [1, 2]
Rank 1: [3, 4]
```

执行求和类型的 AllReduce 后：

```text
Rank 0: [4, 6]
Rank 1: [4, 6]
```

而 AllGather 是把分片按顺序收集：

```text
操作前：Rank 0 持有 [A]，Rank 1 持有 [B]
操作后：Rank 0、Rank 1 都持有 [A, B]
```

ReduceScatter 可以先粗略理解为 AllReduce 的结果再切分：

```text
先把各 Rank 对应位置的数据相加，再让每个 Rank 只保留结果的一部分
```

#### 数据并行（DP）

每张卡保存完整模型，处理不同的数据。每张卡算出的梯度不同，因此更新参数前必须同步梯度，典型操作是 **AllReduce**。

#### 张量并行（TP）

把同一个矩阵乘法切到多张卡。某一层的局部输出需要组合后才能进入下一步，常见操作是 **AllReduce、AllGather、ReduceScatter**。

#### 流水线并行（PP）

把不同网络层放在不同设备，设备之间传递激活值与梯度，主要表现为相邻 Stage 的 **Send/Recv**。

#### ZeRO / FSDP

把优化器状态、梯度甚至参数分片保存。计算前后需要临时收集或重新分片，核心操作通常是 **AllGather** 和 **ReduceScatter**。

#### 专家并行（EP）

MoE 模型把不同专家放到不同设备，Token 要被路由到对应专家，典型操作是 **AlltoAll**。

## 01-3｜从 PyTorch 调用到 HCCL

::: info 本单元目标
围绕 **从 PyTorch 调用到 HCCL** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

以数据并行梯度同步为例。反向传播从最后一层向前执行，某个梯度 Bucket 填满后就可以立即发起 AllReduce，不需要等待所有梯度生成。图中蓝色是反向计算，红色是 HCCL 通信，它们重叠得越多，通信暴露在训练关键路径上的时间就越少。

![从反向传播到 HCCL 的概念调用链](/images/llm/pytorch-to-hccl.svg)

```text
Transformer 训练
  → loss.backward()
  → DDP 梯度同步逻辑
  → PyTorch distributed / ProcessGroup
  → Ascend PyTorch 适配层
  → HCCL AllReduce API
  → HCCL 算法、拓扑与传输执行
  → NPU、片间互联与节点间网络
```

这不是具体版本的源码函数清单，而是后续阅读代码时用于定位职责的概念地图。

### 集合通信算子开发需要的四种视角

#### 1. 语义视角

输入数据分布是什么？操作完成后，每个 Rank 应该得到什么？

#### 2. 算法视角

数据被切成几块？经过几轮？每轮谁向谁发送？总通信量是多少？

#### 3. 系统视角

拓扑、链路、内存、Stream、同步和并发怎样影响执行？

#### 4. 模型视角

这个 Collective 是由哪种并行策略触发的？位于前向还是反向？是否处于关键路径？能否与计算重叠？

只懂通信 API 容易看不清优化价值；只懂模型又容易忽略真正的硬件瓶颈。后续学习会不断在这四种视角之间切换。

### 一组贯穿课程的基础概念

#### 张量与设备内存

张量在模型代码中是一个带 shape 和 dtype 的数学对象；执行时，它最终对应一段设备内存。通信库通常不理解这段数据代表“梯度”还是“激活”，它更关心：

- 起始地址在哪里；
- 有多少个元素；
- 每个元素是什么数据类型；
- 使用什么归约操作；
- 哪些 Rank 参与通信。

#### 同步与等待

如果 Rank 0 已经进入某个 Collective，而 Rank 1 还在计算，Rank 0 可能需要等待。分布式性能问题经常不是链路本身太慢，而是不同 Rank 到达通信点的时间不一致，这叫负载不均衡或 Straggler 问题。

#### 带宽与时延

- **时延（Latency）**：一次通信从发起到开始产生有效结果的固定成本；
- **带宽（Bandwidth）**：稳定传输阶段每秒能搬运多少数据；
- 小消息更容易受时延支配，大消息更容易受带宽支配。

后续会使用简化模型 `T ≈ α × 通信轮次 + β × 数据量` 分析通信算法，其中 `α` 代表单轮启动时延，`β` 代表传输单位数据的时间。

### 参考答案

建议先独立回答，再展开核对。

::: details 1. 为什么单卡训练不需要跨设备集合通信？

因为模型参数、输入、激活和梯度都在同一设备内，数据可以通过本地显存读写完成流动，没有其他 Rank 需要交换数据。

单卡内部仍然存在不同计算单元之间的数据搬运与同步，但这不属于“跨设备集合通信”。集合通信解决的是多个 Rank 共同参与的数据交换与聚合问题。

:::

::: details 2. DDP 为什么通常需要 AllReduce？

DDP 在每个 Rank 上保存相同的完整模型，但给不同 Rank 分配不同数据。不同数据会产生不同的本地梯度：

```text
Rank 0 → 数据 A → 梯度 dW₀
Rank 1 → 数据 B → 梯度 dW₁
```

如果两个 Rank 直接使用各自的梯度更新模型，参数会逐渐不同，模型副本便不再一致。AllReduce 可以把所有本地梯度求和或求平均，并让所有 Rank 得到相同结果，因此每个模型副本会执行相同更新。

:::

::: details 3. FSDP 为什么常见 AllGather 和 ReduceScatter？

FSDP 平时让每个 Rank 只保存一部分参数，以减少单卡显存占用。某一层开始计算前，需要把其他 Rank 的参数分片临时收集起来，这对应 AllGather。

反向传播得到完整梯度后，需要在多个 Rank 间完成梯度聚合，但每个 Rank 最后只保留自己负责的梯度分片，这对应 ReduceScatter。

```text
计算前：参数分片 --AllGather--> 临时完整参数
反向后：完整梯度 --ReduceScatter--> 聚合后的梯度分片
```

:::

::: details 4. MoE 为什么容易产生 AlltoAll？

MoE 把不同专家部署到不同设备，而一个 Rank 当前持有的 Token 可能被路由到任意专家。因此每个 Rank 都可能向其他多个 Rank 发送 Token，同时从其他 Rank 接收 Token。

专家计算完成后，还要把输出送回 Token 原来的位置。这个“多对多交换”的数据模式与 AlltoAll 的语义相符，通常会出现一次分发和一次回传。

:::

::: details 5. 从 loss.backward() 到设备执行，中间大致经过哪些层？

概念调用链是：

```text
loss.backward()
→ Autograd 沿计算图生成梯度
→ DDP Hook 发现梯度或 Bucket 就绪
→ ProcessGroup 发起 Collective
→ 昇腾框架适配层调用 HCCL
→ HCCL 选择算法、拓扑与传输方式
→ Runtime / 驱动提交任务
→ NPU 与互联链路执行
```

不同软件版本的具体函数名会变化，但各层职责基本保持一致。

:::

::: details 6. 优化 AllReduce 时，为什么需要知道它来自 DP 还是 TP？

因为来源决定通信所处的模型位置、消息大小、调用频率以及它能否与计算重叠：

- DP AllReduce 通常聚合参数梯度，可以按 Bucket 启动，并与反向计算重叠；
- TP AllReduce 常位于某一层的前向或反向关键路径，下一步计算可能必须等待结果，延迟更敏感；
- 两者的通信组规模和拓扑也可能不同。

只优化通信算子本身的峰值带宽，不一定能改善端到端训练性能。必须先知道它在整个计算图中为什么出现、谁在等待它。

:::
