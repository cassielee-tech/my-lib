# AI Agent 工程化知识树：从模型接入到生产治理

> 本文根据《AI Agent 工程化知识树》思维导图整理。原图中的案例和数字已转换为更通用的工程表述，避免把特定模型、框架或一次 Benchmark 的结果当成固定结论。

## 本章导学

::: tip 本文只记住 3 件事
1. 生产 Agent 包含模型基座、数据记忆、控制流、工具执行和生产治理五层。
2. 模型负责建议动作，可信宿主程序负责参数校验、授权和真实执行。
3. Agent 能上线的标准不是“能跑 Demo”，而是可恢复、可观测、可评测、可审计。
:::

**建议节奏：** 核心路径 12 分钟；全文较长，建议按五层拆成 3 次阅读，每次 15～20 分钟。

**15 分钟主线：** 五层知识树、生产请求闭环和最后的生产就绪检查表。

- [ ] 我能说出五个工程层次
- [ ] 我能解释 Function Calling 的执行者是谁
- [ ] 我能为一个 Agent 找出缺失的治理能力

## 1. 先建立全景

一个能演示的 Agent，可能只需要模型、Prompt 和几个工具；一个能进入生产环境的 Agent，还要处理模型故障、状态恢复、权限、安全、成本、评测和可观测性。

可以把 Agent 系统拆成五个层次：

![AI Agent 工程化五层知识树](/images/agent/agent-engineering-tree.svg)

| 层次 | 核心问题 | 典型组件 |
| --- | --- | --- |
| 基础设施与模型基座 | 模型如何稳定、经济地提供能力？ | API Gateway、推理引擎、缓存、限流 |
| 数据与记忆 | Agent 从哪里获取上下文和长期知识？ | 会话记忆、Embedding、向量库、RAG |
| 大脑与控制流 | 多步骤任务怎样规划、重试和恢复？ | Structured Output、State Machine、Checkpointer |
| 动作与工具 | 模型怎样安全地影响外部世界？ | Function Calling、MCP、Sandbox、HITL |
| 生产治理 | 怎样知道它正确、稳定、安全且成本可控？ | Trace、Eval、审计、告警、版本治理 |

这五层不是五个独立服务，而是同一条请求链路中的不同职责。

## 2. 一次 Agent 请求怎样流动

![生产级 Agent 的请求执行闭环](/images/agent/agent-production-loop.svg)

```text
用户请求
  → 身份校验、配额与风险检查
  → 加载会话状态和相关知识
  → 模型判断下一步动作
  → 参数校验与权限检查
  → 宿主程序执行工具
  → 结果写回状态
  → 继续规划或生成最终答案
  → 记录 Trace、Token、延迟和评测数据
```

如果工具失败，系统不应只是把异常文本塞回模型无限重试。它需要明确的超时、重试上限、幂等策略、降级路径和人工接管点。

## 3. 第一层：基础设施与模型基座

### 3.1 模型接入与 API Gateway

企业往往同时使用云端模型、私有模型和不同供应商。API Gateway 为业务提供相对稳定的统一入口。

主要职责包括：

- **协议适配**：把不同模型的请求、流式事件、工具调用和错误码转换为内部统一协议；
- **模型路由**：根据任务类型、延迟、价格、上下文长度和数据等级选择模型；
- **负载均衡**：在经过授权的 Endpoint 和额度范围内分发请求；
- **超时与熔断**：模型持续失败时快速阻断，防止故障扩散；
- **降级策略**：主模型不可用时切换备用模型或返回受限能力；
- **用量核算**：记录 Prompt、Completion、Cache Token 和费用；
- **租户隔离**：不同用户、团队和应用拥有独立配额与权限。

::: warning 统一协议不等于能力完全一致
“OpenAI-compatible”通常只表示接口形态相似。不同模型在 Tool Calling、Structured Output、上下文长度、流式事件和错误语义上仍可能不同，网关不能假装这些差异不存在。
:::

多账号、多密钥负载均衡必须遵守供应商条款和每个租户的合法配额，不能把“绕过 Rate Limit”作为系统设计目标。

### 3.2 本地推理引擎

数据敏感、成本稳定性或低延迟要求较高时，可以评估私有化部署，但它并不是所有敏感业务的唯一方案。还可以使用专有云、数据不留存 API、可信执行环境或脱敏等措施。

本地推理常见能力：

| 技术 | 解决的问题 | 注意事项 |
| --- | --- | --- |
| Paged Attention | KV Cache 按 Block 分配，降低预留浪费和碎片 | 不保证固定的显存利用率 |
| Continuous Batching | 请求完成后立即补入新请求，提高设备利用率 | 调度会影响 TTFT 与 TPOT |
| Quantization | 以 INT8/INT4 等低位格式存储权重 | 节省比例和精度损失依模型与 Kernel 而定 |
| Prefix Cache | 相同前缀复用已计算的 KV | 需要设计命中、淘汰和租户隔离 |
| Speculative Decoding | 用草稿模型一次提出多个候选 Token | 收益取决于接受率和验证成本 |

不能仅凭“7B 模型”推断显存。还需要知道精度、量化元数据、KV Cache、Batch、上下文长度和运行时 Workspace。

### 3.3 流式输出与取消传播

HTTP 一次性返回适合短结果；大模型生成时间较长时，SSE、WebSocket 或流式 RPC 可以更早展示结果，改善用户感知延迟。

完整链路必须支持取消传播：

```text
用户点击停止
  → 前端终止请求
  → API Server 感知连接取消
  → Orchestrator 停止后续节点
  → 模型服务终止生成
  → 工具任务按安全策略取消或等待收尾
  → 释放 KV Cache、连接和临时资源
```

如果只断开前端连接，底层模型仍继续生成，就会产生“用户看不到、系统仍付费”的无效计算。

## 4. 第二层：数据、记忆与 RAG

### 4.1 记忆不是把所有历史都塞进 Prompt

Agent 的记忆可以分为：

| 类型 | 保存内容 | 生命周期 |
| --- | --- | --- |
| 工作记忆 | 当前任务目标、中间结果、待办和错误 | 一次任务 |
| 会话记忆 | 最近对话及其摘要 | 一次或多次会话 |
| 长期语义记忆 | 文档、规范和事实知识 | 持久化 |
| 长期情景记忆 | 用户过去做过什么、系统发生过什么 | 持久化且需权限控制 |

上下文窗口是模型当前能看到的输入，数据库才是持久存储。二者不能混为一谈。

### 4.2 短期记忆

最简单的实现是保存最近 $N$ 轮对话，但生产系统应按 Token Budget 而不是只按轮数截断：

```text
System 指令
+ 当前用户输入
+ 工具定义
+ 检索资料
+ 最近对话
≤ 模型上下文预算
```

历史过长时可以生成摘要，但摘要是有损压缩。应保留重要实体、决策、未完成事项和来源引用，并允许回到原始记录核验。

Redis List、ZSet 或关系数据库都可以保存会话，选择取决于查询模式、持久性和一致性需求，而不是“Agent 必须使用 Redis”。

### 4.3 长期记忆与异步 Embedding

文档进入向量库前通常经历：

```text
数据源 → 解析 → 清洗 → 切片 → 元数据 → Embedding → 索引
```

大规模入库可用消息队列解耦解析、Embedding 和写入，以实现削峰、失败重试与断点恢复。每条记录应保存 Embedding 模型版本；更换模型后，旧向量和新向量不能默认处于同一空间。

冷热分层也不是简单地把“旧数据”全部移走。应结合访问频率、业务价值、合规保留期和召回要求决定存储层级。

### 4.4 知识预处理

RAG 效果很大程度取决于数据质量：

- 按标题、段落、代码块或表格结构切片；
- 使用适度 Overlap，避免关键语义被边界截断；
- 保存来源、章节、时间、作者、租户和权限等元数据；
- 删除模板噪声、重复页眉页脚和不可解释乱码；
- 为文档更新设计版本、删除和重新索引流程；
- 解析 PDF 表格、图片和扫描件时保留结构关系。

固定“500 字、重叠 50 字”只是起点，不是所有文档的最佳参数。

### 4.5 混合检索、RRF 与 Rerank

向量检索擅长语义相似，BM25 更擅长错误码、函数名和专有名词等精确关键词。常见检索链路是：

```text
Query
  ├─ BM25 关键词检索 ─┐
  └─ Vector 语义检索 ─┤→ RRF / 加权融合 → Reranker → Top-k Context
                       ┘
```

RRF（Reciprocal Rank Fusion）按多个结果列表中的排名融合：

$$
score(d)=\sum_{r\in R}\frac{1}{k+rank_r(d)}
$$

它不要求 BM25 分数与向量相似度处于同一数值尺度。随后可用 Cross-Encoder 对 Query 与候选文档进行更精确的相关性判断。

元数据过滤应在向量检索前尽量缩小合法范围，但“提速几十倍”并非固定结论，取决于数据规模、过滤选择性和索引实现。

### 4.6 GraphRAG 适合什么

当问题依赖实体关系、多跳路径和网络拓扑时，可将实体与关系保存在图数据库，再与文本检索组合。例如：设备 A 连接设备 B、B 属于某集群、某故障影响哪些上游服务。

GraphRAG 增加了实体抽取、关系维护和查询规划成本。普通文档问答不应为了追求新概念而强行引入图数据库。

## 5. 第三层：核心大脑与控制流

### 5.1 Prompt as Code

Prompt 不只是自然语言文案，更像模型与宿主程序之间的接口契约。它应具备：

- 明确的目标和边界；
- 不同来源内容的结构化分区；
- 工具选择和输出格式约束；
- 无法完成时的行为；
- 版本号、测试集和变更记录。

XML 或 Markdown 标签能帮助模型区分区域，但只是提示结构，不能构成真正的安全边界，也不能自动阻止 Prompt Injection。

### 5.2 Structured Output

当后端要反序列化模型输出时，应优先使用模型 API 的 JSON Schema/Structured Output 能力，并在宿主程序再次校验：

```text
模型生成 JSON
  → Schema 校验
  → 业务规则校验
  → 权限检查
  → 执行或返回模型修复
```

“JSON Object”只保证语法上可能是 JSON，不一定满足字段类型、枚举、必填项和业务规则。

### 5.3 从线性脚本到状态机

单步任务可以顺序执行；包含分支、循环、重试、审批和长时间等待的任务，更适合显式状态机或有向图。

```text
State = {
  goal,
  current_step,
  tool_results,
  retry_count,
  error,
  approval_status
}
```

- **Node**：执行模型调用、工具调用或确定性代码；
- **Edge**：无条件转移；
- **Conditional Edge**：根据 State 选择下一节点；
- **Checkpointer**：在关键节点持久化 State；
- **Interrupt**：暂停并等待人工输入；
- **Resume**：从已保存状态继续执行。

显式状态比把全部进度藏在对话文本里更容易调试、恢复和审计。

### 5.4 ReAct 的工程表达

ReAct 的核心是“根据当前状态选择动作，观察外部结果，再决定下一步”。生产系统不需要强迫模型向用户暴露完整内部思维过程，可以记录结构化的：

```text
当前状态 → 选择工具 → 工具参数 → 观察结果 → 下一状态
```

这已经足够用于执行、追踪和评测。

### 5.5 Multi-Agent 不是默认答案

常见协作模式：

- **Supervisor**：中央 Agent 分配任务给专业 Agent；
- **Router**：按输入类型路由到不同 Agent；
- **Critic/Reviewer**：独立检查结果并要求修订；
- **Parallel Workers**：并行研究互不依赖的子问题；
- **Handoff**：一个 Agent 将状态和责任移交给另一个 Agent。

只有当任务确实存在专业边界、并行价值或独立审核需求时才引入 Multi-Agent。否则它会增加 Token、延迟、错误传播和调试难度。

## 6. 第四层：动作与工具链

### 6.1 Function Calling 的本质

LLM 通常不会因为生成了一段 JSON，就自动访问数据库或执行命令。它负责提出结构化的工具调用意图，宿主程序负责校验和执行。

标准生命周期是：

1. **Define**：宿主程序向模型提供工具名称、说明和参数 Schema；
2. **Select**：模型选择工具并生成参数；
3. **Validate**：宿主程序验证 Schema、权限和业务约束；
4. **Execute**：真正调用函数、API、数据库或沙盒；
5. **Return**：以 Tool Result 形式把结果送回模型；
6. **Continue**：模型继续调用工具或生成最终答案。

::: danger 模型输出不是可信指令
工具名、参数、路径、SQL 和 URL 都是不可信输入。即使 Schema 校验通过，也必须进行权限、资源范围和业务规则校验。
:::

### 6.2 MCP 解决什么

MCP（Model Context Protocol）把 Agent 与外部能力之间的连接标准化。可以先理解为：

```text
Agent Host
  └─ MCP Client ← 协议连接 → MCP Server
                                 ├─ Tools
                                 ├─ Resources
                                 └─ Prompts
```

Function Calling 描述一次模型怎样表达工具调用；MCP 更关注应用怎样发现、连接和调用外部能力。使用 MCP 不会自动解决认证、授权、网络隔离和工具安全。

### 6.3 Sandbox 与权限边界

高风险工具应放入隔离环境，并组合以下机制：

- 默认最小权限；
- 文件目录、网络域名和命令白名单；
- CPU、内存、磁盘、时长和输出大小限制；
- 临时环境和任务结束后的清理；
- 密钥按调用注入，不直接暴露给模型；
- 写入、删除、发送、支付等操作进行人工审批；
- 全量审计工具名称、参数、调用者与结果。

Human-in-the-loop 不应只做成一个“确认”按钮。审批界面要明确展示将执行什么、影响什么资源、能否撤销。

## 7. 第五层：生产治理与高可用

原思维导图只列出了这个主干。生产落地时，至少需要补齐以下内容。

### 7.1 可观测性

一次 Trace 应能串起：

```text
用户请求
  → 模型路由
  → Prompt / Context 版本
  → 每次模型调用
  → 每次工具调用
  → RAG 检索与引用
  → 状态转移
  → 最终结果
```

关键指标包括成功率、端到端延迟、TTFT、模型/工具错误率、Token 与费用、缓存命中率、检索召回、重试次数和人工接管率。

日志要脱敏。可观测性不能成为泄露 Prompt、密钥和用户隐私的新风险。

### 7.2 评测体系

Agent 不能只评最终答案，还应分层评估：

| 层次 | 评测问题 |
| --- | --- |
| 模型 | 是否理解目标并输出合法结构？ |
| 检索 | 是否召回正确资料，引用是否支持结论？ |
| 工具 | 是否选择正确工具和参数？ |
| 轨迹 | 是否走了合理步骤，有无无效循环？ |
| 结果 | 最终任务是否正确完成？ |
| 安全 | 是否越权、泄露数据或受注入影响？ |
| 系统 | 延迟、费用、稳定性是否达标？ |

评测集应包含正常样本、边界样本、工具故障、恶意输入和历史线上回归样本。Prompt、模型、检索或工具变更后都应运行回归评测。

### 7.3 高可用与一致性

- 对暂时性错误使用有上限的指数退避重试；
- 对写操作使用 Idempotency Key，避免重试造成重复发送或扣款；
- 用 Circuit Breaker 阻断持续失败的依赖；
- Checkpoint 在可恢复性和写入成本之间选择粒度；
- 区分“工具实际成功但响应丢失”和“工具没有执行”；
- 对超时任务保留人工查询和补偿入口；
- 为模型、Prompt、工具 Schema 和知识库建立版本关联。

### 7.4 安全治理

生产 Agent 面临的风险包括 Prompt Injection、间接注入、越权工具调用、数据外泄、恶意文件、SSRF、命令注入和供应链风险。

核心原则是：

> 模型负责建议，可信宿主负责授权；自然语言负责表达意图，确定性代码负责执行安全策略。

## 8. 一张生产就绪检查表

### 模型与网关

- [ ] 是否有明确的超时、重试、熔断和降级？
- [ ] 是否按租户记录 Token、费用、配额和模型版本？
- [ ] 不同模型的工具与流式协议差异是否显式处理？

### 数据与记忆

- [ ] 上下文是否按 Token Budget 组装？
- [ ] 长期记忆是否有租户和权限过滤？
- [ ] 文档是否支持更新、删除、重建索引和版本追踪？
- [ ] 检索结果是否保留来源并能核验？

### 工作流

- [ ] State 是否显式、可持久化、可恢复？
- [ ] 循环是否有最大步数和预算？
- [ ] 重试是否区分可恢复错误与永久错误？
- [ ] 高风险节点是否支持暂停和审批？

### 工具与安全

- [ ] 工具参数是否同时进行 Schema 和业务校验？
- [ ] 是否采用最小权限、沙盒和资源限制？
- [ ] 写操作是否幂等、可审计、尽量可撤销？
- [ ] 密钥是否与模型上下文隔离？

### 质量与运维

- [ ] 是否存在离线评测集和线上反馈闭环？
- [ ] 是否能追踪一次任务的模型、检索、工具和状态节点？
- [ ] 告警能否定位到租户、模型、工具和依赖服务？
- [ ] 版本发布是否有灰度、回滚和回归评测？

## 9. 推荐学习顺序

如果有传统后端经验，可以按下面顺序推进：

```text
Function Calling
  → 显式状态与单 Agent 循环
  → Structured Output 与错误恢复
  → MCP 与工具权限
  → RAG 与记忆
  → Checkpoint / HITL
  → Eval / Trace / 安全
  → Multi-Agent
  → 推理性能与大规模治理
```

不建议一开始就搭建复杂 Multi-Agent 平台。先把一个 Agent 的状态、工具、失败恢复和评测做好，再扩展角色数量。

## 10. 小结

- Agent 工程化不是给模型套一层 API，而是构建可恢复、可观测、可评测、可授权的执行系统；
- 模型网关屏蔽接口差异，但不能抹平不同模型的能力差异；
- 记忆需要分层，RAG 需要完整的数据处理、检索、融合与重排链路；
- 复杂任务应使用显式 State、条件边、Checkpoint 和中断恢复；
- LLM 负责提出工具调用，可信宿主程序负责验证、授权和执行；
- MCP 解决连接标准化，不自动解决工具安全；
- Multi-Agent 只应在专业分工、并行或独立审核确有价值时使用；
- 生产系统必须同时建设 Trace、Eval、安全、成本和高可用机制。
