### 1. 先认人：谁在参与

集合通信发生在一个**小组**里：每个成员有个编号（**Rank**），小组总人数是 **World Size**，小组本身叫**通信域**。同一个员工可以同时在"技术组"和"项目组"——rank 也可以同时在多个通信域里（TP 组、DP 组各一个）。

一次通信就是一场**小组协作动作**：定义它只需两张快照——**开始时每人手里有什么、结束时每人手里有什么**。

::: details 小测 1：为什么"第 3 个 rank"不等于"第 3 张卡"？
rank 是逻辑编号，物理卡的编号（NPU ID/Chip ID/逻辑 ID）可能和它错位。协作快不快取决于物理位置（谁和谁挨着），不取决于编号——谈性能必须把 rank 映射回物理拓扑。
:::

### 2. 六个协作动作：开始谁有什么，结束谁有什么

8 个人的办公室，每人手里一份报表：

| 动作 | 开始 | 结束 | 办公室版本 |
| --- | --- | --- | --- |
| **Broadcast** | 老板有文件 | **全员**有 | 老板群发邮件 |
| **Reduce** | 各有各的 | **只有老板**拿到汇总 | 各组交表，老板汇总 |
| **AllReduce** | 各有各的 | **全员**有汇总 | 每人都要一份汇总表 |
| **AllGather** | 各有一页 | 全员有整本（拼起来） | 每人复印自己那页发全员 |
| **ReduceScatter** | 各有整份 | 汇总后**各拿一块** | 汇总完每人只留自己负责段 |
| **AlltoAll** | 各有发往不同人的包裹 | 定向收到包裹 | 各部门互寄快递 |

**一条黄金恒等式**（背下来，后面全是它）：

```text
AllReduce = Reduce + Broadcast（先交老板再群发）
          = ReduceScatter + AllGather（先分头汇总，再互相补齐）← 优化重点！
```

第二种拆法妙在：**中间状态每人只经手 1/N**——下一课的 Ring 算法就是它的直接实现。

::: details 小测 2：为什么说 AllReduce 的账约是 AllGather 的两倍？
因为 AllReduce 语义上就是 RS+AG 两段接力：每 rank 经手约 2·S·(N−1)/N 字节，而 AllGather 只有一段 S·(N−1)/N。恒等式不只是语义游戏，它直接写在账本上。
:::

### 3. 快递计费：α-β-γ 三本账

任何一次通信的耗时：

$$
T \approx \alpha \times 轮次 + \beta \times 字节/带宽 + \gamma \times 本地计算
$$

- **α = 起步价**：每轮的固定成本（启动、握手、同步）；
- **β = 每公斤运费**：字节搬运时间；
- **γ = 打包费**：本地规约、压缩的计算。

两个世界的分界线：**1 KB 的小消息**，运费忽略不计，起步价说了算——**谁轮次少谁赢**；**1 GB 的大消息**，起步价忽略不计，运费说了算——**谁的链路走得满谁赢**。这句话就是"小消息和大消息选不同算法"的全部原理。

最后记住**两层选型**：先选**原语**（语义层，由数据需求决定，选错了算法再好也白搭——比如用 AllGather+本地求和模拟 AllReduce，多传 N 倍字节）；再选**算法**（实现层，看大小 × 人数 × 拓扑三张牌）。

::: details 小测 3：某代码 AllGather 收集所有 rank 的梯度再本地求和，N=8。比 AllReduce 多传多少？
AllGather 让每 rank 收到全部 8 份完整梯度（8S 字节量级），而 AllReduce 每 rank 只需经手约 2S。多传约 4 倍字节——这不是算法问题，是原语选错了，无法靠优化弥补。
:::

### 3 句话带走

1. 语义=两张快照：**开始谁有什么、结束谁有什么**；六个动作各就各位；
2. 黄金恒等式：**AllReduce = RS + AG**，中间态每人只经手 1/N——一切高效算法的出发点；
3. 三本账：**起步价 α、运费 β、打包费 γ**；小消息比轮次、大消息比链路满载。

### 黑话小词典

## 01-1｜通信的坐标系：Rank、通信域与消息

::: info 本单元目标
围绕 **通信的三个坐标** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

谈原语之前，先把坐标系立起来——三个词定义了所有集合通信的舞台。

### 2. Rank：参与者及其编号

**Rank 是参与一次通信任务的最小逻辑单位**（通常一个进程管一张卡，rank = 进程编号，从 0 起）。配套两个量：

- **World Size**：通信组里 rank 的总数 N；
- **通信域（Communicator）**：一组成员的集合。一个任务可以建多个域（如 TP 组、DP 组各一个），一个 rank 可以同时属于多个域——**同一条物理链路上跑着多个逻辑通信组**，这是后面理解拓扑与并发的钥匙。

::: warning Rank ≠ 设备
rank 是逻辑编号，卡数、芯片、容器都可能让"第几个 rank"和"第几张物理卡"错位（NPU ID/Chip ID/逻辑 ID 三层，见 [CANN 常用命令](../ascend/cann常用命令.md)）。谈拓扑时必须把 rank 映射回物理位置——第 5 章的主题。
:::

#### 2.1 消息：通信的货物

一次通信由**消息**描述：字节大小、数据类型、以及**每个 rank 拿哪一块**（布局）。集合通信的语义差异，本质上就是"出发时各 rank 持有什么、结束时各 rank 持有什么"这两张快照的差别。

#### 2.2 三类通信方式

| 方式 | 谁参与 | 例子 | 特点 |
| --- | --- | --- | --- |
| 单播 P2P | 两个 rank | Send / Recv | 最灵活，要自己管同步 |
| 集合 Collective | 整组 rank | AllReduce 等 | 语义固定，库可全局优化 |
| 集合的积木 | —— | Broadcast / Reduce | 既是原语又是更复杂原语的部件 |

《模型全景》第 1 章说过"并行策略把计算切开、集合通信把数据连起来"——本章给这句话装上发动机。

## 01-2｜六个核心原语的语义卡片

::: info 本单元目标
围绕 **六大原语的输入输出与恒等式** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

设 N 个 rank，每人持有向量的一份（长度 S 字节，或切好的 N 块）。六张卡片只回答：**开始时谁有什么、结束时谁有什么**。

#### 3.1 六张语义卡片

| 原语 | 开始 | 结束 | 谁拿到结果 | 典型用途 |
| --- | --- | --- | --- | --- |
| **Broadcast** | rank 0 有 X | 全员有 X | 全员 | 参数同步、下发指令 |
| **Reduce** | 全员各有 Xᵢ | 归约结果（ΣXᵢ）在 root | 仅 root | 收集汇总到主节点 |
| **AllReduce** | 全员各有 Xᵢ | 全员有 ΣXᵢ | **全员** | DDP 梯度同步 |
| **AllGather** | rank i 只有第 i 块 | 全员有完整拼接结果 | 全员 | TP 拼激活、FSDP 收参数 |
| **ReduceScatter** | 全员各有完整 Xᵢ | rank i 有 ΣX 的第 i 块 | **各拿一块** | FSDP 分发梯度、TP 反向 |
| **AlltoAll** | rank i 持有发往各家的块 | 各家收到定向投递的块 | 定向交换 | MoE 的 Dispatch/Combine |

形状视角（把通信看成张量变形）：

```text
Broadcast:   [S]@root        → [S]@all
AllReduce:   [S]@each        → [S]@all（数值=归约）
AllGather:   [S/N]@each      → [S]@all（拼接）
ReduceScatter: [S]@each      → [S/N]@each（归约+切分）
AlltoAll:    [N 块]@each     → [N 块]@each（按目标重排，总量不变）
```

#### 3.2 一条黄金恒等式

**AllReduce 有两种等价分解**：

```text
AllReduce = Reduce           + Broadcast     （先汇总到 root，再广播）
AllReduce = ReduceScatter    + AllGather     （先分头规约，再拼完整）
```

第二种是重点：它把"人人要全量"拆成两段**每人只经手 1/N 的中间态**——Ring 算法（第 2 章）正是它的直接实现。记住这张拆解图，后面所有算法都是在"怎么高效实现 RS + AG"上做文章。

#### 4. 语义之间的对偶

- **AllGather ↔ ReduceScatter** 互为对偶：一个"拼"、一个"归约后切"；
- **AllReduce** 是"Reduce 的全员版"，也是"RS + AG 的组合体"；
- **AlltoAll 最特殊**：不是"拼/切"，是**定向重分发**——出发前就要知道每块发谁（MoE 的路由结果），这也是它容易失衡的根源（第 4 章）。

## 01-3｜代价模型：α、β、γ 与三本账

::: info 本单元目标
围绕 **α-β-γ 代价模型** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

语义回答"传什么"，代价模型回答"多久"。它与 [HCCL 源码 5](../ascend/hccl-source/05-coll-algorithms.md) 的代价模型是同一套思想。

### 5. 一条公式三本账

$$
T \approx \alpha \times R + \beta \times \frac{Bytes}{BW_{eff}} + \gamma \times C
$$

| 项 | 含义 | 什么时候主导 |
| --- | --- | --- |
| **α（延迟项）** | 每轮通信的固定成本：启动、握手、同步 | **小消息、轮次多的算法** |
| **β（带宽项）** | 真正的字节搬运时间 | **大消息** |
| **γ（计算项）** | 本地规约/打包计算 | Reduce 类操作、压缩打包 |

#### 5.1 两个直觉例子

- **1 KB 的 AllReduce**：字节搬运只要约 1µs，但一次启动就要几十 µs——**α 碾压 β**，选算法要看谁轮次少；
- **1 GB 的 AllReduce**：搬运要几百 ms，α 忽略不计——**β 碾压 α**，选算法要看谁让每条链路走得最满。

**这就是"小消息和大消息选不同算法"的全部原理**（第 3 章展开）。

#### 6. 给每个原语记账：每 rank 经手多少字节

设 N 个 rank、消息总量 S（每人 S/N 块），理想实现下**每 rank 经手的字节数**：

| 原语 | 每 rank 发送 | 每 rank 接收 |
| --- | --- | --- |
| Broadcast | S（root）/ 0（其他） | S |
| Reduce | S | S（root） |
| AllReduce | ≈ 2·S·(N−1)/N | ≈ 2·S·(N−1)/N |
| AllGather | S·(N−1)/N | S·(N−1)/N |
| ReduceScatter | S·(N−1)/N | S·(N−1)/N |
| AlltoAll | ≤ S·(N−1)/N（按路由） | 同左 |

两个要点：

1. **AllReduce 的账最重**（约 2 倍）：因为它语义上等于 RS + AG 两段——恒等式在账本上显形；
2. 账本算的是**理想下界**；真实实现还有 chunk 头、打包、同步开销——实测永远比账本差一点，**差距本身就是调优空间**。

::: tip 与《单卡执行系统》第 5 章 Roofline 的关系
Roofline 是"单算子三本账"（FLOPs/Bytes/峰值），本模型是"通信三本账"（轮次/字节/带宽）。两者在"通信计算重叠"时合流（第 5 章）：总时间 = max(计算, 通信) 的区间才谈得上被隐藏。
:::

## 01-4｜从语义到选型

::: info 本单元目标
围绕 **原语选型的三个维度** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

语义卡片 + 代价账本到手，可以做第一次选型了——注意区分两层：**选原语**（语义层，不能错）和**选算法**（实现层，第 2-3 章的主题）。

#### 7.1 第一层：选原语（由数据需求决定）

从并行策略的**数据需求**倒推原语（《并行策略》的完整版将在课 12-17 展开）：

| 需求 | 原语 | 场景 |
| --- | --- | --- |
| 每人都要同一份归约结果 | AllReduce | DP 梯度同步 |
| 只要 root 要结果 | Reduce | 收集日志、指标 |
| 每人要完整拼接 | AllGather | TP 前拼激活、FSDP 收参数 |
| 归约后各拿一块 | ReduceScatter | FSDP 梯度、TP 反向 |
| 按目标定向重分发 | AlltoAll | MoE Dispatch/Combine |
| 只发一份给全员 | Broadcast | 参数初始化、指令 |

::: warning 常见误用：用错原语
- 用 **AllGather + 本地相加** 实现 AllReduce：多传了 N 倍字节（每人收全量 N 份）；
- 用 **AllReduce 实现 Reduce**：白白让所有 rank 等待并接收不需要的数据；
- 该 **ReduceScatter** 的地方用 AllReduce：多付一倍带宽，还给下游留了切分成本。

原语错一级，性能差几倍——**语义层的错误无法靠算法层弥补**。
:::

#### 8. 第二层：选算法的三个维度（预告）

同一原语有多种算法实现（Ring/Tree/RD……），选型看三个维度：

1. **消息大小**：小消息 α 主导（选轮次少的），大消息 β 主导（选链路满载的）；
2. **rank 数 N**：轮次项随 N 增长的速度不同（Ring 是 O(N)，Tree/RD 是 O(log N)）；
3. **拓扑**：机内/机间带宽差一个量级，非对称拓扑改变一切（第 5 章）。

这三张牌怎么打，正是第 2-3 章的全部内容；而通信库把这套决策自动化，就是 HCCL 里 **selector** 模块的工作（[HCCL 源码 5](../ascend/hccl-source/05-coll-algorithms.md)）。

本章收束：**语义卡片是词汇，α-β-γ 是语法**——下一章用它们完整推导第一个算法：Ring AllReduce。

### 10. 自测题

1. Rank、World Size、通信域分别是什么？
2. 为什么说"rank 是逻辑编号，谈拓扑必须映射回物理位置"？
3. 六个原语各自的"结束时谁拿到什么"？
4. 写出 AllReduce 的两种分解，哪种是优化重点、为什么？
5. AllGather 和 ReduceScatter 的对偶关系是什么？
6. AlltoAll 与其他五个原语的本质区别是什么？
7. 写出 α-β-γ 公式并说明各项何时主导。
8. 为什么 AllReduce 的理想账约是 AllGather 的两倍？
9. 列举两个"选错原语"的例子及其代价。
10. 算法选型看哪三个维度？

::: details 自测答案

1. Rank：参与通信的逻辑单位（通常一进程一卡）；World Size：组内 rank 总数；通信域：一组成员的集合，一个任务可建多个域。
2. 物理卡编号（NPU ID/Chip ID/逻辑 ID）与 rank 编号可能错位；算法性能取决于物理位置（谁和谁近），不取决于逻辑编号。
3. Broadcast 全员有 X；Reduce 仅 root 有结果；AllReduce 全员有归约结果；AllGather 全员有完整拼接；ReduceScatter 各自持有归约结果的一块；AlltoAll 各自收到定向投递给它的块。
4. Reduce+Broadcast 与 ReduceScatter+AllGather。后者是重点：中间态每人只经手 1/N，是 Ring 等高效算法的结构。
5. AllGather 是"拼接"（[S/N]→[S]），ReduceScatter 是"归约后切分"（[S]→[S/N]）——方向相反、互为逆操作的一半。
6. AlltoAll 不是"拼/切"而是**定向重分发**：出发前每块就指定了收件人，总量不变但布局按目标重排。
7. T ≈ α×轮次 + β×字节/带宽 + γ×本地计算。小消息/多轮次算法 α 主导；大消息 β 主导；含规约或压缩的操作 γ 不可忽略。
8. 因为 AllReduce 语义上等于 RS+AG 两段，每 rank 经手约 2·S·(N−1)/N，而单段原语只有 S·(N−1)/N。
9. 如：AllGather+本地求和替代 AllReduce（多传约 N 倍字节）；AllReduce 替代 Reduce（所有人陪跑并多收数据）。
10. 消息大小、rank 数、拓扑。

:::

### 11. 本课小结

- 坐标系：Rank × 通信域 × 消息，语义=两张快照的差别；
- 黄金恒等式：AllReduce = RS + AG，一切高效算法的出发点；
- AlltoAll 是定向重分发，与其他原语本质不同；
- 三本账：轮次 × α、字节 × β、计算 × γ；小消息与大消息是两个世界；
- 选型两层：原语由数据需求决定（错了无法补救），算法由大小×N×拓扑决定。
