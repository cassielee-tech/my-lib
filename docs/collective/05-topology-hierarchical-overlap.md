### 1. 两层世界：同城骑手 vs 跨省干线

一家电商的配送网络：**同城**有海量骑手专线（快、便宜、随便跑）；**跨省**只有几家干线卡车（慢、贵、大家挤着用）。算力集群一模一样：

- **机内**（一台服务器 8 张卡之间）：HCCS/NVLink 专线，百 GB/s；
- **机间**（跨服务器）：网卡走交换网络，几十 GB/s——**差近一个量级**。

第 2 章的"环"只是**送货顺序**（逻辑编排）。如果排顺序时不看地图——送一票要在两省之间来回蹿——干线就全是冤枉流量。**排布必须贴着地图**：同城的 8 个站点连着送，跨省只送"汇总件"。

::: details 小测 1：为什么"逻辑环 ≠ 物理连线"会造成灾难？
环上相邻的 rank 若大多在不同机器，几乎每一跳都挤机间"共用公路"——每卡约 2S 字节过网；而按节点分段排布后，只有少数跳跨机，过网流量降到"每节点一份"。
:::

### 2. 分层：各城市先集货，干线只跑汇总件

8 个城市、每城 8 个仓库要统一库存。聪明的做法分三步：

```text
① 各城市内部先对账（同城骑手跑） → 每城得到一份汇总
② 8 个城市各派代表互相同步汇总（干线只运 8 份）
③ 代表回城广播给其余 7 仓（又是同城骑手）
```

数字感受一下（512 MB 梯度）：乱序直送约 40 ms 走干线；分层后干线只运"每城一份"、8 张网卡分担，约 **4.5 ms**——**快了一个量级**，原因只有一条：**贵链路少搬字节**。

两个细节：① 城市代表如果只有一张网卡，896 MB 串行过一张卡会把优势吃光——要**多张网卡分担**（第 3 节的伏笔）；② 干线上的 8 人小组怎么同步（环/树/配对）、城内怎么收发，可以**各自选型**——每层挑最合适的算法。

::: details 小测 2：分层的本质一句话是什么？
让贵链路少搬字节：机间流量从"每卡一份 2S"降到"每节点一份 2S"。拓扑感知排布的 flat ring 能达到同量级——分层只是它的显式形式，不是魔法咒语。
:::

### 3. 兑现三板斧：拆包裹、多卡车、边装边发

算法对了、路线贴了，实测带宽还是上不去？差距在**兑现率**：

- **Chunk（拆包裹）**：512 MB 一整包直运，装车、核对、卸货的间隙全是空泡；拆成 1 MB 小包流水发运——第 k 包在路上时第 k+1 包在装车。代价：包太小则"每包手续费"占比上升，有甜点区间。
- **Channel（多卡车）**：一条路一辆车跑再满也有限；多辆车各走一条路（多网卡、多 lane、多队列），吞吐 ≈ 单路 × 车数。代价：每辆车要独立装卸区和调度（缓冲与同步开销）。
- **重叠（边装边发）**：仓库这边还在打包后面的货，前面打好的包已经在路上——通信藏进计算。要三个条件：**车道分开**（网卡/通信引擎 vs 计算核心）、**货等得起**（数据就绪、后面计算不依赖没到的货）、**有人排班**（显式编排 + 同步点，如 FSDP 的分桶）。

有的货藏不住：**TP 每层的输出必须拼全才能算下一层**——通信卡在关键路径上。此时只剩两招：**压缩包裹**（量化，字节砍半）或**改流程**（TP→TP+SP，把一次大通信拆成前后向两半）。

::: details 小测 3：MoE 的 A2A 堵了，三板斧里先用哪个？
先看是"单路利用率"还是"总吞吐"问题：链路没打满 → 拆小流水（chunk）+ 多路并行（channel）压缩空泡；若通信量本身在关键路径 → 回到模型侧（均衡路由/限流）或压缩（量化）。三把钥匙常常一起拧。
:::

### 3 句话带走

1. **两层世界**：机内专线 vs 机间公路，差一个量级——rank 排布必须贴地图；
2. **分层 = 贵链路少搬字节**：先城内集货、干线只运汇总件，每层还能各自选算法；
3. **兑现三板斧**：拆包裹（chunk）铺流水、多卡车（channel）铺并行、边装边发（重叠）藏通信——藏不住的就压缩或改流程。

## 05-1｜拓扑：通信的物理地图

::: info 本单元目标
围绕 **两层拓扑与 rank 排布** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

前四章的账本都默认"链路同质"——真实机器不是。

### 1. 两层世界

一台 AI 服务器内部 vs 服务器之间，是两个带宽量级：

| 层 | 典型互联 | 量级 | 形态 |
| --- | --- | --- | --- |
| **机内**（跨卡） | 昇腾 HCCS / NVLink / 昆鹏 UB | 百 GB/s 级 | 近似全互联（任意两卡高速直连） |
| **机间**（跨机） | PCIe 网卡 / RoCE / InfiniBand | 几十 GB/s 级（每卡） | 交换网络（多跳、共享） |

- 机内/机间**差近一个量级**，而且机内是"专线"、机间是"共用公路"；
- 关于 AI Server 内部的完整叙事见 [大模型基础：AI Server](../model/01-landscape.md#_01-2-并行策略为什么产生通信) 与 [算力厂商加速卡专题](../device/accelerator-cards-2026.md)；HCCL 如何探测这两层拓扑，见 [HCCL 源码 4：通信引擎与任务执行](../ascend/hccl-source/04-comm-engines.md)。

#### 1.1 第 2 章的伏笔：逻辑环 ≠ 物理连线

环是**逻辑编排**（第 2 章 warning）。同一批 64 个 rank（8 机 × 8 卡），两种排布：

```text
不管拓扑的环（rank 乱序）：环上相邻的 rank 大多在不同机器
   → 几乎每一跳都挤机间"共用公路" → 每卡约 2S 字节过网

拓扑感知的环（按节点分段排布）：同机的 8 个 rank 排在一起
   → 环上只有 8 跳跨机器，其余 56 跳走机内专线
   → 过网流量骤降到"每节点一份"量级
```

### 2. 拓扑感知：通信库的第一课

真实通信库（HCCL/NCCL）启动时都要做**拓扑探测**：识别哪些 rank 同机、经什么链路互联、有几张网卡——然后才决定算法与排布。这就是 [HCCL 源码 4](../ascend/hccl-source/04-comm-engines.md) 里"Server 内/Server 间"两套场景的由来。

**一个反直觉的结论**：拓扑感知排布的 flat ring，机间流量已经接近显式分层方案（下一单元）——因为贵的链路只搬"每节点一份"。所以：

::: warning 别背"分层一定快"
分层不是魔法咒语，它的本质只有一句话：**让贵的链路少搬字节**。凡是达到这个效果的排布/算法组合都算数——显式分层只是其中最清晰的一种形式。
:::

## 05-2｜分层算法：先内后外

::: info 本单元目标
围绕 **分层 AllReduce 的结构与流量账** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

把"让贵链路少搬字节"写成显式算法，就是分层（hierarchical / two-level）。

### 3. 三步舞：机内归约 → 机间归约 → 机内广播

8 机 × 8 卡 = 64 rank 的分层 AllReduce：

```text
第 1 步（机内）：每台机器内部做 Reduce（机内树/环）
   → 每节点得到一份"该节点的部分和"S 字节，全程走机内专线

第 2 步（机间）：每节点派代表（leader）组成 8 人小组做 AllReduce(S)
   → 只有机间链路干活，且只搬每节点一份

第 3 步（机内）：leader 把结果广播给机内其余 7 卡（机内树）
   → 全员拿到全量 ✓
```

#### 3.1 流量账（S=512 MB，机内 200 GB/s、机间每卡 25 GB/s）

| 方案 | 每卡过网流量 | 网络耗时（8 卡并行分担后） |
| --- | --- | --- |
| 乱序 flat ring | ~2S ≈ 1008 MB | ≈ 40 ms |
| 分层（或拓扑感知 ring） | 节点共 ~2S·7/8 ≈ 896 MB，8 张网卡分担 ≈ **112 MB/卡** | ≈ 4.5 ms + 机内时间 |

**约一个量级的差距**——来源只有一个：机间链路从"每卡搬 2S"变成"每节点搬 2S"。

::: warning 注意"代表"的网卡
第 2 步若只用 leader 一张网卡，机间 896 MB 串行过一张卡（≈36 ms）反而吃掉优势——所以工程上让**多张网卡/多条通道**分担机间流量，这正是下一单元 Channel 的伏笔。
:::

### 4. 每层各选算法

分层的第二红利：**两级可以独立选型**（复用第 3 章地图）：

- 机间 8 人小 AllReduce：rank 少 → **Tree/RD**（轮次少）或 **Ring**（S 大时）；
- 机内 Reduce/Broadcast：全互联高带宽 → **Tree**（层级天然匹配）或专用引擎卸载；
- HCCL 的分级通信正是这个结构：机内/机间场景分别走不同算法与链路（见 [HCCL 源码 4](../ascend/hccl-source/04-comm-engines.md)、[HCCL 源码 5](../ascend/hccl-source/05-coll-algorithms.md)）。

```text

语义（18）→ 算法（19/20）→ 原语场景（21）→ 拓扑与分层（22）
```

## 05-3｜Chunk 与 Channel：拆小、铺满

::: info 本单元目标
围绕 **chunk 与 channel 的分工** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

算法对了、拓扑贴了，实测带宽还是上不去？差的是**兑现率**。两个旋钮：**Chunk** 管粒度，**Channel** 管并行度。

### 5. Chunk：拆小，铺成流水

第 2 章见过它：2N 分块让环上"在途数据"变多。一般化地说——

**大块直传的问题**：一块 512 MB 从头传到尾，链路上任一时刻只有"一个包"在飞，**收发两端的处理间隙（打包、校验、拷贝）全是空泡**。

**Chunk 化**：切成许多小块（如 1 MB），流水线推进——rank 在收第 k 块时同时发第 k+1 块：

```text
直传：  [═══════ 512MB ═══════]          链路有空泡
分块：  [1][2][3][4][5]...[512] 全部在途  空泡被流水填满
```

- **收益**：β 项逼近理论值（链路利用率打满）；
- **代价**：块太小则"每块固定开销"（启动、校验）占比上升——**块大小有个甜点区间**，通信库会按消息大小与链路特性自动选。

### 6. Channel：多路，各走一条

单条通信路径（一个网卡队列、一对收发缓冲）打满也就一张卡的带宽。**Channel = 多条互相独立的通信路径并行**：

- 物理来源：多网卡（每卡 4/8 张 RDG/RoCE 网卡）、HCCS/NVLink 的多条 lane、网卡多队列；
- 编排：每个 channel 独立跑一份算法（如各自一个小环），数据在 channel 间再切分——**吞吐 ≈ 单路 × channel 数**，直到物理带宽打满；
- **代价**：每个 channel 要独立的收发缓冲与同步状态——**内存占用和调度开销随 channel 数上涨**，所以不是越多越好（HCCL 的 buffer 管理与 channel 规划见 [HCCL 源码 5](../ascend/hccl-source/05-coll-algorithms.md)）。

#### 6.1 两个旋钮的分工

| | Chunk | Channel |
| --- | --- | --- |
| 解决 | 链路空泡（单路利用率） | 单路带宽上限（总吞吐） |
| 维度 | 时间上拆细 | 空间上铺开 |
| 代价 | 块太小开销占比涨 | 缓冲与调度开销涨 |
| 甜点 | 存在最优块大小 | 打满物理带宽即止 |

第 4 章 MoE 的"多小块流水 + 多 channel"缓解，正是这两个旋钮一起拧。

## 05-4｜通信计算重叠：从公式到实践

::: info 本单元目标
围绕 **重叠的条件、手段与边界** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

前面都是"把通信本身变快"；最后一板斧是"让通信**看起来不存在**"。

### 7. 重叠的三个条件

《单卡执行系统》第 7 章讲过 Stream/Event 异步执行，通信版同理（详见 [《单卡执行系统》第 7 章重叠单元](../device/07-stream-event-async.md#_07-4-重叠的艺术-让设备闲不下来)）：

1. **资源独立**：通信走网卡/通信引擎，计算走 AI Core——互不抢座位（昇腾上 HCCL 可用独立引擎，见 [HCCL 源码 4](../ascend/hccl-source/04-comm-engines.md)）；
2. **依赖允许**：被通信的数据已就绪（如梯度已算完），且当前计算不依赖还没到的数据；
3. **显式编排**：要把"哪段计算配哪段通信"排进不同流，并设好同步点——不会自动发生。

#### 7.1 典型手段：分桶（bucketization）

FSDP 的经典操作（模型侧叙事见 [《训练与推理系统》第 1 章](../systems/01-training-loop.md#_01-4-训练显存与梯度通信)）：

```text
不分桶：所有层反向算完 → 一次性 AllReduce 全部梯度（通信干等计算）
分桶  ：梯度按参数桶分组，一个桶算完立即发起该桶的 RS/AllReduce
        → 反向还在算后面的层时，前面桶的通信已在飞行中
```

桶大小的权衡：桶大 → 通信次数少但重叠窗口小；桶小 → 重叠充分但小消息化（回到第 3 章 α 项的坑）。

### 8. 重叠的边界：藏不住的部分

**TP 的逐层通信藏不住**：前向每层输出要 AG 拼全才能算下一层——通信在**关键路径**上，重叠没有依赖空间。此时只剩两条路：

1. **压缩通信量**：梯度/激活量化（FP32→BF16/FP8，字节直接砍半或更多）；
2. **改算法/改语义**：TP→TP+SP（AllReduce 拆成 AG+RS 分挂前后向）、改并行度配比——回到第 1 章"从语义到选型"的起点。

#### 8.1 《集合通信》合龙：一条完整的因果链

```text
语义（18）：要什么结果？最小够用的原语是哪个？
算法（19/20）：α 主导选 log 轮次，β 主导选 Ring；分界点算得出
场景（21）：AG/RS/A2A 各挂 TP/SP/FSDP/MoE 的哪一步
拓扑（《并行策略》02-1/2）：贵链路少搬字节——拓扑感知 + 分层
兑现（《并行策略》02-3/4）：chunk 铺流水、channel 铺并行、重叠藏进计算
```

从"想要一个全组求和"到"在真实集群上把带宽跑满"——这条链就是集合通信的全部故事。下一专栏（[《昇腾与 HCCL》](../ascend/index.md)）：把这条链逐条落到昇腾硬件与 HCCL 源码上。

```text
   → 逻辑 rank 必须贴物理拓扑排布

分层（05-2）：机内归约 → 代表机间归约 → 机内广播

```

### 10. 自测题

1. 机内与机间互联的典型形态与量级差？
2. "逻辑环 ≠ 物理连线"在拓扑语境下意味着什么？
3. 乱序排布为什么让机间流量爆炸？
4. 分层 AllReduce 的三步分别是什么、各走哪层链路？
5. 分层方案机间流量降到多少？为什么说"分层不是魔法"？
6. 第 2 步只用 leader 单网卡会发生什么？解法是什么？
7. Chunk 解决什么问题？代价是什么？
8. Channel 的物理来源与代价？
9. 重叠的三个条件是什么？
10. TP 的逐层通信为什么藏不住？剩下哪两条路？

::: details 自测答案

1. 机内全互联专线（HCCS/NVLink/UB，百 GB/s 级）；机间交换网络（PCIe/RoCE/IB，几十 GB/s 级每卡）——差近一个量级。
2. 环是通信库的逻辑编排；物理网络是交换式的。同一逻辑环在不同 rank 排布下，跨机跳数完全不同。
3. 乱序时环上相邻 rank 大多跨机，几乎每跳都挤机间链路——每卡约 2S 字节过网。
4. 机内 Reduce（机内专线）→ 各节点代表做机间 AllReduce(S)（机间链路）→ leader 机内广播（机内专线）。
5. 每节点 ~2S(K−1)/K（K=节点数），即"每节点一份"；因为拓扑感知的 flat ring 也能达到同量级——分层只是"让贵链路少搬字节"的显式形式。
6. 节点全部机间流量串行过一张网卡，优势被吃掉；用多网卡/多 channel 分担。
7. 链路空泡（单路利用率）；块太小则每块固定开销占比上升，有甜点区间。
8. 多网卡、多 lane、多队列；代价是每 channel 独立收发缓冲与同步状态，内存和调度开销上涨。
9. 资源独立（计算/通信不抢座位）、依赖允许（数据就绪且无前向依赖）、显式编排（分流+同步点）。
10. 前向每层输出 AG 拼全才能算下一层——通信在关键路径上没有重叠空间；只能压缩通信量（量化）或改算法/语义（TP+SP 拆分、调并行配比）。

:::
