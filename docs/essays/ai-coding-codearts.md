AI Coding 已经不再只是“自动补全下一行代码”。编辑器中的 AI 开始读取整个项目、调用终端、修改多个文件、运行测试，并在失败后自行修正。开发者的工作重心也随之变化：从亲手完成每一处实现，逐渐转向定义问题、提供上下文、审查方案和承担最终质量责任。

这篇文章整理自一次关于 **AI Coding 发展与 CodeArts 功能**的分享。相比逐页复述演讲内容，我更想留下几个能够长期复用的问题：AI 编码工具由哪些部分组成？为什么有时很好用、有时又频频犯错？怎样把它真正纳入软件工程流程？人仍然必须负责什么？

## 一、AI Coding 经历了什么变化

AI 编程的发展可以粗略分成五个阶段：

1. **规则式补全**：根据关键词、语法和已有符号提供确定性候选；
2. **神经网络补全**：开始根据局部上下文预测一行或一小段代码；
3. **大模型参与编程**：通过自然语言生成函数、测试和解释；
4. **AI 原生编辑器与 Coding Agent**：理解项目并执行多步骤任务；
5. **多智能体和工程化落地**：多个专业 Agent 协作，能力进入团队流程。

真正的转折不只是模型生成得更准，而是系统从“给一个建议”走向了“围绕目标持续行动”。一个现代 Coding Agent 通常要同时具备：

- 项目级上下文检索；
- 任务规划与状态跟踪；
- 文件、终端、Git 等工具调用；
- 编译、测试和静态检查；
- 失败后的反馈与修正；
- 权限控制和人工确认。

## 二、一个 Coding Agent 是怎样组成的

从外部看，我们只是输入一句“给用户列表增加分页”。系统内部却要完成一条相当长的链路。

### 1. 大模型：理解与生成

代码大模型仍然建立在 Token 预测之上。代码、注释、文档、提交记录和问题描述让模型逐渐学会语法模式、API 用法和一部分工程意图。

编辑器中的光标补全还常使用 **FIM（Fill in the Middle）**：同时给模型光标之前和之后的内容，让它补全中间缺失部分。这比只根据前文继续生成更符合代码编辑场景。

模型擅长生成候选方案，但它并没有天然看到完整项目，也不会自动拥有文件和终端权限。这些能力来自外围系统。

### 2. Codebase：找到真正相关的上下文

大型代码库无法每次完整塞入模型上下文。常见做法是：

1. 对代码、文档和符号建立索引；
2. 根据用户任务检索相关片段；
3. 结合符号引用、调用关系和目录结构扩大上下文；
4. 把筛选后的材料交给模型理解和生成。

这可以看成面向代码的 RAG。向量检索负责寻找语义相近内容，符号和依赖图负责补充结构关系。仅仅搜到“看起来相似”的代码还不够，系统还要知道接口在哪里定义、谁调用了它、改动会影响哪些模块。

代码库自身的质量会直接影响检索效果：模块边界混乱、重复实现过多、命名随意、文档长期失真，都会让 AI 更难获得正确上下文。AI Coding 并没有让软件工程基本功失效，反而放大了良好工程结构的价值。

### 3. Agent：把目标变成行动循环

常见 Agent 循环可以概括为：

> 感知当前状态 → 制定计划 → 调用工具 → 观察结果 → 修正计划

例如“增加分页”可能被拆成：

1. 搜索已有列表接口和分页约定；
2. 确认数据库查询方式；
3. 修改请求参数和响应结构；
4. 更新前端调用；
5. 补充测试；
6. 执行测试并修正失败。

关键不是第一次生成是否完美，而是系统能否获得真实执行反馈，并在受控范围内继续修正。

### 4. Tools 与 MCP：让模型能够操作外部世界

模型可以通过结构化调用使用文件读写、代码搜索、终端、浏览器、数据库和 Git 等工具。MCP 则提供了一种连接 AI 应用与外部工具、数据源的开放标准，让能力不必都硬编码在一个客户端内部。

但“能够调用”不等于“可以随意调用”。删除文件、强制推送、部署生产环境、执行数据库写操作等行为必须经过权限门控。工具能力越强，审计和确认机制越重要。

### 5. 上下文、记忆与验证

长任务会不断产生搜索结果、日志和中间结论。上下文管理需要决定哪些信息继续保留、哪些压缩成摘要、哪些可以丢弃。项目中的规则文件则可以长期记录构建方式、代码风格、测试命令和禁止事项。

验证闭环负责把“看起来正确”转化为“至少通过了可执行检查”：

- 能否编译；
- 单元测试是否通过；
- 静态检查是否出现新问题；
- 改动是否超出任务范围；
- Git Diff 是否符合预期。

## 三、主流工具的四种形态

### IDE 插件

代表形态是在既有 IDE 中加入补全、对话和 Agent 功能。迁移成本低，适合不希望改变编辑器习惯的开发者。

### AI 原生编辑器

从交互设计上把代码库检索、多文件编辑和对话作为核心能力，适合高频使用 AI 的个人开发和快速迭代。

### 终端 Coding Agent

直接在项目目录中工作，擅长搜索、执行命令、修改文件和处理 Git。它与现有编辑器解耦，也更适合自动化和远程环境。

### 云端开发 Agent

在隔离环境中异步执行较完整的开发任务，能够自行安装依赖、运行项目并提交结果。它更接近任务委派，但对环境复现、权限和结果验收要求更高。

工具选型不应该只比较“谁更聪明”。真正需要考虑的是：

- 是否适应现有开发环境；
- 能否正确理解私有代码库；
- 工具权限是否可控；
- 是否支持团队规则和审计；
- 模型、延迟和 Token 成本；
- 是否能够私有化或满足合规要求。

## 四、怎样让 AI 编程真正有效

### 1. 把任务拆小

“重构这个系统”几乎没有可操作边界；“把用户查询中的分页参数抽成 `PageRequest`，保持现有 API 兼容，并补充三个边界测试”则更容易执行和验收。

任务越大，AI 越容易在尚未理解全局时作出过多假设。先完成能够独立验证的小闭环，再逐步扩大范围。

### 2. 给验收标准，而不只是描述愿望

一个好的任务至少应明确：

- 要解决的问题；
- 允许修改的范围；
- 输入输出和兼容要求；
- 关键边界条件；
- 必须通过的测试或检查；
- 明确禁止的行为。

### 3. 复杂任务先 Plan，再 Act

先让 AI 搜索项目并给出计划，人确认方向和影响范围后再执行。规划不是为了制造文档，而是尽早暴露错误假设，避免改完十几个文件才发现理解错了需求。

### 4. 给它项目中的正确范例

一段同项目、同风格的现有实现，往往比一大段抽象描述更有效。范例同时传递了目录位置、命名方式、异常处理和测试习惯。

### 5. 建立验证闭环

AI 完成修改后至少要经历：

> 查看 Diff → 编译或类型检查 → 运行相关测试 → 检查异常与安全边界 → 人工 Review

生成代码并不意味着责任转移。测试覆盖不到的需求理解、架构影响和安全风险仍需要人判断。

### 6. 小步提交，保持可回滚

让一次提交只表达一个目的。出现问题时能够定位是哪一步引入的，也可以在不破坏其他成果的情况下回退。

## 五、AI Coding 的能力边界

AI 当前比较擅长的任务通常具有共同特征：目标清楚、上下文可获得、结果能够验证。例如：

- 模式化代码和脚手架；
- 局部多文件修改；
- 代码解释与项目问答；
- 边界明确的 Bug 修复；
- 单元测试、文档和重复性工程工作。

仍然需要人重点把关的场景包括：

- 模糊需求背后的业务取舍；
- 跨系统、跨团队的架构决策；
- 隐性依赖和复杂故障；
- 安全、隐私与合规审查；
- 大规模遗留系统的全局影响；
- 最终责任归属。

我的判断是：**AI 是高效协作者，但不是可以托管责任的工程师。**

软件工程的核心任务一直是驾驭复杂性。模块化、分层、接口契约、测试、评审和变更管理，不只是为了方便人类协作，也是在为 AI 创造更清晰、更可检索、更容易验证的工作边界。

## 六、CodeArts 代码智能体提供了什么

华为云码道 CodeArts 的完整产品范围覆盖需求、代码、构建、测试和发布等软件交付环节；其中代码智能体侧重把 AI 能力带入 IDE、插件、CLI 和 Agent 工作空间。

结合分享材料与官方文档，可以把其代码智能体能力归纳为：

### Codebase

为存量代码建立索引，结合语义检索、符号信息和代码依赖关系，帮助 Agent 定位与任务相关的实现。官方更新记录还提到向量与图谱的混合检索，以及大代码仓的端云协同理解。

### Agent 与 Agent Team

Agent 可以围绕自然语言任务进行规划、修改文件和验证；多智能体形态则由主 Agent 拆分任务，让拥有独立上下文的子 Agent 并行执行，再汇总结果。

### 规则、Skills 与 MCP

团队可以沉淀项目规则、可复用技能和外部工具连接，使 AI 不只依赖一次对话中的临时提示。

### 探索与规范

原型阶段更重视快速试验，交付阶段更重视需求、设计、任务和验证过程。无论产品如何命名这些模式，背后的核心都是根据风险选择不同的自主程度与约束强度。

### 企业治理

企业使用 Coding Agent 还需要考虑模型管理、私有知识、成员权限、操作日志、Token 配额和安全审计。这些能力决定了工具能否从个人尝试进入组织流程。

产品功能变化很快，具体模型、套餐、配额和支持平台应以当前官方文档为准，而不应长期依赖一份演讲材料中的静态数字。

## 七、提效应该怎样衡量

代码行数和 AI 建议采纳率很容易测量，却未必代表真正价值。更多代码可能意味着更多维护成本，高采纳率也不能证明需求正确。

更值得关注的是端到端结果：

- 同类任务从开始到交付用了多久；
- PR 从提交到合并的周期是否缩短；
- Review 返工次数是否下降；
- 缺陷率和线上故障是否变化；
- 开发者查资料和等待反馈的时间是否减少；
- Token、模型和基础设施投入是否值得。

量化指标仍然无法捕捉全部体验。例如减少上下文切换、降低陌生项目理解成本，很难用一个数字描述。因此更现实的方法是采用“结果指标 + 成本指标 + 定性反馈”，而不是寻找一个万能的 AI 提效百分比。

## 八、从 AI for Coding 到 AI for All

代码最早成为 Agent 的成熟场景，是因为它具有相对明确的结构和验证方式：能够编译、能够运行、能够测试。但 RAG、工具调用、规划和验证闭环并不只适用于代码。

同样的思路可以延伸到研发全流程：

- **需求阶段**：整理会议记录、发现歧义、形成结构化需求；
- **方案阶段**：检索历史决策、比较技术选型、检查遗漏；
- **测试阶段**：生成用例、分析失败模式、整理回归结果；
- **运维阶段**：汇总日志与监控信息、辅助定位根因；
- **协作阶段**：检索工单、文档和历史讨论，回答“以前为什么这样设计”。

这里真正值得复用的不是某个 IDE，而是一套工作模式：

> 明确目标 → 找到可信上下文 → 调用受控工具 → 获得真实反馈 → 由人验收结果

## 结语

AI Coding 正从局部补全走向项目级协作，但模型能力只是其中一层。代码库索引决定它能看到什么，Agent 循环决定它怎样行动，工具权限决定它能做什么，验证体系决定我们能相信什么。

对开发者而言，比记住某个产品功能更重要的是建立新的工程习惯：把任务拆小、把标准说清、把上下文管好、让每一步都可以验证和回滚。

AI 可以加速代码的产生，却不会自动承担软件的后果。定义问题、驾驭复杂性和对最终结果负责，仍然是人的核心价值。
