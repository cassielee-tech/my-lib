## 第 1 章｜全景：从大模型到集合通信

完整正文 → [第 1 章｜全景：从大模型到集合通信](01-landscape.md)

> 适用：时间紧，或完整版跟不动时。这页用一家连锁餐厅讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 一家餐厅变成连锁店之后

你训练模型，就像经营一家餐厅：

- **菜谱**（模型参数）= 怎么做菜的全部知识；
- **做生意**（训练）= 每天按顾客反馈调整菜谱：做一批菜（前向）→ 顾客打分（Loss）→ 分析哪道菜该改（梯度）→ 改菜谱（更新参数）。

只有一家店时，一切在店内解决。**单卡训练不需要集合通信**——所有材料、账本、修改意见都在这一家店里。

店做大了要开分店（多张卡），麻烦立刻出现：每家店都在改自己的菜谱，改完之后**各家的菜谱就不一样了**。连锁品牌不允许这种事——必须有人负责"对账"。这个对账系统，就是**集合通信**。

::: details 小测 1：为什么单卡训练不需要集合通信？
因为参数、数据、梯度都在同一张卡内，本地显存读写就能完成一切数据流动。集合通信解决的是"多个 Rank 之间的数据交换与聚合"——没有第二个参与者，就没有这个问题。
:::

### 2. 分店有三种开法，对账方式各不相同

| 开法 | 怎么切 | 产生的对账 |
| --- | --- | --- |
| **数据并行 DP** | 每家店用**同一本菜谱**，接待**不同的顾客** | 各店改菜谱的意见不同 → 意见**汇总求平均**（AllReduce） |
| **张量并行 TP** | **一道菜由多家店合炒**（把一个大矩阵拆开） | 每家只炒出半成品 → 要**拼成完整的一道菜**（AllReduce / ReduceScatter） |
| **流水线并行 PP** | 按工序分店：洗菜店→切菜店→炒菜店 | 半成品**按顺序传给下一家**（点对点发送） |

还有两种变体：**FSDP** 像把菜谱**撕开分家保存**，用之前先拼回完整（AllGather），改完再撕开分回去（ReduceScatter）；**MoE** 像专科分诊，病人要在分店之间转来转去（AlltoAll）。

::: warning 关键
**模型定义计算，并行策略把计算切开，集合通信把切开的数据重新连起来。** 想知道一次通信"为什么存在"，先问"切的是什么"。
:::

::: details 小测 2：数据并行为什么通常需要 AllReduce？
因为每家店（Rank）用不同数据（顾客）算出了不同的修改意见（本地梯度）。如果各改各的，菜谱（参数）会越来越不一样。AllReduce 把所有梯度汇总求平均，让每家拿到同一份意见，改出同一本菜谱。
:::

### 3. 从你敲下一行代码，到对账车出发

在 PyTorch 里你只写了一句 `loss.backward()`，背后是一条完整的物流链：

```text
loss.backward()
→ Autograd 算出梯度（分店整理好意见）
→ DDP 把意见装箱（Bucket）
→ ProcessGroup 发起对账（AllReduce）
→ 昇腾适配层调用 HCCL（物流公司接单）
→ HCCL 选路线和车队（算法、拓扑）
→ Runtime/驱动发车（任务下发）
→ NPU 和互联链路真正运货
```

**HCCL 就是那条物流线**：它住在框架和硬件之间，把"对账"这个抽象要求变成真实的传输任务。

::: details 小测 3：优化一个 AllReduce 算子时，为什么必须知道它来自 DP 还是 TP？
因为来源决定了它的"快递属性"：DP 的梯度对账可以攒大箱、走夜路（不着急、可与计算重叠）；TP 的对账卡在下一道工序前（关键路径、延迟敏感）。同样是 AllReduce，快递的急缓和路线完全不同，优化手法也不同。
:::

### 第 1 章 · 3 句话带走

1. 单店不需要对账，**多店才需要**——并行为什么产生通信；
2. **切法决定对账方式**：DP 汇总意见、TP 拼半成品、PP 传半成品；
3. `loss.backward()` 到真实传输隔着一条链，**HCCL 是框架和硬件之间的物流公司**。

## 第 2 章｜张量、矩阵乘法、计算图与反向传播

### 1. 张量就是一张多维表格

别被"张量"吓到，它就是**一张有多层结构的 Excel 表**：

- `[8]` = 一列 8 个数；
- `[4, 8]` = 4 行 8 列的表；
- `[2, 4, 8]` = 两本这样的表钉在一起。

**Shape 就是表格的尺寸**。模型里流动的所有数据——输入、权重、中间结果——全是这样的表格。

表格之间最重要的运算叫**矩阵乘法**（一次"对账式"的批量乘加）。它有条铁律：

```text
[M, K] × [K, N] → [M, N]
        ↑
  左表的列数必须等于右表的行数，对完账这个维度就"消失"
```

有了这条规则，你就能心算任何一层网络输出的尺寸，还能顺手算出数据量（元素个数 × 每个数的字节）。

::: details 小测 1：`[2, 4, 8]` 的表格 × `[8, 16]` 的表格，结果是什么尺寸？
前两维 `[2,4]` 表示有 2×4=8 个"词条"，每个词条是长度 8 的向量。每个向量乘 `[8,16]` 变成长度 16 → 结果 `[2, 4, 16]`。消掉的维度永远是"左尾 = 右头"的那一对。
:::

### 2. 出了次品怎么追责：计算图与反向传播

工厂每天出货，质检发现总有问题（Loss 不为零）。**是谁的锅？**

前向生产时，工厂顺便填了一张**流程单**（计算图）：每道工序用了什么原料、做了什么运算。追责时就把它倒过来走：

```text
质检结果（Loss）
  ← 最后一道工序担多少责任（局部梯度）
  ← 链式法则层层分摊：我的责任 = 我下游传回来的责任 × 我这道工序的敏感度
  ← 一直追溯到每个参数头上
```

每个参数分到的"责任值"就是**梯度**。两个关键事实：

1. **梯度和参数的 Shape 一定相同**——每个参数都要有一个责任值，不多不少；
2. **追责 ≠ 改参数**：`loss.backward()` 只是算出责任清单；`optimizer.step()` 才真的按清单调整参数。之后还要 `zero_grad()` 清空旧清单，否则新旧责任会混账。

::: details 小测 2：`backward()` 之后模型参数变了吗？
没有。`backward()` 只是把梯度算出来、记到每个参数的 `.grad` 里；要等 `optimizer.step()` 读这些梯度才真正修改参数。顺序永远是：算梯度 → （多卡时对账）→ 更新 → 清零。
:::

### 3. 多个车间一起干：责任也要对账

工厂开了多个车间（多张卡），每个车间用自己的原料批次干活，于是**各自追出的责任清单不一样**。

如果各改各的，每个车间的"生产标准"（参数）就分家了。所以：**更新参数之前，必须先把各车间的责任清单汇总**（AllReduce 求平均），让所有车间按同一份清单调整。

聪明的做法是不等全部追完责再对账：**追责是从后往前逐层进行的，后面几层的清单一出来就先装箱发出**（Bucket），对账和前面的追责同时进行——这就是"通信与计算重叠"。

::: details 小测 3：为什么梯度汇总可以和反向计算重叠？
因为反向传播从最后一层往第一层进行：后面层的梯度先生成，先装箱发走（AllReduce 在独立通道异步跑）；与此同时前面的层还在继续算梯度。等最前面的梯度装箱时，后面的对账已经完成大半。
:::

### 第 2 章 · 3 句话带走

1. 张量就是多维表格，**Shape 是尺寸，矩阵乘法的尺寸规则能心算一切**；
2. 反向传播就是**按流程单倒着追责**，梯度 = 每个参数的责任值，Shape 与参数相同；
3. 多卡训练**必须先对账（汇总梯度）再改参数**，且可以让对账追责并行。

## 第 3 章｜Tokenization、Embedding 与语言模型目标

完整正文 → [第 3 章｜Tokenization、Embedding 与语言模型目标](03-tokenization-embedding.md)

> 适用：时间紧，或完整版跟不动时。这页用一场"文字接龙考试"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 把文章剪成积木，再给积木编号

模型不认识字，只认识数字。所以第一步是**剪纸**（Tokenization）：

```text
"我爱集合通信" → ["我", "爱", "集合", "通信"] → [102, 88, 4520, 3977]
```

- 剪出的每块叫 **Token**：可能是一个字、一个词、半个词，甚至一个符号——**不等于字或词**；
- 每块积木在**总目录**（词表）里有唯一编号：**Token ID**；
- 这本目录和模型是**配套出厂**的——换一本目录，同一个编号对应的就是另一块积木，模型直接查错。

编号只是"第 37 号货架"。第二步是**取货**（Embedding）：按编号从货架上取下一个**意义盒子**——一个长度为 H 的数字向量。从此模型操作的不再是编号，而是这些可计算、可学习的向量。

::: details 小测 1：Token、Token ID、Embedding 的关系？
剪出的积木块（Token）→ 它在词表目录里的编号（Token ID）→ 按编号从参数表取出的数字向量（Embedding）。三步走完，文字才变成模型能计算的数字。为什么 Tokenizer 必须和模型配套？因为编号和货架是绑定的，换目录就取错货。
:::

### 2. 考场规则：挡板与空位

一批考卷（Batch）一起改，题干有长有短。为了让表格尺寸对齐，短卷子末尾要**凑数空位**（Padding）。

考场里有两块完全不同的"挡板"（Mask）：

| 挡板 | 挡住什么 | 为什么 |
| --- | --- | --- |
| **Padding Mask** | 凑数的空位 | 空位不是内容，别让它干扰计算 |
| **Causal Mask** | **右边的未来** | 接龙考试不许偷看答案 |

Causal Mask 是这个考场的灵魂：第 5 个位置的考生只能看到第 1～5 个位置，**绝不能看到第 6 个**——因为第 6 个词正是它要预测的答案。

::: details 小测 2：Padding Mask 和 Causal Mask 能同时用吗？
能，它们解决两个不相干的问题：一个挡"凑数的假位置"，一个挡"未来的真答案"。训练时通常两块都装上。
:::

### 3. 出题的方式：全体考生同时作答

训练的出题法极其朴素：**把输入整体右移一位当答案**。

```text
输入：  [我, 爱, 集合, 通信]
答案：  [爱, 集合, 通信, !]      ← 每个位置都在预测"下一个词"
```

每个位置交卷的是一张**打分表**（Logits）：对词表里 V 个候选词各打一个分。注意**打分表不是概率**——要经过 Softmax 归一化后，才能读成"50% 是'通信'"。

因为 Causal Mask 的存在，**一次前向就能让所有位置同时作答**，不用一个词一个词来——训练高效；而生成文本时才需要逐词迭代（那是《训练与推理系统》第 3 章的故事）。

这套流程的尺寸链值得背下来：`[B,S] 编号 → 查表 → [B,S,H] 向量 → …… → [B,S,V] 打分表`。

::: details 小测 3：长度为 S 的序列（含开头、结尾标记），能出几道题？
S−1 道。第 1 到第 S−1 个位置各预测自己的"下一个"，最后的结尾标记之后没有答案了。这也是为什么训练吞吐用 tokens/s 衡量比"条数"更公平——每条文本剪出的积木数都不一样。
:::

### 第 3 章 · 3 句话带走

1. 文字进模型要走三步：**剪积木（Token）→ 查编号（ID）→ 取向量（Embedding）**，目录和模型配套；
2. 两块挡板各管各的：**Padding Mask 挡空位，Causal Mask 挡未来**；
3. 训练就是**右移一位的接龙考试**，一次前向全体作答，交卷的是打分表（Logits）。

## 第 4 章｜Self-Attention、QKV 与多头注意力

完整正文 → [第 4 章｜Self-Attention、QKV 与多头注意力](04-self-attention.md)

> 适用：时间紧，或完整版跟不动时。这页用一场会议室里的"听谁说话"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 会议室里，每个词都在决定"听谁的"

想象一场圆桌会议，**每个座位上坐着一个词**。轮到"它"发言时，它要做一件事：**从全场挑出值得听的人，把他们说的话按重要程度混合成自己的新理解**。

每个人为这场社交准备了两样东西：

- **Q（Query，我的关注点）**："我想找什么信息？"——一张写着需求的卡片；
- **K（Key，我的名牌）**："我能提供什么？"——挂在胸前的标签。

匹配规则粗暴简单：**拿我的 Q 卡片去对每个人的 K 名牌打分**（做点积）。分数越高，说明对方越值得听。

但打完分还差一步——真正被拿走的内容不是名牌，而是名牌背后的**V（Value，我的实际内容）**。所以完整流程是：

```text
我的 Q × 大家的 K → 打分表 → 除以 √D → Softmax 变成"注意力预算"
                                                  ↓
                     新理解 = 按预算比例，把大家的 V 加权混合
```

::: details 小测 1：Q、K、V 分别是什么角色？
Q 是"我要找什么"（当前词的检索需求），K 是"我有什么"（每个位置用于被匹配的标签），V 是"我实际给什么"（被打分后真正被取走混合的内容）。Q 和 K 决定权重，权重作用在 V 上。
:::

### 2. 考场纪律与多组目光

**为什么除以 √D？** 会议室人一多（向量维度 D 一大），点积分数天然膨胀，Softmax 会"一家独大"到饱和，训练就不好学了。除以 √D 把分数压回正常量级——**人越多，越要压低嗓门**。

**Causal Mask 在哪一步介入？** 在 Softmax **之前**：把"未来座位"的分数直接改成 −∞，Softmax 之后概率精确为 0，剩下的座位重新分配预算。**会议规则：只能听已经发言的人**。

**多头（Multi-Head）是什么？** 同一场会议，每组人用**不同的目光**看：有的组盯语法搭配，有的组盯语义关联……每组独立走一遍"打分→混合"，最后把各组的结论拼起来。拼完总宽度不变（每头小一点，头数多一点），但看的维度多了。

::: details 小测 2：为什么 Causal Mask 必须加在 Softmax 之前？
先设 −∞ 再 Softmax，未来位置的指数为 0，概率精确变 0，其余位置自动重新归一化——数学上干净。如果 Softmax 之后才动手改概率，还得手工再归一化一次，容易出错还破坏"每行预算和为 1"的约定。
:::

### 3. 这场会议的成本

打分表是一张 **S×S 的大表格**（每个座位对每个座位打分）：

- 序列长度翻倍，表格变成 **4 倍**（平方增长）——长文本会议开不起；
- 这张大表还要写进仓库（显存）再取出来用——来回搬运很贵。

**FlashAttention 是更聪明的会议流程**：把座位分小组、在场内小黑板上（片上存储）就地算完打分和混合，大表格**从不落到仓库**。**会议的结论一点没变，省的是跑仓库的腿**——它改变执行方式，不改变数学。

::: details 小测 3：FlashAttention 改变了 Attention 的数学结果吗？
没有。它计算的 Attention 数值语义完全相同，只是把"生成完整 S×S 中间表、写入 HBM、再读回"改成"分块在片上流动计算"，省掉了中间数据的搬运。属于《并行策略》第 2 章会再见的"IO 优化"。
:::

### 第 4 章 · 3 句话带走

1. 每个词拿 **Q 卡片对全场 K 名牌打分**，按比例混合 V 内容，得到新理解；
2. **除以 √D 压嗓门，Causal Mask 在 Softmax 前挡未来，多头=多组目光**；
3. 成本是 **S×S 打分表**：长文本平方爆炸，FlashAttention 省搬运不改结论。

## 第 5 章｜RMSNorm、SwiGLU 与完整 Decoder Block

完整正文 → [第 5 章｜RMSNorm、SwiGLU 与完整 Decoder Block](05-decoder-block.md)

> 适用：时间紧，或完整版跟不动时。这页用一条标准生产车间讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 一条标准车间流水线

上一章的会议室（Attention）只是一个工位。把工位们串起来，就得到大模型的基本重复单元——**Decoder Block**。一层 Block 是一条标准车间流水线，**每个工件（Token）从头走到尾**：

```text
工件进车间
  ① 整理工装（RMSNorm：把数值尺度调均匀）
  ② 会议工位（Attention：工件之间交换信息） → 结果叠回主路
  ③ 再整理工装（第二次 RMSNorm）
  ④ 深加工工位（MLP：每个工件独立深加工） → 结果叠回主路
工件出车间（进入下一层，同样的车间再走一遍，走 N 遍）
```

两个设计巧思：

- **整理工装（RMSNorm）**：不改变工件尺寸，只把数值"整理服帖"，防止越走越爆/越走越没声；
- **主路不动（残差连接）**：传送带上的原件永远保留，工位的加工结果**加上去**而不是替换掉。原件永远直达，学习时信号也有捷径可走——这就是为什么现代模型能堆几十层。

::: details 小测 1：Pre-Norm Block 的执行顺序？
整理（Norm）→ 会议（Attention）→ 叠回主路（残差相加）→ 再整理（Norm）→ 深加工（MLP）→ 再叠回（残差相加）。注意顺序是"先整理再进工位"（Pre-Norm），而且残差相加要求工位输出必须恢复到和主路一样的尺寸。
:::

### 2. 两个工位，干完全然不同的活

| 工位 | 混合什么 | 类比 |
| --- | --- | --- |
| **Attention（会议工位）** | **不同 Token 之间**交换信息 | 工件们开会互通有无 |
| **MLP（深加工工位）** | **每个 Token 内部**的特征变换 | 每个工件独立进机器精雕 |

MLP 工位内部是三台机器的**闸门结构（SwiGLU）**：

```text
原件 → [闸门机 Gate]：哪些特征放行？
     → [候选机 Up]：准备候选内容
     → 两者逐位相乘（闸门决定放行多少）
     → [收回机 Down]：压回原尺寸，好接回主路
```

::: details 小测 2：Attention 和 MLP 分别负责什么？
Attention 沿序列维混合——让不同位置的信息互相流动（"它"知道上下文）；MLP 逐 Token 独立——在特征维做非线性深加工（"它"自己变聪明）。一个管"交流"，一个管"内功"。
:::

### 3. 车间的账本：参数、显存和拆机器

**参数量两句话就能算**（H 是隐藏宽度，I 是中间宽度）：

- Attention：Q/K/V/输出四个 `[H,H]` 投影 ≈ **4H²**；
- MLP：闸门/候选/收回三个 `[H,I]` 级矩阵 ≈ **3HI**。

通常 `I ≈ 2.75H`，所以 **MLP 才是参数大户**。

两个反直觉的账：

1. **参数多 ≠ 慢**。整理工装（Norm）、闸门相乘这类"每读一个数只算一下"的轻活，反而常是时间杀手——它们天生是搬运瓶颈（AI Infra 会展开）；
2. **参数量 ≠ 显存**。训练时还要存梯度、优化器的两本账、所有中间半成品——实测常是参数的十几倍。

最后是**拆机器（张量并行 TP）**：一台大机器拆给多个车间各拿一半，各干各的再**拼结果**——这一"拼"，就是 AllReduce 通信的由来。

::: details 小测 3：为什么参数量不等于训练显存？
训练显存 = 权重 + 梯度 + 优化器状态（AdamW 每个参数还要两本历史账）+ 前向激活（随 Batch 和序列长度增长）+ 通信装箱等运行开销。参数只是四项中的一项。
:::

### 第 5 章 · 3 句话带走

1. 一层 Block = **两次"整理→工位→叠回主路"**：先是会议（Attention），再是深加工（MLP）；
2. 分工明确：**Attention 管 Token 之间交流，MLP 管每个 Token 内部加工**（参数大户是 MLP：3HI）；
3. **参数多≠慢、参数量≠显存**；拆机器（TP）干活的"拼结果"就是 AllReduce。

| 术语 | 人话 |
| --- | --- |
| Decoder Block | 一条标准车间流水线，整个模型重复 N 条 |
| RMSNorm | 进工位前整理工装（调数值尺度，不改尺寸） |
| 残差连接 | 主路原件保留，加工结果"加上去" |
| Pre-Norm | 先整理再进工位（现代主流顺序） |

## 第 6 章｜RoPE、位置编码与长上下文

完整正文 → [第 6 章｜RoPE、位置编码与长上下文](06-rope-long-context.md)

> 适用：时间紧，或完整版跟不动时。这页用"座位号与时钟指针"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 一个尴尬的事实：会议室里没人记得座位号

上一章的会议有个隐患：Attention 打分只看**内容**（Q 对 K 的匹配），**完全不知道谁先说谁后说**。

把"我、爱、你"和"你、爱、我"放进会议室——如果只看名牌内容不看顺序，两张打分表可能一模一样。这不行：**"狗咬人"和"人咬狗"必须是两回事**。

所以需要给每个座位发**座位号**（位置编码）。老办法是把号码牌直接贴在工件上（加一个位置向量）；现代主流做法更巧妙——**RoPE（旋转位置编码）**。

::: details 小测 1：没有位置编码的 Attention 缺了什么？
缺顺序和距离信息。它只能按内容匹配，分不清"我爱你"和"你爱我"，也不知道两个词隔了多远。
:::

### 2. 时钟指针：转角度，记距离

RoPE 的思路一句话：**给每个词的 Q 和 K 装上时钟指针，两个词的距离就是指针的夹角**。

想象每个 Q/K 向量是一排**两两一组的时钟**：

- 位置 1 的词，指针都从 12 点出发；位置 2 的词，指针多转一格……位置越靠后，转得越多；
- **不同组转速不同**：有的像秒针（转得快，管近距离），有的像分针时针（转得慢，管远距离）；
- 妙处在**点积只看夹角**：位置 m 的 Q 和位置 n 的 K 做点积，转过的角度互相抵消，只留下 **(n − m)** 的差——**相对距离**自然浮现，与"从第几位开始数"无关。

三个容易问的问题：

- **转 Q 和 K，不转 V**——因为分数只由 Q/K 决定，V 是被取走的内容，不需要记距离；
- **指针不改变长短**——旋转不改变向量长度，信息量不丢；
- **几乎没有额外参数**——转速是公式定好的，不是学出来的。

::: details 小测 2：为什么 RoPE 通常只旋转 Q 和 K？
因为位置信息只需要进入"打分"环节：转了 Q 和 K，点积里就带上了相对距离；V 负责"被取走的内容"，转它没有意义，还会扰动内容本身。
:::

### 3. 会议室扩容：不止是指针不够用

想支持更长的上下文，就像把 100 座的会议室扩成 10000 座，至少三道坎：

1. **指针没见过大角度**：训练时指针最多转过 100 格，推理时要转 10000 格——陌生相位，模型没学过（解决思路：RoPE Scaling 等外推技巧）；
2. **打分表平方爆炸**：10000 座意味着 1 亿格的打分表（S² 增长）——计算和显存都吃不消（解决思路：Sliding Window、FlashAttention）；
3. **笔记本堆成山**：每个座位的历史记录（KV Cache）都要留着，越长攒得越多（解决思路：GQA、量化、分页管理）。

::: warning 关键
**长上下文不是"把长度参数改大"就完事**——位置外推、平方计算、缓存显存是三件独立的事，要分别解决。
:::

::: details 小测 3：直接把 RoPE 的缓存表扩到 32K，就能获得 32K 长上下文吗？
不能。表能查到 32K 的角度，但模型训练时从没见过那些相位，效果不可靠（需要外推/微调）；而且就算位置没问题，S² 的注意力计算量和 KV Cache 显存照样压垮你。三道坎一道都绕不开。
:::

### 第 6 章 · 3 句话带走

1. Attention **只认内容不认顺序**，必须有人记座位号——RoPE 就是座位号系统；
2. **转 Q/K 的指针，点积只剩夹角（相对距离）**；不转 V、不加参数、不改长度；
3. 长上下文有三道坎：**陌生相位、平方打分表、KV Cache 山**，要分别解决。

| 术语 | 人话 |
| --- | --- |

| RoPE | 旋转式座位号：转指针、算夹角 |
| 旋转对 / 频率 | 两两一组的时钟指针 / 各组转速 |
| 相对位置 | 夹角（n−m），大家一起挪座位也不变 |
