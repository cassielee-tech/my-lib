## 0. 用例三层模型与选型

一次需求验证通常要三层用例，各有不可替代的覆盖面：

| 层 | 载体 | 覆盖什么 | 不覆盖什么 | 成本 |
|---|---|---|---|---|
| **UT** | `test/ut/**/`，gtest | 函数级纯逻辑（门禁矩阵、窗口有效性、参数校验） | 数据面、选路、内存语义 | 秒级 |
| **ST（仿真桩）** | `test/st/algorithm/testcase/*.cc` | 任务图、选路、内存语义、同步、checker 断言 | 真实带宽、真实对称内存注册 | 分钟级 |
| **真机** | `hccl_test` 二进制 + `NPU_*` 用例 + `run_*.sh` | 真实带宽、真实对称窗口注册、多轮 loop、确定性 | 穷举参数矩阵 | 分钟~小时级 |

**选型口诀**：
- 参数矩阵（dtype/op/数据量/root/拓扑）→ 先 ST 铺开，便宜；
- 运行态开关（对称内存/in-place/图模式）→ 能被 ST 仿真表达的留在 ST，不能的**明确标「留待真机」**（见方法论 §2.3 口径平移），不要用仿真臆造；
- 带宽/注册/确定性 → 只信真机。

## 1. ST 用例写法（仓内仿真）

真实文件：`src/ops/all_gather_v/...`（算子）+ `test/st/algorithm/testcase/all_gather_v_testcase.cc`、`reduce_aicpu_testcase.cc`。

### 1.1 骨架四件套

一个算子的 ST 用例文件，通常拆成四部分职责：

```cpp
// ① fixture：统一管理环境变量的 Set/Reset，避免用例间污染
class ST_ALL_GATHER_V_TEST : public ::testing::Test {
    void TearDown() override { unsetenv("HCCL_OP_EXPANSION_MODE"); ... }
    void SetUp() override { ResetAlgEnvConfigInitState(); }
};

// ② Dispatch：单 rank 的一侧逻辑（分配 send/recv buffer + 调一次 HcclXX）
//    由框架多 rank 并发驱动，传入 rankId / V 类参数 / comm / stream
static HcclResult AllGatherVDispatch(u32 rankId, u64 totalCount, VDataDesTag vDataDes, ...);

// ③ Run（可选）：拓扑 + 参数化的入口，统一走 RunVMultilevelTest
static void RunAllGatherVMultilevel(const TopoMeta& topoInfo, VDataDesTag vDataDes) {
    RunVMultilevelTest(topoInfo, vDataDes, nullptr, AllGatherVDispatch, CheckAllGatherV);
}

// ④ Check：交给 checker（任务图 GenAndCheckGraph → 内存/同步/语义三段校验）
```

关键分工：**Dispatch 只做「我这一 rank 怎么发/收」**，**Check 只做「全局任务图对不对」**，两者解耦后，加新参数（displs 空洞、非法）只需改 Dispatch，不必重写全局校验。

### 1.2 参数化：拓扑与 V 类数组

- 拓扑用 `TopoMeta` / `GenTopoMeta(pod, srv, rank)` 表达层级，注释写清楚「几 pod×几 srv×几 rank=总卡数、topoLevelNums」：

```cpp
GenTopoMeta(topoMeta, 2, 2, 4); // 2pod×2srv×4rank=16卡, topoLevelNums=3
```

- V 类算子用 `VDataDesTag { counts[], displs[], dataType }`，counts 非均匀、displs 空洞都能表达：

```cpp
VDataDesTag vDataDes;
vDataDes.counts  = {2, 3, 1};
vDataDes.displs  = {0, 5, 8};   // 带空洞布局
```

### 1.3 负向用例怎么写（返回码/回退/门禁）

负向用例的核心是**断言「该拒绝/该回退」而非「跑通」**，常用三类：

1. **入参非法**：断言入口返回 `HCCL_E_PARA`：
   ```cpp
   // 非法/重叠 displs、in-place → HCCL_E_PARA
   EXPECT_EQ(RunAllGatherVWithBuffers(topoMeta, vDataDes, false), HCCL_E_PARA);
   ```
   （`st_all_gather_v_invalid_displs_test` / `overlap_displs_test` / `inplace_test`）

2. **强制选路回退**：`setenv("HCCL_ALGO", "reduce:sole{mesh}")` 强行选非白名单算法，断言结果正确（即回退 CCL）：
   ```cpp
   setenv("HCCL_ALGO", "reduce:sole{meshtwoshot}", 1);
   RunReduceTest(...);
   ```
   （`st_reduce_aicpu_2level_16rank_fp32_sum_solemesh_gate_test` / `twoshot_gate_test`——对称门禁否决后恒回退 CCL）

3. **64bit/PROD 门禁**：int64/uint64/fp64/PROD 组合各铺一条，配合 `auto`（自适应选路）与 `spec`（指定 token）双模式。

### 1.4 checker 红线断言（语义契约）

语义 checker 里加「红线断言」直接写进算子语义校验，随全量 ST 零误伤验证：

- `CHK_RED_002`：非 root recvBuf **零写入**（对称路径红线，root-only 直写不得落到非 root）；
- `CHK_RED_003`：sendBuf **零污染**（严格模式下输入只读）。

它们通过 `strictBufferContract` 开关做 AICPU 域 opt-in（HostDPU 等非对称实现按 API 契约不承诺非 root recvBuf 内容，豁免）。落点见 `reduce_semantics_checker.cc` 与 `reduce_aicpu_testcase.cc:179` 的 `root8_nonroot_unwritten_test`。

### 1.5 用例命名与 STC 编号 1:1

`st_all_gather_v_displs_hole_test` ↔ STC `ST_AGV_SYM_005`。命名把「算子_算法/引擎_参数特征」拼清楚，跑完结果直接回填 STC，消灭「结果-用例」映射歧义（方法论 §5.4）。

## 2. UT 用例写法（函数级门禁）

真实文件：`src/ops/op_common/sym_mem_gate.{h,cc}` + `test/ut/common/sym_mem_gate/sym_mem_gate_test.cc`。

### 2.1 最小闭包编入（关键前提）

门禁纯逻辑（`IsReduceOpSymMemAllowed` / `IsReduceOpSymMemDeterministic` / `NeedSymMemInputSide` / `IsSymMemWindowValid`）**从 `op_common.cc` 拆到独立 `sym_mem_gate.cc`**，UT 只编这一两个 .cc + stub，**不链全 `libhccl.so`**（全链路 C++ 符号被裁剪，链库级 UT 编不过）。CMake 里显式列出源码：

```cmake
set(SYMEM_UT_FILES
    sym_mem_gate_test.cc
    stub/hcomm_stub.cc stub/op_common_stub.cc
    ${PROJECT_SOURCE_DIR}/src/ops/op_common/op_common.cc
    ${PROJECT_SOURCE_DIR}/src/ops/op_common/sym_mem_gate.cc
    ${PROJECT_SOURCE_DIR}/src/common/log.cc)   # 按 -ffunction-sections/-Wl,--gc-sections 裁剪未引用依赖
```

### 2.2 门禁矩阵：opType × algName × topoLevelNums

确定性门禁是纯函数，用「矩阵式」铺断言最划算：

```cpp
// 3 参数 opType 分派：AR/RS/RSV 共白名单，Reduce 独立白名单
EXPECT_TRUE(IsReduceOpSymMemDeterministic("AicpuAllReduceSoleNHR", &topo1, HCCL_CMD_ALLREDUCE));
EXPECT_TRUE(IsReduceOpSymMemDeterministic("AicpuReduceSoleNHR", &topo2, HCCL_CMD_REDUCE));   // 多级才放行
EXPECT_FALSE(IsReduceOpSymMemDeterministic("AicpuReduceSoleNHR", &topo1, HCCL_CMD_REDUCE));  // 单级早退
```

覆盖点：各 opType 白名单、级数放行/否决、空 topo 防御、非归约 opType 拒绝。

### 2.3 stub 桩写法（探测接口行为注入）

对称探测接口 `HcclCommSymWinGet` 用 stub 注入「成功/失败/空句柄/调用计数」，这样能测「探测失败回退」「单边探测」等依赖探测结果的路径：

```cpp
extern int g_utSymWinGetRet;        // 探测返回值
extern bool g_utSymWinReturnNull;   // 成功但句柄为空
extern unsigned g_utSymWinGetCalls; // 探测次数（区分 input/output 侧）
extern unsigned g_utSymWinFailFirstN; // 前 N 次强制失败
```

（`test/ut/common/sym_mem_gate/stub/hcomm_stub.h`）

## 3. 真机用例与驱动脚本

### 3.1 工具与用例命名

真机用 CANN 自带 `hccl_test` 单算子二进制（`all_gatherv_test` / `reduce_test` 等），用例名约定 `NPU_<OP>_<FEATURE>_<序号>_<子集>`：

- `NPU_AGV_SYM_001_base_8r_64m` = AGV / 对称 / 001 / base 档 / 8 rank 64MB；
- `NPU_RED_SYM_001_parallel_sym_16r_root15` = Reduce / 对称 / Parallel 算法对称 / root=15。

关键参数（`hccl_test` 通用，详见 `tools/hccl_test/README.md`）：

| 参数 | 含义 | 本需求常用 |
|---|---|---|
| `-b/-e` | min/max bytes | 数据量档（1m/16m/64m/512m） |
| `-n/-w` | iters / warmup_iters | 性能计量控制 |
| `-m 1` | symmetric_memory 开 | 对称 vs base（`-m 0`）对照 |
| `-d/-o/-r` | datatype / op / root | Reduce root 矩阵 |
| `-c` | check 结果校验 | 0 off / 1 quiet |

### 3.2 run_*.sh 驱动：CASES 分片 + 单用例重跑

真机驱动脚本的关键是**能分片 + 能单用例重跑**，分别对应「全量回归」和「失败复现」：

```bash
# 全量（脚本内遍历 CASES）
bash run_agv_reduce_npu_test.sh

# 只重跑失败用例（环境变量注入 CASE 列表）
CASES="NPU_AGV_SYM_001_base_8r_64m NPU_RED_SYM_004_fp32_prod" bash run_agv_reduce_npu_test.sh
```

输出要做**结构化汇总**（每用例一行：`result / algo / symlog / errors / perf`），失败用例自动收进「失败/未知列表」，方便二次重跑（见方法论 §6「自带自动汇总 + 判读说明」）。

### 3.3 plog 解析判读：四字段

真机判读看四个字段，缺一不可：

```text
result  : PASS/UNKNOWN（success=1,failed=0）
algo    : AicpuAllGatherVSoleMesh / AicpuReduceSoleNHR / AicpuReduceParallelMeshNHR
symlog  : HcclCommSymWinRegister,symmetric（对称真的注册成功）
directwrite: reduce root-only direct write enabled（Reduce 直写判据）
errors  : 0（有 ERROR 必须逐条归因）
```

判读要点：**`algo` 必须是 hccl 层算法名**（`Aicpu*`），若看到 HCOMM 层 `Ins*` 或 `algName[]` 空，是版本不对齐，不是结果错误（见 §5.1）。

## 4. 脚本写法经验（env 驱动 + 可复现）

### 4.1 env 驱动单点用例 + 外层循环

用例代码只写「读环境变量的单点用例」，扫描/矩阵/二分全在外层脚本，用例代码零改动零编译（方法论 §5.2）。本需求用的 env 变量：

| 变量 | 用途 |
|---|---|
| `HCCL_OP_EXPANSION_MODE=AI_CPU` | 固定 AICPU 引擎 |
| `HCCL_ALGO=reduce:sole{mesh}` | 强制选路（负向回退） |
| `HCCL_INDEPENDENT_OP=1` | 独立算子模式 |
| `HCCL_ST_SYM_WIN=1` / `HCCL_ST_HCOMM_VERSION` / `LD_PRELOAD=libst_symwin.so` | ST 对称桩 |

对称/非对称对照，靠「带不带这三项 env」切换，而不是复制两份用例。

### 4.2 结果结构化落盘 + 一一对应

- stdout 全量 `tee` 落盘；plog 目录与用例目录一一对应（`npu_logs/<时间戳>/<用例名>/debug/plog/`）；
- 汇总输出 TSV/JSON（逐用例 winner/cost/result），一次批量跑产出结构化结果，不必逐用例起进程（方法论 §4.3）；
- 失败重跑用 `CASES=... bash run_*.sh` 注入式，不写死。

### 4.3 版本/环境自检（本次最大教训）

**真机/远程验证前，先自检部署产物是否就是本次代码编译的**：

```bash
# ① 部署的 libhccl.so 大小/时间 vs 本次编译产物
ls -la --time-style=full-iso /usr/local/Ascend/*/aarch64-linux/lib64/libhccl.so
# ② 若时间/大小对不上（如 14MB vs 本次 21MB），说明没重新部署，别跑，跑了也是替旧代码背锅
```

再补 CANN/HCOMM 版本、`npu-smi` 芯片型号（Ascend950DT/910B 直接影响对称能力）、留 md5 证据。

### 4.4 后台与可复现

- 长任务 `nohup ... < /dev/null > log 2>&1 &`，不断 stdin 否则挂会话（方法论 §1.1）；
- 日志命名带「提交/日期」，脚本头写注释：「什么算通过、偏差多大算异常」。

## 5. 踩坑清单（本次实战）

| 坑 | 现象 | 根因 | 处置 |
|---|---|---|---|
| **旧 so 未部署** | ST 全 36/37 失败、`dataType=255`；真机 `No aicpu algorithm`、`algName[]` 空 | 真机/远程的 `libhccl.so` 是旧版（如 11-14 14MB），与本次代码 ABI/选路不对齐 | 重新 `--pkg`→解压→覆盖 `libhccl.so`（md5 校验）再跑（§3.1 链接 `已安装` so） |
| **对称内存驱动不支持** | `aclrtMemGetAddressRange` 返回 `FEATURE_NOT_SUPPORT`(207000) | 驱动/固件不支持 VMM 地址查询，对称注册必然失败 | 换「支持对称内存」的机器；普通机器验证不了 sym 用例 |
| **ST 链接已安装 so** | `--pkg` 后直接 `--st`，ST 仍连旧 libhccl | ST 用例链接 `${ASCEND_HOME_PATH}/lib64/libhccl.so`，不在 build 目录 | 硬顺序：`--pkg`→安装 so→`--st --noexec`→运行（方法论 §3.1） |
| **host RoCE flush 非致命 ERROR** | 每用例带 `RegisterLocalMr Failed ... ret=3` | HostDpu flush 注册 host RoCE MR 失败，`Flush() will skip` | 非致命，判读时 `grep -v flush_handle`；功能不受影响 |
| **UT 硬编码 x86_64** | `hccl_res_expt.h: No such file`，aarch64 编译失败 | `selector_mapper` CMake 写死 `x86_64-linux` 路径 | master 既有问题；aarch64 验证时跳过该 UT，不算本需求失败 |
| **rsync 误带 x86 缓存** | UT 链接 `i386:x86-64 architecture of gtest.a incompatible` | rsync 把 macOS 的 `third_party/lib_cache`（x86 预编译 gtest）同步过去 | rsync 排除 `third_party/lib_cache`，让远程按 aarch64 重编 |
| **误提交编辑器目录** | `git add -A` 把 `.claude/` 带进提交 | 没有 .gitignore / 本地排除 | `git rm --cached` + 加入 `.git/info/exclude`（备份文件 `.bak_*` 同理不入库） |

## 6. 产物与回填

### 6.1 归档结构（方法论 §8.1）

```text
<归档目录>/
├── 全量运行日志（INFO 级，证据完整）
├── 结构化结果（json/tsv：逐用例 result/algo/winner/perf）
└── 用例/驱动脚本/补丁副本（可复现）
```

### 6.2 STC 回填格式

STC（`05-STC.xlsx`）每行十列：`编号 / 类型 / 测试项 / 标题 / 级别 / 预置条件 / 输入 / 操作步骤 / 预期结果 / 用例执行情况`。

「用例执行情况」回填惯例（方法论 §8.2），**只保留最后一次结论、简洁记录**：

```text
PASS（2026-11-19；2节点×8 Ascend950DT/CANN9.3.0 hccl_test；AGV 5/5 errors=0；
sym 512m 105.50 GB/s（2.14x）、loopTimes=1；algo=AicpuAllGatherVSoleMesh；日志npu_logs/20261119_084827）
```

要点：日期 + 环境 + evidence（提交/版本/日志）+ 本条 specifics（winner/关键数据）；仿真口径要注明「仓内仿真口径」，真机口径注明机型/卡数；不可执行条目写「不适用/留待补验」而非「未执行」。

### 6.3 PR 描述测试结论

PR 描述「测试」段只保留量化结论、简洁为要（删过程性说明）：

```markdown
**NPU 真机（2 节点×8，Ascend950DT，CANN 9.3.0）**：全量 PASS、errors=0——AGV 5/5
（algo=AicpuAllGatherVSoleMesh，对称 512m 2.14x：49.24→105.50 GB/s、loopTimes=1）；
Reduce SoleNHR/Parallel（root∈{0,8,15}、16m/512m 多轮）全通过；非白名单算法/int64/fp64/prod 负向回退全对。
```

过程性记录（如「某次失败系旧 so 导致」）写在 STC 或评论里，不进 PR 描述。
