## 01-1｜AI Infra 分层与执行对象

::: info 本单元目标
围绕 **AI Infra 分层与执行对象** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

先把刚才那张餐厅画抬出来：这个单元要做的，就是把"客人点单到上菜"中间的**每一站**走一遍。下面出现的每一层都不是"又一个要背的名词"，而是传菜链上的一环——你写的一行 `y = x @ weight`，从进后厨到出锅，要依次路过它们。

大模型基础关注“模型要计算什么”，AI Infra 关注“这些计算怎样在真实系统中高效完成”。

一个完整的大模型系统不仅有模型，还包括：

```text
模型与算法
  → 训练/推理引擎
  → 深度学习框架
  → 图编译与算子
  → Runtime、驱动与通信库
  → GPU/NPU、内存与互联网络
```

AI Infra 的工作不是单纯让某个 Kernel 更快，而是在正确性、性能、成本、稳定性和可维护性之间做系统性优化。

常见目标包括：

- **放得下**：模型参数、激活、优化器状态和 KV Cache 不超过容量；
- **算得快**：充分利用矩阵、向量等计算单元；
- **搬得快**：减少 HBM、Host 与设备、设备之间的数据搬运；
- **扩得开**：设备数量增加后仍获得有效加速；
- **跑得稳**：长时间任务不会因抖动、超时或单点故障频繁中断；
- **用得省**：用更少设备、更低能耗完成相同工作量。

### 2. 从一行模型代码到设备执行

假设模型代码中有一行矩阵乘法：

```python
y = x @ weight
```

它并不等于“Python 直接控制计算单元做乘法”。中间会经过多层系统：

![一段模型计算如何穿过 AI Infra 软件栈](/images/ai-infra/model-to-device-execution.svg)

#### 2.1 模型与框架层

框架接收 Tensor 和算子调用，检查 Shape、DType、Device 等信息，并构建动态图或静态计算图。

这一层关心：

- 输入输出是什么；
- 是否需要梯度；
- 算子之间有什么依赖；
- 张量位于哪个设备。

#### 2.2 图编译与算子层

编译器或算子分发系统为当前 Shape 和数据类型选择实现，也可能进行算子融合、常量折叠、内存复用和调度优化。

这一层关心：

- 使用哪个 Kernel；
- 是否需要重新编译；
- 数据布局是否匹配；
- 多个算子能否融合；
- 工作空间需要多少内存。

#### 2.3 Runtime 与驱动层

Runtime 管理设备内存、Stream、Event 和任务提交。Host 通常只是把任务放入设备队列，设备随后异步执行。

这一层关心：

- 任务在哪条 Stream 上；
- 任务之间怎样同步；
- 数据何时搬入或搬出；
- Kernel Launch 是否形成空隙；
- 错误怎样返回 Host。

#### 2.4 硬件层

设备从 HBM 读取数据，搬到更靠近计算单元的片上存储，再由矩阵或向量单元执行，最后写回结果。

这一层关心：

- 计算单元是否吃满；
- HBM 带宽是否饱和；
- 片上空间是否足以复用数据；
- 访存是否连续、对齐；
- 不同流水阶段是否互相等待。

#### 2.5 通信层

如果张量被切到多张设备，原本的本地数据依赖会变成通信。框架调用通信库，通信库根据 Rank、拓扑和消息大小选择算法，再由链路真正传输。

对 HCCL 开发来说，需要同时理解：

```text
上层为什么需要这次通信
      ↓
通信前后的张量布局怎样变化
      ↓
HCCL 怎样把语义拆成传输与归约任务
      ↓
任务怎样落到 Stream、链路和设备执行
```

### 3. Host、Device、Kernel、算子分别是什么

这些词经常一起出现，但含义不同。

| 概念 | 基本解释 |
| --- | --- |
| Host | 通常指运行应用程序、框架和调度逻辑的 CPU 侧 |
| Device | 实际执行大规模张量计算的 GPU/NPU 等加速设备 |
| 算子（Operator） | 面向模型语义的计算单元，例如 MatMul、Softmax、AllReduce |
| Kernel | 算子在特定硬件、Shape、DType 和布局下的一种底层实现 |
| Runtime | 管理内存、Stream、Event、任务下发和设备执行的软件层 |
| Stream | 保持任务顺序的一条异步执行队列 |
| Event | 用于记录进度、计时或建立不同 Stream 依赖的同步对象 |

一个算子不一定只对应一个 Kernel。例如 LayerNorm 可能被拆成多个 Kernel，也可能与相邻算子融合成一个 Kernel。反过来，一个融合 Kernel 也可能承载多个上层算子的语义。

## 01-2｜性能指标与时间线

::: info 本单元目标
围绕 **性能指标与时间线** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

还是那家餐厅：**客人**关心"我的菜多久上"（延迟），**老板**关心"一晚上能翻多少台"（吞吐）——两种"快"经常打架：为了批量出菜（增大 Batch），单桌可能反而等更久。这个单元先拆开几种不冲突的"快"，再教你看一张后厨时间线。

不同场景中的“快”并不相同。

#### 4.1 延迟 Latency

完成一次请求或一次训练 Step 需要多久。

推理常见指标：

- **TTFT**：从请求到第一个 Token 的时间；
- **TPOT**：生成阶段相邻 Token 的平均时间；
- **E2E Latency**：整个请求从开始到结束的时间。

#### 4.2 吞吐 Throughput

单位时间完成多少工作，例如：

- Tokens/s；
- Samples/s；
- Steps/hour；
- Requests/s。

增大 Batch 往往提高吞吐，却可能增加单个请求排队时间和延迟。因此，脱离业务目标谈“性能提升”没有意义。

#### 4.3 扩展效率 Scaling Efficiency

假设单卡吞吐为 $T_1$，$N$ 卡吞吐为 $T_N$：

$$
Speedup(N)=\frac{T_N}{T_1}
$$

$$
ScalingEfficiency(N)=\frac{T_N}{N\times T_1}
$$

若单卡为 100 tokens/s，8 卡为 680 tokens/s：

$$
Speedup=6.8,\qquad ScalingEfficiency=\frac{680}{800}=85\%
$$

多卡吞吐提高了 6.8 倍，但没有达到理想的 8 倍。损失可能来自通信、同步、负载不均衡或额外数据处理。

#### 4.4 利用率 Utilization

利用率描述某种资源被使用的程度，但必须说明是哪种资源：

- 计算单元利用率；
- HBM 带宽利用率；
- 网络带宽利用率；
- 设备忙碌时间占比；
- 模型 FLOPs 利用率。

“设备利用率 100%”不等于“程序已经最优”。设备可能一直在执行低效的小 Kernel，也可能大量时间都在搬数据。

### 5. 一次任务的时间花在哪里

最粗略地看，一次任务可能包含：

$$
T_{total}=T_{host}+T_{compute}+T_{memory}+T_{comm}+T_{sync}+T_{idle}
$$

实际执行中部分阶段可以重叠，所以不能总把各项简单相加。更准确的做法是观察时间线上的依赖关系和关键路径。

![串行执行与计算通信重叠为何产生不同总时延](/images/ai-infra/performance-timeline-overlap.svg)

图中即使通信量完全相同，只要把通信藏到计算之后，总时延就会下降。性能分析不仅要统计“做了多少”，还要判断“它是否暴露在关键路径上”。

#### 5.1 关键路径

关键路径是决定任务最早完成时间的最长依赖链。优化不在关键路径上的操作，可能让局部指标变好，却不能缩短总时间。

例如：

- 某次通信耗时 10 ms，但被 15 ms 计算完全覆盖，它不是当前首要瓶颈；
- 某个 Host 同步只有 2 ms，却阻断所有后续 Kernel，它可能直接增加 2 ms 总时延；
- 某 Rank 比其他 Rank 慢 8 ms，Collective 会让所有 Rank 等待它。

## 01-3｜计算、访存与通信瓶颈

::: info 本单元目标
围绕 **计算、访存与通信瓶颈** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

餐厅变慢只有三种可能：**厨师忙不过来**、**食材运不进来**、**菜品在桌间传来传去**。下面三个小节给的不是三种"标签"，而是三种"证据链"——判断当前是哪一种在拖时间时，先想画面，再用指标对照确认。

#### 6.1 Compute-bound：计算受限

计算单元已接近有效峰值，继续减少访存未必能显著加速。常见于较大的、形状友好的 GEMM。

典型证据：

- 矩阵计算单元忙碌；
- 有效 FLOPs/s 较高；
- HBM 带宽未必达到峰值；
- 增加理论带宽对耗时改善有限。

常见优化方向：更好的 Tiling、提高并行度、使用低精度计算单元、改善矩阵 Shape。

#### 6.2 Memory-bound：访存受限

计算单元在等待数据，性能主要受 HBM 或其他存储层带宽限制。Norm、激活函数、逐元素操作以及 Decode 中读取大量权重，常容易受到带宽影响。

典型证据：

- HBM 带宽接近设备有效上限；
- 计算利用率不高；
- 每读写很多字节只完成少量 FLOPs；
- 融合算子、减少中间写回后明显加速。

常见优化方向：算子融合、数据复用、连续访存、减少布局转换、量化。

#### 6.3 Communication-bound：通信受限

多设备执行中，大量时间花在设备间传输、同步或等待慢 Rank。

典型证据：

- Collective 位于关键路径且暴露时间长；
- 增加卡数后扩展效率快速下降；
- 链路带宽不足或小消息启动开销突出；
- Rank 间到达 Collective 的时间差很大。

常见优化方向：通信计算重叠、更合适的 Collective 算法、增大消息聚合粒度、分层通信、改善负载均衡。

::: warning 三类瓶颈不是互斥标签
同一次训练可能在 GEMM 阶段 Compute-bound，在 Norm 阶段 Memory-bound，在梯度同步阶段 Communication-bound。必须针对具体时间段和算子下结论。
:::

## 01-4｜数量级、算术强度与峰值

::: info 本单元目标
围绕 **数量级、算术强度与峰值** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

动手测之前先动笔。这个单元教的三笔"下界账"，相当于**上菜前的估时**：一道炖菜至少要 40 分钟，你 20 分钟就开始催，催的就是不该催的人——先算下界，能避免在不可能快的地方白费力气。

在打开 Profiling 工具前，可以先做三个粗估算。

#### 7.1 计算时间下界

$$
T_{compute}^{min}=\frac{FLOPs}{Peak\ FLOPs/s}
$$

假设一个算子需要 20 TFLOPs，设备理论峰值为 200 TFLOPs/s：

$$
T_{compute}^{min}=\frac{20}{200}s=100ms
$$

这是理想下界。真实程序通常达不到理论峰值。

#### 7.2 访存时间下界

$$
T_{memory}^{min}=\frac{Bytes}{MemoryBandwidth}
$$

若需要从 HBM 搬运 120 GB，有效带宽为 1.2 TB/s：

$$
T_{memory}^{min}=100ms
$$

#### 7.3 通信时间下界

简单的延迟—带宽模型为：

$$
T_{comm}\approx\alpha\times R+\frac{Bytes}{EffectiveBandwidth}
$$

- $\alpha$：一次通信步骤的固定启动与同步代价；
- $R$：通信轮次；
- `Bytes`：实际经过链路的数据量；
- `EffectiveBandwidth`：考虑拓扑和协议后的有效带宽。

小消息通常更容易被 $\alpha$ 主导，大消息更容易被带宽项主导。这也是通信库需要根据消息大小选择不同算法的原因之一。

### 8. 算术强度：连接计算与访存

算术强度 Arithmetic Intensity 定义为：

$$
AI=\frac{FLOPs}{Bytes\ moved}
$$

它表示每搬运一个 Byte 数据完成多少次计算。

- AI 低：数据刚搬来只算几下，更可能 Memory-bound；
- AI 高：同一份数据被反复计算，更可能 Compute-bound。

下一阶段会专门学习 Roofline Model。现在先记住：**性能不仅由 FLOPs 决定，也由为了完成这些 FLOPs 必须搬多少数据决定。**

### 9. 为什么理论峰值不能直接代表实际性能

硬件规格中的峰值往往依赖理想条件：

- 特定数据类型；
- 足够大的规则矩阵；
- 完美的数据对齐；
- 没有依赖和气泡；
- 数据已经及时到达计算单元；
- 所有并行单元都获得均匀任务。

真实模型可能受到以下损失：

- Shape 太小或维度不友好；
- Kernel Launch 过于频繁；
- 数据布局转换；
- 分支和 Padding；
- Pipeline 气泡；
- HBM、片上 Buffer 或网络等待；
- 不同 Rank 负载不均衡。

所以性能优化的任务，是解释“理论能力为什么没有转化为有效吞吐”。

## 01-5｜性能分析流程与常见误区

::: info 本单元目标
围绕 **性能分析流程与常见误区** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

最后这个单元是一套**办案流程**：拿到"餐厅整体变慢"的现象，先看整条时间线找到关键路径，再缩小到具体工序，提出一个可以被实验推翻的假设——而不是一上来就冲进后厨盯着最忙的那个厨师。

![从性能现象到根因验证的分析漏斗](/images/ai-infra/performance-analysis-funnel.svg)

#### 第一步：定义问题和指标

错误示例：“训练有点慢。”

更好的描述：“模型在 8 卡下平均 Step Time 为 2.4 s，目标是 2.0 s；与 4 卡相比，扩展效率从 91% 降到 76%。”

明确：

- 优化对象；
- 工作负载和输入 Shape；
- 硬件与软件版本；
- 基准值和目标值；
- 关注延迟、吞吐、成本还是扩展效率。

#### 第二步：建立可复现基线

固定模型、Batch、Sequence Length、精度、设备数、预热次数和测量区间。不要把第一次编译、数据加载或缓存预热混入稳定运行时间。

#### 第三步：看端到端时间线

先看整体，不要一开始钻进某个 Kernel：

- Host 是否频繁空等；
- Kernel 之间是否有大空隙；
- 通信是否位于关键路径；
- 不同 Rank 是否同步到达；
- 是否存在周期性抖动。

#### 第四步：缩小到阶段和算子

把训练 Step 拆成数据加载、前向、反向、通信、优化器，再定位占比最大的阶段和算子。

#### 第五步：提出可以验证的假设

例如：

- “这个算子受 HBM 带宽限制”；
- “小 Kernel 过多导致 Launch Gap”；
- “Rank 3 数据处理慢，使其他 Rank 在 AllReduce 等待”；
- “通信没有与反向计算重叠”。

#### 第六步：用对照实验验证

一次只改变一个主要变量，例如 Batch、消息大小、设备数、数据类型或是否开启融合。若多个变量一起变化，就很难知道收益来自哪里。

#### 第七步：验证端到端收益

局部 Kernel 加快不等于任务加快。最终必须重新测量端到端指标，并检查正确性、稳定性和资源占用是否退化。

### 11. 性能分析中的常见错误

1. **只看平均值**：平均值会掩盖 P99 抖动和个别慢 Rank。
2. **只看算子耗时排序**：高占比算子不一定有优化空间，也不一定在关键路径上。
3. **把相关性当因果**：网络利用率高与通信慢同时出现，不代表带宽一定是唯一根因。
4. **混用不同测试条件**：Batch、Shape、精度或版本不同的结果不能直接比较。
5. **忽略预热与编译**：首次运行开销与稳态性能是两个问题。
6. **只优化局部**：一个 Kernel 快了，却引入额外布局转换或同步，总时间可能更慢。
7. **只看单 Rank**：集合通信性能由整个通信组和最慢参与者共同决定。
8. **没有正确性检查**：低精度或异步优化可能提高速度，却造成数值错误或竞态。

2. 算子和 Kernel 有什么区别？

4. Latency、Throughput 和 Scaling Efficiency 分别描述什么？
5. 为什么设备利用率 100% 不代表程序已最优？
6. 什么是关键路径？
7. Compute-bound、Memory-bound、Communication-bound 各自受什么限制？
8. 算术强度的定义是什么？
9. 小消息通信为什么更容易受固定延迟影响？
10. 为什么局部 Kernel 加速后必须重新测量端到端指标？

::: details 自测答案

1. 模型算法关注要计算的函数与学习目标；AI Infra 关注这些计算如何在硬件和集群上高效、稳定、经济地执行。
2. 算子是上层计算语义，Kernel 是它针对特定硬件、Shape、数据类型和布局的底层实现；二者不一定一一对应。
3. 管理设备内存、Stream、Event、任务下发、同步以及 Host 与 Device 之间的协作。
4. Latency 是完成一次任务的时间；Throughput 是单位时间完成的工作量；Scaling Efficiency 衡量多设备吞吐相对理想线性增长的比例。
5. 它可能只表示设备一直有任务执行，但这些任务可能 Shape 很小、计算效率低或主要在搬运数据。
6. 决定任务最早完成时间的最长依赖链；只有缩短关键路径，端到端时间才一定下降。
7. 分别受计算单元吞吐、存储系统带宽和设备间通信/同步能力限制。
8. $AI=FLOPs/Bytes\ moved$，表示每搬运一个 Byte 完成多少次计算。
9. 总时间中的启动、同步等固定成本不会随消息字节数同比下降，小消息的数据传输时间很短，固定成本占比因而更大。
10. 局部优化可能不在关键路径上，也可能引入额外转换、同步或资源竞争，只有端到端测量才能确认真实收益。

:::

### 15. 本课小结

- AI Infra 连接模型、框架、编译、Runtime、算子、通信库和硬件；
- 一行模型代码要经过多层软件，最终才成为设备上的计算与搬运任务；
- 性能目标必须明确是延迟、吞吐、扩展效率、成本还是稳定性；
- 性能问题可初步分为计算、访存和通信受限，但结论必须针对具体阶段；
- FLOPs、搬运字节数和通信轮次可以帮助建立理论下界；
- 时间线和关键路径比孤立的算子耗时更能解释端到端性能；
- 正确流程是定义指标、建立基线、观察全局、提出假设、对照验证、确认端到端收益。
