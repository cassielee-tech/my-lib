# 第 5 章｜数据并行与 DDP

> 本课目标：从"为什么不同步梯度就会发散"推出 DP 的通信必然性；算清 DDP 每步的通信账；理解 Bucket 分桶与通信计算重叠各自的动机与权衡；能手写朴素 DDP 并说清生产级 DDP 多做了什么。

## 本章导学

::: tip 本课只记住 3 件事
1. **DP = 完整模型复制 + 数据切片 + 梯度取平均**：各卡看到不同数据、梯度必然不同，不做 AllReduce 就是 N 个各自漂移的模型——通信是数学正确性的一部分，不是性能优化。
2. **Bucket 分桶是粒度的折中**：按单参数通信 → 小消息 α 主导；全量一次通信 → 无法与反向重叠——桶"攒一批再发"，平衡两头。
3. **重叠的前提天然成立**：通信的是已算完的梯度、依赖它的是反向结束后的 `optimizer.step()`——中间整段反向都可以与通信并行，双流时间线把 M 秒藏进 N 秒。
:::

## 05-1｜DP 语义：为什么必须 AllReduce

::: info 本单元目标
围绕 **"梯度取平均的数学必然性"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

先把分店那张画立起来：N 家店各接待各的客人，各算各的利润——如果月底不统一对账，下个月 N 家店就按 N 套进货策略各走各路，连锁当场散伙。这个单元要做的，就是把"必须对账"这句话背后的数学推导清楚，再量一量这本账本身有多厚。

### 1. 数据并行在切什么

与后面所有章节不同，DP **不切模型**：每张卡一份完整副本，切的是**数据**——global batch 均分为 N 份，每卡各喂一份。

```text
rank 0: 模型副本 + batch[0:B/N]     rank 1: 模型副本 + batch[B/N:2B/N]
rank 2: 模型副本 + batch[...]        rank 3: 模型副本 + batch[...]
```

前向各算各的 loss，反向各算各的梯度——到这里为止**零通信**。通信发生在哪？反向结束、更新之前。

### 2. 为什么不做 AllReduce 就会发散

关键事实：**各卡数据不同 → 各卡梯度不同**。如果各自直接更新：

```text
θ⁽⁰⁾ ← θ - lr·g⁽⁰⁾        ← rank 0 只往自己的数据方向走
θ⁽¹⁾ ← θ - lr·g⁽¹⁾        ← rank 1 走另一个方向
……
```

一步之后，N 张卡上出现 **N 个不同的模型**；下一步的数据再进来，差异继续放大——这不是"变慢"，是**训练在数学上已经错了**。

正确语义等价于"大 batch SGD"：

$$
\bar{g} = \frac{1}{N}\sum_{i=0}^{N-1} g^{(i)},\qquad \theta \leftarrow \theta - \text{lr}\cdot\bar{g}
$$

$\bar g$ 的求解动作正是 **AllReduce(avg)**（回扣 [《集合通信》01-2 原语卡片](/comm-ascend/01-collective-semantics-cost.md#_01-2-六个核心原语的语义卡片)）——所以 DP 的通信不是"性能问题"，是**算法本身的一步**。

#### 2.1 每步通信账

用 Ring 账本（[《集合通信》02-4](/comm-ascend/02-ring-allreduce.md#_02-4-ring-的账本与变体)）给 DDP 每步记账：

- 通信对象：**全量梯度** $S = 2\times$参数量（BF16 字节）；
- 每卡流量：$2S\cdot\frac{N-1}{N}$——**与 batch 大小无关**；
- 扩展性来源：batch 越大 → 反向计算越久 → 同样的通信量被越厚的计算摊薄。

**算例**：7.5B 模型、BF16、8 卡（机间 25 GB/s）：$S = 15$ GB，每卡流量 $2\times15\times\frac78 \approx 26$ GB，通信时间 $\approx 1.05$ s；batch 32×2048 token 的反向约 10 s（@300 TFLOPS）——**通信约占一步的 10%**，重叠后几乎可藏（05-4 展开）。

::: tip 位置回顾
"梯度 AllReduce 发生在反向与 `optimizer.step()` 之间"——这句在 [《训练与推理系统》01-4](/model-systems/01-training-loop.md#_01-4-训练显存与梯度通信) 出现过的话，现在有了完整的推导与账本。
:::

## 05-2｜从朴素 DDP 到生产级 DDP

::: info 本单元目标
围绕 **"生产级 DDP 比朴素版多做的三件事"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

用对账的话说：下面的十行朴素版相当于"等月底账全部记完，再一次性寄出"——数学上对，但寄账那段时间全店停工。生产级 DDP 做的全部事情，就是让账"边记边寄"。读那三件事时可以一直带着这个问题：它在消灭哪一段停工？

### 3. 朴素版：十行写对 DP

语义清楚后，朴实现呼之欲出——在 [第 4 章](04-distributed-basics.md#_04-4-工程实操-跑起来与排障)的骨架上加三行：

```python
model = ...
for data in loader:                      # 每卡各自的数据分片
    loss = model(data).loss
    loss.backward()                      # 各算各的梯度
    for p in model.parameters():         # ★ 全量梯度取平均
        dist.all_reduce(p.grad)          #   （world group 上）
        p.grad /= world_size
    optimizer.step()                     # 同步更新 → 副本保持一致
    optimizer.zero_grad()
```

数学上完全正确。但性能上有个硬伤：**反向全部结束才发起第一次通信**——通信 M 秒 + 反向 N 秒 串行相加，一步 = N+M。生产级 DDP 的全部工作就是消灭这个串行。

::: warning 别用错 DP
`torch.nn.DataParallel`（单进程多线程）受 GIL 与线程调度拖累，早已不推荐；本章的 `DistributedDataParallel`（DDP）= 多进程 + 通信库，与第 4 章"一进程一卡"对齐。
:::

### 4. 生产级 DDP 多做的三件事

`DistributedDataParallel(model, device_ids=[local_rank])` 包一层，它做了：

1. **起点对齐**：构造时把 rank 0 的参数 **Broadcast** 给全员——保证 N 个副本从同一起点出发（不然第 5.1 节的"同步"从第一步就不成立）；
2. **梯度就绪即通信**：给每个参数注册反向 hook——**某个参数的梯度一算完，立刻发起它的通信**，不等反向结束。通信与剩余层的反向并行，这是重叠的入口；
3. **Bucket 组织**：就绪即发的粒度不是"单参数"而是"桶"——按反向完成顺序攒桶、桶满即发（05-3 展开）。

从本章往下钻一层：DDP 发起的每次 AllReduce 最终走进 [HCCL 的 AllReduce 调用链](/comm-ascend/hccl-hcomm/06-allreduce-call-chain.md)（HCCL 源码 6）——框架侧"什么时候发"，通信库侧"怎么跑"，正好接成一条线。

```text
DDP（本章）：何时发 → 逐桶、就绪即发
HCCL（HCCL 源码 6）：怎么跑 → 算法选择 → 引擎执行 → 环形流水
```

## 05-3｜Bucket：分桶的艺术

::: info 本单元目标
围绕 **"桶大小的两端权衡"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

寄账有两个极端：记一笔寄一笔，快递起步价（延迟 α）能把你逼疯；月底一次寄完，全店停工等快递。折中是**分章寄**——这一章记完，快递立刻出发，记账员继续记下一章。桶就是"章"，下面两张账单算的是这一章该多厚。

"梯度就绪即通信"的粒度怎么选？两个极端都不可行——**Bucket 是折中的艺术**。

### 5. 两个极端的账

| 粒度 | 通信次数 | 每次大小 | 问题 |
| --- | --- | --- | --- |
| 按单参数 | 数千~数万次/步 | KB 级 | **α 主导**：每次启动成本 × 巨量次数（回扣 [《集合通信》03-3 分界线](/comm-ascend/03-tree-algorithms-selection.md#_03-3-选型地图-大小消息的分界线)） |
| 全量一次 | 1 次/步 | 全部梯度（GB 级） | **无法重叠**：必须等反向全部结束才能发（05-2 的朴素版硬伤） |
| **Bucket** ✅ | 梯度总量 ÷ 桶容量 | 默认 25 MB 级 | 大到 β 高效、小到反向早期就能发出第一桶 |

桶大小是一个**可调旋钮**（`bucket_cap_mb`，PyTorch 默认 25 MB）：桶大 → 次数少（带宽利用率高）但重叠窗口小；桶小 → 重叠充分但滑向小消息化。这与 [《集合通信》05-3 的 Chunk](/comm-ascend/05-topology-hierarchical-overlap.md#_05-3-chunk-与-channel-拆小、铺满) 是同一个"粒度权衡"在不同层的化身。

### 6. 桶的编排：按反向顺序装填

DDP 不是按模型定义顺序装桶，而是**按反向传播的完成顺序**：

1. **启动时重排**：DDP 分析（或首次反向时记录）各参数梯度的就绪顺序，按此顺序把参数映射进桶——**先算完的梯度，排进先出发的桶**；
2. **首桶刻意小**：让第一桶尽早凑满、尽早发出——流水线"尽快点燃"，后续桶均衡大小；
3. **桶满即发**：某桶内全部梯度就绪 → 立即对该桶发起一次 AllReduce（在 world group 上，Ring 算法，回扣 [《集合通信》02 章](/comm-ascend/02-ring-allreduce.md#_02-1-为什么是环-拓扑的自然性)）。

```text
反向完成顺序（从输出层往输入层）：
  out_proj → norm2 → mlp.w2 → mlp.w1 → norm1 → attn.wv → ... → embed

桶 0（小）：out_proj, norm2          ← 反向刚开始就凑满、就发出
桶 1：      mlp.w2, mlp.w1
桶 2：      norm1, attn.wv, ...
```

::: tip 一句话
**Bucket 把"何时通信"从"反向结束后"提前到"反向进行中"**，把"发什么"从"单参数"攒成"25 MB"——一次改动同时解决 α 主导与无法重叠两个极端问题。
:::

## 05-4｜通信计算重叠：把等待藏起来

::: info 本单元目标
围绕 **"DDP 重叠的三个条件为何天然成立"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

现在把两条流水线摆在一起看：记账员记后面几章时，前面几章已经在路上——这就是重叠。它能成立的原因很朴素：寄的是**已经记完的章**，等货的只有月底统一进货（`optimizer.step()`）。这个单元讲这种摆法怎么落地、哪几段藏不住。

### 7. 双流时间线

[《单卡执行系统》07-4](/execution-parallel/07-stream-event-async.md#_07-4-重叠的艺术-让设备闲不下来) 给过重叠的三个通用条件——DDP 是它们最经典的落地：

| 通用条件 | DDP 中的化身 |
| --- | --- |
| 资源独立 | 计算 stream 与通信 stream（HCCL 挂在通信流上，不占 AI Core） |
| 依赖允许 | 通信的是**已就绪的梯度**；依赖它的是 `optimizer.step()`——在反向全部结束之后 |
| 显式编排 | 桶满 → 记录 Event → 通信流等 Event 后发 AllReduce；step 前等最后一桶完成 |

```text
计算流：  [反向: 桶2的层][桶1的层][桶0的层]═══╗
                     └Event┘  └Event┘        ║ [optimizer.step]
通信流：  ·········[等桶0]═AllReduce═[等桶1]═AllReduce═╣
                                              ║
时间 ────────────────────────────────────────► max(反向, 通信) ≪ 反向+通信
```

**收益**：串行 N+M 变成约 `max(N, M)`。用 05-1 的算例（反向 10 s、通信 1 s）：一步从 11 s 回到约 10 s——通信被整段藏进反向。

### 8. 边界：藏不住的部分

重叠不是魔法，三条边界要记牢：

1. **通信 > 反向时藏不住**：小模型、大梯度、慢网络（如跨机 8 卡跑 7B 模型）——通信 M 超过反向 N，多出来的部分照样裸奔。出路：压通信量（梯度量化/压缩）或换算法（[HCCL 源码 5](/comm-ascend/hccl-hcomm/05-coll-algorithms.md)），更彻底的是让通信量本身降下来——**第 9 章 ZeRO/FSDP 的预告**；
2. **最后的同步点无法去掉**：`optimizer.step()` 必须等最后一桶——同步语义的下界，省不掉，只能靠桶的排布让它早到；
3. **梯度累积是免费省钱**：累积 K 步再通信 → 通信次数 ÷ K（数学上等价于 K 倍大 batch 的 DP，回扣 [《训练与推理系统》01-2](/model-systems/01-training-loop.md#_01-2-梯度累积与-adamw-状态)）。

::: tip 本章收束
DDP 一步的完整画像：**world group 上、逐桶发起的 Ring AllReduce，桶按反向顺序装填，通信流与计算流用 Event 编排重叠**。下一章进入 Tensor Parallel——通信从"步与步之间"走进"层与层内部"，从 world group 走进机内小组。
:::

8. DDP 按什么顺序装桶？为什么首桶要小？
9. DDP 重叠的三个通用条件分别对应什么？
10. 哪些通信是重叠藏不住的？各有什么出路？

::: details 自测答案

1. 切数据（global batch 均分）；每卡一份完整模型副本 + 自己的数据分片。
2. N 张卡出现 N 个不同模型且差异逐步放大；因为缺失的是算法本身的取平均步骤，正确性缺失而非效率缺失。
3. $\bar g=\frac1N\sum g^{(i)}$，$\theta\leftarrow\theta-\text{lr}\cdot\bar g$——等价于用整个 global batch 算一次梯度再更新。
4. 全量梯度 $S=2\times$参数量（BF16 字节）；每卡 $2S\frac{N-1}{N}$；通信量只由模型决定，batch 增大只增加反向时长、摊薄通信占比。
5. 通信必须等反向全部结束才发起，一步 = 反向 N + 通信 M 串行相加。
6. 构造时 Broadcast rank 0 参数对齐起点；梯度就绪即触发通信（backward hook）；Bucket 组织通信粒度。
7. 单参数：次数巨量、α 主导；全量一次：无法与反向重叠。Bucket 攒成 25 MB 级：大到带宽高效、小到反向早期即可发出。
8. 按反向传播完成顺序（先算完先进桶）；首桶小使其尽早凑满发出、尽快点燃流水线，后续桶均衡。
9. 资源独立 = 计算/通信双流；依赖允许 = 通信已就绪梯度、消费者是 step；显式编排 = Event 同步 + step 前等最后一桶。
10. 通信时长超过反向的部分（出路：压缩/换算法/减量——ZeRO）；step 前的最后同步（语义下界，靠排布提前）；梯度累积可整段免掉。

:::

### 11. 本课小结

- DP 的通信是算法的一部分：AllReduce(avg) ⇔ 大 batch SGD；
- 每卡流量 $2S\frac{N-1}{N}$ 与 batch 无关——DP 的扩展性来自计算摊薄通信；
- DDP 三件事：起点对齐、就绪即发、分桶组织；
- Bucket 解决"α 主导 vs 无法重叠"的两难，按反向顺序装填、首桶小先点燃；
- 双流重叠把 N+M 压到 max(N,M)；藏不住的部分各有各的出路。
