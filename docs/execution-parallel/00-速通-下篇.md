## 第 1 章｜MoE、Router 与 Expert Parallel

完整正文 → [第 1 章｜MoE、Router 与 Expert Parallel](01-moe-expert-parallel.md)

> 适用：时间紧，或完整版跟不动时。这页用一家医院讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 分诊台医院：养一百个医生，每人只看两个病人

普通模型（Dense）像**全科诊所**：每个病人来了，全部医生都上手——知识多，但每个病人都贵。

**MoE 是分诊台医院**：

- **Router（分诊台护士）**：看一眼病人（Token），决定挂哪几个科；
- **Expert（专科医生）**：很多位，但每人只在自己的诊室等；
- **Top-k**：每个病人**只挂 k 个科**（常见 k=1 或 2）。

医院还通常**只把深加工工位（FFN/MLP）换成多科诊室**——会议室（Attention）等其他科室照旧，不是整座医院复制八份。

于是出现一个奇妙的账本：**全院养着 100 位医生（总参数巨大），但每个病人只惊动 2 位（单 Token 计算稀疏）**。这就是 MoE 的核心交易：**用显存买知识，用稀疏省计算**。

注意：没被挂号的医生也要发工资——**全部 Expert 的权重都占显存**，不管今天有没有病人。

::: details 小测 1：MoE 总参数量大，每个 Token 的计算量也大吗？
不一定。Router 让每个 Token 只激活 Top-k 个 Expert（比如 128 位医生里挑 2 位），单 Token 的计算量只看被激活的少数专家。总参数决定显存，激活参数决定计算——两个数字要分开看。
:::

### 2. 挂号不均的连锁反应

分诊台没有上帝视角，**挂号会冷热不均**：某几个科天天爆满，另一些科闲得喝茶。

这一件事同时引发三层灾难：

1. **模型层面**：爆满科室的病人被压缩、冷门科室的医生学不到东西（训练不充分）；
2. **设备层面**：排队严重的科成为**全院瓶颈**——所有人都等它（Straggler）；
3. **效率层面**：单个医生一次只看两三个病人，**诊室利用率极低**（小 GEMM 效率差）。

解法是**Capacity（接诊上限）**：给每个科设每日限额，超出限额的挂号被排队填充或丢弃。同时训练时加**辅助 Loss** 鼓励分诊台摊平负载。代价：限额意味着**可能丢病人**（Token 被丢弃/填充）——模型质量和负载均衡是一对要谈判的矛盾。

::: details 小测 2：为什么需要 Expert Capacity？
不设上限的话，热门 Expert 的输入张量大小完全随路由波动，无法预留稳定的显存和计算规划，还会让排队失控。设上限让每科接诊量可控、张量尺寸固定；代价是溢出的 Token 可能被填充或丢弃。
:::

### 3. 多院区：AlltoAll 登场

医生太多，一家院区放不下——**Expert Parallel（EP）把科室分布到多家分院**（多张卡）。

现在病人要跨院区看病了，前向需要**两次全院快递**：

```text
Dispatch AlltoAll：把每个 Token 送到「它挂的医生所在的分院」
  → 各地医生看诊
Combine AlltoAll：把诊断结果寄回「病人原来的医院」，按原顺序拼回病历
```

为什么用 AlltoAll 而不是 AllGather？**AllGather 是"每家医院都拿到所有病人"**——绝大部分病人和你没关系，纯浪费。AlltoAll 是"各家只收自己要看的病人"——精准的多对多交换。

和《模型全景》第 1 章的 AllReduce 对比一下语义：AllReduce 汇总的是**同一份东西的不同意见**（DP 的梯度）；AlltoAll 交换的是**不同的东西给不同的人**（MoE 的 Token）。

::: details 小测 3：MoE 前向为什么需要两次 AlltoAll？
Dispatch 把 Token 发到 Expert 所在的 Rank 完成计算；但最终输出必须回到 Token 原来的位置、按原顺序拼接，否则后面的层就乱了。所以一次"发过去看病"，一次"把结果寄回来"。反向传播还有对应的逆向交换。
:::

### 第 1 章 · 3 句话带走

1. MoE = **分诊台医院**：总参数（显存）大，单 Token 激活（计算）稀疏——两个账分开算；
2. **挂号不均**同时伤害模型质量、设备负载和 GEMM 效率，Capacity 是带代价的解药；
3. EP 的跨院区看病 = **Dispatch + Combine 两次 AlltoAll**，与 AllReduce 的"汇总意见"语义不同。

## 第 2 章｜现代模型的效率设计：GQA、量化与长上下文

完整正文 → [第 2 章｜现代模型的效率设计：GQA、量化与长上下文](02-efficient-llm-design.md)

### 1. 记者们共享档案柜：MHA、MQA、GQA

还记得《训练与推理系统》第 3 章的"桌上笔记"（KV Cache）吗？长会话+高并发时，**笔记比课本还占地方**。怎么省？

先看现状（**MHA**）：编辑部有 32 个记者（Q 头），**每人一个专属档案柜**（自己的 K/V 头）——柜子总共 32 组。

省钱思路：**柜子共享，记者不减**。

| 方案 | 档案柜 | 效果 |
| --- | --- | --- |
| **MHA** | 每人一个柜 | 效果最好，柜子最贵 |
| **GQA** | 每 4 人共用一个柜 | 柜子降到 1/4，效果只掉一点点（现代主流） |
| **MQA** | 全编辑部共用一个柜 | 柜子最少，效果掉得多些 |

关键澄清：**减的是档案柜（K/V 头），不是记者（Q 头）**。省下来的直接对应：KV Cache 显存 ↓、Decode 时每字要读的笔记量 ↓。

::: details 小测 1：GQA 会减少 Q 头（记者）吗？
不会。GQA 只共享 K/V 头（档案柜）——40 个 Q 头配 8 个 KV 头是常见配置，KV Cache 直接降到 MHA 的 8/40。Q 头数量和表达能力基本保留。
:::

### 2. 口袋书工程：量化

**量化 = 把精装书印成口袋书**：原来每个数字用 16 位存（BF16），现在 8 位（INT8）甚至 4 位（INT4）——**书架（显存）直接省一半或四分之三**。

三个必须知道的细节：

1. **印什么书分三档**：只压**权重**（Weight-Only，书压薄）、权重和**便签**（激活）一起压（W8A8）、压**档案柜**（KV Cache 量化）——压的东西不同，收益位置不同；
2. **要配换算表**（Scale）：低位整数和原浮点范围之间要建映射，读的时候还得换算回来（反量化）——**换算本身有开销**；
3. **省书架 ≠ 省时间**：读口袋书还是要换算，速度快慢取决于**印刷厂设备**（硬件和 Kernel 是否支持低位计算）。INT4 的书不保证读得快 4 倍——**位宽直接决定的只有存储量**。

::: details 小测 2：权重从 BF16 换成 INT4，推理一定快 4 倍吗？
不一定。存储量确实变成 1/4，但实际速度还取决于：硬件有没有 4-bit 计算单元、反量化的开销、Kernel 写得好不好、以及原来的瓶颈是不是显存带宽。如果原瓶颈是别的，压书架根本帮不上忙。
:::

### 3. 四件不同的工具，别拿锤子拧螺丝

长上下文和推理优化领域，四个名字经常被混为一谈，其实**各治一种病**：

| 工具 | 治什么病 | 机理 |
| --- | --- | --- |
| **FlashAttention** | 打分表来回搬运太贵 | 精确全量计算，只省搬运（IO），**不改数学** |
| **Sliding Window** | 全场打分开不起 | 干脆**只跟附近 W 个座位开会**（近似，改了关注范围） |
| **RoPE Scaling** | 座位号没见过大角度 | 改转速/缩放角度，治**位置外推**，不改计算量 |
| **PagedAttention** | 笔记本分配浪费碎片 | 按需分页租格子，治**管理**，不减少笔记内容本身 |

诊断口诀：先分清病根是**搬运、范围、外推还是碎片**，再选工具。

::: details 小测 3：FlashAttention 和 Sliding Window 都让长文本变快，本质区别是什么？
FlashAttention 算的还是精确的全量注意力，只是换了执行方式省 IO——结果不变；Sliding Window 直接砍掉了远距离的关注——计算量真的变少，但这是近似，模型行为也变了。一个是"跑得聪明"，一个是"少跑路"。
:::

### 第 2 章 · 3 句话带走

1. GQA/MQA 是**记者共享档案柜**：减 K/V 头不减 Q 头，直接省 KV Cache；
2. 量化是**口袋书工程**：位宽直接决定的只有存储，速度还看硬件与 Kernel；
3. 四件工具各治一病：**FlashAttention 治搬运、Window 砍范围、RoPE Scaling 治外推、Paged 治碎片**。

## 第 3 章｜综合实战：拆解一个现代 LLM

完整正文 → [第 3 章｜综合实战：拆解一个现代 LLM](03-llm-systems-analysis.md)

> 适用：时间紧，或完整版跟不动时。这页用"一家店的开业预算"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 看图纸，算设备清单：从配置到参数量

拿到一个模型的配置文件（图纸），就能**心算出它的家底**：

```text
H（隐藏宽度）、I（中间宽度）、L（层数）、V（词表大小）、头数……
  → 每层：Attention ≈ 4H² + MLP ≈ 3HI
  → 全部层 × L，再加词表查表 V×H
  → 总参数量 P ≈ ……
```

两个省钱设计要认得：

- **GQA**：K/V 投影比 Q 投影窄（柜子少），每层再省一笔；
- **权重共享**：进门查表和出门打分（Embedding 与 LM Head）**共用同一份 V×H 参数**——直接省一个大件。

最后乘上每个参数的字节数（BF16 = 2 字节），就得到**权重显存**：7.5B 参数 ≈ 15 GB。

::: details 小测 1：为什么 GQA 模型的 K/V 投影参数比 Q 投影少？
Q 有 32 个头（投影输出宽 4096），共享后 K/V 各只有 8 个头（输出宽 1024）。头少 → 投影矩阵窄 → 参数少。这正是第 2 章"档案柜"在参数账本上的体现。
:::

### 2. 仓库和电费：显存与算力的两本账

**仓库账（显存）**——推理时：权重 + 笔记（KV Cache）+ 工作台（激活/Workspace）。**训练时还要再添三样**：

```text
权重 + 梯度（同样大小）+ 优化器两本账（AdamW 的 m 和 v，又是两份）
→ 常说"训练显存 ≈ 16 字节/参数"的量级，还没算激活
```

这就是为什么"推理 14 GiB 的模型，训练可能要 100+ GiB"。

**电费账（FLOPs）**——两句粗估口诀：

- **推理一次前向 ≈ 2P**（P 是参数量，每 Token 过一遍参数）；
- **训练一步 ≈ 6P**（前向 + 反向 + 更新，反向约是前向两倍）。

注意这是"数量级"口径：长序列时 Attention 里随 S² 增长的部分没算全，但**选卡、估时间、做预算**足够用了。

::: details 小测 2：为什么训练比推理多吃这么多显存？
训练多了：梯度（和权重一样大）+ 优化器状态（AdamW 每个参数两本历史账 m/v）+ 必须保存的前向激活（反向要用）。推理的 KV Cache 只是"笔记"，训练这三样才是大头。
:::

### 3. 开分店：五种切法一张表

单卡装不下/太慢，就要"开分店"（多卡并行）。**五种切法切的东西完全不同**：

| 切法 | 切什么 | 一句话 |
| --- | --- | --- |
| **DP** | 切**数据** | 每店同一本菜谱，接待不同顾客 |
| **TP** | 切**矩阵/头** | 一台大机器拆给多家合用 |
| **PP** | 切**层** | 按楼层流水线分工 |
| **CP** | 切**序列** | 长会议拆到多间会议室接力 |
| **EP** | 切**专家** | 科室分布到多分院 |

**用哪种通信，由"下一道工序需要什么形状的数据"决定**：下一层要完整数据 → AllGather 拼回来；要按份求和 → AllReduce / ReduceScatter；要把 Token 按去向重分发 → AlltoAll。这不是背出来的，是**顺着张量切分方向推出来的**——《模型全景》第 1 章那句话在收官处闭环：**切法决定对账方式**。

::: details 小测 3：TP 把 MLP 的 Down 投影按行切开，各卡算出"部分和"，下一步要完整输出——需要什么通信？
AllReduce（或 ReduceScatter）：完整输出 = 各卡部分和相加。这就是"下一道工序需要什么形状"决定通信原语的直接例子——要拼完整就归约，要分片就 ReduceScatter。
:::

### 第 3 章 · 3 句话带走

1. **看图纸算家底**：每层 4H²+3HI，乘层数加词表，GQA 和权重共享是两个常见折扣；

## 第 4 章｜分布式基础：Rank、通信域与拓扑

完整正文 → [第 4 章｜分布式基础：Rank、通信域与拓扑](04-distributed-basics.md)

### 1. 工号与签到：一进程一卡

新公司开业，第一件事是**人事登记**：

- 每位员工 = 一个**进程**；每人一张专属工位（一张卡）——**一进程一卡**。不让一个人占两张工位（管不过来），也不让两人挤一张（会打架/OOM）；
- 入职先到前台签到（`MASTER_ADDR:PORT` 就是前台地址），**人齐了才开工**——这就是 rendezvous。有人堵在路上没签到，全员干等，这就是最常见的"卡在 init"；
- 签完到每人领到身份牌：**全局工号**（rank：0 号、1 号……）、**本楼层工位号**（local_rank）、**公司总人数**（world_size）。工号 0 和工号 8 都可能是"3 楼 0 号工位"——不同楼层各有一套本地编号。

谁组织这一切？**启动器 torchrun**——它负责拉人（拉起进程）、发身份牌（注入环境变量）、守前台（组织签到）。

::: details 小测 1：为什么"一进程一卡"而不是一个进程管全部卡？
一个进程管多卡 = 所有 Host 侧工作（下发算子、管理内存）挤在一个脑袋里，还一崩全崩；一进程一卡各自独立调度、故障隔离——这是分布式训练的默认组织方式。
:::

### 2. 项目组：谁和谁一伙

公司默认有个**全员大群**（world group）——`init_process_group` 一建就是它，不指定组的集合通信都在大群里吼。

但真干活要按**项目组**（Process Group）：视觉组 8 个人拉个小群，群里的事（集合通信）只在群内广播，别的组根本听不见。关键三条：

1. 项目组 = **成员名单 + 沟通工具**（后端：HCCL 就是昇腾的"公司内线"）；
2. **一人可以身兼多组**：你可以同时在"视觉组"（机内 8 卡的 TP 组）和"跨部门评审组"（跨机的 DP 组）——混合并行的本质就是每人多重身份；
3. 组怎么划分，决定了**谁和谁之间要传数据**——这就引出下一节。

::: details 小测 2：`dist.all_reduce(t, group=tp_group)` 里不传 group 会怎样？
作用于默认的全员大群（world group）——全公司都参与这次 AllReduce，而不是只有你那 8 人小组。
:::

### 3. 就近组队：排号的隐形价值

同一层楼喊话**秒到**（机内 HCCS 专线，百 GB/s）；跨楼层要走电梯间（机间网卡，慢近一个量级）。

所以排工位时有大学问：**node-major 排号** = 按楼层整层分配（3 楼拿工号 0-7，4 楼拿 8-15）——项目组恰好同层，沟通全走楼内喊话 ✅。

反面教材：HR 图省事"轮流发牌"（round-robin），视觉组 8 人散在 4 个楼层——**每次组会全员跑电梯**，每层通信都挤慢链路 ❌。最阴险的是：**代码、算法、通信量一模一样，只是组员落位错了——任务能跑，就是慢**。这种 bug 不报错，只在 Profiling 里现形。

::: details 小测 3：任务能跑但通信耗时占了 60%，代码审查没问题——先查什么？
先查启动参数的排号方式：是不是 rank 分配让通信组横跨了机器（round-robin/乱序）？node-major 一行参数的事，量级的收益。
:::

### 第 4 章 · 3 句话带走

1. **一进程一卡 + 工号体系**：rank 全局、local_rank 机内，torchrun 负责拉人/发牌/签到；
2. **项目组（PG）决定谁和谁通信**：混合并行 = 一个 rank 身兼多组；
3. **node-major 排号让组落进机内快链路**：排号错误不报错、只变慢——免费的性能藏在启动参数里。

## 第 5 章｜数据并行与 DDP

完整正文 → [第 5 章｜数据并行与 DDP](05-ddp.md)

> 适用：时间紧，或完整版跟不动时。这页用"连锁分店对账"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 分店与强制对账：为什么必须 AllReduce

你开了 8 家**连锁分店**（8 张卡），每家都有完整菜单（完整模型副本），各自接待自己的客人（不同的数据分片）。

一个月下来各算各的利润（各自的梯度）——问题来了：**如果不统一**，下个月 8 家店的进货策略（参数更新）就各走各路，连锁店当场散伙。所以月底必须做一件事：**8 家利润求平均，全体按平均值统一进货**——这个动作就是梯度 AllReduce。

记住这句：**不做 AllReduce 不是"慢一点"，是训练在数学上直接错了**。所以 DP 的通信是算法本身的一步，不是性能优化。

账本有多厚？梯度 ≈ 2×参数量（BF16）——7.5B 模型就是 15 GB，每卡过手约 2×15×7/8 ≈ 26 GB（Ring 账本）。好消息：这笔账**跟 batch 大小无关**——batch 越大、算得越久，同样的运费被摊得越薄，这就是 DP 好扩展的原因。

::: details 小测 1：为什么说 DP 的通信"不是性能问题"？
因为缺少 AllReduce 时各副本会漂移成 N 个不同模型，训练结果在数学上就是错的——它是算法（等价大 batch SGD）的组成部分。
:::

### 2. 账本分章寄：Bucket

对账的正确姿势不是"月底一次性寄 15 GB"——那样要等所有账算完（反向结束）才能寄，寄的那段时间全店停工。

也不是"记一笔寄一笔"——几万笔快递，每笔的起步价（延迟 α）能把人逼疯。

**分章寄**：把账本按记账完成顺序分成若干章（**Bucket，每章约 25 MB**）——这一章记完，快递立刻出发；记账员继续记下一章。章的大小是个旋钮：太大 → 拖到最后才能寄；太小 → 快递太碎、起步价占比飙升。这就是分桶的两端权衡。

::: details 小测 2：桶为什么按"反向完成顺序"装，而不是按模型定义顺序？
反向是从输出层往输入层走的——先算完的梯度装进先出发的桶，通信才能尽早开始；按定义顺序装桶会让"早就算完的梯度"干等"晚才算完的同伴"。
:::

### 3. 边记账边寄：重叠

现在把两条流水线摆在一起：

```text
记账员（计算流）：  [记第3章][记第2章][记第1章]══╗ → 统一进货(step)
                            └已寄┘ └已寄┘      ║
快递员（通信流）：  ·····[等第1章]→寄→[等第2章]→寄→╝
```

**记账员记后面几章时，前面几章已经在路上**——串行的"记账 10 秒 + 寄账 1 秒"变成约 10 秒。能做到的原因：寄的是**已经记完的章**、等货的只有月底统一进货（step）——中间整段时间天然空闲。

但有三样藏不住：①快递比记账还慢时（小模型+慢网），多出来的照样堵；②"统一进货"前必须等最后一章到货（语义下界）；③如果本月记 K 次账才对一次账（**梯度累积**），运费直接除以 K——免费的省钱。

::: details 小测 3：反向 4 秒、通信流忙 9 秒、一步 10 秒——瓶颈在哪？
通信。通信已经从第 1 秒就在飞（重叠生效），但 9 秒 > 4 秒，裸奔的 5 秒藏不住——出路：压通信量（量化/压缩）、换算法、或上第 9 章的 ZeRO/FSDP。
:::

### 第 5 章 · 3 句话带走

1. **DP = 完整模型 + 数据切片 + 梯度求平均**：不做 AllReduce 就是分店散伙，数学错误；
2. **Bucket = 账本分章寄**：按反向顺序装桶、桶满即发，避开"太碎（α）"与"太整（不能重叠）"两个极端；
3. **重叠 = 记账寄货双流水线**：串行 N+M 变 max(N,M)；藏不住的部分靠压量、换算法或梯度累积。

## 第 6 章｜Tensor Parallel

完整正文 → [第 6 章｜Tensor Parallel](06-tensor-parallel.md)

> 适用：时间紧，或完整版跟不动时。这页用"多人共卷一场大考试"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 竖着切卷子：Column Parallel

一场大考试，答案纸太大一个人写不完（单层放不下/算太慢）——4 个同学**合作做同一张卷子**。

**竖着切**（Column Parallel）：答案纸竖着裁成 4 条，每人领一条。每人需要**完整的题目**（输入 X 复制一份），各自算各自条上的答案（$Y = [XW_1 | XW_2 | \cdots]$）。结果：每人手里是完整答案的 1/4 竖条——**输出天然分片**。

这一招的附带好处：题目册（权重 $W$）也每人只拿 1/4——**模型显存直接除以人数**。这是 DP（每人一套完整卷子各答各的题）永远做不到的。

::: details 小测 1：TP 和 DP 分别切什么？
DP 切数据（每人完整模型、不同题目）；TP 切模型（同一份题目、答案分工）——两把刀切不同的轴，所以能叠加使用。
:::

### 2. 横着切：Row Parallel 与黄金组合

**横着切**（Row Parallel）：题目横着裁，每人拿 1/4 道题，各自算出"**部分贡献**"——把 4 人的贡献**加总**才是完整答案（$Y = \sum X_i W_i$）。加总这个动作就是 **AllReduce**。

Megatron 的黄金组合是**先竖后横**：

```text
完整题目 → [竖切: 各答 1/4 答案] → [逐项检查 GeLU: 各查各条 ✓] → [横切: 各出部分贡献] → 加总(AllReduce) → 完整答案
```

妙在两处"恰好"：竖切的输出**恰好**是横切需要的输入格式（中间零通信）；检查环节（GeLU）是逐项的，**恰好**各查各的（零通信）。整层只付一次"加总"的钱。Attention 更妙——**多头 = 天生竖切**，每头的注意力在自己手里完整算完。

::: details 小测 2：ColP→GeLU→RowP 中间为什么零通信？
ColP 输出列分片 = RowP 需要的输入分片，天然衔接；GeLU 逐元素，在分片上做结果一样。
:::

### 3. 一层四次点名：为什么 TP 住机内

算总账时 TP 看起来很省：每次通信只有一层激活（128 MB 级），不像 DP 每步寄全部梯度（15 GB 级）。**但频率反了**：

- DP：一步一次对账（分桶后几十次快递），而且记账员可以边记账边寄；
- TP：**每层 4 次全员集合**（前向 2 + 反向 2），32 层 = 128 次/步——而且**藏不住**：下一题的题目要等这题答案拼齐才能发（下一层输入 = 本层 AllReduce 输出）。

128 次 × 128 MB：在**机内专线**（200 GB/s）≈ 0.14 秒/步，能忍；走**跨机网络**（25 GB/s）≈ 1.1 秒/步——每步白烧一秒。所以铁律：**TP 组必须挤在同一台机器里，tp = 每机卡数**；想扩更多卡，用 DP/PP 包在外面。

补救招（TP+SP）：出口其实**不用拿完整答案**——每人只留自己那段（ReduceScatter），需要时再拼（AllGather）——一次 AllReduce 拆成两半，通信量立减一半。

::: details 小测 3：为什么 DDP 的通信能重叠、TP 的不能？
DDP 通信的是梯度，等它的是 step（反向全部结束后才用）——中间整段反向都能并行寄；TP 的通信结果是下一层的输入——不给就开不了工，只能压缩（TP+SP），藏不了。
:::

### 第 6 章 · 3 句话带走

1. **ColP 竖切**（输入复制、输出分片）、**RowP 横切**（输入天然分片、输出部分和求和）——先竖后横，中间零通信；
2. **TP 显存 ÷N，但每层 4 次 AllReduce 且不可重叠**——通信小而贵，频率即惩罚；
3. **TP 度 = 每机卡数**：这种通信只能贴机内专线；TP+SP 用"只留自己那段"再砍一半。

| TP | 多人共卷一场大考试：切答案，不切题量 |
| Column Parallel | 竖着切答案纸：每人一条，各答各的 |
| Row Parallel | 横着切题目：各出部分贡献，加总才是答案 |

## 第 7 章｜Pipeline Parallel

完整正文 → [第 7 章｜Pipeline Parallel](07-pipeline-parallel.md)

> 适用：时间紧，或完整版跟不动时。这页用"洗车流水线"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 四个工位的流水线：切深度

一家洗车店扩建成**四工位流水线**：冲水 → 打泡沫 → 刷洗 → 擦干。每辆车从工位 1 进、工位 4 出。

对应到训练：模型 32 层**按深度切成 4 段**（stage），每段住一台机器。数据像车一样流过去：前向从 Stage 0 流到 Stage 3，反向再流回来。

这种切法的通信便宜到不像话：**只有相邻工位递车**（P2P 传一个 micro-batch 的边界激活，MB 级）——不需要全员集合、不需要传梯度/参数（那些按层分家了，各存各的）。**模型再大，递的也只是"这层的输出"**——所以 PP 是三把刀里唯一**天生跨机友好**的（TP 只能挤机内，PP 的工位可以横跨厂房）。

::: details 小测 1：为什么 PP 的通信量与模型大小无关？
因为 stage 之间只传"边界激活"（这层算完的输出，大小由 batch×序列×隐层决定）；参数和梯度各 stage 自存自用，从不需要搬家。
:::

### 2. 车队拆小批 + 空转时刻：Bubble

只洗**一辆大车**（整 batch 一次流过）？工位 4 要等车缓缓漂过前三个工位才开工——同一时刻**只有一个工位在干活**。

聪明做法：把车队拆成 **M 辆小车**（micro-batch）**连续注入**——第 1 辆还在工位 2，第 2 辆已进工位 1。稳态时四个工位全部满负荷；空转只剩两头：**开头等第一辆车流到最深（fill）、结尾等最后一辆反向流回最浅（drain）**——这段空转就叫 **Bubble**。

公式一张名片：**Bubble 率 = (S−1)/(M+S−1)**（S = 工位数，M = 车数）。S=4 时：M=4 辆 → 空转 43%；M=64 辆 → 空转 4.5%。**车越多，启动/排空的固定开销摊得越薄**。

::: details 小测 2：S=8、M=56 时 Bubble 率是多少？
(8−1)/(56+8−1) = 7/63 = 11.1%。
:::

### 3. 边洗边交车：1F1B

新问题：GPipe 式调度（**所有车全洗完，再统一返工检查**）要求暂存**全部 M 辆车**的洗车记录（激活内存 O(M)）——想加大 M 压空转？先把暂存区撑爆。

关键洞察：**第 1 辆车的返工不必等第 64 辆洗完**——它自己的工序早就结束了。于是 **1F1B**：工位先热身（S−1 辆前向），之后**每接收一辆新车，就送走一辆检查完的旧车**——一进一出交替，暂存区里**恒定只有约 S 辆车**（内存 O(M)→O(S)）。

注意：1F1B **不减少空转**（两头还是要等），它解放的是暂存区——于是你能放心把 M 加到 64，**空转被间接压到 4.5%**。进阶版 Interleaved（每个工位再细分 v 个小段）能把空转再除以 v，代价是递车更碎更频繁。

::: details 小测 3：1F1B 既然不省时间，为什么人人都在用？
它省内存（O(M)→O(S)），允许加大 M；Bubble 率随 M 下降——"解内存、不解时间，最终解时间"。
:::

### 第 7 章 · 3 句话带走

1. **PP 按深度切**：只有相邻 stage 递车（P2P 激活，MB 级），三把刀里唯一跨机友好；
2. **Bubble = (S−1)/(M+S−1)**：micro-batch 连续注入填满流水线，两头空转靠大 M 摊；
3. **1F1B 边洗边交车**：在途激活 O(M)→O(S)，解放 M 上限，间接压死 Bubble。

### 第 7 章 · 黑话小词典

| 术语 | 人话 |
| --- | --- |
| stage | 流水线的一个工位（一段连续的层，住一台机器） |
| micro-batch | 车队里的一辆小车：batch 切小、连续注入 |
| Bubble | 流水线两头的空转（fill + drain） |

## 第 8 章｜Context Parallel（序列并行）

完整正文 → [第 8 章｜Context Parallel（序列并行）](08-context-parallel.md)

> 适用：时间紧，或完整版跟不动时。这页用"分组看监控查案"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 切时间段：谁需要通信

一段 **4 小时的监控录像**要查线索，4 个侦探**每人只看 1 小时**（序列切分）。

先检查查案流程里哪些活是"各看各的"：整理画面、写时间戳（Norm/MLP）——**逐分钟独立，切了毫无影响，零沟通**。唯一的问题是**做笔录**（Attention）：写第 3 小时的笔录，需要**之前所有时段**的关键线索——你手里只有第 3 小时的（causal：后面的 token 要看前面的 K/V）。

于是整章只剩一道题：**线索（K/V）怎么送到每个人手里**。这就是 CP 的全部通信。

::: details 小测 1：为什么 CP 下 MLP 完全不用通信？
MLP 的矩阵乘在**特征维**（h→4h→h）上做，每个 token 独立过 MLP——序列切成几段，各段各算，结果一分不差。
:::

### 2. 两条送线索的路：复印全套 vs 圆桌轮传

**路线 A——复印全套（AllGather）**：每人把手里 1 小时的线索卡复印 4 份，全员交换——**每人桌上摊开完整的 4 小时线索**，然后各自安静写自己那段的笔录。简单、直接，但两个毛病：**桌上要摊得下全套**（显存峰值 = 全长 K/V，CP 省的显存又借回去了）；**复印期间全体干等**（通信不可重叠）。

**路线 B——圆桌轮传（Ring）**：线索按小时分装成 4 叠，沿圆桌轮流转——你写第 3 小时笔录的过程中，依次收到第 0、1、2 小时的线索叠，**边收边写**（在线合并笔录），桌上**永远只有一叠**。传的总量和复印一样，但：桌上不堆（峰值低）、传阅时间被写笔录盖住（**通信与计算重叠**）——代价是调度复杂了一点点。

::: details 小测 2：两条路线的通信总量差多少？
一样！都约等于全长 K/V 的 (N−1)/N。差别全在**显存峰值**（全套 vs 一叠）和**可重叠性**（干等 vs 边传边算）。
:::

### 3. 三角形的活：别让有人闲死

causal 有个隐藏坑：**第 0 小时的人写笔录不用看任何更早的线索（没有更早），第 3 小时的人要看全部 3 叠**——工作量是一个三角形，有人闲死有人忙死。而轮传的节拍由**最慢的人**决定——又见木桶效应。

解法很朴素：**排班时把重的活错开均摊**（zigzag/斜切）——不按"谁的那小时归谁"分，按"每人总活量相等"分，四个人各背约一半三角形的当量。

一句话总结选型：**短序列、机内**，复印全套就够；**长序列、跨机**（通信量大），必须圆桌轮传把通信藏进笔录里——序列越长，每叠越重，越好藏。

::: details 小测 3：为什么序列越长，Ring 的"藏"越有效？
传输一叠线索的时间不变（正比于块大小），但**写完一叠笔录的时间随块变重而变长**——计算时间 ≥ 传输时间时，传阅完全被覆盖。
:::

### 第 8 章 · 3 句话带走

1. **CP 切序列**：只有 Attention 欠沟通（要看全长 K/V），其他层零通信；
2. **两条路**：AllGather 复印全套（简单、峰值高、干等）vs Ring 圆桌轮传（峰值低、边传边算、调度复杂）；
3. **causal 是三角形**：均衡排班（zigzag）别让木桶效应吃掉省下的时间；TP 切 head × CP 切序列 = 4D 并行完全体。

### 第 8 章 · 黑话小词典

| 术语 | 人话 |
| --- | --- |
| CP / 序列并行 | 监控按小时分给 4 个侦探 |
| K/V 流动 | 让每人都能看到全时段的关键线索 |
| AllGather | 复印全套线索摊桌上：简单但占地方 |
| Ring 轮传 | 线索叠沿圆桌轮转，边收边写 |

## 第 9 章｜ZeRO、FSDP 与混合并行

完整正文 → [第 9 章｜ZeRO、FSDP 与混合并行](09-zero-fsdp.md)

> 适用：时间紧，或完整版跟不动时。这页用"合租分摊三样东西"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 三样东西，八份复制：ZeRO 的洞察

8 个人合租办公，每人都买了**一整套装备**：常用工具（参数 15 GB）、每周的作业本（梯度 15 GB）、还有一座**巨型工具房**（优化器状态 60 GB）——每人 90 GB，全楼 720 GB，其中 630 GB 是一模一样的 7 份复制。

ZeRO 的灵魂拷问：**工具房真的需要每人一座吗？** 观察发现：修工具是**各修各的**（优化器更新逐参数独立）——每人只负责 1/8 的家伙，完全可以。于是三级递进，**最贵的先切**：

- **ZeRO-1（切工具房）**：每人保管 1/8 的优化器状态——显存 90→37.5 GB，**其他什么都不用改，白省**；
- **ZeRO-2（加切作业本）**：梯度也各管一段——上交作业时每人**只留自己那段**（AllReduce 换成 ReduceScatter），**运费还减半**，纯赚；
- **ZeRO-3（加切工具）**：连参数都拆开分放——要用时再拼，显存 11.25 GB，但**每次开工前都得先把工具凑齐**（AllGather 参数），运费涨到 1.5 倍——放不下才用的最后手段。

::: details 小测 1：为什么 Z2 的通信量反而比 DP 少？
梯度分片后每人只需要"自己负责那段参数"的梯度——AllReduce（每人拿全长）降级成 ReduceScatter（各留一段），流量正好减半。
:::

### 2. 用时借、用完还：FSDP

ZeRO-3 的"拼工具"听起来很笨重——FSDP 把它做成了**图书馆模式**：

- 平时：所有书拆页分放在 8 个书架（参数分片）；
- 干活：**今天要用第 3 章就把第 3 章借齐**（逐层 AllGather），**看完立刻还**（释放），桌上永远只有一章；
- 妙招（prefetch）：**读第 3 章的时候，第 4 章已经在快递路上**——借书时间被读书盖住（通信与计算重叠）。

它和 TP 的本质区别一句话：**TP 连"算"都切了**（每人算自己那块，激活也省）；**FSDP 只切"存"**（拼齐了整层完整地算，激活不省）。所以 TP 吞吐极限高但只能机内、工程重；FSDP 简单弹性、随便跨机，但通信多一点——**没有免费的刀，只有匹配的刀**。

::: details 小测 2：FSDP 的显存峰值是什么？
当前拼齐的那一层（完整）+ 全部激活——参数省了，但激活因为"计算不切"而没省。
:::

### 3. 五把刀的排班表：组合

最后把五把刀放回工具墙，**开方前先诊断——什么放不下？**

| 诊断 | 开方 |
| --- | --- |
| 都放得下，要吞吐 | DP（+Z1/Z2 免费优化） |
| 单层放不下 | TP（机内 8 卡） |
| 总体放不下、想简单 | FSDP/ZeRO-3（一行 wrap） |
| 总体放不下、要极限 | Megatron 3D（TP 机内 × PP 跨机 × DP 扩展） |
| 序列放不下 | CP（切序列） |
| MoE | EP（专家分布式） |

每个策略 = 把一种冗余换成一种通信；组合 = **让每种通信落到性格匹配的链路**（TP 给机内专线、PP 给跨机 P2P、DP 给慢网也能忍的重叠流）。收官一句话：本专栏讲清了"为什么通信"——每个需求都能在《集合通信》的供给表里找到对应的那一行。

::: details 小测 3：70B 预训练、64 机 8 卡、要极限吞吐，怎么配？
TP=8（机内贴 HCCS）× PP 跨机分段（P2P 边界激活）× DP 用剩余卡扩展；激活紧张再叠 CP——即 Megatron 3D/4D 配方。
:::

### 第 9 章 · 3 句话带走

1. **ZeRO 按最贵的先切**：O 白省、G 减半（RS）、P 要付 AG 的钱——显存 ÷N 的三级台阶；
2. **FSDP = 图书馆模式**：逐层用时拼、用完还，prefetch 把借书藏进读书——只切存储、不切计算；
3. **组合先诊断**：什么放不下决定用哪把刀；每种并行都是"冗余换通信"，让通信落到匹配的链路。
