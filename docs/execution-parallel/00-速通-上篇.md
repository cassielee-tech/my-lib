## 第 1 章｜AI Infra 全景与性能分析方法

完整正文 → [第 1 章｜AI Infra 全景与性能分析方法](01-landscape-performance.md)

> 适用：时间紧，或完整版跟不动时。这页用一家餐厅讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 你写了一行代码，然后呢？

你的模型代码像一份**菜谱**：它写的是"我要一道宫保鸡丁"，不是"怎么炒"。

菜谱自己不会变成菜。它要经过一条链：

```text
菜谱（你的 PyTorch 代码）
  → 前台接单（框架：检查点什么菜、料够不够）
  → 后厨翻译（编译器：把菜谱变成具体工序，用哪口锅几分钟）
  → 后厨调度（Runtime：安排灶台，记住先来后到）
  → 灶台开火（硬件：厨师真的开始炒）
```

两个容易混淆的词，用餐厅区分：**Host** 是前台经理（CPU），**Device** 是后厨（NPU/GPU 加速卡）。你的代码在前台跑，真正的炒菜在后厨。

::: details 小测 1：为什么 NPU 看不懂你的 Python 代码？
因为硬件只认自己的"炒菜动作"（指令），不认菜谱。中间必须有人一层层翻译：框架 → 编译器 → Runtime → 硬件。这整条翻译链，就是 AI Infra 要研究的东西。
:::

### 2. 餐厅只会以三种方式变慢

假设生意慢了，原因逃不出三种，对应三种"慢"：

**① 厨师忙不过来（计算瓶颈，Compute-bound）。** 订单排到门口，厨师从开火到打烊没停过。这时再加快进货也没用——瓶颈在人。

**② 食材运不进来（访存瓶颈，Memory-bound）。** 厨师站着干等食材：仓库（显存）到操作台（片上小台面）的路太窄。厨师再快也白搭——瓶颈在路。

**③ 分店之间传菜（通信瓶颈，Communication-bound）。** 多店协作一桌宴席，一辆送餐车堵在路上，所有分店等它一个人。多卡训练就是这种宴席——瓶颈在路上的车。

::: warning 关键
三种慢的药方完全不同：缺人加人、路窄修路、车堵疏车。**先分清是哪种，再动手**。而且它们常常轮流出现：这个时段缺人，下个时段堵车。
:::

::: details 小测 2：厨师全程有空，订单却没变快，最可能是哪种？
② 或 ③——计算单元闲着，说明菜没送到手上：要么食材运不进来（访存），要么等别家分店的数据（通信）。
:::

### 3. 怎么判断哪里慢：先计时，再下结论

好的餐厅经理不问厨师"你觉得哪里慢"，而是**看监控录像**——对应到我们的世界就是 Profiling（性能分析工具）：把每个环节花了多少毫秒摊开看。

看监控时问三个问题：

1. **食材现在在哪？**（数据在仓库还是操作台，在哪家分店）
2. **有多少食材？**（数据的字节数）
3. **谁在等谁？**（哪个工位停着，在等什么）

还有一个聪明的**记账法**：每份食材能出几道菜。术语叫**算术强度**：计算量 ÷ 搬运量。

- 解冻一整头牛只做一盘牛肉——搬运太亏，天生容易②慢；
- 一筐土豆做一百盘薯条——搬得值，值得雇更好的厨师（①慢才是瓶颈）。

对于"天生搬运亏"的菜，出路不是修路，是**合并菜单**（把几道工序合成一道，食材别来回搬）。

::: details 小测 3：每搬 1 字节只做 0.2 次计算的算子，大概率卡在哪？
② 访存。搬运太亏（算术强度太低），计算单元基本在等数据。优化方向是合并工序/融合算子，而不是让"厨师"更快。
:::

### 第 1 章 · 3 句话带走

1. 一行代码要穿过 **前台→翻译→调度→灶台** 才变成结果，每一层都可能拖慢；
2. 慢只有三种：**厨师**（计算）、**食材**（访存）、**传菜**（通信），先分清再动手；
3. 好的优化像好的经理：**看监控计时、不凭感觉**；每次只改一处，改完复测。

## 第 2 章｜GPU/NPU 执行模型与计算单元

完整正文 → [第 2 章｜GPU/NPU 执行模型与计算单元](02-execution-model.md)

> 适用：时间紧，或完整版跟不动时。这页用三支施工队讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 同一个工程，三支队伍三种干法

第 1 章的餐厅只说了"后厨很忙"，没说厨师**怎么**干活。现在拆开看三支队伍：

- **老师傅装修队（CPU）**：几位全能师傅，什么活都会，讲究**每件事利索做完**（低延迟）。但人少——碰上"铺一万块瓷砖"这种规则重复的活就抓瞎；
- **大工地人海队（GPU）**：几百个小工，每人只会一个简单动作。不怕谁在等料——**只要有别的工位能开工，就先让别人干**，用人数掩盖等待（吞吐）；
- **预制板厂（NPU）**：干脆不接杂活，只做"盖楼标准件"（矩阵运算）。浇筑机、打磨线、领班各司其职，专用料道送料——**用专用换极致效率**。

为什么会长成这样？**预算（晶体管）花的地方不同**：装修队花在师傅的经验（控制逻辑+大缓存），人海队花在人手（海量计算单元），预制厂花在专用设备和料道。

::: details 小测 1：CPU、GPU、NPU 处理"等料"的策略有何本质区别？
CPU 尽量不让等待发生（乱序执行、大缓存提前备料）；GPU 不消灭等待，而是**用人海掩盖**——等料的工位先闲着，让就绪的工位顶上；NPU 靠**软件把送料排成流水**，让浇筑机抬头时料永远在台上。
:::

### 2. 人海队和预制厂的组织架构

**人海队的班制（GPU）**：小工不是单干的，**32 人一班（Warp）绑在同一根横杆上齐步走**——同一时刻全班只做一个动作，各自搬各自的砖（SIMT）。

- **走岔路（分支分歧）**：16 人要左转、16 人要右转？全班只能先陪左边走一趟、再陪右边走一趟——**两趟时间都付**；
- **吊机（Tensor Core）**：普通工一次搬一块砖，吊机**一次吊一整块预制板**（小矩阵块）。要喂饱它，活必须切成规整的大块——切得零碎就退回人肉搬运。

**预制厂的岗位（NPU）**：浇筑机（**Cube**，矩阵乘加）、打磨线（**Vector**，逐元素/向量）、领班（**Scalar**，算地址、发号施令），外加专职料车（**DMA/MTE**）从大仓库送料进车间。

::: details 小测 2：为什么说"一次矩阵乘法不只是浇筑机在干活"？
因为它是整条生产线的协作：领班（Scalar）算好每批料的位置，料车（DMA）把料从 HBM 送进车间缓冲区，浇筑机（Cube）乘加，成品再经出货口（FixPipe）写回。任何一环慢，浇筑机就只能停线等——瓶颈往往不在"机器不够快"，而在"料没到"。
:::

### 3. 说明书上的 1000 TFLOPS，为什么实测只有几百

工地上的效率漏斗，一层层打折扣：

| 损失 | 工地版本 |
| --- | --- |
| 并行度不足 | 人手没派满，一半工位闲着 |
| 尾块效应 | 最后一车料只够半班人干，后半程天然半速 |
| 数据供给不足 | 料车供不上，机器空转 |
| 执行方式惩罚 | 队形散（分支分歧）、砖不规整（形状不对齐） |
| 频率/功耗墙 | 天太热被迫放慢；还有"慢卡"拖累全场等它 |

关键是：**效率是乘法**。人手 0.8 × 供料 0.8 × 队形 0.9 ≈ 0.58——每项看着都还行，乘起来只剩六成。所以优化要**先找最小的那项**，不是平均用力。

::: details 小测 3：Profiling 显示时间线前半段满载、后四分之一骤降——最可能是哪种损失？
尾块效应。任务数没被工位数整除：前几轮人人有活，最后一轮只剩部分工位有料干，后半程利用率天然减半。解法是调整切分（Tile 尺寸/数量），让尾块尽可能小。
:::

### 第 2 章 · 3 句话带走

1. 三支队伍：**老师傅求快（CPU）、人海队靠多（GPU）、预制厂靠专（NPU）**——预算花在哪决定哲学；
2. GPU 的命门是**并行度**（32 人齐步走，怕分歧、怕零碎），NPU 的命门是**料道**（搬运要软件组织好）；
3. **利用率是乘法**：人手 × 供料 × 队形 × 节奏，优化先修最小的那项。

## 第 3 章｜存储层次与数据搬运

完整正文 → [第 3 章｜存储层次与数据搬运](03-memory-hierarchy.md)

> 适用：时间紧，或完整版跟不动时。这页用一家工厂的物料摆放讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 越近的台面越小越贵

第 2 章的预制厂能转起来的前提是：**料得送到机器跟前**。先看工厂的空间布局：

```text
手边工具袋（寄存器）     最快·最小·就手
工作台（片上 SRAM）      快·小·一批料就在机器旁
车间货架（L2）           稍大·稍慢
厂区大仓库（HBM）        几十 GB·一趟数百纳秒
中央仓库（DDR/硬盘）     更大·更远
```

物理现实很残酷：**快 = 贵 = 小，大 = 慢 = 远**，没有一层能又大又快又便宜——所以全世界的芯片都长成这座金字塔。

看存储要分清三个独立指标：**容量**（放多少料）、**延迟**（跑一趟多久）、**带宽**（这条路上每秒能过多少车）。一个直觉数字：跑一趟大仓库的时间，够浇筑机干几百上千次活——**不是机器慢，是料远**。

::: details 小测 1：容量、延迟、带宽分别决定什么？
容量决定哪些料必须住在厂外（切分的可行性）；延迟决定单趟等待多长（GPU 用换班掩盖、NPU 用流水绕开）；带宽决定持续供给的上限——流水排得再好，每秒进厂的车数超了带宽就是饿。
:::

### 2. 车间货架的两种管法：自动补货 vs 自己拉料

片上那层"工作台+货架"（SRAM），谁来决定放什么？两条路线：

- **Cache（自动补货货架）**：你用过什么，智能货架自动帮你备什么（硬件按访问历史）——省心，但**这次备没备上要看运气**（命中率）；
- **Buffer（手动料架）**：自己列清单、叫料车按单送（软件显式搬运，NPU 的 UB/L1/L0）——**行为完全可控、能精确排流水**，但"何时进料、料架够不够"全要自己操心。

GPU 两种都有（L1/L2 自动 + Shared Memory 手动）；**NPU 主要走手动路线**——这就是为什么 Ascend C 算子代码里要写搬运语句。另外分清两个仓库：**HBM** 是贴着车间的厂区大仓库（带宽大、容量小），**DDR** 是 CPU 侧的中央仓库（容量大、路远）。

::: details 小测 2：Cache 和 Buffer 的核心区别？
谁来决定内容：Cache 由硬件按访问历史自动管理，程序员省心但不可控；Buffer 由软件显式指定装什么，可控可排流水但要自己管理容量与生命周期。"Cache 友好"只要访问连续即可，"Buffer 友好"还必须回答何时搬入、何时用完、空间够不够。
:::

### 3. 搬运比加工贵得多

工厂的账本：**跑一趟仓库的油钱，是台面上拧一颗螺丝的上百倍**。算性能别只看干了多少活，要看**每车料出了多少货**（复用次数 = 计算量 ÷ 搬运量）：

- **逐元素算子**：一车料只出一件货——天生亏本，机器再快也白搭。出路不是修路，是**拼单**：把这道工序并进邻居的合同里，料顺路捎带（算子融合）；
- **矩阵乘法**：一车料能反复用——天生赚钱，块切得越大每车料用得越多次（但受工作台大小限制）；
- **摆放方式（Layout）**：料按取货顺序码放 vs 乱堆。转码（Transpose）= 全部搬出来重码一遍，**超贵**，能省则省。

三个省钱方向连成一句话：**少搬（融合）、重用（分块）、搬巧（对齐连续）**。

::: details 小测 3：每搬一个字节只做 0.2 次计算的算子，该修路还是该拼单？
拼单（融合）。它的亏是"天生的"（理想算术强度就这么低），修路（提高带宽利用率）只能小赚一点。把它并入邻居算子、让数据顺路，才是治本。
:::

### 第 3 章 · 3 句话带走

1. 存储是金字塔：**越近越快越小越贵**；容量、延迟、带宽三个指标分开算；
2. 片上 SRAM 两种管法：**Cache 自动补货、Buffer 自己拉料**；GPU 混用，NPU 主打手动；
3. **搬运比计算贵百倍**：少搬（融合）、重用（分块）、搬巧（对齐）——每车料出的货才是关键。

## 第 4 章｜Kernel、Tiling 与流水线

完整正文 → [第 4 章｜Kernel、Tiling 与流水线](04-kernel-tiling-pipeline.md)

> 适用：时间紧，或完整版跟不动时。这页用一个工程怎么分包讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 项目经理和施工队：一份合同 的两半

前面两章认识了机器和料，现在看**一个具体任务怎么派下去**。任务书就叫 **Kernel**，它天然分两半：

```text
项目经理（Host 侧）                  施工队（Device 侧）
看图纸、算分包方案（切分参数）  →     每队拿到同一份图纸，
发任务单（Launch 下发）              按自己的队号认领自己的区段
                                    循环干活：进料 → 加工 → 出货
```

关键机制是**按队号认领**（SPMD）：图纸只画一份，每支施工队（执行单元）拿到队号（GPU 的 blockIdx / NPU 的 Block Index），自己算出"我负责第几段"。**代码写一份，所有队各干各的段**。

还有个隐形成本：**每次开工都要开班前会（Launch 开销，微秒级）**。任务大时无所谓；任务只有 10 微秒的活，班前会跟干活一样久——**大量小任务串联时，工地全是开会的空隙**。解法：把几件小事打包成一个合同（算子融合），或整栋楼签一个总合同一次下发（图模式下沉）。

::: details 小测 1：为什么小算子多的网络反而慢？
不是算得慢，是"开会"开会了：每个小 Kernel 都要付一次下发开销（班前会），计算本身可能只有几微秒，会却要开一样久。设备时间线上全是 Kernel 之间的空隙。所以要么融合算子，要么走图模式整图下发。
:::

### 2. 分包的两级：先分队，再分层

大工程（比如 8192×8192 的矩阵乘法）怎么切？**两级分包**：

- **第一级，分队（多核切分）**：把大楼切成 256 个区块，64 支队各领几块——决定**人手是否铺满**（并行度、尾块）；
- **第二级，分队内分层（核内切分）**：每队内部按层循环进料，料在工作台上反复加工——决定**每车料的复用**（搬运量）。

分包方案要过**四本账**：

1. 工作台放得下吗（容量）；
2. 尺寸按模数对齐吗（对齐，否则机器效率打折）；
3. 每队都有活、尾块小吗（并行）；
4. 一车料能用几次（复用，块尽量大）。

**一条铁律——承重墙不能乱切**：切到"求和"的维度（归约维，比如矩阵乘法的 K 维），各队只能算出半成品，**必须有人负责合拢**（规约通信）。其他维度随便切，归约维切了要付通信的钱。

::: details 小测 2：为什么归约维（K 维）是特殊维度？
因为沿 K 切开后，每队拿到的是"部分和"，不是最终答案——必须跨队累加合并才能出结果。M/N 维切块天然独立（各算各的输出块），K 维切块天然要"合拢"。这个"合拢"在单机是额外 Kernel，在多机就是 Reduce 通信。
:::

### 3. 三班倒：让机器不等料

分包好了，串行干法还是亏：**进料的时候机器闲着，加工的时候进料车闲着**。

流水干法 = **三班倒**：进料班、加工班、验收班同时上班，靠**料斗**衔接（队列：进料斗放"已到的料"，出料斗放"已完成的货"）。再加一个**双料斗**（Double Buffer）：A 料斗正在用，B 料斗已经在卸——机器一抬头，下一批料永远在台上。

三条冷水，泼给"流水万能"的幻想：

1. **工程太小**：只有三批料，刚开工就收工，流水没热身就结束；
2. **某班天然慢**：进料 4ms、加工 1ms——流水后节奏由进料决定，加工班 75% 时间闲着。**流水只能消除互相等，治不了瓶颈本身**（该加大复用、减少搬运还得做）；
3. **大门口限流**：所有队的料车加起来不能超过大门通行能力（HBM 带宽）——超了就是超了，加料斗没用。

::: details 小测 3：进料 4ms、加工 2ms、验收 1ms，流水后节奏是多少？加工班空闲率多少？
节奏由最慢的一班决定：4ms 出一批货。加工班每 4ms 只干 2ms 的活，空闲 50%。此时优化方向是修进料（加大分块提高复用、减少搬运），而不是再加缓冲级数。
:::

### 第 4 章 · 3 句话带走

1. Kernel = **项目经理的分包合同 + 施工队按队号认领**；小任务最怕班前会（Launch 开销）；
2. Tiling 两级：**分队铺满人手 × 分层榨干复用**，四本账（容量/对齐/并行/复用）都要过，**归约维切了要付合拢的钱**；
3. 流水（队列 + 双料斗）只能消除"互相等"，**治不了瓶颈、突破不了大门限流**。

## 第 5 章｜FLOPs、带宽、算术强度与 Roofline

完整正文 → [第 5 章｜FLOPs、带宽、算术强度与 Roofline](05-flops-bandwidth-roofline.md)

> 适用：时间紧，或完整版跟不动时。这页用一家工厂的产能天花板讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 工厂的三本账

前面四章工地运转起来了，现在要回答：**干得好不好？下次往哪改？** 先学会记账，记三本：

1. **干了多少活**（FLOPs）：矩阵乘法 `[M,K]×[K,N]` = 2MNK（一次乘加记 2）；训练一步约为前向的 3 倍；
2. **进了多少料**（Bytes）：理想下界 = 输入读一遍 + 输出写一遍；**实际只会更多**（中间料进出仓库、转码、重读）；
3. **每车料出多少货**（算术强度 AI = FLOPs ÷ Bytes）。

第 3 本账要记两笔：**理想 AI**（用理想下界算——这道工序**天生的命**）和**实际 AI**（用实测搬运量算——**这个实现干得怎么样**）。分清这两笔，才知道该怪工序还是怪实现。

::: warning 一个天坑：口径
"算力 400 TFLOPS"必须看清是什么精度下的——BF16、FP8、稀疏、稠密，数字差好几倍。算账时活和产能必须同口径，否则整张图都是错的。
:::

::: details 小测 1：理想 AI 低和实际 AI 低，分别说明什么？
理想 AI 低是"命不好"——工序天生搬运重（如逐元素），优化计算没用，只能融合改命。实际 AI 远低于理想是"干得差"——实现多搬了很多冤枉料（中间结果落仓库、转码、重读），修实现就能赚回来。
:::

### 2. 一条屋顶线

工厂产能有个天花板公式：

```text
产能上限 = min( 机器总产能,  每车料产出 × 大门吞吐 )
                     ↑屋顶↑      ↑左坡的斜率↑
拐点 = 机器总产能 ÷ 大门吞吐
```

画在对数坐标上就是一条"屋顶"：左边斜坡 + 水平屋顶。例：400 TFLOPS ÷ 2 TB/s = **拐点 200**（FLOPs/Byte）。

- 工序落在**左坡**（AI < 200）：进料是瓶颈（**Memory-bound**）——机器再多也没用；
- 工序落在**屋顶**（AI > 200）：机器是瓶颈（**Compute-bound**）——门再宽也没用。

两个数字感受一下：逐元素加 AI≈0.17，上限 0.17×2TB/s ≈ 0.34 TFLOPS——**只用到机器的 8.5%**；大 GEMM AI≈1365，稳稳压在屋顶上。注意：**屋顶是天花板不是成绩单**——实际能摸到屋顶七八成已属优秀，它的价值是指出方向，不是承诺满分。

::: details 小测 2：AI=1365 的大 GEMM 实测只有 200 TFLOPS（屋顶 400），问题在哪？
问题在"实现质量"而不是"工序的命"：理想 AI 已经在屋顶区，实测低说明是队形（形状不对齐）、尾块、供料没排好等执行问题——按第 2、4 章的检查单修实现。
:::

### 3. 图上只有两个方向

诊断完，行动只有两个方向：

- **向上爬**（更贴近自己那段的线上限）：修路——对齐连续、排流水、修尾块。**修实现**；
- **向右挪**（每车料出更多货）：改命——**工序合并**（融合；FlashAttention 是教科书案例：中间的 S 矩阵不落仓库，AI 暴涨直达屋顶）、加大分块榨复用、原料压缩（低精度，注意精度账）。

最后记住屋顶线**不管的事**：排队和签认（延迟/同步）、队形和尾块、跨厂运输（通信）、班前会（启动开销）。所以完整的判断三件套是：**屋顶线定方向，时间线找证据，约束账定手段**——单图不可定论。

::: details 小测 3：三种情况各选方向：① 逐元素加夹在两个 GEMM 之间；② GEMM 实测屋顶六成、时间线尾段骤降；③ 朴素 Attention 的中间矩阵反复进出仓库。
① 向右：拼单融合，搭邻居的顺路车；② 向上：修尾块/切分（命已在屋顶，是实现问题）；③ 向右：Flash 化，中间结果不落仓库——AI 大幅右移。
:::

1. 先记三本账（活、料、每车料产出），**理想 AI 看命、实际 AI 看实现，口径必须一致**；
2. 屋顶线一条：**左坡进料瓶颈、屋顶机器瓶颈，拐点 = 机器产能 ÷ 大门吞吐**；

## 第 6 章｜Eager、计算图与图编译

完整正文 → [第 6 章｜Eager、计算图与图编译](06-eager-graph-compilation.md)

> 适用：时间紧，或完整版跟不动时。这页用"装修队现场干 vs 先画施工图"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 现场指挥的装修队：写一行，干一步

PyTorch 默认的干活方式（**Eager**）像一个听现场指挥的装修队：你喊一句"铺这块砖"，队里立刻铺这块砖；再喊"勾缝"，立刻勾缝。

每一嗓子指令都要走完整的传达链：

```text
你喊话（Python 代码）→ 领班翻译成工序（算子拆解）
→ 查手册选工具（分发）→ 派工开工（Launch）→ 工人干活（设备执行）
```

**每一步都真实存在，每一步都要付钱**（解释、翻译、派工各有开销）。大工序无所谓；**满屋都是"钉一颗钉子"级的小活时，派工的嗓子和时间全耗在传达上**——工地时间线上全是活与活之间的空隙。

但现场干有两个真本事：**每步都能叫停检查**（调试），**想改方案随时改**（任意 Python 控制流）——研究和实验离不开它。

::: details 小测 1：为什么"小算子特别多"的网络在 Eager 下最吃亏？
因为三层组织成本（Python 解释、分发查表、Launch 派工）是**按算子次数收的**，和活的大小无关。小活干 8 微秒、派工 5 微秒，一半时间在走流程。大活（一个 GEMM 干几毫秒）摊薄这点派工费无所谓。
:::

### 2. 施工图：让总工看见整个工程

现场指挥的致命短板：**领班只看得见眼前这一步**。他不知道步骤 3 和步骤 4 其实能合并干。

**计算图**就是把整段工程记录下来的一张施工图：**节点是工序，边是材料依赖**（上一步的产出是下一步的投入）。拿到完整图纸，总工（编译器）能做的事立刻多起来：

- **合并工序**（算子融合）：抹灰+打磨+刷漆一趟完成，材料不落地——省搬运；
- **堆场复用**（内存复用）：这堆料用完了，场地腾给下一堆——降峰值显存；
- **一次交底**（整图下发）：不用每步都喊一嗓子，整图计划一次交给工地——省 Launch 空隙。

图纸有两种画法：**边干边记**（动态图，PyTorch 本色）和**先画完再干**（静态图，老牌路线）。`torch.compile` 是折中高手：**描图员**（Dynamo）趁你第一次干活时把流程描成图，**优化师**（Inductor）把图改得更高效，之后的每次执行都直接用优化版。

::: details 小测 2：Eager 和图模式各自"看得见"什么？
Eager 只看得见当前这一个算子——它没有资格决定"把 Norm 和激活合并"，因为它根本不知道后面还有个激活。图模式看得见整段依赖关系：相邻（融合）、生命周期（内存复用）、全图（整图下发）都由此而来。
:::

### 3. 施工图不是免费的

用图要付四笔钱，心里要有数：

1. **首次规划慢**（warmup/编译耗时）：第一次要把图描出来、优化好——训练前几步慢很正常；部署可以提前画好（离线编译）；
2. **户型变了要重画**（guard / recompile）：图是在"三室一厅"上优化的，来了"两室"就得重画。**变长输入最伤**——反复重画的时间可能超过省下的时间；
3. **图里塞不进的就断**（graph break）：调试打印、动态 Python、不支持的算子会把图切碎，碎段之间退回现场模式——图越碎，越白忙；
4. **干法微变**：合并工序可能改变浮点求和顺序——数值几乎不变，但比对时会看到微小差异。

实践口诀：**先 Eager 跑对，再图模式跑快**；收益不达预期，先查"重画了几次"（recompile），再查"图断了几处"（graph break）。

::: details 小测 3：一个变长输入的推理服务开了图模式，性能反而更差——最可能的原因？
guard 频繁失效 → recompile 风暴：每个新长度都触发一次重新编译，编译耗时吞掉了融合和整图下发省下的时间。对策：动态 shape 编译、固定 padding，或干脆对这段退回 Eager。
:::

### 第 6 章 · 3 句话带走

1. Eager 写一行干一步：**灵活好调试，但按算子次数付组织成本，小算子链最吃亏**；
2. 计算图给编译器全局视角：**合并工序、堆场复用、一次交底**——分别省搬运、显存、Launch；
3. 图有四笔账：**首译慢、户型变要重画、塞不进就断、干法微变**——先跑对再跑快。

## 第 7 章｜Stream、Event 与异步执行

完整正文 → [第 7 章｜Stream、Event 与异步执行](07-stream-event-async.md)

> 适用：时间紧，或完整版跟不动时。这页用"工地车道与签认单"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 下单就给你单号：异步执行

你在 App 上下单（调用算子），**立刻收到单号（函数返回）**——但货还在仓库排队（设备队列里等执行）。

为什么必须这样？因为你（Host）写单子的速度比工地（Device）干活快**上万倍**。如果每单都站在门口等货，你 99% 的时间在发呆。所以所有框架都是：**你只管连续下单，工地按单号顺序慢慢干**。

两个立刻要改的习惯：

- **别乱问"货到哪了"**：`.item()`、`.cpu()`、`print(张量)` 都是在逼系统"当场交货"——每一次都是踩刹车；
- **别信报错位置**：工地在第 50 单出了事故时，你已经写到第 200 单、跑到无关的代码行——Python 堆栈基本是假线索。排障时临时改成"下单即等货"模式（`ASCEND_LAUNCH_BLOCKING=1`），事故当场暴露。

::: details 小测 1：为什么 `print(loss.item())` 会拖慢训练循环？
`.item()` 需要真实数值，Host 必须阻塞等设备把前面所有任务算完——异步流水被掐断。放在循环里就是每步踩一次刹车。改法：降低频率、积累后统一打印。
:::

### 2. 车道与签认单：Stream 和 Event

任务不能全挤一条道。**Stream（流）= 单行车道**：同一条道上的车**严格按序、绝不超车**——拷贝、计算、通信混在一条道上时，谁也别想抢先。

想要并行，就修多条道：

```text
计算道：[GEMM] [Norm] [GEMM] …
搬运道：[进货 batch+1] [出货 result]      ← 与计算道同时跑
对账道：[AllReduce 梯度桶1] [桶2]        ← 与计算道同时跑
```

但跨道就出安全问题：**B 道要用 A 道刚生产的料，怎么知道料好了？**——**签认单（Event）**：

- `record`：A 道干完这段在单子上盖章；
- `wait`：B 道看到这章才开工。

两种经典病，对号入座：

| 病 | 症状 | 病因 |
| --- | --- | --- |
| **漏发签认单** | 结果**偶发**错误，跑十次错一次 | 数据竞争：用了还没生产完的料 |
| **盖章太勤** | 永远正确但**慢得像串行** | 滥同步：流水线被反复掐断 |

::: details 小测 2：代码里所有任务都在默认流上，看起来分了几个函数，实际执行形态是什么？
彻底串行。默认流是单行道（有些语义下还会给所有其他道踩刹车），函数怎么拆都不改变任务排队顺序。想并行必须真正使用多条 Stream，并配 Event 声明依赖。
:::

### 3. 让车流跑满：重叠的艺术

并行设计只有一个公式：**把没有依赖的任务分道，用签认单接上必要的依赖。**

三种标准打法：

1. **提前备料**：算 batch N 的同时，搬运道已经在进 batch N+1 的料（Double Buffer 的任务级放大版）；
2. **边对账边干活**：反向传播从后往前逐层出梯度，后层的梯度装桶先发去 AllReduce，通信道和对账之余的反向计算同时跑——DDP 加速的核心秘密；
3. **多段接力**：不同任务段各占一条道，把设备每个部件都喂饱。

失败的两种样子：**假并行**（道修了、闸门全关——时间线上一条道在跑另一条道全在等）和**错并行**（没盖章就抢料——偶发出错）。诊断都靠时间线：Profiling 一拉，空隙和咬死一目了然。

::: details 小测 3：多流程序结果偶发错误，第一怀疑什么？怎么验证？
第一怀疑跨流数据竞争——某条流用了另一条流尚未写完的数据。验证：在可疑访问前补 Event 依赖（或临时加 synchronize），错误消失即确诊。
:::

### 第 7 章 · 3 句话带走

1. **下单 ≠ 到货**：调用返回只是任务入队；`.item()` 是刹车，报错位置是假线索；
2. **Stream 是单行道**：同流按序、跨流并行；**Event 是签认单**，跨道取料必须盖章；
3. 重叠公式：**无依赖分道 + 有依赖盖章**；漏盖章 = 偶发错误，滥盖章 = 假并行。

## 第 8 章｜数据类型、布局与算子融合

完整正文 → [第 8 章｜数据类型、布局与算子融合](08-dtype-layout-fusion.md)

> 适用：时间紧，或完整版跟不动时。这页用"建材规格与码放"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 建材规格：范围、精度、位宽的三角

选数据类型 = 给工地选建材规格。一块浮点数由**指数位（管范围：能表示多大）+ 尾数位（管精度：数得多准）**拼成：

| 规格 | 直觉 |
| --- | --- |
| FP32 | 全能标准料——又大又准，但**贵**（4 字节） |
| FP16 | 表面平整（精度高）但**怕极端尺寸**（最大 65504，超了直接报废） |
| BF16 | **不怕大数**（范围同 FP32）但表面毛糙（精度低） |
| FP8 | 极省料但娇气，前沿工程专用 |

为什么现在的大模型训练几乎都选 BF16？因为训练里**大数（梯度、激活）比精细度更容易出事**——BF16 用精度换范围的买卖是划算的。

换规格的账要算三本：**显存带宽直接受益**（位宽减半，Bytes 减半）；**机器峰值要看档位**（矩阵单元对不同精度有不同峰值，先核对）；**精度账单要单独管**（误差会积累）。

::: details 小测 1：FP16 和 BF16 都占 2 字节，为什么训练主流选 BF16？
FP16 指数位只有 5 位，最大只能表示 ±65504——训练中的大梯度/大激活轻松超限变 Inf，还得靠 Loss Scaling 救。BF16 指数位 8 位（范围同 FP32）几乎不溢出，代价只是尾数精度低。对训练来说"不炸"比"更准"重要。
:::

### 2. 哪里用什么料：混合精度的分配表

聪明的工地**不是全屋换廉价料**，而是按用途分配：

```text
填充墙（激活、前向权重）     → BF16      量大，省着用
承重结构（累加器、Norm 统计）→ FP32      误差会积累/被当除数，不能省
账本正本（优化器里的权重、m/v）→ FP32    长期累计，必须精细
```

三条铁律：**累加用高精度**（几千次加法的误差会滚雪球）、**统计量要准**（Norm 的均值方差是除数，歪了整层歪）、**正本要精细**（优化器状态的 FP32 正本配 BF16 计算副本）。

推理更激进：直接上"口袋书"——权重压成 INT8/INT4 存储（量化）、KV Cache 也能压。**省料 ≠ 省时间**：读口袋书要换算（反量化），快不快看印刷厂设备（硬件支持）。

::: details 小测 2：为什么矩阵乘加的累加器必须用 FP32？
一次 GEMM 里每个输出元素是几千次乘加的累加。用低精度累加，每次的舍入误差会迅速积累成系统性偏差——高精度累加器把误差摁在可接受范围内，这是"用局部贵换整体准"。
:::

### 3. 码放与合并工序：Layout 和融合

**码放方式（Layout）**：同一批料可以按图排（NCHW）也可以按位置排（NHWC）——**没有绝对好的摆法，只有跟最大消费者配不配**。改摆法（Transpose/Reformat）= **全部搬出来重码一遍**（一读一写，真实发生）；更阴险的是**隐式重码**：图编译时相邻算子要的摆法不一致，编译器悄悄插一个 Reformat——代码里看不到，时间线里全是它。

**合并工序（融合）**：把几道小工序合成一趟干完（中间材料不落地），三派手艺按序取用：

1. **预制构件**（内置融合算子）：FlashAttention 这类——别人替你造好了，优先用；
2. **总工自动优化**（编译器融合）：torch.compile / GE 的模式匹配——免费但有限；
3. **老师傅手写**（手写 Kernel）：Ascend C 自定义算子——收益最大、成本最高，是 Ascend C 算子开发的主线。

**不是所有邻居都该合并**：逐元素链、Norm 链该融（省的是搬运，账本"向右挪"）；**两个大 GEMM 之间不该融**——本来就是机器满转的工序，合并不增加产出还伤灵活性。

::: details 小测 3：把 `RMSNorm + Add + 激活` 融成一个 Kernel，收益记在哪本账上？
搬运账（第 5 章的"向右挪"）：三个中间结果原本要各写回 HBM 再读出，融合后全部留在片上——Bytes 大减、AI 右移。顺带还有 Launch 账（3 个任务变 1 个）。这类"低算术强度链"是融合的最佳标的。
:::

### 第 8 章 · 3 句话带走

1. 类型是三角交换：**BF16 用精度换范围**胜出训练；换低精度时**显存立刻受益、峰值先核对档位**；
2. 混合精度按对象分配：**填充省（激活）、承重精（累加/统计）、正本细（优化器状态）**；
3. 布局跟最大消费者走（**重码是真实的一读一写**）；融合三派按序用，**逐元素链该融、大 GEMM 之间不该融**。
