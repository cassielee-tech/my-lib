# 第 3 章｜存储层次与数据搬运

> 本课目标：说清 HBM、Cache、片上 Buffer 和寄存器的区别与联系；解释数据搬运为什么经常比计算更贵；掌握局部性与复用这两种降低搬运成本的基本思路，为第 4 章的 Tiling 与流水线做准备。

## 本章导学

::: tip 本课只记住 3 件事
1. 存储是金字塔：越靠近计算单元，越快、越小、越贵；没有一层能同时做到"大、快、便宜"。
2. 搬一字节的能耗和延迟远高于算一次乘加——让数据少动、复用，是所有性能优化的底层逻辑。

## 03-1｜存储金字塔：容量、延迟与带宽

::: info 本单元目标
围绕 **存储金字塔** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

先回到工厂那张画：工具袋、工作台、货架、大仓库，越近的台面越小越贵。这个单元回答两件事：厂子为什么非要这么摆，以及衡量每一层时要分清"放多少料、跑一趟多久、每秒过多少车"。下面正文讲的金字塔和三个指标，就是给这张画记账。

理想中的存储应该容量大、速度快、便宜。物理上这三者互相矛盾，于是所有计算系统都长成了同一座金字塔。

### 2. 为什么必须是金字塔

工艺决定了基本矛盾：

- **快的存储贵且小**：SRAM 单元面积约是 DRAM 的数倍到数十倍，片上只能放几十 MB；
- **大的存储慢且远**：HBM/DDR 容量大，但物理上离计算单元远，信号传输和器件速度决定了延迟和带宽上限；
- **容量每升一层，速度大约降一个数量级**，逐层递推就得到金字塔结构。

```text
        寄存器            最快·最小·每线程/单元私有
       ┌────────┐
       │ Shared │          片上 SRAM：GPU 的 Shared Memory / NPU 的 UB、L1
       ├────────┤
       │  L2    │          全 SM/全核共享的片上缓存
       ├────────┤
       │  HBM   │          设备内存：几十 GB，带宽 TB/s 级
       ├────────┤
       │ DDR/SSD│          Host 内存与盘：更大更慢
       └────────┘          越往下：越大·越慢·越便宜
```

### 3. 三个必须分清的指标

| 指标 | 含义 | 常见量级（设备内存级） |
| --- | --- | --- |
| **容量** | 能装多少数据 | HBM：几十～上百 GB |
| **延迟** | 一次访问要等多久 | HBM：数百 ns；片上 SRAM：个位数 ns |
| **带宽** | 单位时间最多搬多少字节 | HBM：1～10 TB/s 级 |

三个指标经常被混为一谈，但它们独立地影响性能：

- **延迟**决定单次等待的时长——GPU 靠 Warp 切换隐藏它，NPU 靠流水线组织绕开它（见 02-2、02-3）；
- **带宽**决定持续供给的上限——流水线再好，单位时间进来的数据量超过带宽就一定饿；
- **容量**决定什么必须留在片上、什么必须住在外面——它决定了 Tiling 的可行空间。

::: tip 量级直觉
一次 HBM 访问的时间里，一个 Tensor Core 已经可以完成成百上千次乘加。这就是"计算等数据"成为常态的根源：**不是计算慢，是数据远。**
:::

带宽与利用率的关系还取决于访问方式：同样的总数据量，连续大块访问（顺序、对齐）能逼近峰值带宽；碎片化小访问（跨行跳跃、不对齐）会让有效带宽大幅下降。这也是后面 Layout 讨论的物理基础。

## 03-2｜认识每一层：HBM、Cache、Buffer 与寄存器

::: info 本单元目标
围绕 **HBM、Cache、片上 Buffer 与寄存器** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

金字塔每一层在工厂里都有实物：寄存器是手边的工具袋，片上 SRAM 是机器旁的工作台，HBM 是贴着车间的厂区大仓库，DDR 是 CPU 那边的中央仓库。工作台区域的管法分两派：一派是智能货架自动帮你补货（Cache），一派是自己列清单、叫料车按单送（Buffer）。这个单元就给这些层各发一张"身份证"，顺便对齐 GPU 和 NPU 的叫法差异。

金字塔的每一层都真实存在，但名字在不同平台上不一样。本单元给它们各发一张"身份证"。

#### 3.1 寄存器：计算的直通车

寄存器是计算单元直接读写的一等公民，延迟最低、带宽最高，但容量最小（每个 SM/AI Core 分到的寄存器堆以 KB 计）。Kernel 里的局部变量、Tile 的小块数据最终都要进寄存器才能参与计算。**寄存器不够用时会触发溢出（Spill）**——数据被临时赶回片下存储，性能明显下降。

#### 3.2 Cache 与 Buffer：两种片上 SRAM 哲学

片上 SRAM 快但小，"谁来决定它装什么"分成了两条路线：

| | **Cache（缓存）** | **Buffer（显式缓冲）** |
| --- | --- | --- |
| 装什么由谁决定 | 硬件自动（按访问历史） | 软件显式（代码指定搬什么） |
| 典型代表 | CPU 各级 Cache、GPU 的 L1/L2 | GPU 的 Shared Memory、NPU 的 UB/L1/L0 |
| 优点 | 透明，编程省心 | 行为可预期，能精确排流水 |
| 代价 | 命中率不确定、不可搬控 | 编程负担重，要自己管理容量与生命周期 |

GPU 两者都有：L1/L2 是 Cache，Shared Memory 是可编程 Buffer；NPU 主推 Buffer 路线：UB（Unified Buffer）服务 Vector 通路，L0A/L0B/L0C 服务 Cube 通路，由 DMA/MTE 指令显式搬运（详见 《昇腾与 HCCL》的 [01-1](/comm-ascend/00-ascend-cann.md#_0-0-npu、达芬奇架构与-ai-core)）。

::: warning "Cache 友好"不等于"Buffer 友好"
依赖硬件缓存的代码只要访问局部性好即可；显式 Buffer 的代码还必须回答"数据何时搬入、何时用完、空间够不够"——这是第 4 章流水的核心问题。
:::

#### 3.3 HBM 与 DDR：设备内存的两个世界

- **DDR**：挂在 CPU 侧的系统内存，容量大（几百 GB～TB 级）、带宽相对低；
- **HBM**：通过 3D 堆叠和超宽接口贴在加速芯片旁的设备内存，容量小一个量级，带宽高数倍。

加速卡的"显存"指 HBM。大模型能否跑起来首先看它：权重、激活、KV Cache 都住在这里。各代主流卡的显存容量与带宽对比：

![主流 AI 加速器显存容量与 HBM 带宽对比](/images/ai-infra/accelerator-memory-bandwidth-map.svg)

同一张卡上还区分**计算可用的理论带宽**与**实际有效带宽**：访问模式、页冲突、读写混合比都会打折。做性能分析时，用"实测搬了多少字节 ÷ 耗时"得到有效带宽，再与理论值比较。

#### 4. 把金字塔拼回 GPU 与 NPU

两种平台的存储层次对照（示意，具体容量随代际变化）：

```text
GPU：     寄存器 → Shared Memory（显式）+ L1（自动） → L2 → HBM
NPU：     寄存器 → UB / L1 → L0A/L0B/L0C（显式搬运）        → HBM
共同点：  越靠近计算单元越快越小；大任务必须切 Tile 分批搬运
差异点：  GPU 允许硬件自动搬运兜底；NPU 要求软件显式编排
```

第 2 章的执行模型在这里闭环：**Warp 切换和 Cube 流水，本质上都是在用"计算组织"掩盖"金字塔下层慢"这个物理事实。**

## 03-3｜数据搬运的代价：为什么数据比计算贵

::: info 本单元目标
围绕 **数据搬运的代价** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

工厂账本上最扎眼的一行：跑一趟仓库的油钱，是台面上拧一颗螺丝的上百倍。所以看性能别只问机器干了多少活，要问**每车料出了多少货**——一车料只出一件货的工序天生亏本，机器再快也白搭；一车料能反复用的工序天生赚钱。下面的能耗数字和公式，就是把这本账一笔笔算给你看。

"数据比计算贵"不是口号，可以从能耗、时间两个维度量化。

#### 5.1 能耗视角：搬一个字节的代价远超算一次

芯片能耗的量级规律（数量级示意，随工艺变化）：

```text
一次 FP16 乘加（寄存器内）      基准 1
读一次片上 SRAM（一级 Buffer）   ~ 数十倍
读一次 HBM                      ~ 数百倍及以上
跨设备传输（一次 NVLink/HCCS）   更高，且还要叠加协议与路由
```

含义：**如果每个数据只算一次就从 HBM 读，能量几乎全花在搬数据上，计算本身近乎免费。** 能效优化的本质就是提高"每次搬运服务的计算次数"。

#### 5.2 时间视角：带宽决定下界

第 1 章（01-4）的访存时间下界在这里落地——用工厂的话说，就是"这趟活最少要多久 = 总料量 ÷ 每秒能进厂的车数"：

$$
T_{memory}^{min}=\frac{Bytes}{EffectiveBandwidth}
$$

关键在于**Bytes 怎么数**。同一个算子，实现方式不同，实际搬运量可以差几倍：

| 算子 | 朴素实现的搬运 | 说明 |
| --- | --- | --- |
| 逐元素 `y = x + w` | 读 x、读 w、写 y | 每元素搬运 3 份数据，只做 1 次计算 |
| GEMM（未复用） | 理论上每输出都要重读整行整列 | 搬运量随规模爆炸 |
| GEMM（分块复用） | 每块数据在片上被反复使用 | 搬运量大幅下降 |

#### 6. 复用次数：一个统一的账本

把账算成单一指标——**复用次数 R = 计算次数 / 搬运字节次数**：

- 逐元素算子：$R \approx 1/3$ 量级——典型 Memory-bound，优化空间不在"算"；
- GEMM $[M,N] \times [N,K]$：每个输入元素被复用 $N$ 或 $M$ 次——分块越大复用越高，但受片上容量限制；
- LayerNorm / Softmax：沿归约轴多趟读写——需要融合或片上多趟计算来减少往返。

这直接解释了 01-3 的瓶颈分类和 01-4 的算术强度：**$AI$ 高的算子（GEMM）值得优化到 Compute-bound；$AI$ 低的算子（逐元素、Norm）天生为搬运所困，出路是融合与复用。**

#### 6.1 三条降搬运的路线

1. **少搬**：去掉不必要的数据往返（中间结果留在片上、算子融合）；
2. **重用**：分块让每个字节参与更多计算（Tiling，第 4 章）；
3. **搬巧**：连续对齐访问逼近峰值带宽，减少格式转换（Layout，03-4）。

#### 6.2 搬运与计算的赛跑

一个 Tile 的生命周期里，搬运和计算在赛跑：

```text
不好：搬入 ──► 计算 ──► 搬出 ──► 搬入 ──► 计算 ──► 搬出   （串行，互相等待）
好：  搬入1 ──► 搬入2 ──► 搬入3          （搬运流水）
          计算1 ──► 计算2 ──► 计算3      （计算流水，与搬运重叠）
```

理想情况下计算单元看不到搬运延迟——它一抬头，下一个 Tile 已经在片上。这就是 **Double Buffer / 流水线**，第 4 章的主题。本章只需要记住结论：**流水线的原料，是本章的复用账本和容量约束。**

## 03-4｜局部性、复用与 Layout

::: info 本单元目标
围绕 **局部性与数据复用** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

既然料贵，怎么省钱？三个字：少搬、重用、搬巧。翻译成工厂话：能拼进邻居合同的工序就别单独跑一趟（融合），一车料尽量在台面上多用几次（分块），料按取货顺序码放、别乱堆（Layout）。这个单元讲这三招背后的共同原理——局部性。

存储层次决定了"数据贵"，那么软件怎样少付这个代价？答案是利用局部性，并把数据摆放成硬件喜欢的样子。

#### 7.1 两种局部性

- **时间局部性**：刚用过的数据很快会再用——把它留在最快的层（片上 Buffer / 寄存器）；
- **空间局部性**：用了地址 A，大概率接着用 A+1、A+2——把它和邻居一起成块搬运。

存储层次的所有软硬件机制（Cache 行、预取、Tile 分块）都在奖励这两种局部性。**代码与局部性合拍，性能免费提升；对着干，每一层都在惩罚你。**

#### 7.2 用局部性解释常见现象

| 现象 | 局部性解释 |
| --- | --- |
| 按行遍历行主序矩阵快，按列慢 | 行访问空间局部性好；列访问每步跨一整行 |
| 融合的 Norm+Add 比两个算子快 | 中间结果留在片上（时间局部性），省一次往返 HBM |
| 小 Batch 推理带宽利用率低 | 数据块小且频繁，搬运启动开销占比高 |
| Transpose 显式算子有成本 | 改变了空间局部性，需要额外一趟读写 |

#### 7.3 分块：把局部性工程化

GEMM 分块是局部性的教科书案例。设片上 Buffer 能装下 $[T_m, T_k]$ 和 $[T_k, T_n]$ 的块：

```text
外层：按块循环扫完整矩阵
  内层：块驻留片上，完成 T_m × T_n × T_k 次乘加
收益：每个字节从 HBM 搬一次，在片上参与 ~T 次计算（复用次数 ↑）
约束：块大小受 Buffer 容量限制——这就是 Tiling 的"调参空间"
```

块太小：复用少、搬运多；块太大：放不下或挤占其他数据的驻留空间。**Tile 尺寸的本质，是在容量约束下最大化复用次数**——第 4 章将把这套账本变成具体的切分策略。

#### 8. Layout：数据的摆放方式

同样一份张量，内存里有多种摆法：

| 布局 | 记法 | 对谁友好 |
| --- | --- | --- |
| 行主序 | NHWC / NDHWC（C 连续） | 通道维连续访问、卷积加速 |
| 列主序 / NCHW | NCHW（H、W 连续） | 部分框架默认、逐像素访问 |
| 分块布局 | 按块交织存放 | Tensor Core / Cube 的分块加载 |

三个实用结论：

1. **布局没有绝对好坏，只有与访问模式是否匹配**：卷积的默认布局和 GEMM 的默认布局可以不同；
2. **布局转换不是免费的**：Transpose、Reformat 都要真实读写 HBM——算子融合时常把"转换"和"计算"合并来摊薄成本；
3. **跨层接口的布局要协商**：框架算子、通信原语、Kernel 各有偏好，布局不一致时插入的隐式转换是常见的隐形开销（本专栏第 8 章展开）。

### 10. 自测题

1. 为什么存储不能一层做到"又大又快又便宜"？
2. 容量、延迟、带宽三个指标分别决定什么？
3. Cache 和 Buffer 的核心区别是什么？各举一个代表。
4. HBM 与 DDR 的定位差异是什么？
5. 寄存器溢出（Spill）为什么会显著降低性能？
6. 从能耗视角解释"计算免费、搬运昂贵"。
7. 复用次数 R 怎么定义？逐元素算子和大 GEMM 的 R 量级差多少？
8. 时间局部性和空间局部性分别是什么？各对应什么优化？
9. Tile 尺寸选择的本质权衡是什么？
10. 布局转换为什么有真实成本？什么时候值得主动做转换？

::: details 自测答案

1. 工艺上快存储（SRAM）面积大、成本高，无法做大容量；大容量存储（DRAM/HBM）物理上离计算单元远、器件慢。三者相互矛盾，只能分层组合。
2. 容量决定什么数据必须驻留在片外；延迟决定单次等待时长（GPU 用 Warp 切换、NPU 用流水隐藏）；带宽决定持续数据供给的上限。
3. Cache 由硬件按访问历史自动管理（CPU 各级 Cache、GPU L1/L2）；Buffer 由软件显式指定装什么（GPU Shared Memory、NPU UB/L1/L0）。前者透明但不可控，后者可预期但编程负担重。
4. DDR 是 CPU 侧系统内存，容量大带宽相对低；HBM 通过 3D 堆叠贴近加速芯片，容量小一个量级但带宽高数倍，是放权重、激活和 KV Cache 的地方。
5. 溢出把本应留在寄存器的数据赶回片下存储，每次使用都要重新经历长延迟和带宽消耗。
6. 一次 HBM 读取的能耗是一次寄存器内乘加的数百倍以上；若每个字节只算一次就搬运，能量几乎全部花在搬运上，计算开销可忽略。
7. R = 计算次数 / 搬运字节次数。逐元素算子 R 约 1/3；GEMM 中每个输入元素被复用 N 或 M 次，大矩阵下 R 可达数百上千——相差三个数量级，决定了前者天生 Memory-bound、后者可优化到 Compute-bound。
8. 时间局部性：刚用的数据很快再用，留在最快层；空间局部性：相邻地址即将被用，成块搬运。分别对应数据驻留/融合与连续访问/分块。
9. 本质是在片上容量约束下最大化复用次数：块越大复用越高、搬运越少，但受 Buffer 容量与寄存器压力限制，还要兼顾并行度和尾块。
10. 转换需要真实读写 HBM（一趟读 + 一趟写），且可能破坏访问局部性。当转换后的布局能让后续多个算子的访问/分块效率显著提升、或能与计算融合摊薄成本时，才值得做。

:::

### 11. 本课小结

- 存储金字塔是物理约束的必然：越近越快越小越贵；
- 片上 SRAM 分两种哲学：Cache 硬件自动、Buffer 软件显式，GPU 两者兼备，NPU 以 Buffer 为主；
- 搬运比计算贵：能耗差数百倍，带宽决定时间下界；
- 复用次数 R 统一账本：R 低天生 Memory-bound（融合出路），R 高可优化到 Compute-bound（Tiling 出路）；
- 局部性是软件的抓手：时间局部性靠驻留与融合，空间局部性靠连续访问与分块；
- Layout 是双刃剑：匹配访问模式则快，不匹配则引入昂贵的隐式转换。
