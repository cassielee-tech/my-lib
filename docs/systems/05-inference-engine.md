# 第 5 章｜推理引擎与 KV Cache 管理

> 本课目标：理解从训练循环到推理服务的三重转变；掌握 Continuous Batching 的迭代级调度为什么带来量级吞吐提升；算清 KV Cache 的显存账并用 Paged Attention 与 Prefix Cache 两件套管理它；说出多卡推理的通信形态。

## 本章导学

::: tip 本课只记住 3 件事
1. **推理不是"没有反向的训练"**：自回归生成使请求耗时不可预知、batch 维度随时变化——按训练思路（静态 batch、一次前向）做服务必然低效，**推理引擎的全部设计都在对抗"不可预知"**。
2. **Continuous Batching = 迭代级调度**：每生成一步就重组 batch——完成的请求立刻退出、排队的新请求立刻补位，GPU 永远满负荷。静态批"整批等最慢"的浪费就此消灭。
3. **KV Cache 两件套**：**Paged Attention** 用分页消灭预留浪费（碎片 60-80% → <10%），**Prefix Cache** 让共享前缀只算一次——显存账本的两把省刀。
:::

## ⚡ 速通（约 5 分钟）

### 1. 高峰期的奶茶店：三重转变

训练像**后厨试菜**：一锅一锅按配方做，每锅时间固定；推理像**高峰期的奶茶店**：客人一个接一个、每杯做多久看心情（生成多少字不可预知）、还得既快又稳（吞吐 × 延迟双指标）。

朴素开店的两种亏法：**一单一单做**（设备喂不饱——Decode 每步本来就吃不满算力，串行把不满乘以订单数）；**攒一大单一起做**（静态批：3 秒做完的柠檬茶陪 5 分钟的杨枝甘露**等到底**，门口新客一直排队）。两层亏同源：**批的边界是死的，客人是活的**。

::: details 小测 1：静态批的浪费出在哪？
整批的生命周期跟了最慢的请求：提前完成的空转陪等 + 新请求排队等批边界。
:::

### 2. 流水补位：Continuous Batching

聪明店长改了规矩：**不看单、看杯**——每出一步活（生成一个 token）就重新排一次工位：做完的立刻端走，排队的新单**立刻补进空位**，设备永远满负荷。

对应术语：**迭代级调度**——调度的单位从"一次请求"降到"一步生成"。利用率从约 40%（陪等）拉到接近 100%。新瓶颈随之浮出：**操作台上能同时摆多少杯**（显存里装得下多少 KV Cache）。

::: details 小测 2：连续批之后，并发的上限由什么决定？
显存——能装下多少个请求的 KV Cache，就 能同时服务多少请求。
:::

### 3. 冰格分格存料：Paged Attention 与预制茶底

**存料问题**：每杯进行中的茶都要占一格"续杯缓存"（KV Cache ≈ 0.5 MB/token，一杯 32K 上下文的茶要 16 GB！）。朴素做法是给每杯**预留最大杯子**——大部分杯子用不满，操作台 60-80% 全是空格浪费。

**分格（Paged Attention）**：把操作台划成小冰格（固定大小的物理块，如 16 token/格），**用几格占几格**，每杯记一张"我的料在哪几格"的表（块表）——逻辑上连续、物理上散装，浪费从 60-80% 降到 <10%，能同时做的杯数翻倍。

**预制茶底（Prefix Cache）**：所有客人都要的"标准茶底"（系统提示 4K token）**只做一次**存进冰格，后面的客人直接舀——省一遍制作（Prefill 计算），多个客人还能共享同一格（显存）。

::: details 小测 3：为什么前缀的 KV 能共享？
causal attention：前面的 token 看不到后面——前缀的 KV 只由前缀自己决定，与后文无关，天然可复用。
:::

### 3 句话带走

1. **推理 ≠ 没有反向的训练**：请求时长不可预知，一切设计都在对抗它；
2. **连续批看杯不看单**：迭代级调度，完成即走、新到即补——吞吐钥匙；
3. **冰格分格 + 预制茶底**：分页消灭预留浪费、前缀缓存共享算一次——显存与计算的双省。

## 05-1｜从训练循环到推理服务

::: info 本单元目标
围绕 **"推理与训练的三重转变"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 1. 三重转变

第 3 章（选修）建立了单请求视角：Prefill 算一遍、Decode 逐 token 生成。现在把镜头拉到服务视角，推理相对训练发生了三重转变：

| 维度 | 训练 | 推理 | 后果 |
| --- | --- | --- | --- |
| **计算结构** | 前向 + 反向 + 优化器更新 | **只有前向**（自回归地重复） | 权重只读；KV Cache 成为主要动态状态 |
| **请求时长** | 一步固定（batch 定了就定了） | **不可预知**（生成多少 token 由模型决定） | batch 维度随时变化——调度的噩梦 |
| **优化目标** | 吞吐（loss 下降快） | **吞吐 × 延迟双指标**（下一章展开） | 不能只顾快，还要顾"快得均匀" |

第三行的"不可预知"是全部麻烦的根源：一个请求可能生成 10 个 token 就停（EOS），另一个可能写 4000 字——**你永远不知道 batch 里谁先走**。

### 2. 朴素服务的两张账单

**朴素做法 A：逐请求串行**（batch=1）——简单，但 GPU 喂不饱：Decode 每步只读一遍权重算一个 token（[第 3 章 03-1](03-inference-kv-cache.md#_03-1-生成循环、prefill-与-decode) 讲过 Decode 天然吃不满算力），串行等于把这份不满乘以请求数。

**朴素做法 B：静态批**——攒 N 个请求拼成 batch，一起进、一起出。问题出在"一起出"：生成 10 token 的请求早完成了，却要陪生成 4000 token 的**等到底**——提前完成的算力被空转浪费，新请求在门外排队。

```text
静态批（N=3）：
req A ██████（完成）······················ ← 空转陪等
req B ██████████████████（完成）········· ← 空转陪等
req C ██████████████████████████████（完成）
新请求 ·····································█ ← 一直排队
```

两张账单指向同一个结论：**问题的本质是"批的边界是死的，而请求是活的"**——解法就是让批活起来（下一单元）。

::: tip 一句话定位
推理引擎（vLLM/SGLang 等）= **调度器**（批怎么活）+ **显存管理器**（KV 怎么放）+ **执行器**（前向怎么跑快）——本章按这三块展开，前两块是重点。
:::

## 05-2｜Continuous Batching：迭代级调度

::: info 本单元目标
围绕 **"迭代级调度"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 3. 静态批的边界为什么是死的

静态批按"请求"为边界组批：整批进 → 整批出。死边界的代价在 05-1 的账单里已经看到——**提前完成的空转** + **新请求的排队**。两层浪费同源：**批的生命周期跟了最慢的请求**。

### 4. 把调度粒度从"请求"降到"迭代"

**Continuous Batching（连续批处理，Orca 首创、vLLM 普及）**：调度的基本单位不是一次请求，而是**一步 Decode 迭代**——每生成一个 token，就重新组一次批：

```text
迭代 t：  [A B C]  一起算一步 → A 生成完毕（EOS）！
迭代 t+1：[B C D]  A 退出、结果返回；排队中的 D 立刻补位
迭代 t+2：[B C D]  ……
```

三行设计读出全部收益：

| 机制 | 消灭的浪费 |
| --- | --- |
| 完成即退出 | 提前完成请求的空转陪等 |
| 新到即补位 | 新请求的排队（等批边界） |
| 每步重组 | batch 大小自适应负载，GPU 持续满载 |

**Prefill 与 Decode 同批混跑**：新请求补位时先做它的 Prefill（可与其他请求的 Decode 拼在同一次前向）——这一步埋下"两种负载互相干扰"的种子，是[第 6 章](06-pd-scheduling.md)的主角，本章先按下不表。

#### 4.1 吞吐的量级变化

定性算一笔：设请求生成长度分布 100~1000 token（均值 400）。

- 静态批：批的实际占用 = 最长请求（约 1000）→ **平均利用率 ≈ 40%**；
- 连续批：每个槽位完成即换新 → 利用率逼近 **100%**（瓶颈只剩显存能装下多少 KV——这正是下一单元的主题）。

vLLM 论文实测：同等硬件下连续批 + 分页相对静态批吞吐提升 **数倍到二十倍量级**（取决于负载），核心贡献正是这两件套。

::: tip 与训练的对照
训练的 batch 在一步内是常量、跨步基本不变（DP 切好的世界）；推理的 batch **每一步都变**——调度器的存在感完全不同。这是"训练引擎"与"推理引擎"分家的根本原因。
:::

## 05-3｜Paged Attention：KV Cache 分页

::: info 本单元目标
围绕 **"分页消灭预留浪费"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

连续批把 GPU 喂饱后，新的瓶颈浮出水面：**显存能装下多少并发请求的 KV Cache**——装得越多，并发越高。

### 5. 先复习 KV Cache 账

回扣 [第 3 章 03-2](03-inference-kv-cache.md#_03-2-kv-cache-保存什么、占多少显存)：每 token 的 KV = 2（K+V）× 层数 × hidden × 2 字节（BF16）。Llama-7B 级（32 层、h=4096）：

$$
0.5\ \text{MB/token} \times 32\text{K 上下文} \approx 16\ \text{GB/请求}
$$

一张 64 GB 的卡，去掉权重 14 GB 和激活，**满打满算服务 2-3 个满上下文请求**——并发被显存卡死。

### 6. 预留式分配的浪费

朴素管理：请求到达时按**最大上下文**预留连续显存（因为 KV 必须连续？未必！）。

```text
预留式（按 max_len=32K 分配）：
req A（实际用 2K）：[██░░░░░░░░░░░░░] 32K 槽位 → 30K 浪费
req B（实际用 5K）：[█████░░░░░░░░░░] 32K 槽位 → 27K 浪费
                              内部碎片 60~80% + 外部碎片（槽位对不齐）
```

**浪费 60-80%** 意味着：显存账本上 64 GB，真正存 KV 的只有十几 GB——并发被"预留"吃掉了。

### 7. 分页：按需分配的逻辑块

**Paged Attention（vLLM）** 把操作系统的分页思想搬进 KV Cache：

- KV Cache 切成固定大小的**物理块**（如 16 token/块）；
- 每个请求持有一张**块表**（block table）：逻辑块号 → 物理块号——序列在逻辑上连续，在物理上散装；
- 每生成一个 token，只在**当前块**追加；块满了再分配新块——**用到多少占多少**。

```text
分页后：
req A（2K）: 128 个物理块，紧凑排布 → 浪费 < 块大小的尾数（<10%）
新请求：有空闲块就能进 → 并发 ↑
```

三重收益：**内部碎片降到尾块级别**（<10%）；**外部碎片消失**（物理块任意拼装）；**能装下的并发数大幅上升**——同样的卡，服务请求数翻倍是常态。

::: tip 认识这个模式的出处
"逻辑连续、物理散装 + 映射表"就是 [《单卡执行系统》03 章](../device/03-memory-hierarchy.md#_03-1-存储金字塔-容量、延迟与带宽) 讲过的虚拟内存分页——推理引擎把一个老思想用在了新状态上。代价是 attention kernel 要**按块表寻址**（gather），这是 Paged Attention kernel 比朴素 attention 复杂的原因。
:::

## 05-4｜Prefix Cache 与多卡推理

::: info 本单元目标
围绕 **"前缀复用与多卡推理通信"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

分页解决了"装得下"，本单元解决"算得少"与"多卡怎么办"。

### 8. Prefix Cache：共享前缀只算一次

真实服务的请求常常共享长前缀：系统提示词（几千 token）、few-shot 模板、多轮对话的历史。

**Prefix Cache 的规则**：前缀部分的 KV Cache 只依赖前缀 token 本身（causal attention 的性质——前面的 token 看不到后面，[《模型全景》04-2](../model/04-self-attention.md#_04-2-缩放点积与-causal-mask)），**与后文无关**。于是：

```text
请求 1: [系统提示 4K + 问题 1]  → Prefill 一次，4K 的 KV 入缓存
请求 2: [系统提示 4K + 问题 2]  → 命中！4K 的 KV 直接复用，只 Prefill 问题部分
```

省两笔账：**计算**（Prefill 的 FLOPs 按命中长度免掉）与**显存**（分页块级复用，多个请求共享同一批物理块——只读共享，天然安全）。管理策略通常是 LRU：缓存满时淘汰最久未用的前缀块。

一句话定位：**Prefix Cache 是 KV Cache 上的"内容寻址缓存"**，命中率越高收益越大——系统提示越长、请求越同质，越是划算。

### 9. 多卡推理：通信挂回到熟悉的钩子上

单卡装不下（权重或 KV 或吞吐不够）时，推理并行登场——通信需求回到本课程的主线上：

| 手段 | 通信形态 | 回扣 |
| --- | --- | --- |
| **TP 推理** | 每层 2 次 AllReduce（前向）——与训练同构 | [《并行策略》06 章](../parallel/06-tensor-parallel.md) |
| **EP 推理（MoE）** | 每层 dispatch/combine 的 AlltoAll | [《集合通信》04-4](../collective/04-gather-scatter-alltoall.md#_04-4-moe-的-alltoall-为什么难) |
| **PD 分离的 KV 传输** | Prefill→Decode 实例间大块 P2P | [第 6 章](06-pd-scheduling.md)（下一章主角） |

值得先记的一个差异：**训练的通信"大而低频"（梯度 AllReduce），推理的 Decode 通信"小而高频、延迟敏感"**——每生成一个 token 就要过一遍每层通信，任何一次通信的微秒级抖动都直接累积进每个字的延迟（[第 3 章 03-4](03-inference-kv-cache.md#_03-4-推理指标、服务与通信) 的伏笔）。这正是推理成为通信库另一半主战场的原因——算法选择、拓扑贴合的要求与训练侧同源（[HCCL 源码 5](../ascend/hccl-source/05-coll-algorithms.md)）。

::: tip 本章收束
推理引擎三件套到此集齐：**调度器**（连续批：批活起来）+ **显存管理器**（分页 + 前缀复用：装得下、算得少）+ **执行器**（多卡通信：挂回主线）。下一章把镜头对准"指标"——TTFT、TPOT 与吞吐的三角制约，以及它的终局解法 PD 分离。
:::

### 把本章串成一条主线

请先合上各单元正文，沿"转变 → 调度 → 显存 → 多卡"复述整章；遇到断点时，再回到对应单元查阅。

```text
转变（05-1）：只有前向 · 请求时长不可预知 · 吞吐×延迟双指标
   朴素两账单：串行喂不饱 / 静态批整批等最慢
        ↓
调度（05-2）：Continuous Batching —— 迭代级调度
   完成即退出 · 新到即补位 · 每步重组 → 利用率 40% → ~100%
        ↓
显存（05-3）：KV 账 0.5MB/token → 预留式浪费 60-80%
   Paged Attention：逻辑连续物理散装 · 块表映射 · 浪费 <10%
        ↓
进阶（05-4）：Prefix Cache 共享前缀只算一次（计算+显存双省）
   多卡推理：TP 的每层 AllReduce / EP 的 A2A / PD 的 KV 传输
   —— Decode 通信小而高频、延迟敏感，与训练通信互补
```

### 10. 自测题

1. 推理相对训练的三重转变是什么？哪一条是调度麻烦的根源？
2. 静态批的两层浪费分别是什么？
3. Continuous Batching 的调度单位是什么？三个机制各消灭什么浪费？
4. 连续批之后，新的瓶颈是什么？
5. 每 token 的 KV 显存公式是什么？Llama-7B 级是多少？
6. 预留式分配的浪费来自哪两个来源？典型比例是多少？
7. Paged Attention 的三个核心机制是什么？靠什么映射结构？
8. 分页的代价是什么？
9. Prefix Cache 为什么合法（causal 的哪条性质）？省哪两笔账？
10. 推理 Decode 通信与训练通信的性格差异是什么？

::: details 自测答案

1. 只有前向（无反向/优化器）；请求时长不可预知（自回归）；吞吐×延迟双目标。时长不可预知是根源——batch 维度随时变。
2. 提前完成请求的空转陪等；新请求排队等批边界。
3. 一步 Decode 迭代。完成即退出、新到即补位、每步重组——分别消灭空转、排队、批大小失配。
4. 显存能装下多少并发请求的 KV Cache。
5. 2 × 层数 × hidden × 2 字节；32×4096×2×2 ≈ 0.5 MB/token。
6. 内部碎片（按 max_len 预留、实际用不满）+ 外部碎片（连续槽位对不齐）；合计 60-80%。
7. 固定大小物理块、按需分配、块表（逻辑块→物理块）映射。
8. Attention kernel 按块表寻址（gather），实现比朴素连续 KV 复杂。
9. 前缀的 KV 只依赖前缀 token（causal：前面的 token 看不到后面）；省 Prefill 计算与 KV 显存（块级共享）。
10. 训练：大而低频（梯度 AllReduce，可重叠）；Decode：小而高频、延迟敏感（每 token 每层通信，抖动直接累积进延迟）。

:::

### 11. 本课小结

- 推理引擎 = 调度器 + 显存管理器 + 执行器，对抗的核心是"不可预知"；
- 连续批把批边界从"请求"降到"迭代"——吞吐的钥匙；
- 分页把 KV 浪费从 60-80% 压到 <10%——并发的钥匙；
- 前缀复用让共享前缀只算一次——计算与显存的双省；
- 多卡推理的通信挂回主线钩子（TP/EP/PD），Decode 的延迟敏感是通信库的另一半战场。
