## 第 1 章｜大模型训练循环

完整正文 → [第 1 章｜大模型训练循环](01-training-loop.md)

> 适用：时间紧，或完整版跟不动时。这页用一个学生的学习闭环讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 学生的一天：做题、对答案、改方法

训练一个模型，就是一个学生无限重复的学习循环：

```text
拿一批练习册（取数据）
  → 做题（前向传播）
  → 对答案算错多少（Loss）
  → 复盘每道错题错在哪（反向传播，得到梯度）
  → 调整学习方法（optimizer.step 更新参数）
  → 撕掉草稿纸（zero_grad 清空梯度）
  → 下一批
```

最容易犯的错：**复盘 ≠ 改方法**。`loss.backward()` 只是算出"每个知识点该怎么调"的清单；要等 `optimizer.step()` 才真的调。而且**复盘完不清零**，下次的清单会和这次的混在一起——所以 `zero_grad()` 不能省。

::: details 小测 1：一次最小的参数更新包含哪几步？
取数据 → 前向算 Loss → 反向算梯度 → （多卡时对账）→ `optimizer.step()` 更新参数 → `zero_grad()` 清空梯度。其中 backward 和 step 是两件事，中间还隔着优化器和可能的通信。
:::

### 2. 三个聪明的学习技巧

**技巧一：攒作业（梯度累积）。** 显存不够一次批改 32 本练习册？每次只批 4 本，批 8 次**攒在一起再统一调整**。效果上等效大 batch，代价是时间——**省的是桌面（峰值激活显存），不是功夫**。等效批量的公式：`4 × 8 × 卡数`。

**技巧二：聪明的复习计划（AdamW + 学习率）。** 普通学生（SGD）对每个知识点一视同仁；AdamW 给每个参数记**两本账**：

- m 账本：最近错题的**平均方向**（一阶矩）；
- v 账本：最近错题的**波动大小**（二阶矩）。

更新时看方向、除以波动——**常错的多改，偶尔错的少改**。学习率则是"每次敢改多大"：开学先小步试探（Warmup），期末再精雕细琢（Decay）。

**技巧三：铅笔草稿（混合精度）。** 正式作业用钢笔（FP32 保存关键数字），大量草稿用铅笔（FP16/BF16 算得快、存得省）。铅笔的坑：**特别小的数会被擦掉**（下溢）——所以先用放大镜把 Loss 放大再算，算完再缩回来（Loss Scaling）。

::: details 小测 2：梯度累积能省时间吗？
不能。它省的是显存：允许把大 batch 拆成多个小 micro-batch，峰值激活变小。计算总量一点没少，反而因为多轮循环略慢。它是"用时间换显存"。
:::

### 3. 教室里有很多同学：对账的时机

一个班几十个同学（多张卡），每人分到不同的练习册。各自的复盘结论不同，**调整方法前必须先对账**（AllReduce 求平均）——否则每人一套方法，模型分家。

聪明的对账时机：**复盘是从后往前逐题进行的，后面几题的清单一出来就先装箱发走**，对账和前面的复盘同时进行（通信与计算重叠）。

记住这条**正确的顺序链**，很多诡异 bug 都是它错了：

```text
反向 → 对账 → 放大还原（unscale）→ 裁剪 → 更新 → 清零
```

（裁剪是"防止某次情绪化大改"：梯度太大就整体按比例压小。注意必须在放大还原**之后**裁剪，否则裁的是被放大的假数值。）

::: details 小测 3：使用 Loss Scaling 时，为什么裁剪前必须先 unscale？
因为梯度当时还是被放大的（真实值 × scale）。直接裁剪，裁的是放大后的假象，真实的梯度大小判断全错。先 unscale 还原真实梯度，再算范数、再裁剪。
:::

### 第 1 章 · 3 句话带走

1. 训练循环 = **做题→对答案→复盘→改方法→清草稿**，`backward()` 和 `step()` 是两件事；
2. 三个技巧：**攒作业省显存不省时间**、**AdamW 记两本账**、**铅笔草稿配放大镜**；
3. 多卡必须**先对账再更新**，可以让对账和复盘并行——顺序链错了就是 bug。

## 第 2 章｜训练显存与计算优化

完整正文 → [第 2 章｜训练显存与计算优化](02-training-memory-compute.md)

> 适用：时间紧，或完整版跟不动时。这页用"书桌空间管理"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 书桌上摆了什么：四个大件

训练一个大模型，就像在一张**固定大小的书桌**上同时摊开四样东西：

| 大件 | 书桌版 | 占地规律 |
| --- | --- | --- |
| 权重 | 课本 | 随模型大小（2 字节/参数） |
| 梯度 | 错题记录 | 同上（2 字节/参数） |
| **优化器状态** | **两本复习账 + 一份钢笔正本** | **12 字节/参数，最大固定件** |
| **激活** | **演算草稿堆** | **唯一疯长的：随 batch × 序列长 × 层数** |

前三个加起来 = **16 字节/参数**。7.5B 的模型光"课本+账本"就要 120 GB——还没开始演算，书桌已经满了。而真正压垮书桌的往往是**草稿堆**：反向传播要用前向的中间结果，全得留着，长序列任务里草稿比课本还多。

::: details 小测 1："16 字节/参数"是哪来的？
BF16 权重 2 + BF16 梯度 2 + FP32 钢笔正本 4 + FP32 一阶矩 4 + FP32 二阶矩 4 = 16。注意优化器一家就占 12——最大固定件是"复习账本"，不是课本。
:::

### 2. 扔草稿的学问：重计算

草稿堆怎么治？最经典的一招：**前向时别全留着，反向要用哪段就现演算哪段**。

```text
普通：前向把每层草稿留全 ────► 反向直接翻
重计算：只存每段"开头" ────► 反向到该段，从头重演一遍 ──► 用完即扔
```

- **省**：草稿堆缩小一个数量级（治的是激活**总量**）；
- **付**：反向多干一遍前向的活——最多 **+33%** 时间；

聪明版叫**选择性重算**：只扔"**占地方大、重算便宜**"的草稿——比如 Attention 的 softmax 中间矩阵（存它要 S² 的地方，重算只是一次 softmax），而大 GEMM 的输入留着的性价比更高。花小钱办大事，现代框架默认用它。

::: details 小测 2：重计算为什么最多 +33% 而不是 +100%？
训练一步的活 ≈ 前向 1 份 + 反向 2 份。重计算多付的是"一遍前向"，1+2 变 2+2——多的是 4 份里的 1 份，所以约 33%。选择性重算连这份都只付一小角。
:::

### 3. 腾挪三式：分批、寄存、换笔

**分批摊（梯度累积）**：32 本练习册一次摊开 vs 分 8 次、每次 4 本——**治草稿的"峰值"**（逐次算逐次收）。总时间不变，买的是"塞得下"。

**寄存家里（Offload）**：把复习账本、错题记录寄存到家里书架（Host 内存），要用时取回来——书桌腾出几十 GB。**代价**：来回取要走慢速通道（PCIe，比书桌内部通道慢一个量级），而且家里的"计算器"（CPU）也慢——吞吐明显下降，属于"跑起来总比跑不起来好"的兜底。

**换笔写（混合精度）**：草稿全用铅笔（BF16 2 字节）而不是钢笔（FP32 4 字节）——**权重、梯度、草稿同时减半**，唯一的"全面减字节"手段，精度账要单独管（《单卡执行系统》第 8 章细账）。

最后是**工作流**：OOM 了别乱调参——先看曲线（启动就爆 = 固定件放不下；每步爬升回落 = 草稿峰值；**越跑越涨 = 泄漏 bug 不是容量**），再按对照表选工具，**改一处、复测一次**。

::: details 小测 3：显存曲线每个 step 都比上一个高一点，最终 OOM——先怀疑什么？
泄漏，不是容量不足：张量被引用没释放、计算图/缓存越积越多。容量不足的表现是每步峰值稳定但超限；单调上涨是 bug，先修泄漏再谈省显存。
:::

### 第 2 章 · 3 句话带走

1. 书桌四件套：**课本+错题+复习账 = 16 字节/参数的固定件**，**草稿堆（激活）是唯一疯长的**；
2. 四件工具各治一样：**重算治激活总量（付时间）、分批治峰值（不付）、寄存放固定件（付通道）、换笔全面减半（管好精度）**；
3. OOM 先看曲线再选工具：**越跑越涨是泄漏 bug**，改一处复测一次。

## 第 3 章｜自回归推理与 KV Cache

完整正文 → [第 3 章｜自回归推理与 KV Cache](03-inference-kv-cache.md)

> 适用：时间紧，或完整版跟不动时。这页用一场"开卷接龙考试"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 先通读题干，再逐字作答

推理就是让模型考试，而且是**接龙考试**：给你题干，一个字一个字往下接。

这场考试分两段，节奏完全不同：

- **Prefill（通读题干）**：把整个 Prompt 一次性读进去，**并行处理**——题干各位置可以同时算（反正它们互相不偷看）。产出：第一个答案字 + 一整套笔记；
- **Decode（逐字作答）**：每轮只读**最新写下的那个字**，结合笔记，算出下一个字，写下来，再算下一个——**天生串行**，没法提前算。

为什么必须一个字一个字来？因为第 101 个字依赖你实际写下的第 100 个字——**未来还没发生，没法并行**。

::: details 小测 1：TTFT 和 TPOT 分别对应考试的哪一段？
TTFT（首字时间）≈ 排队 + 通读题干到写出第一个字；TPOT（每字间隔）= 逐字作答阶段平均每写一个字的时间。用户体感："多久开始回我" 和 "回复 drip 得多快"。
:::

### 2. 桌上的笔记：KV Cache

逐字作答最怕什么？**每写一个字都把整道题重读一遍**。

好消息：题干和已写部分每经过一层会议室（Attention），每个字都会留下**K 名牌和 V 内容**——把它们抄在便利贴、留在桌上，就是 **KV Cache**。下轮只需要：

```text
新字的 Q 卡片 → 只跟桌上的历史 K/V 打分 → 混合 → 下一个字
```

**历史完全不用重算**。两个有意思的细节：

- **为什么不存 Q？** 历史字的"我要找什么"用过即弃——未来的字不会再去查询**过去**的 Q，但会不断查询**过去**的 K/V；
- **笔记有多大？** `层数 × 长度 × 并发桌数 × KV 头数 × 头宽 × 2（K 和 V 各一份）`——五个因子全线性，**长会话 + 高并发时笔记比课本（模型权重）还占地方**。

服务端还有个奶茶店智慧：**Continuous Batching**——不等整批客人做完再接新单，谁做完了立刻腾桌接新人，桌子永远不空转。

::: details 小测 2：KV Cache 为什么按层保存、又为什么不保存 Q？
每一层会议室都有自己的投影（每层一套 K/V），所以要按层各存一份。而 Q 是"当前字要找什么"——每个字只用一轮就作废，未来不会复用历史的 Q；历史的 K/V 却会被未来的每个新字反复查询。
:::

### 3. 写字的胆量：采样与它的代价

算出下一个字，不是直接取分数最高的——还有"胆量"旋钮：

- **Temperature**：胆量大小。低 = 稳妥复读（分布尖锐），高 = 敢说骚话（分布平缓）——但它只改胆量，**不修正知识错误**；
- **Top-k / Top-p**：只在最有把握的 k 个 / 累计概率 p 内挑字，把胡话候选先划掉。

最后是**多卡考试的隐形成本**：Decode 每轮的活很少、又必须一步步来，于是**每一步的通信延迟直接累积到每个字**——Decode 阶段对延迟（而不是带宽）极其敏感。

::: details 小测 3：Temperature 调低，模型会更"准确"吗？
不一定。它只让分布更尖锐——模型本来就笃定的答案更稳，但模型不知道的知识并不会因此变对。Temperature 改的是"敢不敢"，不是"会不会"。
:::

### 第 3 章 · 3 句话带走

1. 推理两段式：**Prefill 并行通读题干，Decode 逐字串行接龙**——TTFT 和 TPOT 分别对应两段；
2. **KV Cache = 留在桌上的历史笔记**（每层的 K/V，不存 Q），随长度/层数/并发线性涨；
3. 采样是胆量旋钮（**不修正知识**）；Decode 的通信**怕延迟不怕带宽**。

## 第 4 章｜预训练、SFT、LoRA 与偏好对齐

完整正文 → [第 4 章｜预训练、SFT、LoRA 与偏好对齐](04-post-training-alignment.md)

> 适用：时间紧，或完整版跟不动时。这页用"培养一个作者"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 从"会写字"到"会聊天"

预训练出来的模型（Base 模型）像个读遍全网的**书呆子作者**：你给它"如何配置环境"，它可能接"变量并重启电脑，这是开发中常见的步骤……"——**它只会续写，不会"回答你"**。

要变成贴心的对话助手，需要两步再教育：

- **SFT（拜师学艺）**：师傅（人类标注者）写出大量"问题→标准回答"的示范，学生照着学**行为**——什么时候该停下、怎么组织回答、怎么承认不会；
- **偏好对齐（迎合读者）**：在两个都"对"的回答里，学会读者更喜欢哪个。

注意 **继续预训练 ≠ SFT**：前者是继续海量泛读专业书（还是续写一切），后者是看示范练行为（只学回答部分）。

::: details 小测 1：Base 模型和 Chat 模型的本质差别？
Base 学的是"文本分布"——给什么续什么；Chat 在此之上用示范（SFT）和偏好（对齐）训练出了"对话行为"——遵循指令、分角色、该停就停。同一个知识底子，不同的行为模式。
:::

### 2. 便利贴修改法：LoRA

全书重写一遍（Full Fine-Tuning）太贵了。**LoRA 的思路：原文不动，修改意见写便利贴**。

- 原书（基础权重 W₀）**冻结**，一个字不改；
- 每个要改的地方贴一张便利贴：`ΔW = A × B`，两个**窄长条矩阵**（低秩）拼出修改量；
- 训练时只学便利贴上的字——可训练参数从几十亿骤降到几百万（`r×(d+k)`）。

收益立竿见影：优化器只需给便利贴记账、多卡同步也只传便利贴的梯度。但有件事便利贴**省不掉**：读书本身——前向反向还是要走一遍完整的大模型，计算量和激活显存一点没少。

**QLoRA 再狠一点**：把冻结的原书**复印成压缩版**（量化成 4-bit）省书架空间，便利贴照贴。

::: details 小测 2：LoRA 减少的是哪部分参数？
减少的是"可训练参数"——冻结的基础权重仍然完整存在（QLoRA 只是把它量化存储省显存），训练和更新的只有低秩 A、B 便利贴。所以：优化器状态大减、梯度通信大减，但模型计算量和激活显存基本照旧。
:::

### 3. 迎合读者的两种手法：RLHF 与 DPO

SFT 之后模型会回答了，但两个回答可能"都对却一好一坏"。怎么教它偏好？

**手法一：RLHF（雇编辑打分）**：

```text
写两版回答 → 编辑给每版打分 → 训练一个"打分器"（Reward Model）
→ 让作者按"打分器满意度"继续练笔（强化学习）
```

缺点：流程重——要养一个打分器，还要在线反复试写。

**手法二：DPO（直接对比）**：跳过打分器——直接拿**成对的"更好 vs 更差"回答**（Chosen / Rejected），告诉作者"这版比那版好"，照着拉开差距就行。简单稳定，是目前主流。

最后一个必须清醒的点：**对齐改变的是"说话的倾向"，不是"知识的真假"**——它能教会模型谦虚地说"我不确定"，但不能让它不知道的东西变成知道。对齐不替代事实核查。

::: details 小测 3：偏好对齐能让模型的回答自动变正确吗？
不能。它调整的是行为偏好分布（更长/更礼貌/更谨慎），不是知识本身。模型不知道的事实，对齐后依然不知道——甚至可能更"自信地胡说"。事实性要靠数据和检索解决。
:::

### 第 4 章 · 3 句话带走

1. Base 只会续写，**SFT 用示范教行为，偏好对齐再教"哪种回答更好"**；
2. **LoRA = 冻结原书、只训便利贴**：省优化器和通信，省不掉计算和激活；
3. **RLHF 养打分器，DPO 直接对比成对回答**；对齐改倾向不改知识。

## 第 5 章｜推理引擎与 KV Cache 管理

完整正文 → [第 5 章｜推理引擎与 KV Cache 管理](05-inference-engine.md)

> 适用：时间紧，或完整版跟不动时。这页用"奶茶店高峰期"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 高峰期的奶茶店：三重转变

训练像**后厨试菜**：一锅一锅按配方做，每锅时间固定；推理像**高峰期的奶茶店**：客人一个接一个、每杯做多久看心情（生成多少字不可预知）、还得既快又稳（吞吐 × 延迟双指标）。

朴素开店的两种亏法：**一单一单做**（设备喂不饱——Decode 每步本来就吃不满算力，串行把不满乘以订单数）；**攒一大单一起做**（静态批：3 秒做完的柠檬茶陪 5 分钟的杨枝甘露**等到底**，门口新客一直排队）。两层亏同源：**批的边界是死的，客人是活的**。

::: details 小测 1：静态批的浪费出在哪？
整批的生命周期跟了最慢的请求：提前完成的空转陪等 + 新请求排队等批边界。
:::

### 2. 流水补位：Continuous Batching

聪明店长改了规矩：**不看单、看杯**——每出一步活（生成一个 token）就重新排一次工位：做完的立刻端走，排队的新单**立刻补进空位**，设备永远满负荷。

对应术语：**迭代级调度**——调度的单位从"一次请求"降到"一步生成"。利用率从约 40%（陪等）拉到接近 100%。新瓶颈随之浮出：**操作台上能同时摆多少杯**（显存里装得下多少 KV Cache）。

::: details 小测 2：连续批之后，并发的上限由什么决定？
显存——能装下多少个请求的 KV Cache，就 能同时服务多少请求。
:::

### 3. 冰格分格存料：Paged Attention 与预制茶底

**存料问题**：每杯进行中的茶都要占一格"续杯缓存"（KV Cache ≈ 0.5 MB/token，一杯 32K 上下文的茶要 16 GB！）。朴素做法是给每杯**预留最大杯子**——大部分杯子用不满，操作台 60-80% 全是空格浪费。

**分格（Paged Attention）**：把操作台划成小冰格（固定大小的物理块，如 16 token/格），**用几格占几格**，每杯记一张"我的料在哪几格"的表（块表）——逻辑上连续、物理上散装，浪费从 60-80% 降到 <10%，能同时做的杯数翻倍。

**预制茶底（Prefix Cache）**：所有客人都要的"标准茶底"（系统提示 4K token）**只做一次**存进冰格，后面的客人直接舀——省一遍制作（Prefill 计算），多个客人还能共享同一格（显存）。

::: details 小测 3：为什么前缀的 KV 能共享？
causal attention：前面的 token 看不到后面——前缀的 KV 只由前缀自己决定，与后文无关，天然可复用。
:::

### 第 5 章 · 3 句话带走

1. **推理 ≠ 没有反向的训练**：请求时长不可预知，一切设计都在对抗它；
2. **连续批看杯不看单**：迭代级调度，完成即走、新到即补——吞吐钥匙；
3. **冰格分格 + 预制茶底**：分页消灭预留浪费、前缀缓存共享算一次——显存与计算的双省。

## 第 6 章｜Prefill/Decode 调度与推理指标

完整正文 → [第 6 章｜Prefill/Decode 调度与推理指标](06-pd-scheduling.md)

> 适用：时间紧，或完整版跟不动时。这页用"备菜间与出菜间"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 两种活，两种脾气：一山二虎

一家餐厅后厨干两种活：**备菜**（Prefill——把客人点的整桌原料一次处理完：大刀阔斧、越快越好，是**力气活** compute-bound）和**出菜**（Decode——按客人吃饭节奏一道道热菜、每道都要扫一遍所有货架找料，是**腿脚活** memory-bound）。

两个指标对应两段体验：**TTFT**（等多久上第一道菜）由备菜决定；**TPOT**（每道菜的间隔）由出菜节奏决定。

麻烦在于：连续批让两种活挤在**同一个灶台**——备一大桌菜（几百 ms 的大 Prefill）时，正在出菜的客人**一道菜都等不来**（TPOT 瞬间毛刺）；反过来偏向出菜，新客人的第一道菜又遥遥无期（TTFT 飙升）。**一山二虎，谁都是对方的干扰源。**

::: details 小测 1：为什么 Prefill 和 Decode 的"脾气"相反？
Prefill 是大 GEMM，每个权重被大量 token 复用——算术强度高，吃算力；Decode 逐 token 生成，每个权重只被用一次——算术强度极低，吃带宽。Roofline 上一个在屋顶区、一个在山坡区。
:::

### 2. 大单切小：Chunked Prefill

聪明主厨的缓解法：大桌菜**分次备**——每备一小批（比如 2048 token 的块）就回去出一道菜，来回穿插。出菜节奏的毛刺从"几百 ms"压到"一小批的功夫"，而备菜总量没变。

旋钮在块的大小：块大 → 备菜效率高（大刀快）但毛刺大；块小 → 节奏顺但每批太碎、效率掉——又是熟悉的"拆小换平滑"。**但这只是缓解**：两种活还是共享一个灶台、一套锅具配置（batch 形态、算子选择依然只能选一边）。

::: details 小测 2：Chunked Prefill 没解决什么？
两种负载仍共享同一硬件与同一套配置——性格矛盾只是被时间切片掩盖，不是消失。
:::

### 3. 分家：PD 分离

终局解法：**备菜间与出菜间分开开业**——

```text
备菜间（Prefill 池）：力气活配置、独立扩容 → 只对 TTFT 负责
       ↓ 半成品传送带（KV 传输：0.5MB/token × 上下文，一桌 16K ≈ 8GB）
出菜间（Decode 池）：腿脚活配置、独立扩容 → 只对 TPOT 负责
```

三个赚头：**指标解耦**（TTFT 不够加备菜灶，TPOT 不够加出菜灶，互不拆台）；**配置各得其所**（两山二虎）；**出菜节奏纯净**（没人插队）。一个代价：**半成品要搬**——大块点对点传输，好在延迟宽容（搬运可以和别桌备菜并行），只要求带宽。

什么时候值得分家：两个指标都有硬指标（SLO）、集群够大养得起两个池；小店单灶 + 切块穿插更省。

::: details 小测 3：KV 传输为什么"延迟宽容"？
它在请求交接时发生一次，可与后续新请求的 Prefill 并行进行——不像 Decode 每层的通信那样卡在关键路径上，只要带宽够、总时长不超过收益即可。
:::

### 第 6 章 · 3 句话带走

1. **一山二虎**：Prefill 吃算力、Decode 吃带宽，混跑必然互相干扰——TPOT 毛刺与 TTFT 排队双向伤害；
2. **切块穿插是缓解**：大 Prefill 切小块，毛刺压平但配置矛盾仍在；
3. **PD 分离是根治**：两个池独立扩容配置，用 KV 大块传输买指标解耦——推理通信的另一半版图。
