连续批把 GPU 喂饱后，新的瓶颈浮出水面：**显存能装下多少并发请求的 KV Cache**——装得越多，并发越高。

## 5. 先复习 KV Cache 账

回扣 [第 3 章 03-2](../03-inference-kv-cache/02-kv-cache-memory.md)：每 token 的 KV = 2（K+V）× 层数 × hidden × 2 字节（BF16）。Llama-7B 级（32 层、h=4096）：

$$
0.5\ \text{MB/token} \times 32\text{K 上下文} \approx 16\ \text{GB/请求}
$$

一张 64 GB 的卡，去掉权重 14 GB 和激活，**满打满算服务 2-3 个满上下文请求**——并发被显存卡死。

## 6. 预留式分配的浪费

朴素管理：请求到达时按**最大上下文**预留连续显存（因为 KV 必须连续？未必！）。

```text
预留式（按 max_len=32K 分配）：
req A（实际用 2K）：[██░░░░░░░░░░░░░] 32K 槽位 → 30K 浪费
req B（实际用 5K）：[█████░░░░░░░░░░] 32K 槽位 → 27K 浪费
                              内部碎片 60~80% + 外部碎片（槽位对不齐）
```

**浪费 60-80%** 意味着：显存账本上 64 GB，真正存 KV 的只有十几 GB——并发被"预留"吃掉了。

## 7. 分页：按需分配的逻辑块

**Paged Attention（vLLM）** 把操作系统的分页思想搬进 KV Cache：

- KV Cache 切成固定大小的**物理块**（如 16 token/块）；
- 每个请求持有一张**块表**（block table）：逻辑块号 → 物理块号——序列在逻辑上连续，在物理上散装；
- 每生成一个 token，只在**当前块**追加；块满了再分配新块——**用到多少占多少**。

```text
分页后：
req A（2K）: 128 个物理块，紧凑排布 → 浪费 < 块大小的尾数（<10%）
新请求：有空闲块就能进 → 并发 ↑
```

三重收益：**内部碎片降到尾块级别**（<10%）；**外部碎片消失**（物理块任意拼装）；**能装下的并发数大幅上升**——同样的卡，服务请求数翻倍是常态。

::: tip 认识这个模式的出处
"逻辑连续、物理散装 + 映射表"就是 [《单卡执行系统》03 章](../../device/03-memory-hierarchy/01-memory-pyramid.md) 讲过的虚拟内存分页——推理引擎把一个老思想用在了新状态上。代价是 attention kernel 要**按块表寻址**（gather），这是 Paged Attention kernel 比朴素 attention 复杂的原因。
:::
