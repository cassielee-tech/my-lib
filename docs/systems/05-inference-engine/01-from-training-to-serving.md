# 单元 05-1｜从训练循环到推理服务

::: info 本单元目标
围绕 **"推理与训练的三重转变"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。

## 1. 三重转变

第 3 章（选修）建立了单请求视角：Prefill 算一遍、Decode 逐 token 生成。现在把镜头拉到服务视角，推理相对训练发生了三重转变：

| 维度 | 训练 | 推理 | 后果 |
| --- | --- | --- | --- |
| **计算结构** | 前向 + 反向 + 优化器更新 | **只有前向**（自回归地重复） | 权重只读；KV Cache 成为主要动态状态 |
| **请求时长** | 一步固定（batch 定了就定了） | **不可预知**（生成多少 token 由模型决定） | batch 维度随时变化——调度的噩梦 |
| **优化目标** | 吞吐（loss 下降快） | **吞吐 × 延迟双指标**（下一章展开） | 不能只顾快，还要顾"快得均匀" |

第三行的"不可预知"是全部麻烦的根源：一个请求可能生成 10 个 token 就停（EOS），另一个可能写 4000 字——**你永远不知道 batch 里谁先走**。

## 2. 朴素服务的两张账单

**朴素做法 A：逐请求串行**（batch=1）——简单，但 GPU 喂不饱：Decode 每步只读一遍权重算一个 token（[第 3 章 03-1](../03-inference-kv-cache/01-generation-prefill-decode.md) 讲过 Decode 天然吃不满算力），串行等于把这份不满乘以请求数。

**朴素做法 B：静态批**——攒 N 个请求拼成 batch，一起进、一起出。问题出在"一起出"：生成 10 token 的请求早完成了，却要陪生成 4000 token 的**等到底**——提前完成的算力被空转浪费，新请求在门外排队。

```text
静态批（N=3）：
req A ██████（完成）······················ ← 空转陪等
req B ██████████████████（完成）········· ← 空转陪等
req C ██████████████████████████████（完成）
新请求 ·····································█ ← 一直排队
```

两张账单指向同一个结论：**问题的本质是"批的边界是死的，而请求是活的"**——解法就是让批活起来（下一单元）。

::: tip 一句话定位
推理引擎（vLLM/SGLang 等）= **调度器**（批怎么活）+ **显存管理器**（KV 怎么放）+ **执行器**（前向怎么跑快）——本章按这三块展开，前两块是重点。
:::
