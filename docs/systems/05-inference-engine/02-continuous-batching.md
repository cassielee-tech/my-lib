## 3. 静态批的边界为什么是死的

静态批按"请求"为边界组批：整批进 → 整批出。死边界的代价在 05-1 的账单里已经看到——**提前完成的空转** + **新请求的排队**。两层浪费同源：**批的生命周期跟了最慢的请求**。

## 4. 把调度粒度从"请求"降到"迭代"

**Continuous Batching（连续批处理，Orca 首创、vLLM 普及）**：调度的基本单位不是一次请求，而是**一步 Decode 迭代**——每生成一个 token，就重新组一次批：

```text
迭代 t：  [A B C]  一起算一步 → A 生成完毕（EOS）！
迭代 t+1：[B C D]  A 退出、结果返回；排队中的 D 立刻补位
迭代 t+2：[B C D]  ……
```

三行设计读出全部收益：

| 机制 | 消灭的浪费 |
| --- | --- |
| 完成即退出 | 提前完成请求的空转陪等 |
| 新到即补位 | 新请求的排队（等批边界） |
| 每步重组 | batch 大小自适应负载，GPU 持续满载 |

**Prefill 与 Decode 同批混跑**：新请求补位时先做它的 Prefill（可与其他请求的 Decode 拼在同一次前向）——这一步埋下"两种负载互相干扰"的种子，是[第 6 章](../06-pd-scheduling.md)的主角，本章先按下不表。

### 4.1 吞吐的量级变化

定性算一笔：设请求生成长度分布 100~1000 token（均值 400）。

- 静态批：批的实际占用 = 最长请求（约 1000）→ **平均利用率 ≈ 40%**；
- 连续批：每个槽位完成即换新 → 利用率逼近 **100%**（瓶颈只剩显存能装下多少 KV——这正是下一单元的主题）。

vLLM 论文实测：同等硬件下连续批 + 分页相对静态批吞吐提升 **数倍到二十倍量级**（取决于负载），核心贡献正是这两件套。

::: tip 与训练的对照
训练的 batch 在一步内是常量、跨步基本不变（DP 切好的世界）；推理的 batch **每一步都变**——调度器的存在感完全不同。这是"训练引擎"与"推理引擎"分家的根本原因。
:::
