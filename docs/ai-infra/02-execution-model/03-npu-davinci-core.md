### 6.1 设计思路：为张量计算铺专用通路

GPU 的 SIMT 从图形渲染演化而来，通用性是遗产也是包袱。达芬奇架构则直接面向张量计算设计：

- 不再组织"海量同构线程"，而是提供**功能分化的计算单元**——矩阵、向量、标量各走各的通路；
- 用**多级片上存储 + 显式搬运指令**组织数据流，而不是依赖硬件缓存和线程切换；
- 计算、搬运、控制可以**异步并行**，由队列和同步信号衔接。

### 6.2 AI Core 内部的三种计算单元

| 单元 | 干什么 | 典型算子 |
| --- | --- | --- |
| **Cube** | 矩阵乘加，一条指令完成一次分块矩阵运算 | MatMul、卷积 |
| **Vector** | 逐元素与向量运算 | Add、激活、归一化、部分归约 |
| **Scalar** | 标量计算、地址与循环控制、向其他单元发射指令 | Kernel 内控制流 |

关键认知：**一次 MatMul 不只是 Cube 在工作。** Scalar 准备地址和循环参数，DMA/MTE 单元把数据从 HBM 搬到片上，Cube 做乘加，结果再经 FixPipe 等通路写出。数据通路是流水线，任何一环慢，整条流水就慢。

### 6.3 存储层次：数据要先搬近才能算

```text
HBM（设备内存，大而慢）
  ↓ DMA/MTE 搬入
L1 → L0A / L0B（矩阵输入） → Cube → L0C（累加结果）
UB（Unified Buffer，向量通路的数据驿站）
```

大张量无法一次放进片上存储，必须切成 Tile 分批"搬入—计算—搬出"。**与 GPU 靠硬件缓存自动管理不同，NPU 的数据搬运更多由软件（编译器与算子代码）显式组织**——这是 Ascend C 编程模型的出发点，也是 CANN 篇第 3、4 章的主角。

### 6.4 与 GPU 执行模型对照

| 维度 | GPU（SIMT） | NPU（达芬奇） |
| --- | --- | --- |
| 并行组织 | 海量线程，按 Warp 调度 | 功能分化的计算单元 + 显式队列 |
| 延迟处理 | 线程切换隐藏 | 软件组织搬运与流水，让等待不发生 |
| 数据搬运 | 硬件缓存 + 合并访问 | 显式 Tiling + DMA/MTE 多级搬运 |
| 编程心智 | "让所有线程都有活干" | "把搬运和计算排成流水线" |

两种心智模型会在真实系统中交汇：GPU 的 Kernel 也要做 Tiling（显式管理 Shared Memory），NPU 的编译器也会自动做很多调度。**差异在默认责任划分：GPU 把更多责任交给硬件和调度器，NPU 把更多控制权交给软件。**

### 6.5 架构变体

昇腾产品中，Cube 与 Vector 耦合在一个核心内（耦合架构），或拆分为独立的 AIC（AI Cube）与 AIV（AI Vector）核心（分离架构）。具体型号的资源配比不同，但 Ascend C 用统一编程抽象屏蔽差异——做深度优化时才需要回到目标芯片的实际资源。
