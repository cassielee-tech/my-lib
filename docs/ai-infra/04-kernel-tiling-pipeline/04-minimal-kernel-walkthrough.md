### 7. 逐元素算子的骨架（平台无关伪代码）

```text
────────────── Host 侧 ──────────────
输入 x[N]（N = 1000 万，fp16），输出 y[N]

1. total = N
2. 均分：core_num 个核，每核 per_core = ⌈total / core_num⌉   ← 多核切分
   （不整除时：前 k 个核多处理 1 个元素                       ← 尾块处理）
3. tile_size = min(per_core, 缓冲能容纳的上限，对齐到 256 元素) ← 核内切分
4. Launch kernel(total, per_core, tile_size)

────────────── Device 侧（每个核执行同一份代码）──────────────
idx   = 我的核编号
begin = idx * per_core                        ← 索引认领
end   = min(begin + per_core, total)

为 tile 循环准备双缓冲：
for (t = begin; t < end; t += tile_size):
    cur = min(tile_size, end - t)             ← 末尾不足一 tile 的边界
    异步搬入 x[t : t+cur]  → 缓冲 A/B（交替）
    取出就绪的缓冲：y_tile = x_tile * 2 + 1   ← 计算
    异步搬出 y_tile → y[t : t+cur]
等待全部搬出完成
```

麻雀虽小，五个部件齐全：**切分参数、索引认领、尾块与边界、双缓冲流水、完成同步**。真实的 GEMM Kernel 只是把"计算"换成累加循环、把切分从一维换成三维，骨架完全一致。

### 8. Kernel 调优检查单

拿到一个慢 Kernel，按固定顺序核对：

| # | 检查项 | 对应章节 | 典型症状 |
| --- | --- | --- | --- |
| 1 | 正确性：边界、尾块、精度、对齐 | 本课 | 偶发错误结果、特定 shape 崩溃 |
| 2 | 并行度：block 是否铺满核、尾块多大 | 第 2 课 | 利用率前高后低、小 shape 掉速 |
| 3 | 复用：tile 是否受容量所限偏小 | 第 3 课 | HBM 带宽打满、计算单元饥饿 |
| 4 | 访存模式：是否连续、对齐 | 第 3 课 | 有效带宽远低于理论值 |
| 5 | 流水：搬入/计算/搬出是否重叠 | 本课 | 时间线上三段交替闲置 |
| 6 | 启动开销：Kernel 是否太小太碎 | 本课 | Kernel 间出现空洞 |
| 7 | 数据布局：是否夹带隐式转换 | 第 3 课 | 出现意外的 transpose/reformat |

检查单的第 1 条永远是正确性——**性能优化的前提是结果还对**；第 2～7 条的每一次"确诊"，都对应 CANN 篇第 5 章性能优化的一次实战。
