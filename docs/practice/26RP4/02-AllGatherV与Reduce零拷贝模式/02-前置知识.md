## 0. 一张图看懂这个需求

**需求一句话**：让 AllGatherV 和 Reduce 两个算子也支持"零拷贝"——不再把业务数据先搬进 HCCL 自己的中转内存，而是直接对业务传进来的内存做远端读写。

```
【普通路径】数据要经过 HCCL 的中转内存 ccl buffer
  rank0 用户 sendBuf ──拷贝──▶ 本端 ccl buffer ══网络══▶ 对端 ccl buffer ──拷贝──▶ 用户 recvBuf
                                  （多了 2 次本地拷贝 + 一块中转内存）

【零拷贝路径】直接读写对端用户 buffer
  rank0 用户 sendBuf ────────────网络──────────────────▶ 对端用户 recvBuf
                                  （省掉中转和本地拷贝）
```

全文地图：第 1 章补集合通信概念 → 第 2 章讲清"零拷贝"和"对称内存" → 第 3 章看懂 HCCL 代码结构 → 第 4 章看现有零拷贝怎么实现 → 第 5 章看两个目标算子的数据流与差距。

## 1. 集合通信速成

### 1.1 通信域、rank、root

- **通信域（HcclComm）**：一组一起干活的 NPU 卡的上下文。〔打比方〕一个讨论小组。
- **rank**：卡在通信域内的编号（0, 1, 2...），`rankSize` 是组内的卡数。〔打比方〕组员的学号。
- **root**：Reduce 类算子里被指定接收最终结果的那张卡。〔打比方〕课代表。

### 1.2 四个容易混淆的算子

```
AllGather（每卡贡献等长数据，所有人都拿到全量）：
  rank0:[A]  rank1:[B]  rank2:[C]  rank3:[D]
  结果：每卡都拿到 [A][B][C][D]

AllGatherV（V = variable，每卡贡献的数据长度可以不同）：
  rank0:[A]  rank1:[BB]  rank2:[C]  rank3:[DDD]
  结果：每卡都拿到 [A][BB][C][DDD]（各段长度由 recvCounts 指定）

Reduce（逐元素归约，结果只落在 root）：
  rank0:[1]  rank1:[2]  rank2:[3]  rank3:[4]
  结果：root（假设 rank0）拿到 [10]，其他卡不要求结果

AllReduce（逐元素归约，所有人都拿到结果）：
  rank0:[1]  rank1:[2]  rank2:[3]  rank3:[4]
  结果：每卡都拿到 [10]
```

**关键认知**：Reduce 只服务 root 一张卡；AllReduce/AllGather 服务所有卡。这决定了它们的数据流和"谁需要什么内存"完全不同，也是 Reduce 接入零拷贝更难的根本原因（第 5 章展开）。

### 1.3 in-place 与 out-of-place

- **out-of-place**：输入 `sendBuf` 和输出 `recvBuf` 是两块不同内存。
- **in-place**：两者相同或重叠。

〔代码事实〕AllGatherV 明确禁止 in-place：`sendBuf` 与 `recvBuf` 相同会直接报错（`src/ops/all_gather_v/all_gather_v.cc:166`）。Reduce 是否允许需要按接口约束确认。对零拷贝来说，out-of-place 更安全，因为不存在"边读边写同一块内存"的冲突。

### 1.4 归约操作（reduce op）

对每个元素分别做运算：SUM（求和）、PROD（求积）、MAX（取最大）、MIN（取最小）。〔打比方〕把几张表格叠在一起，每个格子按规则合并。

### 1.5 ccl buffer：HCCL 的中转内存

这是理解"零拷贝到底省了什么"的关键。

HCCL 为了屏蔽用户内存的地址、对齐、注册等差异，历史上会准备一块**跨 rank 的中转内存**，代码里叫 `cclMem` / `HCCL_BUFFER`：

- 数据结构：`AlgResourceCtxSerializable::cclMem`（`src/ops/op_common/inc/alg_param.h:565`）。
- 单次传输上限：`UB_MAX_DATA_SIZE = 256MB`（`src/ops/op_common/inc/alg_param.h:39`），所以大数据要分 loop 搬。

〔打比方〕两个人交换行李，但双方的门禁只认"中转站的寄存柜"：你得先把行李从自己车上搬到寄存柜（本地拷贝），对方再从寄存柜搬到自己车上（又一次本地拷贝）。零拷贝就是让双方直接去对方车上取放。

### 1.6 单算子模式 vs 图模式

- **OPBASE（单算子模式）**：每次调用 `HcclXxx` 现场选算法、下发任务。
- **OFFLOAD（图模式）**：提前把资源/任务编好，执行时回放。

〔代码事实〕`OpMode` 枚举：`src/ops/op_common/inc/alg_param.h:170`。

另外还有"用哪种引擎执行"：

- `COMM_ENGINE_AICPU_TS`：AI CPU 执行（当前零拷贝的主战场）。
- `COMM_ENGINE_AIV`：AI Vector 执行（当前明确不支持零拷贝）。
- `COMM_ENGINE_CCU`：CCU 执行。

〔代码事实〕引擎名映射见 `src/common/comm_engine_utils.h:35-37`。

## 2. "零拷贝"到底是什么

### 2.1 先纠正一个误解

"零拷贝"不是"数据完全不动"。网络/总线该搬的还得搬，它省掉的是**用户内存与 HCCL 中转内存之间的本地拷贝**，以及中转内存本身。

本仓真正生效的开关叫 `supportSymmetricMemory`（对称内存），不叫 `isZeroCopy`：

- `supportSymmetricMemory`：`src/ops/op_common/inc/alg_param.h:688`，真正决定走不走直连。
- `isZeroCopy`：`src/ops/op_common/inc/alg_param.h:743`，全仓没有任何地方把它置 `true`，只用于日志和缓存 key。

所以看到 `isZeroCopy` 不要以为它是功能开关。

### 2.2 对称内存（Symmetric Memory）

**对称内存**：多个 rank 把各自的某块内存按相同的虚拟地址布局注册到通信域，于是"我这块地址"和"你那块地址"能一一对应，HCCL 就能算出"你 rank 上对应我这段数据的地址"。

〔打比方〕小区里每栋楼结构一样、门牌号规则一样。我知道自己住 3 栋 502，就能推出"你住 7 栋 502"的准确位置，不需要你把东西先搬到一个公共仓库。

相关接口：

| 动作 | 接口 | 位置 |
|------|------|------|
| 查询某块用户内存对应的对称窗口 | `HcclCommSymWinGet` | `src/ops/op_common/op_common.cc:4650` 调用 |
| 由窗口 + offset + 对端 rank 取对端地址 | `GetSymWinRemoteMem` | `src/common/hcomm_dlsym/hccl_sym_win_dl.cc:28` |

`HcclCommSymWinGet` 返回两样东西：

- **window（窗口句柄）**：代表"这块注册内存的对称描述"。
- **offset**：这块用户内存相对窗口基址的偏移。

后续拿对端地址时，就是 `窗口 + offset + 对端 rank`。

### 2.3 零拷贝带来的副作用

天下没有免费的午餐，直连用户内存后有几条硬约束：

1. **输入可能被污染**：规约类算子可能直接在输入 buffer 上"读 + 归约"，`sendBuf` 里的原始数据会被改掉。AllReduce/ReduceScatter 的文档已明确提示用户自行备份（`docs/zh/api_ref/comm_op_interface/HcclAllReduce.md:115`）。
2. **不能重执行**：因为输入已被改，网络闪断后无法原样重跑。文档明确：开启零拷贝的 ReduceScatter/AllReduce 不支持重执行（`docs/zh/user_guide/hccl_env/HCCL_OP_RETRY_ENABLE.md:59`）。
3. **AIV 模式不支持**：`docs/zh/user_guide/comm_ops_support_list/comm_ops_support_a3.md:1115`。
4. **不能用 AICPU task cache / warmup**：`src/ops/op_common/algorithm/template/aicpu/task_cache/aicpu_task_cache_policy.cc:62`、`src/ops/op_common/op_common.cc:881`。

## 3. HCCL 代码结构速成

### 3.1 分层：谁依赖谁

```
┌─────────────────────────────────────────────┐
│ coll_comm_ops  集合通信算子（本仓 cann/hccl） │  ← 你主要改这里
├─────────────────────────────────────────────┤
│ coll_communicator_mgr  通信域管理（cann/hcomm）│
├─────────────────────────────────────────────┤
│ base_comm  基础通信/资源/原语（cann/hcomm）    │
└─────────────────────────────────────────────┘
        依赖方向只能自上而下；跨仓调用走 dlsym
```

〔代码事实〕分层与约束见 `docs/zh/architecture/architecture-brief.md:186` 起。HCCL 不能直接 `#include` HCOMM 私有头，跨仓能力通过 `src/common/hcomm_dlsym/` 动态加载。

### 3.2 一个算子的标准目录

以 AllGatherV 为例：

```
src/ops/all_gather_v/
├── all_gather_v.cc / .h          # 对外入口：参数校验、组装 OpParam
├── selector/                     # 算法选择：根据拓扑/数据量选算法名
├── algorithm/
│   ├── executor/                 # 执行器：申请资源、编排、调模板
│   └── template/
│       ├── aicpu/                # AI CPU 模板（具体通信动作）
│       ├── aiv/                  # AI Vector 模板
│       └── ccu/                  # CCU 模板
└── op_graph/                     # 图模式原型
```

〔代码事实〕目录规范见 `AGENTS.md` 第 3 节：新算子必须"selector + algorithm/{executor,template}"。

### 3.3 一次调用的主链路

```
HcclAllGatherV(...)                    ← 用户入口
      │  组装 OpParam（输入/输出/数据量/root/opType...）
      ▼
HcclGetOpExpansionMode(comm, param)    ← 决定用哪个引擎（AICPU_TS/AIV/CCU）
      ▼
Selector(comm, param, topoInfo, algName)  ← 选算法，产出拓扑信息
      ▼
HcclExecOp(comm, param, topoInfo, algName)
      │  查对称内存门禁 / 找 executor / 申请资源
      ▼
Executor::Orchestrate(...)             ← 编排：切 loop、准备模板参数、调模板
      ▼
Template::KernelRun(...)               ← 模板：真正发 send/recv/reduce
      ▼
Channel + Thread + Notify              ← 底层链路、线程、同步
```

核心概念一句话：

| 概念 | 大白话 |
|------|--------|
| **Selector** | 决定"用什么算法"，比如单层 Mesh 还是分层 NHR |
| **Executor** | 决定"怎么组织这次执行"，申请资源、切分数据、循环调用模板 |
| **Template** | 决定"每一段数据怎么搬、怎么算" |
| **Channel** | 本端到某个对端 rank 的一条通信链路 |
| **Thread / Notify** | 并发用的线程与同步信号 |

### 3.4 必须认识的几个结构体

| 结构体 | 作用 | 位置 |
|--------|------|------|
| `OpParam` | 一次算子的全部输入参数 | `src/ops/op_common/inc/alg_param.h:673` |

## 4. 现有零拷贝机制怎么走

这一章是全文的核心：**已支持算子（AllGather/AllReduce 等）是怎么把零拷贝跑通的**，也是 AllGatherV/Reduce 要模仿的模板。

### 4.1 五步链路

```
① 入口探测
   CheckAndSetSymmetricMemory(param)
   对 input/output 分别问 HcclCommSymWinGet：
   拿到了窗口 → supportSymmetricMemory = true
   没拿到     → 保持 false，走普通路径

② 统一门禁 / 回退补齐
   HcclExecOp → RefreshSymmetricMemory
   按最终 algName/engine 再复核一次
   （资源不足回退到 AICPU_TS 时，在这里补做探测）

③ 执行器传参
   supportSymmetricMemory_ = param.supportSymmetricMemory
   SetSymmetricMemoryInfo(param)  // 拷 window + offset

④ 填对端地址
   RestoreChannelMap → FillChannelSymWinPeerAddrs
   对每个 channel 调 GetSymWinRemoteMem，填 remoteInput/OutputGraphMode

⑤ 模板直连
   模板里直接用对端窗口地址读写，跳过 ccl scratch 和本地拷贝
```

对应代码：

| 步骤 | 位置 |
|------|------|
| ① 入口探测 | `src/ops/op_common/op_common.cc:4650` |
| ② 统一门禁/回退 | `src/ops/op_common/op_common.cc:4609`，调用点 `:1046` |
| ③ 执行器传参 | `src/ops/op_common/algorithm/executor/executor_v2_base.h:254` |
| ④ 填对端地址 | `src/ops/op_common/algorithm/executor/executor_v2_base.cc:81` → `src/ops/op_common/algorithm/template/template_utils.cc:647` |
| ⑤ 模板直连示例 | `src/ops/all_gather/algorithm/template/aicpu/ins_temp_all_gather_omnipipe_mesh_1D.cc:125` |

### 4.2 门禁条件

不是所有场景都能零拷贝。公共门禁（`RefreshSymmetricMemory`，`src/ops/op_common/op_common.cc:4609`）：

- HCOMM 版本 ≥ 9.1.0；
- 单算子模式 `OPBASE`；
- 引擎是 `AICPU_TS`；
- 一级拓扑是 `MESH_1D`。

规约类算子额外两条（因为要就地归约）：

- **类型/操作限制**：排除 `int64/uint64/fp64` 与 `PROD`（`IsReduceOpSymMemAllowed`，`src/ops/op_common/op_common.cc:4581`）。
- **确定性限制**：只放行归约顺序确定的算法（`IsReduceOpSymMemDeterministic`，`src/ops/op_common/op_common.cc:4592`），当前是 `AicpuReduceScatterPipeLineMeshNHR` / `AicpuAllReducePipeLineMeshNHR`，且多级拓扑禁止。

〔打比方〕就地归约像"一边传阅文件一边改内容"：如果传阅顺序不固定，最后内容就可能不一样。于是只允许顺序固定的算法走零拷贝。

### 4.3 目前已支持零拷贝的算子

〔代码事实〕`RefreshSymmetricMemory` 的白名单（`src/ops/op_common/op_common.cc:4609`）：

| 算子 | 现状 |
|------|------|
| AllGather | 支持 |
| Broadcast | 支持 |
| AllToAll / AllToAllVC | 支持 |
| AllReduce | 支持（带规约门禁） |
| ReduceScatter | 支持（带规约门禁） |
| **AllGatherV** | **不支持** |
| **Reduce** | **不支持** |

支持表也印证：A3 AI CPU 下 AllGatherV、Reduce 的"单算子零拷贝"是 `×`（`docs/zh/user_guide/comm_ops_support_list/comm_ops_support_a3.md:129`、`:176`）。

## 5. 两个目标算子的数据流与差距

### 5.1 AllGatherV：变长带来的麻烦

AllGatherV 比 AllGather 多了"每段长度可以不同"：

- `sendCount`：本端要发多少元素；
- `recvCounts[r]`：从 rank r 接收多少元素；
- `recvDispls[r]`：从 rank r 的数据写到 `recvBuf` 的哪个偏移。

```
recvCounts = [1, 2, 1, 3]   recvDispls = [0, 1, 3, 4]
recvBuf 布局：[rank0][rank1][rank1][rank2][rank3][rank3][rank3]
                     ↑ displs 决定每段起点
```

〔代码事实〕参数打包在 `param.varData`（`src/ops/all_gather_v/all_gather_v.cc:195` 起），入口直接 `Selector` + `HcclExecOp`（`:274`），**没有调用零拷贝探测**。

模板 `InsTempAllGatherVMesh1D` 里已经有一个"直接写对端"的分支，但它由 `param.opMode == OpMode::OFFLOAD` 驱动（`src/ops/all_gather_v/algorithm/executor/ins_v2_all_gather_v_sole_executor.cc:104`），是**图模式远程内存**，不是对称窗口：

- `enableRemoteMemAccess_` 决定用 scratch 还是对端 output 偏移（`ins_temp_all_gather_v_mesh_1D.cc:154-162`）；
- 普通路径还会做本地拷贝 `LocalDataCopy` 和收尾拷贝 `PostLocalCopy`（`:92`、`:110`）。

**坑点**：`outputSize` 有两种算法——普通路径用 `sum(recvCounts)`（`all_gather_v.cc:207`），图模式用 `max(displs + count)`（`:312`）。对称窗口注册时用哪个口径必须统一，否则可能漏注册或越界。

### 5.2 Reduce：root 语义带来的麻烦

Reduce 是 root 语义，数据流天然不对称：

```
【普通路径】
  非 root：本端 sendBuf ──send──▶ root 的 ccl buffer
  root   ：从各 rank 收到的数据 ──Gather──▶ 本地归约 ──▶ recvBuf
```

〔代码事实〕以 `ReduceMesh1D` 为例：非 root 走 `SendData`（`src/ops/reduce/algorithm/template/aicpu/reduce_mesh_1D.cc:163`、`:168`），root 走 `GatherData` + `ReduceData`（`:144`、`:160`）。

入口 `ReduceOutPlaceCommon`（`src/ops/reduce/reduce.cc:219`）同样**没有零拷贝探测**。

为什么 Reduce 比 AllGatherV 难：

1. **谁需要窗口不确定**：AllGather 每张卡的 input/output 都要用；Reduce 只有 root 需要 output，但"root 直接读各 rank 的 input"又要求所有 rank 都有 input 窗口。方案不同，窗口需求就不同。
2. **没有现成的确定性算法**：现有 AICPU Reduce 算法是 SoleMesh/TwoShot/NHR/Parallel 等（`src/ops/reduce/selector/reduce_auto_selector.cc:282-366`），没有 AllReduce 那种 `PipeLineMeshNHR` 确定性算法。要么新增算法，要么放宽确定性约束——这是需求串讲时必须拍板的点。
3. **就地归约的副作用更敏感**：root 侧一边收一边算，输入污染和重执行约束都要重新评估。

### 5.3 两个算子要动的点（预告）

```
入口 <op>.cc          加 CheckAndSetSymmetricMemory
op_common.cc          白名单加 opType + 门禁
executor              透传 supportSymmetricMemory + SetSymmetricMemoryInfo
template              用 GetSymWinRemoteMem 取对端地址，跳过 scratch/本地拷贝
selector              必要时限制只有确定性算法才允许零拷贝
文档/测试             支持表、输入污染声明、UT/ST
```

## 6. 术语表与常见误区

| 术语 | 一句话解释 |
|------|-----------|
| 通信域 / rank / root | 一组卡 / 卡的编号 / 收结果的卡 |
| ccl buffer | HCCL 的跨 rank 中转内存 |
| 对称内存 | 多 rank 按相同地址布局注册、可互相推算地址的内存 |
| 窗口（window） | 对称内存的注册描述句柄 |
| offset | 用户内存相对窗口基址的偏移 |
| 零拷贝 | 省掉用户内存与 ccl buffer 之间的本地拷贝与中转 |
| 确定性 | 相同输入多次执行得到相同结果（与归约顺序有关） |

**常见误区**：

1. **"零拷贝是完全不拷贝"**——错，网络/硬件搬运仍在，省的是本地中转拷贝。
2. **"`isZeroCopy` 是开关"**——错，真正生效的是 `supportSymmetricMemory`。
3. **"对称内存 = 对称拓扑"**——错。前者是内存注册方式，后者是组网卡数是否对称，两个"对称"不是一回事。
4. **"所有算子都能零拷贝"**——错，有版本/模式/引擎/拓扑/确定性多重门禁，且 AIV 不支持。
5. **"开了零拷贝输入还是原样"**——错，规约类算子可能修改输入。
