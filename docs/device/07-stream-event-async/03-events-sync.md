多流一开，"谁等谁"就必须说清楚。工具箱里有一件精确的、几件粗重的。

### 5.1 Event：最小精确的同步工具

**Event 是插在流里的一个标记点**，两个动作配合使用：

```text
搬运流：  [H2D batch2] ── record(e1)          ← 搬完在此打卡
计算流：  wait(e1) → [GEMM batch2]            ← 看到打卡才能开工
```

- `record`：在流的某个位置插旗——前面的任务都完成时，旗子立起来；
- `wait`：让另一条流在此处暂停——旗子不立，后面的任务不执行。

这套"打卡—等卡"模式是**跨流依赖的标准写法**：既保证了正确性，又把等待限制在必要的最小范围。Event 还兼任计时器（回扣 07-1：测设备耗时）。

### 5.2 四个层次的同步对象

| 层次 | 工具 | 语义 | 代价 |
| --- | --- | --- | --- |
| Host ↔ Device | `synchronize` | Host 阻塞等设备追平 | 大：整条流水被掐断 |
| 流 ↔ 流 | Event `record/wait` | 单向的精确依赖 | 小：只等必要的前驱 |
| 卡 ↔ 卡 | Notify / 跨设备信号 | 设备间任务级通知（CANN Runtime 的 Notify；HCCL 源码专题 H01-4 的同步原语） | 中：跨硬件边界 |
| 组内全员 | Barrier / 集合通信隐式同步 | 所有 Rank 到齐才继续（AllReduce 本身就是栅栏） | 大：等最慢的 Rank |

选型口诀：**能用 Event 不用 synchronize，能用单向等待不用全员栅栏**——同步粒度越粗，"等最慢的人"的浪费越大。

### 6. 两种病：漏同步与滥同步

**漏同步 = 数据竞争。** B 流读了 A 流还没写完的数据：不报错、不崩溃，**结果偶发地错**——依赖时序的 bug，复现困难，是分布式训练里最难查的一类。症状常是"跑十次对九次"。

**滥同步 = 隐形减速。** 循环里放 `.item()`、每步 `synchronize`、所有任务挤默认流——异步流水被反复掐断，设备利用率跌回串行时代。Profiling 时间线上表现为：Kernel 之间大片空隙、CPU 长时间"等待设备"。

::: tip 排障入口
偶发错结果 → 先查跨流访问的数据有没有 Event 保护；慢且空隙多 → 先找隐式同步点（`.item()`/打印/同步拷贝）。用 [msprof](../../ascend/cann常用命令.md) 的时间线直接看两类病灶。
:::
