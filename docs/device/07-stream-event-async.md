## 本章导学

::: tip 本课只记住 3 件事

### 1. 下单就给你单号：异步执行

你在 App 上下单（调用算子），**立刻收到单号（函数返回）**——但货还在仓库排队（设备队列里等执行）。

为什么必须这样？因为你（Host）写单子的速度比工地（Device）干活快**上万倍**。如果每单都站在门口等货，你 99% 的时间在发呆。所以所有框架都是：**你只管连续下单，工地按单号顺序慢慢干**。

两个立刻要改的习惯：

- **别乱问"货到哪了"**：`.item()`、`.cpu()`、`print(张量)` 都是在逼系统"当场交货"——每一次都是踩刹车；
- **别信报错位置**：工地在第 50 单出了事故时，你已经写到第 200 单、跑到无关的代码行——Python 堆栈基本是假线索。排障时临时改成"下单即等货"模式（`ASCEND_LAUNCH_BLOCKING=1`），事故当场暴露。

::: details 小测 1：为什么 `print(loss.item())` 会拖慢训练循环？
`.item()` 需要真实数值，Host 必须阻塞等设备把前面所有任务算完——异步流水被掐断。放在循环里就是每步踩一次刹车。改法：降低频率、积累后统一打印。
:::

### 2. 车道与签认单：Stream 和 Event

任务不能全挤一条道。**Stream（流）= 单行车道**：同一条道上的车**严格按序、绝不超车**——拷贝、计算、通信混在一条道上时，谁也别想抢先。

想要并行，就修多条道：

```text
计算道：[GEMM] [Norm] [GEMM] …
搬运道：[进货 batch+1] [出货 result]      ← 与计算道同时跑
对账道：[AllReduce 梯度桶1] [桶2]        ← 与计算道同时跑
```

但跨道就出安全问题：**B 道要用 A 道刚生产的料，怎么知道料好了？**——**签认单（Event）**：

- `record`：A 道干完这段在单子上盖章；
- `wait`：B 道看到这章才开工。

两种经典病，对号入座：

| 病 | 症状 | 病因 |
| --- | --- | --- |
| **漏发签认单** | 结果**偶发**错误，跑十次错一次 | 数据竞争：用了还没生产完的料 |
| **盖章太勤** | 永远正确但**慢得像串行** | 滥同步：流水线被反复掐断 |

::: details 小测 2：代码里所有任务都在默认流上，看起来分了几个函数，实际执行形态是什么？
彻底串行。默认流是单行道（有些语义下还会给所有其他道踩刹车），函数怎么拆都不改变任务排队顺序。想并行必须真正使用多条 Stream，并配 Event 声明依赖。
:::

### 3. 让车流跑满：重叠的艺术

并行设计只有一个公式：**把没有依赖的任务分道，用签认单接上必要的依赖。**

三种标准打法：

1. **提前备料**：算 batch N 的同时，搬运道已经在进 batch N+1 的料（Double Buffer 的任务级放大版）；
2. **边对账边干活**：反向传播从后往前逐层出梯度，后层的梯度装桶先发去 AllReduce，通信道和对账之余的反向计算同时跑——DDP 加速的核心秘密；
3. **多段接力**：不同任务段各占一条道，把设备每个部件都喂饱。

失败的两种样子：**假并行**（道修了、闸门全关——时间线上一条道在跑另一条道全在等）和**错并行**（没盖章就抢料——偶发出错）。诊断都靠时间线：Profiling 一拉，空隙和咬死一目了然。

::: details 小测 3：多流程序结果偶发错误，第一怀疑什么？怎么验证？
第一怀疑跨流数据竞争——某条流用了另一条流尚未写完的数据。验证：在可疑访问前补 Event 依赖（或临时加 synchronize），错误消失即确诊。
:::

### 3 句话带走

1. **下单 ≠ 到货**：调用返回只是任务入队；`.item()` 是刹车，报错位置是假线索；
2. **Stream 是单行道**：同流按序、跨流并行；**Event 是签认单**，跨道取料必须盖章；
3. 重叠公式：**无依赖分道 + 有依赖盖章**；漏盖章 = 偶发错误，滥盖章 = 假并行。

### 黑话小词典

| 术语 | 人话 |

## 07-1｜异步执行：Host 跑得比 Device 快

::: info 本单元目标
围绕 **Host/Device 异步模型** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

最容易被误解、又最影响一切行为的事实：**你调用一个算子时，它几乎一定还没开始执行。**

### 2. 提交与执行是两件事

```text
Host（CPU）                        Device（NPU/GPU）
y = op(x)                          ┌─────────────────┐
   │                                │ 任务队列：op1 op2 op3 …
   ├─ 解析、分发、打包任务 ────────► │  按顺序慢慢执行     │
   ▼                                │                   │
 立刻返回，继续跑下一行 Python        └─────────────────┘
```

Host 做一次 Launch 只要几微秒；一个 Kernel 执行动辄几百微秒到几毫秒。**如果每次调用都等设备做完再返回，CPU 会有 99% 的时间在干等**——所以所有现代框架都是异步提交：Host 一路把任务塞进队列，设备在后面按序消费。

#### 2.1 队列会"假装"完成你的代码

异步模型下，这段代码的行为需要重新理解：

```python
a = x.npu()          # 拷贝任务入队
b = layer(a)         # 计算任务入队（还在排队！）
print(b.mean())      # ← 隐式同步点：必须等前面全部完成
```

`print` 需要具体数值，框架被迫在此处等待设备追上来——**`.item()`、`.cpu()`、打印、某些日志都是隐式同步点**。一段代码里这种点太多，异步就名存实亡。

#### 2.2 两个必知的副作用

**① 报错是延迟的。** 设备在第 50 个任务处出错时，Host 可能已经提交到第 200 个任务、跑到完全无关的代码行——**Python 堆栈指向的位置基本不可信**。排障时临时改同步执行（`ASCEND_LAUNCH_BLOCKING=1`），让报错当场暴露（详见 [CANN 常用命令速查](../ascend/cann常用命令.md)第 9 节）。

**② 计时必须用 Event。** `time.time()` 测的是"Host 提交完用了多久"，不是设备执行了多久。正确做法：在任务前后向流里插入 Event，执行结束后读 Event 时间差——这本身就是下一单元 Event 的第一个用途。

::: tip 一句话心智模型
**Host 是"写作业单的人"，Device 是"按单干活的班组"**——单子写完不代表活干完；想知道干没干完，得用下一单元的签认单（Event）。
:::

## 07-2｜Stream：任务的单行道

::: info 本单元目标
围绕 **Stream 的顺序语义与多流使用** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

任务排进队列只是第一步——**排进哪条队列**决定它们能不能并行。

#### 3.1 一条 Stream 的语义：严格按序

**Stream（流）是保持任务顺序的异步执行队列**。同一条流上的任务，无论类型（拷贝、计算、通信），**严格按提交顺序执行，绝不乱序、绝不并行**。

这条铁律是理解一切的钥匙：如果你的所有任务都在默认流上，那么"看起来并行"的代码**实际上是彻底串行**的——搬运等计算、计算等通信、谁也别想抢跑。

#### 3.2 多条 Stream：真正的并行车道

不同流之间没有顺序保证，设备可以让它们同时执行（资源允许时）：

```text
计算流：  [GEMM-1] [GEMM-2] [GEMM-3]
搬运流：  [H2D-batch2]  [D2H-result-1]        ← 与计算并行
通信流：  [AllReduce-grad-A] [AllReduce-grad-B] ← 与计算/搬运并行
```

三种典型车道划分：

| 车道 | 干什么 | 典型用户 |
| --- | --- | --- |
| 计算流 | 前向/反向 Kernel | 框架主循环 |
| 搬运流 | H2D/D2H 数据传输 | 数据加载、结果回传 |
| 通信流 | 集合通信 | DDP 梯度同步（《模型全景》第 2 章的重叠，靠的就是它） |

torch_npu/PyTorch 提供 `torch.npu.Stream` 等接口；CANN Runtime 的 Stream 管理正是这些 API 的底层（回扣 [《昇腾与 HCCL》的 01-2](../ascend/00-ascend-cann.md#_0-1-cann-软件栈与模型执行路径) Runtime 七大管理）。

#### 4. 多流的收益与代价

**收益**：设备不同单元（计算单元、DMA、通信链路）同时有活干——这正是第 1 章"谁在等待"问题在系统层的解法。

**代价清单**：

1. **默认流的陷阱**：遗留语义的默认流会与所有其他流隐式同步——在它上面插一个任务等于给全场踩一脚刹车。想并行，任务都要离开默认流；
2. **跨流数据不安全**：B 流要用 A 流产出的数据，必须显式声明依赖（下一单元的 Event），否则就是数据竞争；
3. **资源与切换成本**：每条流有自己的队列与资源；流太多、任务太碎，调度本身成为开销；
4. **内存分配要小心**：分配器跨流复用内存同样需要依赖保护。

::: warning 设计原则
**先问"这两个任务真的没有依赖吗"，再考虑分道。** 多流不是免费的并行开关，而是"用显式依赖管理换取并发"的工程选择。
:::

## 07-3｜依赖与同步：Event、Wait 与 Barrier

::: info 本单元目标
围绕 **Event 与四个层次的同步对象** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

多流一开，"谁等谁"就必须说清楚。工具箱里有一件精确的、几件粗重的。

#### 5.1 Event：最小精确的同步工具

**Event 是插在流里的一个标记点**，两个动作配合使用：

```text
搬运流：  [H2D batch2] ── record(e1)          ← 搬完在此打卡
计算流：  wait(e1) → [GEMM batch2]            ← 看到打卡才能开工
```

- `record`：在流的某个位置插旗——前面的任务都完成时，旗子立起来；
- `wait`：让另一条流在此处暂停——旗子不立，后面的任务不执行。

这套"打卡—等卡"模式是**跨流依赖的标准写法**：既保证了正确性，又把等待限制在必要的最小范围。Event 还兼任计时器（回扣 07-1：测设备耗时）。

#### 5.2 四个层次的同步对象

| 层次 | 工具 | 语义 | 代价 |
| --- | --- | --- | --- |
| Host ↔ Device | `synchronize` | Host 阻塞等设备追平 | 大：整条流水被掐断 |
| 流 ↔ 流 | Event `record/wait` | 单向的精确依赖 | 小：只等必要的前驱 |
| 卡 ↔ 卡 | Notify / 跨设备信号 | 设备间任务级通知（CANN Runtime 的 Notify；HCCL 源码 3 的同步原语） | 中：跨硬件边界 |
| 组内全员 | Barrier / 集合通信隐式同步 | 所有 Rank 到齐才继续（AllReduce 本身就是栅栏） | 大：等最慢的 Rank |

选型口诀：**能用 Event 不用 synchronize，能用单向等待不用全员栅栏**——同步粒度越粗，"等最慢的人"的浪费越大。

#### 6. 两种病：漏同步与滥同步

**漏同步 = 数据竞争。** B 流读了 A 流还没写完的数据：不报错、不崩溃，**结果偶发地错**——依赖时序的 bug，复现困难，是分布式训练里最难查的一类。症状常是"跑十次对九次"。

**滥同步 = 隐形减速。** 循环里放 `.item()`、每步 `synchronize`、所有任务挤默认流——异步流水被反复掐断，设备利用率跌回串行时代。Profiling 时间线上表现为：Kernel 之间大片空隙、CPU 长时间"等待设备"。

::: tip 排障入口
偶发错结果 → 先查跨流访问的数据有没有 Event 保护；慢且空隙多 → 先找隐式同步点（`.item()`/打印/同步拷贝）。用 [msprof](../ascend/cann常用命令.md) 的时间线直接看两类病灶。
:::

## 07-4｜重叠的艺术：让设备闲不下来

::: info 本单元目标
围绕 **任务重叠的设计模式** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

工具齐了——多车道（Stream）+ 签认单（Event）。现在把第 1 章"谁在等待"的答案工程化：**把没有依赖的任务放进不同车道，用 Event 把必要的依赖接上。**

#### 7.1 三种经典重叠模式

**模式 A：搬运与计算（提前备料）**

```text
搬运流：  [H2D batch N+1]                      ← 提前搬下一批
计算流：  [forward N] [backward N]              ← 同时算这一批
Event：    计算 N 用到 batch N+1 前必须等 H2D 完成
```

04-3 的 Double Buffer 是它在 **Kernel 内部**的版本；这里是**任务级**的版本——数据加载、H2D 传输与计算全程流水。

**模式 B：通信与计算（边对账边干活）**

```text
通信流：  [AllReduce bucket-1] [AllReduce bucket-2]
计算流：  [backward layer-31] [backward layer-30] [layer-29] …
```

DDP 的标准操作（《模型全景》第 2 章 《模型全景》02-4 预告过）：反向传播**从后往前**逐层产出梯度，后层梯度装 Bucket 先发走，通信与剩余层的反向同时进行。**前提**：梯度聚合必须在 `optimizer.step()` 之前全部完成——一个跨流的 Event 收尾。

**模式 C：多任务流水（多段接力）**

Prefill 与 Decode 分流、多个 micro-batch 接力、独立子图各占一条流——把"大任务内部的空闲"填满。具体形态在《训练与推理系统》的推理系统两章（待写）和《昇腾与 HCCL》展开。

#### 7.2 重叠的两个敌人

**敌人一：假并行。** 任务名义上分了流，但同步点把执行序重新串成一条线（如每个小任务都 `synchronize`）——车道修了，闸门全关着。**诊断**：时间线上车道存在但互相咬死，总时长 ≈ 串行。

**敌人二：错并行。** 没有依赖关系就分道——数据竞争，偶发错误结果（07-3 的病一）。**诊断**：加同步后正确性恢复，即是它。

### 10. 自测题

1. 为什么框架必须采用异步提交模型？
2. `.item()` 和 `.cpu()` 这类操作为什么是隐式同步点？
3. 设备报错时 Python 堆栈为什么不可信？排障用什么手段？
4. 同一条 Stream 上的任务有什么顺序保证？
5. 所有任务都挤在默认流上，实际执行形态是什么？
6. 三种典型车道是什么？通信流的价值在哪里？
7. Event 的 record 和 wait 分别做什么？
8. 四个层次的同步对象分别适用什么场景？
9. 漏同步和滥同步各自的症状是什么？
10. DDP 通信与反向计算重叠的前提条件有哪些？

::: details 自测答案

1. Host Launch 一次只要微秒级，Kernel 执行常为毫秒级；同步等待会让 CPU 绝大部分时间空转。异步让 Host 连续提交，设备流水执行。
2. 它们需要"具体的数值"而不只是"任务的句柄"，Host 必须等设备把前面的任务真正算完——被迫阻塞。
3. 设备报错时 Host 已提交到更后面的任务、跑到无关代码行。排障用 `ASCEND_LAUNCH_BLOCKING=1` 临时改为同步执行，让报错当场暴露。
4. 严格按提交顺序执行，不乱序、不并行——无论任务是拷贝、计算还是通信。
5. 彻底串行：搬运等计算、计算等通信，任何重叠都不存在。
6. 计算流、搬运流（H2D/D2H）、通信流。通信流让梯度聚合与剩余反向计算并行（DDP 重叠）。
7. record 在流内插旗：前序任务完成后事件成立；wait 让另一条流阻塞到事件成立后才继续——跨流单向依赖的最小工具。
8. Host↔Device 用 synchronize（粗、代价大）；流间用 Event（精确）；设备间用 Notify 等信号；组内全员用 Barrier/集合通信的隐式栅栏（等最慢者）。
9. 漏同步 → 数据竞争、结果偶发错误（跑十次对九次）；滥同步 → 异步流水被反复掐断，时间线大片空隙，性能跌回串行。
10. 反向从后往前逐层产梯度（有时序错位可利用）、梯度按 Bucket 装箱、通信走独立流异步执行、且在 optimizer.step() 前用同步保证全部聚合完成。

:::

### 11. 本课小结

- Host 是写作业单的，Device 是按单干活的——调用返回不代表执行完成；
- Stream 单行道：同流按序、跨流并行；默认流是隐式刹车；
- 同步四层次，粒度由粗到细：synchronize → Event → Notify → Barrier，能细则细；
- 漏同步是偶发 bug 之源，滥同步是隐形减速之源；
- 三种重叠模式（备料/对账/接力）是并发设计的标准件；
- 分析武器是时间线：看空隙找同步病，看咬死找假并行。
