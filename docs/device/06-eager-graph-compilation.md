## 本章导学

### 1. 现场指挥的装修队：写一行，干一步

PyTorch 默认的干活方式（**Eager**）像一个听现场指挥的装修队：你喊一句"铺这块砖"，队里立刻铺这块砖；再喊"勾缝"，立刻勾缝。

每一嗓子指令都要走完整的传达链：

```text
你喊话（Python 代码）→ 领班翻译成工序（算子拆解）
→ 查手册选工具（分发）→ 派工开工（Launch）→ 工人干活（设备执行）
```

**每一步都真实存在，每一步都要付钱**（解释、翻译、派工各有开销）。大工序无所谓；**满屋都是"钉一颗钉子"级的小活时，派工的嗓子和时间全耗在传达上**——工地时间线上全是活与活之间的空隙。

但现场干有两个真本事：**每步都能叫停检查**（调试），**想改方案随时改**（任意 Python 控制流）——研究和实验离不开它。

::: details 小测 1：为什么"小算子特别多"的网络在 Eager 下最吃亏？
因为三层组织成本（Python 解释、分发查表、Launch 派工）是**按算子次数收的**，和活的大小无关。小活干 8 微秒、派工 5 微秒，一半时间在走流程。大活（一个 GEMM 干几毫秒）摊薄这点派工费无所谓。
:::

### 2. 施工图：让总工看见整个工程

现场指挥的致命短板：**领班只看得见眼前这一步**。他不知道步骤 3 和步骤 4 其实能合并干。

**计算图**就是把整段工程记录下来的一张施工图：**节点是工序，边是材料依赖**（上一步的产出是下一步的投入）。拿到完整图纸，总工（编译器）能做的事立刻多起来：

- **合并工序**（算子融合）：抹灰+打磨+刷漆一趟完成，材料不落地——省搬运；
- **堆场复用**（内存复用）：这堆料用完了，场地腾给下一堆——降峰值显存；
- **一次交底**（整图下发）：不用每步都喊一嗓子，整图计划一次交给工地——省 Launch 空隙。

图纸有两种画法：**边干边记**（动态图，PyTorch 本色）和**先画完再干**（静态图，老牌路线）。`torch.compile` 是折中高手：**描图员**（Dynamo）趁你第一次干活时把流程描成图，**优化师**（Inductor）把图改得更高效，之后的每次执行都直接用优化版。

::: details 小测 2：Eager 和图模式各自"看得见"什么？
Eager 只看得见当前这一个算子——它没有资格决定"把 Norm 和激活合并"，因为它根本不知道后面还有个激活。图模式看得见整段依赖关系：相邻（融合）、生命周期（内存复用）、全图（整图下发）都由此而来。
:::

### 3. 施工图不是免费的

用图要付四笔钱，心里要有数：

1. **首次规划慢**（warmup/编译耗时）：第一次要把图描出来、优化好——训练前几步慢很正常；部署可以提前画好（离线编译）；
2. **户型变了要重画**（guard / recompile）：图是在"三室一厅"上优化的，来了"两室"就得重画。**变长输入最伤**——反复重画的时间可能超过省下的时间；
3. **图里塞不进的就断**（graph break）：调试打印、动态 Python、不支持的算子会把图切碎，碎段之间退回现场模式——图越碎，越白忙；
4. **干法微变**：合并工序可能改变浮点求和顺序——数值几乎不变，但比对时会看到微小差异。

实践口诀：**先 Eager 跑对，再图模式跑快**；收益不达预期，先查"重画了几次"（recompile），再查"图断了几处"（graph break）。

::: details 小测 3：一个变长输入的推理服务开了图模式，性能反而更差——最可能的原因？
guard 频繁失效 → recompile 风暴：每个新长度都触发一次重新编译，编译耗时吞掉了融合和整图下发省下的时间。对策：动态 shape 编译、固定 padding，或干脆对这段退回 Eager。
:::

### 3 句话带走

1. Eager 写一行干一步：**灵活好调试，但按算子次数付组织成本，小算子链最吃亏**；
2. 计算图给编译器全局视角：**合并工序、堆场复用、一次交底**——分别省搬运、显存、Launch；
3. 图有四笔账：**首译慢、户型变要重画、塞不进就断、干法微变**——先跑对再跑快。

## 06-1｜Eager 执行：一行代码的即时旅程

::: info 本单元目标
围绕 **Eager 执行链路与开销** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

PyTorch 默认的执行方式叫 **Eager（即时执行）**：你写一行，它做一步。先完整走一遍这一行的旅程。

### 2. 一行代码的五段旅程

```python
h = self.norm(x)
y = self.fc(h)          # 就看这一行
```

```text
① Python 层：属性查找、nn.Module.__call__ 包装、Python 函数调用栈
        ↓
② 算子层：Linear 拆解为 addmm / matmul + add（aten 算子）
        ↓
③ 分发层：Dispatcher 按「设备 + dtype + 布局」查表，选出具体实现
        ↓
④ 下发层：把选中的 Kernel 任务放进设备队列（04-1 的 Launch）
        ↓
⑤ 设备层：NPU/GPU 异步执行，结果留在设备内存
```

关键认知：**每一步都真实存在，且每一步都要付钱。**

#### 2.1 三层开销，小算子链放大

| 开销 | 量级感受 | 什么时候致命 |
| --- | --- | --- |
| **Python 解释** | 每行几十～上百 ns | 几百个算子 × 每次前向 |
| **分发查表** | 微秒内 | 小算子密集网络 |
| **Kernel Launch** | 数 µs/次 | 计算量 < 10 µs 的小算子（04-1 算过：占比可到 37%） |

一条由很多小算子组成的网络（Norm、激活、逐元素），Eager 下 **Host 侧的"组织成本"可能超过 Device 侧的"干活成本"**——设备时间线上全是 Kernel 之间的空隙。

#### 2.2 Eager 的两个真本事

开销归开销，Eager 是研究和调试的主流不是没有原因：

1. **即时反馈**：任何一行都能立刻打印、断点、检查张量值；
2. **任意控制流**：`if loss > threshold:`、动态循环、随机 dropout 路径——想怎么写就怎么写，每一步执行时才确定。

代价的另一面：**Eager 每次只看得见"当前这一个算子"**。相邻的 Norm 和激活明明可以合并成一道工序（第 5 章的"融合"），Eager 没有资格做这个决定——它根本没有"整段计算"的视图。这正是下一单元计算图要解决的问题。

::: tip Autograd 也在 Eager 里记账
《模型全景》第 2 章说过的"流程单"（计算图）正是 Eager 前向时顺手记录的——但它只用于反向求导，**不改变前向的逐步执行方式**。本章说的"图模式"是更进一步：把图拿去**编译优化再执行**。
:::

## 06-2｜计算图：动态图与静态图

::: info 本单元目标
围绕 **计算图的两种获得方式与全局视角的价值** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

计算图在大模型基础里出现过（"流程单"）：**节点是算子，边是张量的生产者-消费者依赖**。系统视角下的问题是：这张图怎么得到、什么时候得到。

#### 3.1 两种得到图的方式

**动态图（define-by-run）**：边执行边形成图。第一次跑 `[B,S,H]` 的输入，跑出来的路径就是一张图；下次如果走了不同分支，就是另一张图。PyTorch Eager 本质是动态图框架（Autograd 的流程单就是这么来的）。

**静态图（define-then-run）**：先把整张图搭好（声明阶段），再喂数据反复执行（运行阶段）。早期 TensorFlow 和 GE 图模式走这条路。

| | 动态图 | 静态图 |
| --- | --- | --- |
| 图何时确定 | 执行时 | 执行前 |
| 控制流 | 任意 Python | 图内声明或固化 |
| 调试 | 直接打印断点 | 要看图结构 |
| 优化空间 | 每次执行局部 | **整图一次性优化** |

#### 3.2 图视角到底多看见什么

Eager 的世界里只有"当前算子"；图的世界里有**整段依赖关系**。这份全局视野直接兑换成优化机会：

```text
看得见相邻 → 算子融合：Norm + Add + 激活合成一个 Kernel
             （中间结果不出片上，05-3 的"向右挪"）
看得见取值 → 常量折叠：能在编译期算完的提前算掉
看得见死路 → 死代码消除：不影响输出的分支直接删
看得见生命周期 → 内存复用：A 张量用完的坑位给 B 用（峰值显存下降）
看得见全图 → 调度与整图下发：任务排好，一次交设备（省 Launch 空隙）
```

::: warning 图是一份契约
深度优化有一个前提：**结构和形状得先固定下来**。图在"什么样的输入"上优化，就只对这样的输入高效——输入变了（shape 变化、走了新分支），要么重新编译，要么落回 Eager。这个"契约"的摩擦力是 06-4 的主题。
:::

## 06-3｜图编译：从 trace 到优化执行

::: info 本单元目标
围绕 **图编译的流水线与收益来源** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

有了图，还要有一套流水线把图变成更高效的执行计划。以 `torch.compile` 为主线看一遍，再对到昇腾的 GE。

#### 5.1 torch.compile 流水线

```text
Python 代码（Eager）
   ↓  Dynamo：拦截 Python 字节码，把执行轨迹"描"成 FX 图
   ↓        └─ 同时记录 guard：这份图有效的条件（shape、dtype、属性……）
FX 计算图
   ↓  Inductor：图优化 → 生成高效 Kernel（Triton）或调用现成库
优化后的执行计划
   ↓  后续调用：guard 通过 → 直接跑编译产物；guard 失败 → 重新编译
```

三个关键机制：

1. **捕获（Dynamo/trace）**：把"代码"翻译成"图"。遇到翻译不了的（打印调试、数据相关的 `if`、不支持的操作）就发生 **graph break**——图断开，断点之间落回 Eager；
2. **编译（Inductor 等）**：在图上做融合、内存规划、Kernel 生成。**首次执行前完成**（JIT），所以第一次调用慢（编译耗时），后面才快——warmup 的来源；
3. **guard**：编译产物绑定了"适用条件"。输入 `shape=[32, 128]` 编译的图，遇到 `[64, 128]` 就不认——**触发 recompile**。`torch.export` 则是显式的静态化路径：提前固化图用于部署（AOT，编译时机从运行时挪到交付前）。

#### 6. 昇腾上的图模式：GE

《昇腾与 HCCL》的 01-2 介绍过 GE 图引擎，本章把它接回主线。`torch_npu` 上 `torch.compile` 可选用 NPU 图后端（如 `npugraph_ex`），进入 GE 的编译执行体系：

| GE 能力 | 对应本章概念 |
| --- | --- |
| 图编译：算子融合 / 自动融合 / 极致内存 / 自动流水 | 全局优化机会（06-2 清单） |
| 图执行：**计算图执行下沉**——整图一次下发 NPU 侧执行 | 消除逐算子 Launch 空隙（04-1） |
| metadef：图与算子的基础数据结构 | 图的"通用语言"（契约的载体） |

推理部署还有一条**离线编译**路线：用 ATC 把模型提前编译成设备格式，部署时直接加载——把"编译耗时"从用户面前挪走。在线 JIT（训练/科研）与离线 AOT（服务部署）是同一套图思想在两个时机的落地。

**收益来源三笔账**（把本专栏上半程的知识兑换回来）：

1. **融合省搬运**：算术强度右移（I05）；
2. **整图下发省空隙**：Host 组织成本摊薄到整图（06-1/04-1）；
3. **内存复用降峰值**：中间张量生命周期分析（I03 的空间账）。

## 06-4｜图模式的边界：代价与选择

::: info 本单元目标
围绕 **图编译的代价与模式选择** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

图编译不是免费午餐。把它当成信仰会踩坑，当成工具才好用。

#### 7.1 四类代价

**① 编译耗时与 warmup。** 首次执行要把图描出来、优化、生成 Kernel——训练前几步慢、服务首请求慢都正常。离线编译（ATC/export）可以把它挪到交付前，但换模型/换 shape 就要重做。

**② guard 失效与 recompile 风暴。** 每个新 shape、每个没见过的新分支都可能触发一次重新编译。**变长输入、动态 batch、数据依赖控制流**的场景里，编译次数可能失控——反复重编译的总耗时超过它省下的时间，比不编译还慢。

**③ graph break。** 图里塞不进去的代码（调试打印、动态 Python 逻辑、不支持的算子）会把图切成几段，段间落回 Eager——**来回切换本身也有成本**，图越碎收益越接近零。

**④ 行为差异。** 融合与重排可能改变浮点求和顺序、触发不同的 Kernel 实现——数值上通常可接受，但做精度比对时会看到微小差异（回扣 05-4 的精度账）。

#### 7.2 一张选择表

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 研究、探索、调试 | Eager | 即时反馈、任意控制流 |
| 训练稳定负载（shape 固定） | 图模式 | 收益三笔账全拿，recompile 少 |
| 变长/动态负载 | 谨慎用图 | 先看 recompile 次数，考虑动态 shape 编译 |
| 推理服务部署 | 离线编译（export/ATC） | 编译耗时挪到交付前，运行时零负担 |

#### 8. 两种模式的全景对比

同一段前向，两条路径：

```text
Eager：    Python → 分发 → Launch → 算子1 → Launch → 算子2 → …（每步过一遍）
图模式：   Python → 一次编译 → 整图优化（融合/内存/调度） → 整图下发 → 设备按图执行
```

实践节奏建议：

1. **先 Eager 跑对，再图模式跑快**——正确性永远第一（04-4 检查单第一条）；
2. 图模式收益不达预期时，按序检查：**recompile 次数 → graph break 位置 → 融合是否真的发生**（用 Profiling 看 Kernel 数量变化）；
3. 记住本章所有优化的**上限**：单机单卡内的重组。多卡之间的并行、通信与任务级并发——图执行内部的任务怎么排队、怎么并行——是下一课 **Stream 与 Event** 的主题。

### 10. 自测题

1. Eager 一次算子调用经过哪五段？
2. Eager 的三层开销分别是什么？哪类网络受害最深？
3. 动态图和静态图的"图何时确定"有何不同？
4. 图视角比 Eager 多看见什么？兑换成哪些优化？
5. torch.compile 流水线里 Dynamo 和 Inductor 各做什么？
6. guard 是什么？什么情况下失效？
7. graph break 是什么？为什么断得越碎收益越接近零？
8. GE 的"计算图执行下沉"回收的是哪笔钱？
9. 在线 JIT 和离线编译（ATC/export）各适合什么场景？
10. 一段变长输入的推理服务用图模式收益很差，最可能的原因是什么？

::: details 自测答案

1. Python 层（解释/调用栈）→ 算子拆解（aten）→ 分发（Dispatcher 查表选实现）→ Launch（任务入设备队列）→ 设备异步执行。
2. Python 解释开销、分发查表开销、Kernel Launch 开销。由大量小算子组成的网络（Norm/激活/逐元素链）受害最深——组织成本可超过干活成本。
3. 动态图执行时逐条形成路径；静态图执行前整体搭好再反复执行。
4. 看得见相邻（融合）、取值（常量折叠）、死路（死代码消除）、生命周期（内存复用）、全图（调度与整图下发）。
5. Dynamo 拦截 Python 字节码把执行轨迹描成 FX 图并记录 guard；Inductor 在图上做优化并生成 Kernel（或调用库）。
6. guard 是编译产物的适用条件（shape、dtype、属性等）；输入变化触发条件不满足即失效，引发 recompile。
7. 图中塞不进的部分（调试、动态 Python、不支持算子）把图切断，段间落回 Eager；图越碎，编译收益越少而切换成本占比越高。
8. 逐算子 Launch 的空隙：整图一次下发设备侧执行，把 Host 组织成本摊薄到整图（对应 06-1/04-1 的账）。
9. JIT 适合训练和科研（负载稳定后持续收益）；离线编译适合服务部署（编译耗时挪到交付前，运行时零负担）。
10. 变长输入使 guard 频繁失效、recompile 风暴——反复重编译的耗时吞掉了融合与下发省下的时间。应考虑动态 shape 编译或固定 padding 策略。

:::

### 11. 本课小结

- Eager 灵活即时，但每步付三层开销，且没有全局视角；
- 计算图是"工序依赖图"：动态图边跑边形成，静态图先建后跑；
- 图的价值在全局：融合、内存复用、整图下发——分别回收搬运、显存、Launch 三笔钱；
- torch.compile = Dynamo 描图 + guard、Inductor 优化；昇腾侧是 GE 编译与计算下沉；
- 图有边界：编译耗时、recompile 风暴、graph break、数值差异；
- 实践节奏：先 Eager 跑对，再图模式跑快；收益不达预期先查 recompile 和 graph break。
