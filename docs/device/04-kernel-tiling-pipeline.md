### 1. 项目经理和施工队：一份合同 的两半

前面两章认识了机器和料，现在看**一个具体任务怎么派下去**。任务书就叫 **Kernel**，它天然分两半：

```text
项目经理（Host 侧）                  施工队（Device 侧）
看图纸、算分包方案（切分参数）  →     每队拿到同一份图纸，
发任务单（Launch 下发）              按自己的队号认领自己的区段
                                    循环干活：进料 → 加工 → 出货
```

关键机制是**按队号认领**（SPMD）：图纸只画一份，每支施工队（执行单元）拿到队号（GPU 的 blockIdx / NPU 的 Block Index），自己算出"我负责第几段"。**代码写一份，所有队各干各的段**。

还有个隐形成本：**每次开工都要开班前会（Launch 开销，微秒级）**。任务大时无所谓；任务只有 10 微秒的活，班前会跟干活一样久——**大量小任务串联时，工地全是开会的空隙**。解法：把几件小事打包成一个合同（算子融合），或整栋楼签一个总合同一次下发（图模式下沉）。

::: details 小测 1：为什么小算子多的网络反而慢？
不是算得慢，是"开会"开会了：每个小 Kernel 都要付一次下发开销（班前会），计算本身可能只有几微秒，会却要开一样久。设备时间线上全是 Kernel 之间的空隙。所以要么融合算子，要么走图模式整图下发。
:::

### 2. 分包的两级：先分队，再分层

大工程（比如 8192×8192 的矩阵乘法）怎么切？**两级分包**：

- **第一级，分队（多核切分）**：把大楼切成 256 个区块，64 支队各领几块——决定**人手是否铺满**（并行度、尾块）；
- **第二级，分队内分层（核内切分）**：每队内部按层循环进料，料在工作台上反复加工——决定**每车料的复用**（搬运量）。

分包方案要过**四本账**：

1. 工作台放得下吗（容量）；
2. 尺寸按模数对齐吗（对齐，否则机器效率打折）；
3. 每队都有活、尾块小吗（并行）；
4. 一车料能用几次（复用，块尽量大）。

**一条铁律——承重墙不能乱切**：切到"求和"的维度（归约维，比如矩阵乘法的 K 维），各队只能算出半成品，**必须有人负责合拢**（规约通信）。其他维度随便切，归约维切了要付通信的钱。

::: details 小测 2：为什么归约维（K 维）是特殊维度？
因为沿 K 切开后，每队拿到的是"部分和"，不是最终答案——必须跨队累加合并才能出结果。M/N 维切块天然独立（各算各的输出块），K 维切块天然要"合拢"。这个"合拢"在单机是额外 Kernel，在多机就是 Reduce 通信。
:::

### 3. 三班倒：让机器不等料

分包好了，串行干法还是亏：**进料的时候机器闲着，加工的时候进料车闲着**。

流水干法 = **三班倒**：进料班、加工班、验收班同时上班，靠**料斗**衔接（队列：进料斗放"已到的料"，出料斗放"已完成的货"）。再加一个**双料斗**（Double Buffer）：A 料斗正在用，B 料斗已经在卸——机器一抬头，下一批料永远在台上。

三条冷水，泼给"流水万能"的幻想：

1. **工程太小**：只有三批料，刚开工就收工，流水没热身就结束；
2. **某班天然慢**：进料 4ms、加工 1ms——流水后节奏由进料决定，加工班 75% 时间闲着。**流水只能消除互相等，治不了瓶颈本身**（该加大复用、减少搬运还得做）；
3. **大门口限流**：所有队的料车加起来不能超过大门通行能力（HBM 带宽）——超了就是超了，加料斗没用。

::: details 小测 3：进料 4ms、加工 2ms、验收 1ms，流水后节奏是多少？加工班空闲率多少？
节奏由最慢的一班决定：4ms 出一批货。加工班每 4ms 只干 2ms 的活，空闲 50%。此时优化方向是修进料（加大分块提高复用、减少搬运），而不是再加缓冲级数。
:::

### 3 句话带走

1. Kernel = **项目经理的分包合同 + 施工队按队号认领**；小任务最怕班前会（Launch 开销）；
2. Tiling 两级：**分队铺满人手 × 分层榨干复用**，四本账（容量/对齐/并行/复用）都要过，**归约维切了要付合拢的钱**；
3. 流水（队列 + 双料斗）只能消除"互相等"，**治不了瓶颈、突破不了大门限流**。

## 04-1｜Kernel 的解剖：入口、索引与启动开销

::: info 本单元目标
围绕 **Kernel 的结构与启动** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

第 1 章说过"算子是语义，Kernel 是实现"。本单元打开 Kernel，看它由哪几部分组成、怎样被启动。

### 2. Kernel 的两半：Host 侧与 Device 侧

一段典型的 Kernel 程序天然分成两半：

```text
Host 侧（CPU）                          Device 侧（每个执行单元）
────────────────────                    ─────────────────────
解析输入 shape/dtype                    入口拿到：全局形状 + 切分参数 + 自己的索引
计算切分参数（block 数、tile 形状）  →    按索引算出"我负责哪一段"
准备输入输出内存地址                     for (我的 tile) {
下发 Kernel（Launch）                       搬入 → 计算 → 搬出
等待/异步获取结果                        }
```

Device 侧的关键机制是**索引认领**：每个执行单元在入口处拿到自己的编号（GPU 的 `blockIdx/threadIdx`，NPU 的 Block Index），用同一份代码、不同的编号，各自负责总任务的一小块。**Kernel 代码只写"一份"，执行却发生在所有单元上**——这就是 SPMD（Single Program, Multiple Data）。

#### 2.1 启动开销：被忽视的固定成本

从 Host 调用到 Device 真正开始执行，存在微秒级的固定开销（Launch Overhead）：参数传递、任务入队、调度分发。

- 一个 Kernel 本身耗时 5 ms，8 µs 的启动开销可以忽略；
- 一个小算子只有 10 µs 计算量，启动开销可能与计算同量级——**大量小 Kernel 串联时，Host 下发跟不上，Device 出现空隙**。

这解释了两个常见优化：**算子融合**（多个小算子合成一个 Kernel）与**图模式下沉**（整图一次性下发，见 《昇腾与 HCCL》的 01-2 的 GE 执行下沉）。也解释了 Profiling 时间线上"Kernel 之间的空洞"从哪来。

#### 2.2 切分参数：Host 与 Device 的合同

Host 算好的切分参数（block 数量、每 block 的 tile 形状、循环次数）随启动一起传给 Device。这份"合同"就是下一单元的 Tiling 策略——**合同签得好，所有单元满负荷、数据高复用；签得差，一部分单元闲置或反复搬运**。

## 04-2｜Tiling：把大算子切成块

::: info 本单元目标
围绕 **Tiling 的两个维度与约束** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

大算子既放不进片上存储，也不能只让一个计算单元干——Tiling 同时解决这两个问题。

#### 3.1 两个维度：先分人，再分趟

```text
一个 [8192, 8192] × [8192, 8192] 的 GEMM

第一层：多核切分（谁做哪块）              第二层：核内切分（每块内部怎么循环）
┌────┬────┬────┬────┐
│ B0 │ B1 │ B2 │ B3 │   256 个输出块        每 block 拿到 [512,512] 输出
├────┼────┼────┼────┤   分给 N 个核          内部沿 K 维再切 16 趟
│ B4 │ B5 │ B6 │ B7 │   → 每个 block          每趟：搬入两块输入 → 累加
├────┼────┼────┼────┤     一次"搬入-计算-搬出"    （tile 循环）
│ …  │ …  │ …  │ …  │
└────┴────┴────┴────┘
```

- **多核切分**决定并行度与尾块（02-4 的利用率账）：block 数最好 ≥ 核数且能整除；
- **核内切分**决定复用次数（03-3 的搬运账）：tile 形状决定每个字节在片上参与多少次计算。

两层各有约束，合在一起就是 Tiling 参数空间：`(block 划分, tile 形状, 循环顺序)`。

#### 3.2 切分维度不是随便选的

以 GEMM $C[M,N] = A[M,K] \times B[K,N]$ 为例：

| 切分轴 | 切的是什么 | 约束与代价 |
| --- | --- | --- |
| M、N（输出维） | 把输出切块，各 block 独立算 | 天然无依赖，最常用 |
| K（归约维） | 把累加拆成多段 | 各段结果要**累加/规约**，跨核切 K 需要额外的 Reduce 通信 |
| 不切 | 整块驻留 | 只有小算子才可行 |

**归约轴是特殊维度**：切它可以降低单次片上需求，但必须有人把部分和合并——这个"合并"就是通信或额外 Kernel。《并行策略》会看到，并行策略里的 ReduceScatter 本质上就是在切归约维。

#### 4. Tile 形状的四本约束账

设计 tile 形状时依次核对：

1. **容量账**：输入/输出 tile + 双缓冲能否放进片上 Buffer（03-4 练习 2 的算法）；
2. **对齐账**：tile 每行的字节数满足对齐要求（常见 32 B 或更大），维度是矩阵单元分块（如 16）的倍数，否则有效带宽和 Tensor Core/Cube 效率打折；
3. **并行账**：block 数覆盖所有核且尽量整除，控制尾块损失（02-4 练习 2）；
4. **复用账**：在容量允许下让 tile 尽量大——搬运量 ≈ 总量 ÷ 复用次数，tile 越大搬运越少。

::: tip 一句话本质
**Tiling = 在容量约束下最大化复用 × 在核数约束下最小化闲置。** 前半句是第 3 章，后半句是第 2 章，本章把它们订成 Host/Device 的合同。
:::

## 04-3｜流水线与 Double Buffer

::: info 本单元目标
围绕 **流水线与 Double Buffer** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

切好 tile 之后，串行执行"搬入—计算—搬出"仍然浪费：计算时搬运单元闲着，搬运时计算单元等着。流水线让它们同时干活。

#### 5.1 用队列把三段衔接起来

硬件提供了独立的搬运单元（GPU 的 DMA 引擎、NPU 的 MTE）和计算单元，它们可以**异步并行**。软件用两个队列把它们衔接：

```text
                IN 队列                OUT 队列
搬运单元 ──写入 tile──► 缓冲区 A/B ──读出结果──► 搬出
                          ▲
计算单元 ── 从缓冲区取数、计算、把结果放回 ──┘
```

计算单元只问 IN 队列"有没有就绪的 tile"，搬出只看 OUT 队列"有没有完成的结果"——**生产者消费者模型**。Ascend C 的 `TQue`/`TPipe` 就是这套机制的 API 化（《昇腾与 HCCL》第 4 章展开）。

#### 5.2 Double Buffer：最小可行的流水

双缓冲 = 两块片上缓冲交替使用：

```text
时间 →
搬运： [搬入 T0][搬入 T1][搬入 T2][搬入 T3]
计算：          [算 T0 ][算 T1 ][算 T2 ]
缓冲：   A 用     B 用     A 用     B 用
```

正在计算 T0（占用 A）时，T1 的数据已经搬进 B。理想情况下，**节奏由最慢的一段决定**（throughput = 1 / max(各段耗时)），而不是各段相加。

三段以上的流水（多级缓冲）可以进一步压平各段抖动，但每多一级就多占一份片上容量——级数与容量又是一对账。

#### 6. 流水什么时候"失灵"

流水不是万能药，三种典型情况：

**① 建立与排空占比过高。** 只有 3 个 tile，流水刚建立就结束了。数据量太小的算子，流水收益有限，不如想办法与其他算子融合。

**② 某一段天然过长。** 搬入 4 ms、计算 1 ms：流水后节奏由搬运决定（4 ms/tile），计算单元 75% 时间空等。**流水只能让"非瓶颈段"不再互相等待，不能缩短瓶颈段本身**——回到 01-3 的瓶颈判断，该减少搬运量（更大 tile、更高复用）还得减。

**③ 存在依赖或同步。** 后一个 tile 的地址依赖前一个的结果（如某些动态算子），或中途必须与别的 Stream/设备同步，流水被切断。

::: warning 流水线与带宽的关系
流水把"时间上的串行"变成"时间上的重叠"，但单位时间搬进芯片的总字节仍受 HBM 带宽上限约束。若多个核的搬运总和已打满带宽，加缓冲级数无用——此时唯一的出路是减少搬运量（提高复用）。
:::

至此，一个高性能 Kernel 的骨架完整了：**索引认领（04-1）→ 两级切分（04-2）→ 队列 + 双缓冲流水（04-3）**。

## 04-4｜最小算子走读与调优检查单

::: info 本单元目标
围绕 **一个最小算子的完整骨架** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

把前三单元拼成一个可复述的整体：一个"每个元素乘 2 再加 1"的逐元素算子，概念骨架长什么样。

#### 7. 逐元素算子的骨架（平台无关伪代码）

```text
────────────── Host 侧 ──────────────
输入 x[N]（N = 1000 万，fp16），输出 y[N]

1. total = N
2. 均分：core_num 个核，每核 per_core = ⌈total / core_num⌉   ← 多核切分
   （不整除时：前 k 个核多处理 1 个元素                       ← 尾块处理）
3. tile_size = min(per_core, 缓冲能容纳的上限，对齐到 256 元素) ← 核内切分
4. Launch kernel(total, per_core, tile_size)

────────────── Device 侧（每个核执行同一份代码）──────────────
idx   = 我的核编号
begin = idx * per_core                        ← 索引认领
end   = min(begin + per_core, total)

为 tile 循环准备双缓冲：
for (t = begin; t < end; t += tile_size):
    cur = min(tile_size, end - t)             ← 末尾不足一 tile 的边界
    异步搬入 x[t : t+cur]  → 缓冲 A/B（交替）
    取出就绪的缓冲：y_tile = x_tile * 2 + 1   ← 计算
    异步搬出 y_tile → y[t : t+cur]
等待全部搬出完成
```

麻雀虽小，五个部件齐全：**切分参数、索引认领、尾块与边界、双缓冲流水、完成同步**。真实的 GEMM Kernel 只是把"计算"换成累加循环、把切分从一维换成三维，骨架完全一致。

#### 8. Kernel 调优检查单

拿到一个慢 Kernel，按固定顺序核对：

| # | 检查项 | 对应章节 | 典型症状 |
| --- | --- | --- | --- |
| 1 | 正确性：边界、尾块、精度、对齐 | 本课 | 偶发错误结果、特定 shape 崩溃 |
| 2 | 并行度：block 是否铺满核、尾块多大 | 第 2 章 | 利用率前高后低、小 shape 掉速 |
| 3 | 复用：tile 是否受容量所限偏小 | 第 3 章 | HBM 带宽打满、计算单元饥饿 |
| 4 | 访存模式：是否连续、对齐 | 第 3 章 | 有效带宽远低于理论值 |
| 5 | 流水：搬入/计算/搬出是否重叠 | 本课 | 时间线上三段交替闲置 |
| 6 | 启动开销：Kernel 是否太小太碎 | 本课 | Kernel 间出现空洞 |
| 7 | 数据布局：是否夹带隐式转换 | 第 3 章 | 出现意外的 transpose/reformat |

检查单的第 1 条永远是正确性——**性能优化的前提是结果还对**；第 2～7 条的每一次"确诊"，都对应 《昇腾与 HCCL》第 6 章性能优化的一次实战。

### 10. 自测题

1. Kernel 的 Host 侧和 Device 侧各负责什么？
2. SPMD 是什么意思？为什么 Kernel 代码只写一份？
3. Kernel Launch 开销对小算子为什么致命？两种应对手段是什么？
4. Tiling 的两个维度分别对应哪两章的哪两个指标？
5. 为什么归约维（K 维）是特殊维度？切它需要付出什么？
6. 设计 tile 形状要核对哪四本账？
7. Double Buffer 怎样工作？流水后的节奏由什么决定？
8. 列出流水线"失灵"的三种典型情况。
9. 为什么缓冲级数再多也不能突破 HBM 带宽上限？
10. 最小算子骨架的五个部件是什么？

::: details 自测答案

1. Host 侧解析 shape、计算切分参数、准备内存、下发 Kernel；Device 侧每个执行单元按索引认领自己的一段，执行"搬入—计算—搬出"循环。
2. Single Program Multiple Data：同一份 Kernel 代码在所有执行单元上运行，靠各自不同的索引处理不同数据块。
3. 启动开销是微秒级固定成本，小 Kernel 的计算量与它同量级，导致 Device 出现空隙、Host 下发跟不上。应对：算子融合（减少 Kernel 数）与图模式下沉（整图一次性下发）。
4. 多核切分对应第 2 章的利用率/尾块；核内分块对应第 3 章的复用次数/搬运量。
5. 归约维切开后各段是部分和，必须累加合并——跨核切 K 需要额外的规约通信或 Reduce 步骤。
6. 容量账（片上放得下）、对齐账（行字节与矩阵分块对齐）、并行账（铺满核、控制尾块）、复用账（容量允许下 tile 尽量大）。
7. 两块缓冲交替：算 A 块时往 B 块搬下一个 tile。节奏由最慢的一段决定（throughput = 1 / max(各段耗时)）。
8. ① 建立与排空占比过高（tile 太少）；② 某段天然过长（瓶颈段无法被流水缩短）；③ 存在依赖或强制同步切断流水。
9. 流水只改变时间上的重叠，不改变单位时间进入芯片的总字节量——那是带宽的物理上限。
10. 切分参数、索引认领、尾块与边界处理、双缓冲流水、完成同步。

:::

### 11. 本课小结

- Kernel 是 Host 合同与 Device 认领的组合，启动开销决定了"小而碎"天然低效；
- Tiling = 容量约束下最大化复用 × 核数约束下最小化闲置；
- 归约维是特殊维度：切它可以，但要为"合并"付通信代价；
- 队列 + 双缓冲是最小可行流水，节奏由最慢段决定；
- 流水不能突破带宽上限，也不能缩短瓶颈段——它只是消除"互相等待"；
- 最小骨架五部件：切分、认领、尾块、双缓冲、同步——真实 GEMM 同构放大。
