> 适用：时间紧，或完整版跟不动时。这页用"建材规格与码放"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 建材规格：范围、精度、位宽的三角

选数据类型 = 给工地选建材规格。一块浮点数由**指数位（管范围：能表示多大）+ 尾数位（管精度：数得多准）**拼成：

| 规格 | 直觉 |
| --- | --- |
| FP32 | 全能标准料——又大又准，但**贵**（4 字节） |
| FP16 | 表面平整（精度高）但**怕极端尺寸**（最大 65504，超了直接报废） |
| BF16 | **不怕大数**（范围同 FP32）但表面毛糙（精度低） |
| FP8 | 极省料但娇气，前沿工程专用 |

为什么现在的大模型训练几乎都选 BF16？因为训练里**大数（梯度、激活）比精细度更容易出事**——BF16 用精度换范围的买卖是划算的。

换规格的账要算三本：**显存带宽直接受益**（位宽减半，Bytes 减半）；**机器峰值要看档位**（矩阵单元对不同精度有不同峰值，先核对）；**精度账单要单独管**（误差会积累）。

::: details 小测 1：FP16 和 BF16 都占 2 字节，为什么训练主流选 BF16？
FP16 指数位只有 5 位，最大只能表示 ±65504——训练中的大梯度/大激活轻松超限变 Inf，还得靠 Loss Scaling 救。BF16 指数位 8 位（范围同 FP32）几乎不溢出，代价只是尾数精度低。对训练来说"不炸"比"更准"重要。
:::

### 2. 哪里用什么料：混合精度的分配表

聪明的工地**不是全屋换廉价料**，而是按用途分配：

```text
填充墙（激活、前向权重）     → BF16      量大，省着用
承重结构（累加器、Norm 统计）→ FP32      误差会积累/被当除数，不能省
账本正本（优化器里的权重、m/v）→ FP32    长期累计，必须精细
```

三条铁律：**累加用高精度**（几千次加法的误差会滚雪球）、**统计量要准**（Norm 的均值方差是除数，歪了整层歪）、**正本要精细**（优化器状态的 FP32 正本配 BF16 计算副本）。

推理更激进：直接上"口袋书"——权重压成 INT8/INT4 存储（量化）、KV Cache 也能压。**省料 ≠ 省时间**：读口袋书要换算（反量化），快不快看印刷厂设备（硬件支持）。

::: details 小测 2：为什么矩阵乘加的累加器必须用 FP32？
一次 GEMM 里每个输出元素是几千次乘加的累加。用低精度累加，每次的舍入误差会迅速积累成系统性偏差——高精度累加器把误差摁在可接受范围内，这是"用局部贵换整体准"。
:::

### 3. 码放与合并工序：Layout 和融合

**码放方式（Layout）**：同一批料可以按图排（NCHW）也可以按位置排（NHWC）——**没有绝对好的摆法，只有跟最大消费者配不配**。改摆法（Transpose/Reformat）= **全部搬出来重码一遍**（一读一写，真实发生）；更阴险的是**隐式重码**：图编译时相邻算子要的摆法不一致，编译器悄悄插一个 Reformat——代码里看不到，时间线里全是它。

**合并工序（融合）**：把几道小工序合成一趟干完（中间材料不落地），三派手艺按序取用：

1. **预制构件**（内置融合算子）：FlashAttention 这类——别人替你造好了，优先用；
2. **总工自动优化**（编译器融合）：torch.compile / GE 的模式匹配——免费但有限；
3. **老师傅手写**（手写 Kernel）：Ascend C 自定义算子——收益最大、成本最高，是 《昇腾与 HCCL》第 4、5 章的主线。

**不是所有邻居都该合并**：逐元素链、Norm 链该融（省的是搬运，账本"向右挪"）；**两个大 GEMM 之间不该融**——本来就是机器满转的工序，合并不增加产出还伤灵活性。

::: details 小测 3：把 `RMSNorm + Add + 激活` 融成一个 Kernel，收益记在哪本账上？
搬运账（第 5 章的"向右挪"）：三个中间结果原本要各写回 HBM 再读出，融合后全部留在片上——Bytes 大减、AI 右移。顺带还有 Launch 账（3 个任务变 1 个）。这类"低算术强度链"是融合的最佳标的。
:::

### 3 句话带走

1. 类型是三角交换：**BF16 用精度换范围**胜出训练；换低精度时**显存立刻受益、峰值先核对档位**；
2. 混合精度按对象分配：**填充省（激活）、承重精（累加/统计）、正本细（优化器状态）**；
3. 布局跟最大消费者走（**重码是真实的一读一写**）；融合三派按序用，**逐元素链该融、大 GEMM 之间不该融**。

## 08-1｜数据类型：范围、精度与位宽的三角

::: info 本单元目标
围绕 **浮点类型的构成与取舍** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

换一个数据类型，是**性价比最高**的系统优化——它同时改写三本账。但先得看懂规格表。

### 2. 浮点数 = 符号 + 指数 + 尾数

一个浮点数的位被切成三段：**指数管范围（能表示多大/多小），尾数管精度（数得多准）**。

| 类型 | 位宽（符/指/尾） | 范围 | 精度 | 直觉 |
| --- | --- | --- | --- | --- |
| FP32 | 1 / 8 / 23 | ~±3.4e38 | 高 | 全能但贵 |
| FP16 | 1 / 5 / 10 | **±65504（小！）** | 高 | 表面平整，怕极端尺寸 |
| BF16 | 1 / **8** / 7 | **同 FP32** | 低 | 不怕大数，但毛糙 |
| FP8 E4M3 | 1 / 4 / 3 | 小 | 低 | 极省但娇气 |
| FP8 E5M2 | 1 / 5 / 2 | 稍大 | 更低 | 比上者更耐极端值 |

两个关键取舍：

1. **FP16 的指数只有 5 位**——最大 65504，大梯度、大激活直接溢出成 Inf（《训练与推理系统》第 1 章的 Loss Scaling 就是为它发明的）；
2. **BF16 牺牲尾数换指数**——范围与 FP32 相同、几乎不溢出，代价是有效数字少。现代 LLM 训练因此普遍选 BF16 而不是 FP16。

#### 2.1 换类型，三本账怎么变

**显存与带宽账**：位宽减半，Bytes 减半——第 5 章 $T_{memory}^{min}=Bytes/BW$ 直接受益；KV Cache、激活这类大件的收益立竿见影。

**计算账**：矩阵单元（Tensor Core / Cube）对不同精度有**不同峰值档位**——通常精度越低峰值越高。但注意两件事：规格表的档位要核对口径（[加速卡专题](accelerator-cards-2026.md)的 Dense/Sparse 教训）；**数据从 HBM 搬进来后，实际乘加仍按单元支持的格式执行**——低精度数据若不被单元原生支持，反而要多一道转换。

**精度账**：误差在累加中最容易积少成多——所以下一单元的第一条规则就是"**累加用高精度**"。

::: tip 与量化的关系
《训练与推理系统》第 6 章（大模型基础）讲过 INT8/INT4 量化——那是"训练后把权重压成整数存储"的路线；本章的 BF16/FP8 是浮点表示本身的降位。两者最终都落到同一个账本上：Bytes 变小、峰值档位变高、精度账要单独管。
:::

## 08-2｜混合精度实践：哪里该用什么精度

::: info 本单元目标
围绕 **按对象选择精度** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

"混合精度"不是把整个模型一刀切换成 BF16，而是**每个对象各用各的精度**——承重处用高规格，填充处用省料。

#### 3.1 训练中的精度分配表

| 对象 | 典型精度 | 为什么 |
| --- | --- | --- |
| 权重（前向/反向用） | BF16/FP16 | 计算主体，省显存带宽 |
| **Master 权重（优化器里的正本）** | **FP32** | 参数更新的累计精度不能丢 |
| 梯度 | BF16/FP16 | 量大，低精度收益直接 |
| **优化器状态（AdamW 的 m/v）** | **FP32** | 统计量对精度敏感，且要配 FP32 正本 |
| 激活 | BF16 | 量最大，最需要省 |
| **累加器 / 归约统计（Norm 的均值方差）** | **FP32** | 见下面的"铁三角" |

三条经验法则：

1. **累加用高精度**：矩阵乘加单元内部用 FP32 累加器——几千次 BF16 乘加的误差若用低精度累加会迅速积累；
2. **统计量要准**：RMSNorm/LayerNorm 的均值方差是"除数"，算歪了整层跟着歪；
3. **BF16 基本免 Loss Scaling**：范围同 FP32，小梯度不容易下溢——这是它取代 FP16 成为 LLM 主流的工程原因（FP16 路线的放大-还原流程见[《训练与推理系统》第 1 章](../systems/01-training-loop.md#_01-3-学习率、混合精度与梯度裁剪)）。

#### 4. 推理侧与排障

**推理**的精度菜单更激进：权重 Weight-Only 量化（INT8/INT4 存储 + 反量化计算）、W8A8（权重激活都低精度）、KV Cache 量化——选型与代价见[《并行策略》第 2 章](../parallel/02-efficient-llm-design.md#_02-2-量化原理、粒度与显存收益)。

**精度问题的两张面孔**：

- **溢出**：出现 NaN/Inf，Loss 突然爆炸——查哪个对象超了范围（FP16 典型）；
- **下溢**：梯度悄悄变 0、Loss 不降——小数值低于表示范围（FP16 梯度典型）。

定位思路：先锁定**第一个出现异常值的张量**（逐层插入检查或开 DEBUG 日志），再决定是升精度、加 scaling 还是换 BF16。

::: warning 别忘了第 6 章的账
图模式融合/重排可能改变浮点求和顺序——精度比对时，先排除"执行顺序差异"再怀疑真正的精度 bug（06-4 的行为差异）。
:::

## 08-3｜Layout：张量在内存里的摆法

::: info 本单元目标
围绕 **布局的系统代价与隐式转换** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

第 3 章（03-4）说过布局是"双刃剑"——本单元从**系统层**看它：布局不只是某个算子的访问模式问题，而是**贯穿全图的账单**。

#### 5.1 同一份数据，几种摆法

```text
逻辑上：图片批次 [N, C, H, W]
物理上（内存里字节怎么排）：
  NCHW：按图片排——同一张图的所有通道放一起
  NHWC：按像素排——同一位置的所有通道放一起（C 连续，对卷积/访存合并友好）
分块布局：为了矩阵单元的分块加载，把数据按块交织存放
```

**没有绝对好的布局，只有与消费方匹配的布局**：卷积可能偏好 NHWC，某个 GEMM 实现要求转置后的矩阵，通信原语对切分后的形状有自己的假设（《集合通信》的伏笔）。昇腾上还有为 Cube 通路服务的专用分块排布格式——名字先不背，记住"**硬件友好 ≠ 人眼友好**"即可。

#### 5.2 转换的真实代价

把数据从一种摆法换到另一种（Transpose / Reformat / Contiguous）= **完整的一读一写**（第 3 章练习算过：`[8,4096,4096]` 的 fp16 张量转置一次 ≈ 537 MB 的 HBM 流量）。

更隐蔽的是**隐式转换**：图编译时，相邻算子期望的布局不一致，编译器自动插入一个 Reformat 节点——它不在你的代码里，却在你的时间线里。**优化好的网络里，Reformat 常常是"白吃白占"的大头之一**：06-3 说的图优化（融合）也包含"转换+计算合并"这类模式。

#### 6. 布局决策的三条原则

1. **先测量再调整**：时间线上找 Reformat/Transpose 节点，算它占总时长的比例——不显著就别动（避免过早优化）；
2. **转换值得发生一次，不值得反复发生**：一次转换后的布局让后续多个算子受益才划算；两个算子各转一次来回折腾是典型浪费；
3. **跟着数据的最大消费者走**：一段计算里最贵的算子（通常是 GEMM/Conv）偏好的布局优先，前后小算子适应它——让"大户"满意，小户的分摊才划算。

## 08-4｜融合：三类手艺与收益边界

::: info 本单元目标
围绕 **三类融合手艺与"该不该融"的判断** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

融合（把多个算子合并成一个 Kernel）是前三章知识的一次总回收：省搬运（I03/I05 的"向右挪"）、省 Launch（06-1）、省中间显存（06-2）。做法分三派。

#### 7.1 三类手艺

| 手艺 | 谁来做 | 典型例子 | 特点 |
| --- | --- | --- | --- |
| **手写融合 Kernel** | 工程师用 Ascend C / CUDA 写 | 自定义算子把 Norm+Add+激活一趟做完 | 收益最大、开发成本最高 |
| **编译器自动融合** | 图编译器模式匹配 | torch.compile / GE 的自动融合、Reformat+计算合并 | 免费但受模式库限制 |
| **内置融合算子** | 框架/算子库预置 | FlashAttention、FusedLayerNorm | 开箱即用，等价于"别人替你手写好了" |

三派不是竞争关系：**优先用内置、缺了靠编译器、都不行才手写**——手写路径就是 《昇腾与 HCCL》第 4、5 章（Ascend C 算子开发）的主线。

#### 7.2 融合收益账与两条铁律

**收益方向**（第 5 章语言）：融合后中间结果不出片上 → 分母 Bytes 减小 → **AI 右移**。对逐元素链，融合前后 AI 可以翻数倍；同时任务数减少，Launch 空隙同步收窄。

**铁律一：不是所有邻居都值得融。**

| 该融 | 不该融 |
| --- | --- |
| 逐元素链（Add、激活、缩放） | 两个大 GEMM 之间（本来就 Compute-bound，融合无收益） |
| Norm 链（统计+归一化+残差） | 需要复用的公共子结果（强行合并伤复用） |
| 投影合并（Q/K/V 三个小 GEMM 并一个） | 差异巨大、shape 不兼容的算子 |
| 转换+计算（Reformat 顺路干活） | 调试期高频变动的代码（先跑对再跑快） |

**铁律二：融合的代价要入账**——可读性与可维护性下降、通用性损失（常绑定特定 shape 范围）、框架接入成本（算子注册、自动微分对接——《昇腾与 HCCL》第 5 章的"框架接入"正是这件事）。

#### 8. 第二阶段收官：执行系统全景

三个旋钮（精度、布局、融合）已集齐，第二阶段的完整拼图：

```text
一行代码
 → Eager 五段 或 图编译（第 6 章）
 → 任务进 Stream，Event 接依赖（第 7 章）
 → 算子内部：精度档位 × 布局匹配 × 融合程度（第 8 章）
 → 设备执行：账本三数字全部被这三根旋钮改写（第 5 章）
```

- [ ] 我能解释同步点、数据布局转换和 Kernel Launch 开销分别藏在哪、何时成为瓶颈。

### 10. 自测题

1. 浮点数的指数位和尾数位分别决定什么？
2. FP16 和 BF16 的核心区别是什么？为什么 LLM 训练主流选 BF16？
3. 换成低精度，哪些账立刻受益？哪笔账要先核对硬件？
4. 训练中哪些对象必须保持 FP32？为什么？
5. 为什么累加器要用高精度？
6. 溢出和下溢各自的典型症状是什么？
7. NCHW 和 NHWC 的区别是什么？布局没有绝对好坏的判断标准是什么？
8. 隐式 Reformat 从哪来？为什么说是隐形账单？
9. 融合的三类手艺是什么？选择顺序？
10. 哪些算子组合值得融合？哪些不值得？各举一例并说明原因。

::: details 自测答案

1. 指数决定表示范围（能多大/多小），尾数决定精度（有效数字多少）。
2. FP16 指数 5 位（范围 ±65504，易溢出，需 Loss Scaling）、尾数 10 位（精度高）；BF16 指数 8 位（范围同 FP32、几乎不溢出）、尾数 7 位（精度低）。LLM 训练大梯度和大激活常见，BF16 的范围安全性胜过 FP16 的精度优势。
3. 显存与带宽账立刻受益（Bytes 按位宽下降）；计算峰值账要先核对矩阵单元是否原生支持该精度档位（口径要对）。
4. Master 权重正本、优化器状态（AdamW 的 m/v）、累加器、归约统计量——这些位置要么做长期累计、要么做除数，低精度误差会积累或放大。
5. 数千次乘加的舍入误差在低精度累加中迅速积累，高精度累加器把误差控制在可接受范围。
6. 溢出：NaN/Inf、Loss 爆炸（数值超范围）；下溢：梯度悄悄变 0、Loss 不降（数值低于最小表示）。
7. NCHW 按图片排布（通道维不连续），NHWC 按像素排布（C 连续）；判断标准是"与最大消费者的访问模式是否匹配"。
8. 图编译时相邻算子期望的布局不一致，编译器自动插入 Reformat 节点——代码里看不到，但真实发生一读一写，出现在时间线上。
9. 内置融合算子（FlashAttention 等）、编译器自动融合（torch.compile/GE）、手写融合 Kernel（Ascend C/CUDA）。顺序：内置优先 → 编译器补位 → 手写兜底。
10. 值得：逐元素链、Norm 链、QKV 投影合并、Reformat+计算合并——中间结果不出片上，AI 右移。不值得：两个大 GEMM 之间（已 Compute-bound，融合无收益）、需复用的公共子表达式（强行合并伤复用）、调试期代码（先跑对再跑快）。

:::

### 11. 本课小结与第二阶段收官

- 数据类型是三角交换：范围、精度、位宽——BF16 靠范围取胜成为训练主流；
- 混合精度按对象分配：计算存储低精度、累计统计高精度；
- 布局匹配最大消费者；转换一次值得、来回折腾是浪费；隐式 Reformat 要上时间线抓；
- 融合三派手艺按序取用；收益方向永远是"AI 右移 + Launch 减少"；
- 第二阶段闭环：图编译（第 6）→ 任务并发（第 7）→ 算子内部三旋钮（第 8）。
