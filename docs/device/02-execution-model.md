### 1. 同一个工程，三支队伍三种干法

第 1 章的餐厅只说了"后厨很忙"，没说厨师**怎么**干活。现在拆开看三支队伍：

- **老师傅装修队（CPU）**：几位全能师傅，什么活都会，讲究**每件事利索做完**（低延迟）。但人少——碰上"铺一万块瓷砖"这种规则重复的活就抓瞎；
- **大工地人海队（GPU）**：几百个小工，每人只会一个简单动作。不怕谁在等料——**只要有别的工位能开工，就先让别人干**，用人数掩盖等待（吞吐）；
- **预制板厂（NPU）**：干脆不接杂活，只做"盖楼标准件"（矩阵运算）。浇筑机、打磨线、领班各司其职，专用料道送料——**用专用换极致效率**。

为什么会长成这样？**预算（晶体管）花的地方不同**：装修队花在师傅的经验（控制逻辑+大缓存），人海队花在人手（海量计算单元），预制厂花在专用设备和料道。

::: details 小测 1：CPU、GPU、NPU 处理"等料"的策略有何本质区别？
CPU 尽量不让等待发生（乱序执行、大缓存提前备料）；GPU 不消灭等待，而是**用人海掩盖**——等料的工位先闲着，让就绪的工位顶上；NPU 靠**软件把送料排成流水**，让浇筑机抬头时料永远在台上。
:::

### 2. 人海队和预制厂的组织架构

**人海队的班制（GPU）**：小工不是单干的，**32 人一班（Warp）绑在同一根横杆上齐步走**——同一时刻全班只做一个动作，各自搬各自的砖（SIMT）。

- **走岔路（分支分歧）**：16 人要左转、16 人要右转？全班只能先陪左边走一趟、再陪右边走一趟——**两趟时间都付**；
- **吊机（Tensor Core）**：普通工一次搬一块砖，吊机**一次吊一整块预制板**（小矩阵块）。要喂饱它，活必须切成规整的大块——切得零碎就退回人肉搬运。

**预制厂的岗位（NPU）**：浇筑机（**Cube**，矩阵乘加）、打磨线（**Vector**，逐元素/向量）、领班（**Scalar**，算地址、发号施令），外加专职料车（**DMA/MTE**）从大仓库送料进车间。

::: details 小测 2：为什么说"一次矩阵乘法不只是浇筑机在干活"？
因为它是整条生产线的协作：领班（Scalar）算好每批料的位置，料车（DMA）把料从 HBM 送进车间缓冲区，浇筑机（Cube）乘加，成品再经出货口（FixPipe）写回。任何一环慢，浇筑机就只能停线等——瓶颈往往不在"机器不够快"，而在"料没到"。
:::

### 3. 说明书上的 1000 TFLOPS，为什么实测只有几百

工地上的效率漏斗，一层层打折扣：

| 损失 | 工地版本 |
| --- | --- |
| 并行度不足 | 人手没派满，一半工位闲着 |
| 尾块效应 | 最后一车料只够半班人干，后半程天然半速 |
| 数据供给不足 | 料车供不上，机器空转 |
| 执行方式惩罚 | 队形散（分支分歧）、砖不规整（形状不对齐） |
| 频率/功耗墙 | 天太热被迫放慢；还有"慢卡"拖累全场等它 |

关键是：**效率是乘法**。人手 0.8 × 供料 0.8 × 队形 0.9 ≈ 0.58——每项看着都还行，乘起来只剩六成。所以优化要**先找最小的那项**，不是平均用力。

::: details 小测 3：Profiling 显示时间线前半段满载、后四分之一骤降——最可能是哪种损失？
尾块效应。任务数没被工位数整除：前几轮人人有活，最后一轮只剩部分工位有料干，后半程利用率天然减半。解法是调整切分（Tile 尺寸/数量），让尾块尽可能小。
:::

### 3 句话带走

1. 三支队伍：**老师傅求快（CPU）、人海队靠多（GPU）、预制厂靠专（NPU）**——预算花在哪决定哲学；
2. GPU 的命门是**并行度**（32 人齐步走，怕分歧、怕零碎），NPU 的命门是**料道**（搬运要软件组织好）；
3. **利用率是乘法**：人手 × 供料 × 队形 × 节奏，优化先修最小的那项。

## 02-1｜三种执行哲学：CPU、GPU 与 NPU

::: info 本单元目标
围绕 **CPU、GPU 与 NPU 的执行哲学** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

同一个矩阵乘法 `y = x @ W`，交给 CPU、GPU 或 NPU，执行方式完全不同。差异不是"谁更快"，而是**硬件把晶体管花在了哪里**。

### 2. 延迟导向与吞吐导向

#### 2.1 CPU：用一切手段压低单线程延迟

CPU 的每个核心都很"重"：大容量多级缓存、乱序执行、分支预测、深流水线。它擅长复杂的控制流——指针追逐、函数调用、动态分支——目标是让**每一条指令尽快完成**。

代价是：核心数量有限，规则的大规模数据并行反而发挥不出优势。

#### 2.2 GPU：用海量线程掩盖延迟

GPU 走向另一个极端：数百上千个轻量核心，每个核心的能力远弱于 CPU 核心，控制逻辑和缓存都被压缩。

它不怕单个线程等待内存——只要同时存在大量可运行的线程，调度器就让"正在等待的"和"已就绪的"交替占用计算单元。**延迟没有被消除，而是被并行度隐藏了。**

#### 2.3 NPU：用专用数据通路做张量计算

大模型负载中，GEMM、卷积等规则矩阵运算占了绝大部分计算量。NPU 干脆放弃通用性，围绕张量计算设计**专用数据通路**：

```text
CPU：   复杂核心 × 少量   →  通用、低延迟、昂贵
GPU：   简单核心 × 海量   →  通用、高吞吐、靠线程隐藏延迟
NPU：   专用通路 + 片上存储层次  →  矩阵计算高能效、不通用
```

三种处理器不是替代关系。一台训练服务器里，CPU 负责框架、调度与数据预处理，GPU/NPU 负责张量计算——异构协作是常态。

### 3. 从晶体管预算看分工

一颗芯片的晶体管数量是有限的，不同架构把预算花在不同地方：

| 维度 | CPU | GPU | NPU |
| --- | --- | --- | --- |
| 晶体管主要花在 | 控制逻辑 + 大缓存 | 大量 ALU + 寄存器堆 | 矩阵计算阵列 + 片上存储通路 |
| 核心数量 | 少（几个到几十个） | 多（数千 CUDA Core） | 多个 AI Core，内部再分 Cube/Vector |
| 延迟处理 | 缩短它（乱序、缓存） | 隐藏它（线程切换） | 组织好搬运，让它不发生（流水） |
| 擅长 | 复杂控制、串行逻辑 | 规模可变的并行计算 | 形状规则的张量运算 |
| 不擅长 | 大规模规则并行 | 复杂分支、串行依赖 | 非张量、动态不规则负载 |

这也解释了为什么**加速卡不能只看 TFLOPS**——峰值来自专用通路在理想条件下的吞吐，真实模型能否吃满，取决于负载特征是否匹配执行模型。产品层面的对比见专题 [2026 主流 AI 加速卡全景](accelerator-cards-2026.md)。

::: warning 术语陷阱
"Core"在三种平台上含义不同：CPU 的 Core 是完整通用核心；GPU 的 Core 是一个线程执行通道；昇腾的 AI Core 是包含多种计算单元和存储的完整计算单元。跨平台比较时先确认对方说的是哪一种。
:::

## 02-2｜GPU 内部：SM、Warp 与 SIMT

::: info 本单元目标
围绕 **SM、Warp 与 SIMT** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

理解 GPU 的钥匙只有三把：SM 是硬件组织，Warp 是调度单位，SIMT 是执行方式。

#### 4.1 SM：GPU 的基本作战单元

一块 GPU 由几十上百个 **SM（Streaming Multiprocessor）** 组成，每个 SM 内部包含：

- 数十个 CUDA Core（标量运算通道）；
- 若干 Tensor Core（矩阵运算单元）；
- 一份寄存器堆（Register File）和共享内存（Shared Memory）；
- Warp 调度器与指令发射单元。

```text
GPU 设备
 ├── SM 0    ├── SM 1    ├── SM 2    ────►
      │           │           │
   CUDA Core × N  Tensor Core  RegFile  SharedMem  Warp 调度器
```

软件侧的 Grid/Block/Thread 会按层级映射到设备/SM/执行通道上。**一个 Kernel 能否吃满 GPU，首先取决于是否有足够多的 Block 分布到所有 SM。**

#### 4.2 Warp：32 个线程锁步走

线程不是逐个调度的，而是每 **32 个线程组成一个 Warp**，作为最小调度单位。同一个 Warp 里的线程在同一时刻执行同一条指令，只是操作不同的数据。

Warp 调度器的工作方式很朴素：

```text
Warp 0：发射指令 ──► 等待数据（访存延迟）……
Warp 1：        ──► 就绪，立即发射
Warp 2：        ──► 就绪，立即发射
……
Warp 0：数据到达，重新排队发射
```

这就是上一单元说的"用并行度隐藏延迟"的具体机制：**只要就绪的 Warp 够多，计算单元就总有活干。**

#### 5. SIMT 的代价与收益

#### 5.1 分支分歧（Divergence）

SIMT（Single Instruction, Multiple Threads）要求一个 Warp 同一时刻只走一条指令路径。如果 32 个线程中有 16 个走 `if`、16 个走 `else`，硬件只能**先串行执行完一个分支，再执行另一个**——两个分支的时间都要付。

对大模型负载影响不大（张量运算里几乎没有数据相关的分支），但动态控制流密集的算子会因此明显变慢。

#### 5.2 Tensor Core：从标量到矩阵块

传统 CUDA Core 一次做一次标量乘加（FMA）；**Tensor Core 一次完成一个小矩阵块的乘加**（如 16×8×8 的分块），输入输出直接放在寄存器里。

大模型绝大多数 FLOPs 由 Tensor Core 贡献——GPU 的"AI 算力"实际指的就是它。这也带来约束：要吃满 Tensor Core，任务必须能切成形状友好的矩阵块，否则就退化到 CUDA Core 甚至更低效的路径。

#### 5.3 执行模型对 Kernel 的三要求

把上面三把钥匙合起来，一个高效 GPU Kernel 需要：

1. **并行度足够**：Block/Warp 数量覆盖所有 SM，且有冗余以隐藏延迟；
2. **访存友好**：合并访问（Coalesced Access），让一个 Warp 的 32 次读尽可能合成少量大事务；
3. **形状规则**：矩阵尺寸对齐 Tensor Core 的分块要求，减少尾块浪费。

第 4 章的 Tiling 与流水线，就是把这三条要求工程化的方法。

## 02-3｜NPU 内部：达芬奇架构与计算单元

::: info 本单元目标
围绕 **达芬奇架构与 AI Core 的计算单元** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

本单元以昇腾 NPU 为例看 NPU 的执行模型；昇腾细节的完整展开在 《昇腾与 HCCL》的 [01-1：NPU、达芬奇架构与 AI Core](../ascend/00-ascend-cann.md#_0-0-npu、达芬奇架构与-ai-core)，此处只保留通用主线。

#### 6.1 设计思路：为张量计算铺专用通路

GPU 的 SIMT 从图形渲染演化而来，通用性是遗产也是包袱。达芬奇架构则直接面向张量计算设计：

- 不再组织"海量同构线程"，而是提供**功能分化的计算单元**——矩阵、向量、标量各走各的通路；
- 用**多级片上存储 + 显式搬运指令**组织数据流，而不是依赖硬件缓存和线程切换；
- 计算、搬运、控制可以**异步并行**，由队列和同步信号衔接。

#### 6.2 AI Core 内部的三种计算单元

| 单元 | 干什么 | 典型算子 |
| --- | --- | --- |
| **Cube** | 矩阵乘加，一条指令完成一次分块矩阵运算 | MatMul、卷积 |
| **Vector** | 逐元素与向量运算 | Add、激活、归一化、部分归约 |
| **Scalar** | 标量计算、地址与循环控制、向其他单元发射指令 | Kernel 内控制流 |

关键认知：**一次 MatMul 不只是 Cube 在工作。** Scalar 准备地址和循环参数，DMA/MTE 单元把数据从 HBM 搬到片上，Cube 做乘加，结果再经 FixPipe 等通路写出。数据通路是流水线，任何一环慢，整条流水就慢。

#### 6.3 存储层次：数据要先搬近才能算

```text
HBM（设备内存，大而慢）
  ↓ DMA/MTE 搬入
L1 → L0A / L0B（矩阵输入） → Cube → L0C（累加结果）
UB（Unified Buffer，向量通路的数据驿站）
```

大张量无法一次放进片上存储，必须切成 Tile 分批"搬入—计算—搬出"。**与 GPU 靠硬件缓存自动管理不同，NPU 的数据搬运更多由软件（编译器与算子代码）显式组织**——这是 Ascend C 编程模型的出发点，也是 《昇腾与 HCCL》第 4、5 章的主角。

#### 6.4 与 GPU 执行模型对照

| 维度 | GPU（SIMT） | NPU（达芬奇） |
| --- | --- | --- |
| 并行组织 | 海量线程，按 Warp 调度 | 功能分化的计算单元 + 显式队列 |
| 延迟处理 | 线程切换隐藏 | 软件组织搬运与流水，让等待不发生 |
| 数据搬运 | 硬件缓存 + 合并访问 | 显式 Tiling + DMA/MTE 多级搬运 |
| 编程心智 | "让所有线程都有活干" | "把搬运和计算排成流水线" |

两种心智模型会在真实系统中交汇：GPU 的 Kernel 也要做 Tiling（显式管理 Shared Memory），NPU 的编译器也会自动做很多调度。**差异在默认责任划分：GPU 把更多责任交给硬件和调度器，NPU 把更多控制权交给软件。**

#### 6.5 架构变体

昇腾产品中，Cube 与 Vector 耦合在一个核心内（耦合架构），或拆分为独立的 AIC（AI Cube）与 AIV（AI Vector）核心（分离架构）。具体型号的资源配比不同，但 Ascend C 用统一编程抽象屏蔽差异——做深度优化时才需要回到目标芯片的实际资源。

## 02-4｜从执行模型到利用率

::: info 本单元目标
围绕 **理论算力与实际利用率之间的落差** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

规格表上的 1000 TFLOPS，为什么实测往往只有几百？因为利用率是**多个比率的乘积**，每一项都在打折。

#### 7.1 五类结构性损失

**① 并行度不足。** Block/Warp 数量铺不满所有 SM，或 AI Core 分到的工作太少。小 Batch、小 Shape、长序列按行切分，都可能出现"一半计算单元在等，一半在干"。

**② 尾块效应。** 任务数不能整除硬件并行度时，最后一批只有部分单元有活。100 个 Tile 跑在 64 个可用单元上：第一轮 64 个全忙，第二轮只有 36 个忙——后半程利用率直接减半。

**③ 数据供给不足。** 计算单元就绪但数据未到：HBM 带宽打满、片上 Buffer 太小放不下复用块、搬运与计算没有形成流水。GPU 上表现为 Warp 全在等内存，NPU 上表现为 Cube 空转等 DMA。

**④ 执行方式惩罚。** SIMT 分支分歧让 Warp 串行走两条路径；形状不对齐让 Tensor Core 退回小分块甚至标量路径；数据布局转换插入额外的搬运和转换 Kernel。

**⑤ 频率与功耗墙。** 持续满载触发降频，规格表通常按 Boost 频率计算峰值。多卡场景还有散热差异导致的"慢卡"——集合同步时所有人等最慢的一张。

#### 7.2 利用率是乘法

假设各环节相对理想情况的表现是：并行度 0.8 × 数据供给 0.8 × 形状效率 0.9：

$$
0.8 \times 0.8 \times 0.9 \approx 0.58
$$

每一项看起来都"还好"，乘起来只剩六成。这就是为什么性能优化要**先找乘积里最小的那一项**，而不是平均用力。

#### 7.3 指标怎么读

| 观察到的现象 | 指向的损失类型 |
| --- | --- |
| SM 利用率高但 Tensor Pipe 利用率低 | 形状不对齐、退出了矩阵通路 |
| 计算单元利用率低、内存带宽高 | 数据搬运主导（Memory-bound），缺复用 |
| 计算与访存都低、时间线上有空泡 | 并行度不足或同步等待 |
| 前段满载、尾段骤降 | 尾块效应 |
| 各卡利用率差异大 | 负载不均或"慢卡"拖累 |

#### 8. 执行模型如何指导优化

每一类损失都有对应的优化手段，它们分布在后续不同课程里：

| 损失 | 优化方向 | 后续课程 |
| --- | --- | --- |
| 并行度不足 | 增大 Batch、合并小算子、调整切分 | 第 4 章 Tiling、第四阶段并行 |
| 尾块 | 调整 Tile 尺寸与切分方式 | 第 4 章 Kernel/Tiling |
| 数据供给 | 提高 HBM 利用、片上复用、Double Buffer | 第 3 章存储层次、第 4 章流水线 |
| 布局与形状 | Layout 转换、对齐、算子融合 | 本专栏第 8 章 |
| 慢卡与不均 | 均衡切分、通信调度 | 第四、五阶段 |

此时回看第 1 章的三类瓶颈判断：**Compute-bound/Memory-bound 的根因，多数都能在本章的执行模型里找到结构解释。** 例如"Device 利用率 100% 却不快"，现在可以解释为：利用率只说明单元没闲，不代表它们在做高效的工作（小分块、分歧分支、反复搬运都算"忙"）。

### 10. 自测题

1. CPU 和 GPU 处理访存延迟的策略有什么本质区别？
2. Warp 是什么？为什么它是 GPU 的最小调度单位？
3. SIMT 的分支分歧为什么会带来接近两倍的时间损失？
4. Tensor Core 与 CUDA Core 的区别是什么？
5. 达芬奇架构中 Cube、Vector、Scalar 分别承担什么？
6. NPU 与 GPU 在"延迟处理"上的策略差异是什么？
7. 为什么说"一次 MatMul 不只是 Cube 在工作"？
8. 列出至少四类"理论算力跑不满"的结构性原因。
9. 为什么利用率是乘法而不是加法？这对优化策略意味着什么？
10. "Device 利用率 100% 但任务不快"，给出至少两种解释。

::: details 自测答案

1. CPU 尽量缩短延迟（乱序执行、多级缓存、分支预测）；GPU 不缩短延迟，而是用大量可运行线程切换来隐藏延迟。
2. Warp 是 32 个线程组成的锁步执行组；硬件按 Warp 而不是按线程发射指令和调度，因此它是调度的最小单位。
3. Warp 同一时刻只能走一条指令路径，两个分支只能串行执行，总时间约等于两条路径之和。
4. CUDA Core 一次执行一次标量乘加；Tensor Core 一次完成一个小矩阵块的乘加，是大模型算力的主要来源。
5. Cube 做矩阵乘加；Vector 做逐元素与向量运算；Scalar 做标量计算、地址与循环控制、指令发射。
6. GPU 靠线程切换隐藏延迟；NPU 靠软件显式组织数据搬运与流水，让等待尽量不发生。
7. Scalar 准备控制流，DMA/MTE 负责搬运，Cube 做乘加，FixPipe 等负责写出——MatMul 是一条多单元流水线，任何一环慢都会拖慢整体。
8. 并行度不足、尾块效应、数据供给不足、执行方式惩罚（分歧/不对齐/布局转换）、频率与功耗墙（含慢卡）。
9. 各环节的效率彼此独立地压缩最终吞吐，损失是相乘的；因此优化应优先作用于乘积中最小的那一项，收益最大。
10. 例如：单元在小分块/低效路径上忙碌（形状不对齐）；Warp 分歧串行执行；反复做数据搬运；忙的不是关键路径上的有效工作。

:::

### 11. 本课小结

- 晶体管预算决定执行哲学：CPU 换延迟、GPU 换吞吐、NPU 换矩阵能效；
- GPU 的钥匙是 SM/Warp/SIMT：并行度是生命线，分支分歧与不对齐是结构性惩罚；
- NPU 的钥匙是功能分化 + 显式搬运：Cube/Vector/Scalar 流水协作，软件组织数据流；
- 两者的心智模型差异：GPU 让所有线程有活干，NPU 把搬运和计算排成流水；
- 利用率是乘法：并行度 × 数据供给 × 形状效率 × 频率，先找最小的那一项；
- 执行模型为第 1 章的三类瓶颈提供了结构性解释，也为 Tiling、流水线与并行课程铺路。
