规格表上的 1000 TFLOPS，为什么实测往往只有几百？因为利用率是**多个比率的乘积**，每一项都在打折。

### 7.1 五类结构性损失

**① 并行度不足。** Block/Warp 数量铺不满所有 SM，或 AI Core 分到的工作太少。小 Batch、小 Shape、长序列按行切分，都可能出现"一半计算单元在等，一半在干"。

**② 尾块效应。** 任务数不能整除硬件并行度时，最后一批只有部分单元有活。100 个 Tile 跑在 64 个可用单元上：第一轮 64 个全忙，第二轮只有 36 个忙——后半程利用率直接减半。

**③ 数据供给不足。** 计算单元就绪但数据未到：HBM 带宽打满、片上 Buffer 太小放不下复用块、搬运与计算没有形成流水。GPU 上表现为 Warp 全在等内存，NPU 上表现为 Cube 空转等 DMA。

**④ 执行方式惩罚。** SIMT 分支分歧让 Warp 串行走两条路径；形状不对齐让 Tensor Core 退回小分块甚至标量路径；数据布局转换插入额外的搬运和转换 Kernel。

**⑤ 频率与功耗墙。** 持续满载触发降频，规格表通常按 Boost 频率计算峰值。多卡场景还有散热差异导致的"慢卡"——集合同步时所有人等最慢的一张。

### 7.2 利用率是乘法

假设各环节相对理想情况的表现是：并行度 0.8 × 数据供给 0.8 × 形状效率 0.9：

$$
0.8 \times 0.8 \times 0.9 \approx 0.58
$$

每一项看起来都"还好"，乘起来只剩六成。这就是为什么性能优化要**先找乘积里最小的那一项**，而不是平均用力。

### 7.3 指标怎么读

| 观察到的现象 | 指向的损失类型 |
| --- | --- |
| SM 利用率高但 Tensor Pipe 利用率低 | 形状不对齐、退出了矩阵通路 |
| 计算单元利用率低、内存带宽高 | 数据搬运主导（Memory-bound），缺复用 |
| 计算与访存都低、时间线上有空泡 | 并行度不足或同步等待 |
| 前段满载、尾段骤降 | 尾块效应 |
| 各卡利用率差异大 | 负载不均或"慢卡"拖累 |

### 8. 执行模型如何指导优化

每一类损失都有对应的优化手段，它们分布在后续不同课程里：

| 损失 | 优化方向 | 后续课程 |
| --- | --- | --- |
| 并行度不足 | 增大 Batch、合并小算子、调整切分 | 第 4 章 Tiling、第四阶段并行 |
| 尾块 | 调整 Tile 尺寸与切分方式 | 第 4 章 Kernel/Tiling |
| 数据供给 | 提高 HBM 利用、片上复用、Double Buffer | 第 3 章存储层次、第 4 章流水线 |
| 布局与形状 | Layout 转换、对齐、算子融合 | 本专栏第 8 章 |
| 慢卡与不均 | 均衡切分、通信调度 | 第四、五阶段 |

此时回看第 1 章的三类瓶颈判断：**Compute-bound/Memory-bound 的根因，多数都能在本章的执行模型里找到结构解释。** 例如"Device 利用率 100% 却不快"，现在可以解释为：利用率只说明单元没闲，不代表它们在做高效的工作（小分块、分歧分支、反复搬运都算"忙"）。
