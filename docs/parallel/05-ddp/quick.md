## 1. 分店与强制对账：为什么必须 AllReduce

你开了 8 家**连锁分店**（8 张卡），每家都有完整菜单（完整模型副本），各自接待自己的客人（不同的数据分片）。

一个月下来各算各的利润（各自的梯度）——问题来了：**如果不统一**，下个月 8 家店的进货策略（参数更新）就各走各路，连锁店当场散伙。所以月底必须做一件事：**8 家利润求平均，全体按平均值统一进货**——这个动作就是梯度 AllReduce。

记住这句：**不做 AllReduce 不是"慢一点"，是训练在数学上直接错了**。所以 DP 的通信是算法本身的一步，不是性能优化。

账本有多厚？梯度 ≈ 2×参数量（BF16）——7.5B 模型就是 15 GB，每卡过手约 2×15×7/8 ≈ 26 GB（Ring 账本）。好消息：这笔账**跟 batch 大小无关**——batch 越大、算得越久，同样的运费被摊得越薄，这就是 DP 好扩展的原因。

::: details 小测 1：为什么说 DP 的通信"不是性能问题"？
因为缺少 AllReduce 时各副本会漂移成 N 个不同模型，训练结果在数学上就是错的——它是算法（等价大 batch SGD）的组成部分。
:::

## 2. 账本分章寄：Bucket

对账的正确姿势不是"月底一次性寄 15 GB"——那样要等所有账算完（反向结束）才能寄，寄的那段时间全店停工。

也不是"记一笔寄一笔"——几万笔快递，每笔的起步价（延迟 α）能把人逼疯。

**分章寄**：把账本按记账完成顺序分成若干章（**Bucket，每章约 25 MB**）——这一章记完，快递立刻出发；记账员继续记下一章。章的大小是个旋钮：太大 → 拖到最后才能寄；太小 → 快递太碎、起步价占比飙升。这就是分桶的两端权衡。

::: details 小测 2：桶为什么按"反向完成顺序"装，而不是按模型定义顺序？
反向是从输出层往输入层走的——先算完的梯度装进先出发的桶，通信才能尽早开始；按定义顺序装桶会让"早就算完的梯度"干等"晚才算完的同伴"。
:::

## 3. 边记账边寄：重叠

现在把两条流水线摆在一起：

```text
记账员（计算流）：  [记第3章][记第2章][记第1章]══╗ → 统一进货(step)
                            └已寄┘ └已寄┘      ║
快递员（通信流）：  ·····[等第1章]→寄→[等第2章]→寄→╝
```

**记账员记后面几章时，前面几章已经在路上**——串行的"记账 10 秒 + 寄账 1 秒"变成约 10 秒。能做到的原因：寄的是**已经记完的章**、等货的只有月底统一进货（step）——中间整段时间天然空闲。

但有三样藏不住：①快递比记账还慢时（小模型+慢网），多出来的照样堵；②"统一进货"前必须等最后一章到货（语义下界）；③如果本月记 K 次账才对一次账（**梯度累积**），运费直接除以 K——免费的省钱。

::: details 小测 3：反向 4 秒、通信流忙 9 秒、一步 10 秒——瓶颈在哪？
通信。通信已经从第 1 秒就在飞（重叠生效），但 9 秒 > 4 秒，裸奔的 5 秒藏不住——出路：压通信量（量化/压缩）、换算法、或上第 9 章的 ZeRO/FSDP。
:::

## 3 句话带走

1. **DP = 完整模型 + 数据切片 + 梯度求平均**：不做 AllReduce 就是分店散伙，数学错误；
2. **Bucket = 账本分章寄**：按反向顺序装桶、桶满即发，避开"太碎（α）"与"太整（不能重叠）"两个极端；
3. **重叠 = 记账寄货双流水线**：串行 N+M 变 max(N,M)；藏不住的部分靠压量、换算法或梯度累积。

## 黑话小词典

| 术语 | 人话 |
| --- | --- |
| DP / DDP | 数据并行 / 它的生产级实现（多进程版） |
| AllReduce(avg) | 全员求和取平均——分店强制统一 |
| Bucket | 账本的一章：约 25 MB，记完即寄 |
| bucket_cap_mb | 章有多厚的旋钮 |

| 双流重叠 | 记账员与快递员同时干活 |
| 梯度累积 | 记 K 次账才对一次账，运费÷K |
