# 第 7 章｜Pipeline Parallel

> 本课目标：理解按深度切分的流水线模型与它极小的 P2P 通信；掌握 micro-batch 流水时间线与 Bubble 率公式；说清 1F1B 为什么不减 Bubble 却是必需品（内存 O(M)→O(S)）；能算 PP 的三本账并把它放进 3D 混合并行。

## 本章导学

::: tip 本课只记住 3 件事
1. **PP = 按层分段接力**：模型沿深度切成 S 个 stage，数据像流水线一样流过——通信只有**相邻 stage 间的 P2P 激活**（三把刀里唯一没有集合通信的），所以**天生跨机友好**。
2. **Bubble 公式**：$\frac{S-1}{M+S-1}$——流水线的启动/排空空转，靠**加大 micro-batch 数 M** 摊薄；但 GPipe 做法下 M 越大、激活内存越爆，矛盾由此产生。
3. **1F1B 解内存不解时间**：交替做前向/反向，把在途激活从 O(M) 压到 O(S)——Bubble 不变，但允许更大的 M，**间接**再压 Bubble。
:::

## ⚡ 速通（约 5 分钟）

> 适用：时间紧，或完整版跟不动时。这页用"洗车流水线"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 四个工位的流水线：切深度

一家洗车店扩建成**四工位流水线**：冲水 → 打泡沫 → 刷洗 → 擦干。每辆车从工位 1 进、工位 4 出。

对应到训练：模型 32 层**按深度切成 4 段**（stage），每段住一台机器。数据像车一样流过去：前向从 Stage 0 流到 Stage 3，反向再流回来。

这种切法的通信便宜到不像话：**只有相邻工位递车**（P2P 传一个 micro-batch 的边界激活，MB 级）——不需要全员集合、不需要传梯度/参数（那些按层分家了，各存各的）。**模型再大，递的也只是"这层的输出"**——所以 PP 是三把刀里唯一**天生跨机友好**的（TP 只能挤机内，PP 的工位可以横跨厂房）。

::: details 小测 1：为什么 PP 的通信量与模型大小无关？
因为 stage 之间只传"边界激活"（这层算完的输出，大小由 batch×序列×隐层决定）；参数和梯度各 stage 自存自用，从不需要搬家。
:::

### 2. 车队拆小批 + 空转时刻：Bubble

只洗**一辆大车**（整 batch 一次流过）？工位 4 要等车缓缓漂过前三个工位才开工——同一时刻**只有一个工位在干活**。

聪明做法：把车队拆成 **M 辆小车**（micro-batch）**连续注入**——第 1 辆还在工位 2，第 2 辆已进工位 1。稳态时四个工位全部满负荷；空转只剩两头：**开头等第一辆车流到最深（fill）、结尾等最后一辆反向流回最浅（drain）**——这段空转就叫 **Bubble**。

公式一张名片：**Bubble 率 = (S−1)/(M+S−1)**（S = 工位数，M = 车数）。S=4 时：M=4 辆 → 空转 43%；M=64 辆 → 空转 4.5%。**车越多，启动/排空的固定开销摊得越薄**。

::: details 小测 2：S=8、M=56 时 Bubble 率是多少？
(8−1)/(56+8−1) = 7/63 = 11.1%。
:::

### 3. 边洗边交车：1F1B

新问题：GPipe 式调度（**所有车全洗完，再统一返工检查**）要求暂存**全部 M 辆车**的洗车记录（激活内存 O(M)）——想加大 M 压空转？先把暂存区撑爆。

关键洞察：**第 1 辆车的返工不必等第 64 辆洗完**——它自己的工序早就结束了。于是 **1F1B**：工位先热身（S−1 辆前向），之后**每接收一辆新车，就送走一辆检查完的旧车**——一进一出交替，暂存区里**恒定只有约 S 辆车**（内存 O(M)→O(S)）。

注意：1F1B **不减少空转**（两头还是要等），它解放的是暂存区——于是你能放心把 M 加到 64，**空转被间接压到 4.5%**。进阶版 Interleaved（每个工位再细分 v 个小段）能把空转再除以 v，代价是递车更碎更频繁。

::: details 小测 3：1F1B 既然不省时间，为什么人人都在用？
它省内存（O(M)→O(S)），允许加大 M；Bubble 率随 M 下降——"解内存、不解时间，最终解时间"。
:::

### 3 句话带走

1. **PP 按深度切**：只有相邻 stage 递车（P2P 激活，MB 级），三把刀里唯一跨机友好；
2. **Bubble = (S−1)/(M+S−1)**：micro-batch 连续注入填满流水线，两头空转靠大 M 摊；
3. **1F1B 边洗边交车**：在途激活 O(M)→O(S)，解放 M 上限，间接压死 Bubble。

### 黑话小词典

| 术语 | 人话 |
| --- | --- |
| stage | 流水线的一个工位（一段连续的层，住一台机器） |
| micro-batch | 车队里的一辆小车：batch 切小、连续注入 |
| Bubble | 流水线两头的空转（fill + drain） |
| GPipe | 全部洗完再统一返工的调度（内存 O(M)） |
| 1F1B | 一辆新车进、一辆旧车出的交替调度（内存 O(S)） |

## 07-1｜为什么是 PP：按深度分段

::: info 本单元目标
围绕 **"按深度切分的通信优势"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 1. 第三把刀：切深度

三把刀凑齐了——DP 切**数据**、TP 切**层内**、PP 切**深度**：

```text
Stage 0（机器 A）   Stage 1（机器 B）   Stage 2（机器 C）   Stage 3（机器 D）
Layer 0-7     →      Layer 8-15    →     Layer 16-23    →    Layer 24-31 + Loss
        激活 ──────P2P────→ 激活 ──────P2P────→ 激活 ──────P2P────→
```

每个 stage 持有 $1/S$ 的层（三大件 ÷S），数据从 Stage 0 注入、逐段前向、在 Stage 3 算 loss、再逐段反向流回。

### 2. PP 的通信账：小到不像话

对比三把刀每步要传的东西：

| 并行 | 通信对象 | 大小（7.5B 级算例） | 通信对象范围 |
| --- | --- | --- | --- |
| DP | 全量梯度 | ~15 GB/步 | world group（全体） |
| TP | 每层激活 × 128 次 | ~128 MB/层 | tp_group（机内） |
| **PP** | **stage 边界激活** | ~128 MB/micro-batch | **只有相邻两台机器** |

PP 的三个结构性优势：

1. **P2P 而非集合**：Send/Recv 只发生在相邻 stage 之间——没有全员集合、没有规约（[HCCL 源码 3](../ascend/hccl-source/03-primitives-and-sync.md) 的 P2P 原语正是干这个的）；
2. **通信量小**：只传一个 micro-batch 的边界激活（B×S×h×2，MB 级），与模型大小**无关**——模型再大，传的还是那层输出；
3. **跨机友好**：相邻机器间点对点走网卡，不需要机内全互联的带宽——**PP 段天然横跨多机**，恰好补上 TP"只能住机内"的短板。

::: warning 但 PP 不是免费的午餐
按深度切分引入了三把刀里独有的一种浪费：**流水线的启动与排空时间（Bubble）**——机器在等数据流到自己这里。这是本章后半段的主角，也是 PP 一切调度算法要对抗的对象。
:::

## 07-2｜Micro-batch 与 Bubble

::: info 本单元目标
围绕 **"Bubble 从哪来、怎么摊"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 3. 朴素流水线：为什么空转

**朴素做法**：一个完整 batch 整体流过 4 个 stage——前向全过一遍，再反向全过一遍：

```text
Stage 0: F ········ ········ ········ B        ← 只有首尾在干活
Stage 1: · F ······ ········ ····· B ·
Stage 2: · · F ···· ······ ···· B · ·
Stage 3: · · · F ·· ···· ·· B · · · ·
时间 ──────────────────────────────────►
         F = 整个 batch 的前向      B = 整个 batch 的反向
```

Stage 3 在等数据到达时全程空转，Stage 0 发出数据后全程空等反向回来——**同一时刻只有一台机器在干活**。

**解法：micro-batch**。把 batch 切成 M 份，像流水线上的零件一样**连续注入**（GPipe 风格：全部前向，再全部反向）：

```text
M=4，f/b = 单个 micro-batch 的前向/反向时长
Stage 0: F1 F2 F3 F4 ·· ·· ·· ·· ·· ·· ·· B4 B3 B2 B1
Stage 1: · F1 F2 F3 F4 ·· ·· ·· ·· ·· B4 B3 B2 B1 ·
Stage 2: · · F1 F2 F3 F4 ·· ·· ·· B4 B3 B2 B1 · ·
Stage 3: · · · F1 F2 F3 F4 B4 B3 B2 B1 · · · · · ·
         └──── fill（填充）────┘└── 稳态 ──┘└─ drain（排空）─┘
```

稳态时段四个 stage 全部满负荷；**空转只剩两头**：开头等第一个 micro-batch 流到最深（fill）、结尾等最后一个反向流回最浅（drain）——这段统称 **Bubble**。

### 4. Bubble 率公式

理想时间（无 Bubble）：$M\times(f+b)$。实际时间：

$$
T = (M + S - 1)\times(f+b),\qquad
\text{Bubble 率} = \frac{(S-1)(f+b)}{T} = \frac{S-1}{M+S-1}
$$

**直觉版**：流水线多了 $S-1$ 个"零件在途"的节拍，零件总数越多（M 越大），这笔固定开销摊得越薄。

| M（S=4） | Bubble 率 |
| --- | --- |
| 4 | 3/7 ≈ **43%** |
| 16 | 3/19 ≈ 16% |
| 64 | 3/67 ≈ **4.5%** |

::: warning 公式里的矛盾
M 越大 Bubble 越小——但 GPipe 要**暂存全部 M 个 micro-batch 的激活**等反向（回扣 [《训练与推理系统》02-1](../systems/02-training-memory-compute.md#_02-1-训练显存账本-四个大件) 的激活账）：M=64 的激活内存是 M=4 的 16 倍。**"用大 M 压 Bubble" 撞上 "激活放不下"**——这个矛盾正是 1F1B 的出场理由（下一单元）。
:::

## 07-3｜1F1B：解内存，不解时间

::: info 本单元目标
围绕 **"1F1B 用交替调度换内存"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 5. 关键观察：反向不必等全部前向

GPipe 的"全部前向 → 全部反向"是一个**不必要的串行**——micro-batch 1 的反向只依赖 micro-batch 1 自己的前向，谁也没规定它必须等 micro-batch M 前向完。

**1F1B（one-forward-one-backward）**：warmup 先做 $S-1$ 个前向把流水线填满，之后**每接收一个新 micro-batch 的前向，就完成一个旧 micro-batch 的反向**，交替推进直到 drain：

```text
Stage 0 视角（S=4, M=8）：
F1 F2 F3 [F4 B1] [F5 B2] [F6 B3] [F7 B4] [F8 B5] · B6 · B7 · B8
└warmup┘ └────────── 稳态：一前向一反向 ──────────┘ └cooldown┘
```

### 6. 1F1B 的账：内存 O(M) → O(S)

稳态下，每个 stage **同时在途的 micro-batch 激活数 ≈ S**（而非 GPipe 的 M）：

| 方案 | 在途激活 | Bubble 率 | 代价 |
| --- | --- | --- | --- |
| GPipe | O(M) 个 | $\frac{S-1}{M+S-1}$ | M 大 → 内存爆 |
| **1F1B** | **O(S) 个** | $\frac{S-1}{M+S-1}$（**不变！**） | 调度与同步更复杂 |

**注意：1F1B 不减少 Bubble**——总时间公式相同。它解放的是内存：M 从"受显存限制"变成"只受你想要的 Bubble 率限制"。于是可以放心加大 M，**间接**把 Bubble 压得更低——这就是"解内存、不解时间，最终解时间"的三段逻辑。

#### 6.1 再进一步：Interleaved 1F1B（虚拟流水线）

Megatron 的改进：每个 stage 把自己的层再切成 $v$ 个**虚拟段**，调度粒度更细——Bubble 从 $(S-1)$ 拍降到约 $(S-1)/v$ 拍。代价是 P2P 次数 ×v 且每次传的激活更碎。一句话记住：**用更碎的通信换更短的空转**。

::: tip 三种调度的一句话族谱
朴素串行（全空转）→ GPipe micro-batch（填满流水，两头空转，内存 O(M)）→ 1F1B（交替推进，内存 O(S)）→ Interleaved（虚拟段，空转再除 v）。
:::

## 07-4｜PP 的三本账与 3D 组合

::: info 本单元目标
围绕 **"PP 的账本与它在混合并行中的位置"** 建立一条可以复述的因果链。读完后，尝试不看正文用一句话解释它。
:::

### 7. PP 的三本账

**通信账** ✅ 最省：相邻 stage 间 P2P 边界激活，MB 级、与模型大小无关、跨机走网卡即可。

**显存账**：三大件 ÷S（每 stage 只存自己那段层）；激活经 1F1B 后只需 O(S) 个 micro-batch 在途——必要时还能叠加 Activation Checkpointing（[《训练与推理系统》02-2](../systems/02-training-memory-compute.md#_02-2-activation-checkpointing-用时间换显存)）再省一档。

**负载均衡账** ⚠️ PP 独有的软肋：流水线的节拍由**最慢的 stage** 决定——Transformer 层数均匀时好切，但 embedding 只在首段、loss 只在尾段，**首尾 stage 常被有意少放几层**来配平；切分不均 = 全流水线陪最慢的 stage 空转。

### 8. 3D 混合并行：三把刀合体

生产级大模型训练的标准形态——三把刀各就其位：

```text
TP（机内 8 卡）    → 层内高速通信贴 HCCS
  × PP（跨机分段）  → 极小 P2P 通信跨机器
    × DP（数据复制）→ 剩余卡组做吞吐扩展
```

回扣 [第 4 章](04-distributed-basics.md#_04-2-通信域-谁和谁是一伙的)的身份系统：每个 rank 同时属于三个组——`tp_group`（机内 8 卡）、`pp_group`（相邻机器的同位卡）、`dp_group`（其余机器的对应卡）。

三种并行的**通信性格**至此凑成完整光谱：

| | DP | TP | PP |
| --- | --- | --- | --- |
| 通信量 | 大（梯度全量） | 小（激活） | 极小（边界激活） |
| 频率 | 低（每步一轮） | 高（每层 4 次） | 中（每 micro-batch 每边界） |
| 形态 | AllReduce（集合） | AG/RS/AllReduce（集合） | **Send/Recv（P2P）** |
| 可重叠 | ✅ | ❌ 关键路径 | ❌ 但量小 |
| 独有代价 | 通信占比 | 延迟敏感 | **Bubble + 负载均衡** |
| 驻留位置 | 任意 | 机内 | **跨机** |

::: tip 本章收束
PP 用"流水线空转"换来了极小且跨机友好的通信——当模型大到 TP+DP 放不下、或集群跨多机时，PP 是承重墙。下一章的 **Context Parallel** 处理三把刀都棘手的最后一个维度：**序列太长**——单层激活沿序列维也放不下时，切序列。
:::

```text
   Bubble = fill + drain：(S-1)/(M+S-1)
   矛盾：大 M 压 Bubble ↔ GPipe 激活内存 O(M) 爆
        ↓
1F1B（07-3）：warmup → 一前向一反向交替 → cooldown
   内存 O(M)→O(S)，Bubble 不变 → 放心加大 M → 间接压 Bubble
   Interleaved：虚拟段把空转再除 v（代价：P2P 更碎）
        ↓
组合（07-4）：通信 ✅ 极小 / 显存 三大件÷S+O(S) 激活 / 负载均衡 ⚠️ 独有软肋
   3D = TP(机内) × PP(跨机) × DP(扩展) —— 三种通信性格凑齐光谱
```

### 10. 自测题

1. 三把刀分别切什么？PP 的切分单位是什么？
2. PP 每步传什么、多大、在谁和谁之间？为什么说与模型大小无关？
3. 为什么说 PP 是三把刀里唯一"没有集合通信"的？
4. 朴素流水线为什么空转严重？micro-batch 怎么解决？
5. 写出 Bubble 率公式。S=4、M=12 时是多少？
6. GPipe 的"大 M"矛盾是什么？
7. 1F1B 的稳态调度是什么？在途激活从多少降到多少？
8. 为什么说 1F1B"解内存、不解时间，最终解时间"？
9. Interleaved 1F1B 用什么换什么？代价是什么？
10. PP 独有的负载均衡问题出在哪？常见对策是什么？

::: details 自测答案

1. DP 切数据、TP 切层内矩阵、PP 切深度（层段）；PP 的单位是 stage（连续若干层）。
2. stage 边界的激活（一个 micro-batch 的 B×S×h×2，MB 级）；只在相邻两个 stage（两台机器）之间 P2P；传的是"层的输出"而非参数/梯度，模型再大这一层输出的大小不变。
3. 它的通信原语是 Send/Recv（点对点），不做 AllGather/Reduce 类的全员规约。
4. 整 batch 串行流过时同一时刻只有一台机器干活；切成 M 个 micro-batch 连续注入后，稳态时段所有 stage 满负荷。
5. $(S-1)/(M+S-1) = 3/15 = 20\%$。
6. M 越大 Bubble 越小，但 GPipe 需暂存全部 M 个 micro-batch 的激活等反向——内存 O(M)，M 大即爆。
7. warmup 做 S−1 个前向，之后每来一个新前向就完成一个旧反向；在途激活从 O(M) 降到 O(S)。
8. Bubble 公式不变所以总时间不变；但内存解放后 M 可以加大，Bubble 率随 M 下降——间接压缩。
9. stage 内再切 v 个虚拟段，调度更细，空转从 (S−1) 拍降到约 (S−1)/v；代价是 P2P 次数 ×v、每次激活更碎。
10. 流水节拍由最慢 stage 决定；embedding/loss 集中在首尾段导致天然不均——首尾 stage 有意少放几层配平。

:::

### 11. 本课小结

- PP 切深度：P2P 边界激活极小且跨机友好，补上 TP 只能住机内的短板；
- Bubble 是 PP 的固有税：$(S-1)/(M+S-1)$，靠加大 M 摊薄；
- GPipe 内存 O(M) 与大 M 矛盾 → 1F1B 交替调度降到 O(S)；
- 三本账：通信最省、显存 ÷S+O(S) 激活、负载均衡是独有软肋；
- 3D 组合（TP 机内 × PP 跨机 × DP 扩展）与三种通信性格光谱收官。
