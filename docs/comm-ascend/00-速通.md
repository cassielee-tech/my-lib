## 第 1 章｜Collective 语义与通信代价模型

完整正文 → [第 1 章｜Collective 语义与通信代价模型](01-collective-semantics-cost.md)

> 适用：时间紧，或完整版跟不动时。这页用"办公室协作动作 + 快递计费"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 先认人：谁在参与

集合通信发生在一个**小组**里：每个成员有个编号（**Rank**），小组总人数是 **World Size**，小组本身叫**通信域**。同一个员工可以同时在"技术组"和"项目组"——rank 也可以同时在多个通信域里（TP 组、DP 组各一个）。

一次通信就是一场**小组协作动作**：定义它只需两张快照——**开始时每人手里有什么、结束时每人手里有什么**。

::: details 小测 1：为什么"第 3 个 rank"不等于"第 3 张卡"？
rank 是逻辑编号，物理卡的编号（NPU ID/Chip ID/逻辑 ID）可能和它错位。协作快不快取决于物理位置（谁和谁挨着），不取决于编号——谈性能必须把 rank 映射回物理拓扑。
:::

### 2. 六个协作动作：开始谁有什么，结束谁有什么

8 个人的办公室，每人手里一份报表：

| 动作 | 开始 | 结束 | 办公室版本 |
| --- | --- | --- | --- |
| **Broadcast** | 老板有文件 | **全员**有 | 老板群发邮件 |
| **Reduce** | 各有各的 | **只有老板**拿到汇总 | 各组交表，老板汇总 |
| **AllReduce** | 各有各的 | **全员**有汇总 | 每人都要一份汇总表 |
| **AllGather** | 各有一页 | 全员有整本（拼起来） | 每人复印自己那页发全员 |
| **ReduceScatter** | 各有整份 | 汇总后**各拿一块** | 汇总完每人只留自己负责段 |
| **AlltoAll** | 各有发往不同人的包裹 | 定向收到包裹 | 各部门互寄快递 |

**一条黄金恒等式**（背下来，后面全是它）：

```text
AllReduce = Reduce + Broadcast（先交老板再群发）
          = ReduceScatter + AllGather（先分头汇总，再互相补齐）← 优化重点！
```

第二种拆法妙在：**中间状态每人只经手 1/N**——下一课的 Ring 算法就是它的直接实现。

::: details 小测 2：为什么说 AllReduce 的账约是 AllGather 的两倍？
因为 AllReduce 语义上就是 RS+AG 两段接力：每 rank 经手约 2·S·(N−1)/N 字节，而 AllGather 只有一段 S·(N−1)/N。恒等式不只是语义游戏，它直接写在账本上。
:::

### 3. 快递计费：α-β-γ 三本账

任何一次通信的耗时：

$$
T \approx \alpha \times 轮次 + \beta \times 字节/带宽 + \gamma \times 本地计算
$$

- **α = 起步价**：每轮的固定成本（启动、握手、同步）；
- **β = 每公斤运费**：字节搬运时间；
- **γ = 打包费**：本地规约、压缩的计算。

两个世界的分界线：**1 KB 的小消息**，运费忽略不计，起步价说了算——**谁轮次少谁赢**；**1 GB 的大消息**，起步价忽略不计，运费说了算——**谁的链路走得满谁赢**。这句话就是"小消息和大消息选不同算法"的全部原理。

最后记住**两层选型**：先选**原语**（语义层，由数据需求决定，选错了算法再好也白搭——比如用 AllGather+本地求和模拟 AllReduce，多传 N 倍字节）；再选**算法**（实现层，看大小 × 人数 × 拓扑三张牌）。

::: details 小测 3：某代码 AllGather 收集所有 rank 的梯度再本地求和，N=8。比 AllReduce 多传多少？
AllGather 让每 rank 收到全部 8 份完整梯度（8S 字节量级），而 AllReduce 每 rank 只需经手约 2S。多传约 4 倍字节——这不是算法问题，是原语选错了，无法靠优化弥补。
:::

### 第 1 章 · 3 句话带走

1. 语义=两张快照：**开始谁有什么、结束谁有什么**；六个动作各就各位；
2. 黄金恒等式：**AllReduce = RS + AG**，中间态每人只经手 1/N——一切高效算法的出发点；
3. 三本账：**起步价 α、运费 β、打包费 γ**；小消息比轮次、大消息比链路满载。

## 第 2 章｜Ring AllReduce 完整推导

完整正文 → [第 2 章｜Ring AllReduce 完整推导](02-ring-allreduce.md)

> 适用：时间紧，或完整版跟不动时。这页用"教室传卷子"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 为什么大家手拉手围成圈

要让 8 个同学合作汇总成绩，有两种笨办法：**全连**（每人跟所有人单独传话——线路铺不开）和**找班长中转**（8 份卷子全挤班长一张桌子——班长就是瓶颈）。

聪明的办法是**围成一个圈**：每人只跟**左右两个邻居**打交道。

两个魔法性质：

1. **没有班长**：每人恒定 2 条线路，第 100 个同学入圈，前辈们压力一点不变；
2. **全员同时动**：任何时刻每人都在"收一张、发一张"——8 条线路同时满负荷，等于 8 倍带宽。

注意：这个"圈"是**排座位的逻辑顺序**，不是真拉网线——通信库让大家按这个顺序传就是了。

::: details 小测 1：环形为什么"没有中心瓶颈"？
每人只有左右两条链路、每个 rank 进出流量恒定；不存在所有数据必经的节点。对比星形：全班数据都挤班长一张嘴，人数越多班长越堵。
:::

### 2. 第一支舞：分头汇总（ReduceScatter）

每人把自己那份成绩切成 4 块（语文/数学/英语/物理），目标：**每人最终负责一科的完整汇总**。

规则只有一句：**每轮每人把一块"累积中的卷子"传给右邻居，从左邻居收一块、加上自己的数**。

4 人、3 轮的手推（拿纸走一遍胜过读十遍）：

```text
第1轮：我发"自己编号"的块给右邻 → 右邻加上自己的数（每块吸收 2 人）
第2轮：把刚加完的那块继续右传   → 每块吸收 3 人
第3轮：再传一轮                → 每块吸收 4 人 = 完全！
```

3 轮后：**每人手里恰好有一块"全组之和"**（我负责数学，数学块就汇聚到我手里）。为什么恰好 3=N−1 轮？一块数据每被传一次多吸收一个人的数，要吸收其余 N−1 个人，就要被传 N−1 跳。

::: details 小测 2：为什么总轮次是 N−1 而不是 (N−1)×N？
因为 N 块数据在环上**同时**流动（每人每轮都在传），不是一块块排队传。N 条流水线并行推进，每条走 N−1 跳，总轮次仍是 N−1。
:::

### 3. 第二支舞：传阅成全（AllGather）

现在每人有一块完整汇总，但目标（AllReduce）是**每人都要全部 4 块**。

规则更简单：**不加法了，把完全块绕圈传阅**——每轮每人把最新拿到的那块发给右邻居。又是 N−1 轮，每人集齐全部块。**AllReduce 完成**。

这就是上一章恒等式的舞蹈版：**AllReduce = RS（边传边加）+ AG（纯传阅）**。

### 4. 结账：魔法与诅咒

$$
T_{Ring} \approx \underbrace{2(N-1)\alpha}_{\text{起步价×轮次}} + \underbrace{\tfrac{2S(N-1)}{N}\cdot\tfrac{1}{BW}}_{\text{运费}}
$$

- **魔法（运费项）**：每人经手 ≤ 2S 字节，**与人数无关**——8 人是 1.75S，1024 人也才 2.0S。加人不加流量；
- **诅咒（起步价项）**：2(N−1) 轮的启动成本**随人数线性膨胀**——1024 人、每次 20µs，光启动就 40ms。

所以：**大消息用 Ring（运费说了算，它运费最低）；小消息别用 Ring（起步价说了算，它轮次太多）**。工程上还常把数据切成 2N 块（而非 N 块）——总量不变，但小包裹流水更满，运费更贴近账面。

::: details 小测 3：1 KB 的梯度同步用 8 rank Ring，会发生什么？
传输本身只要微秒级，但 2×7=14 轮的启动成本（约几百 µs）彻底淹没它——延迟项碾压带宽项。这种场景该换轮次只有 log₂N 的算法（下一课的 Tree/递归倍增）。
:::

### 第 2 章 · 3 句话带走

1. 环 = **没有班长 + 全员同时收发**：拓扑上的人人平等；
2. 两支舞：**RS 边传边加（每人得一块全和）→ AG 纯传阅（每人集齐全部）**= AllReduce；
3. 账本：**运费 ≤ 2S 与人数无关（大消息天选），起步价随人数线性涨（小消息噩梦）**。

## 第 3 章｜Tree、Recursive Doubling 与算法选择

完整正文 → [第 3 章｜Tree、Recursive Doubling 与算法选择](03-tree-algorithms-selection.md)

> 适用：时间紧，或完整版跟不动时。这页用"通知怎么传播"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 配对通话：RD（递归倍增）

公司 8 个人要对齐一条信息，不拉群、不找中转，怎么办？**配对打电话**：

```text
第 1 轮：0↔1、2↔3、4↔5、6↔7 两两对答案 → 每人知道 2 个人的信息
第 2 轮：跟隔一位的伙伴（0↔2、1↔3…）对 → 每人知道 4 个人的
第 3 轮：跟隔三位的伙伴（0↔4、1↔5…）对 → 每人知道全部 8 人的 ✓
```

**距离每轮翻倍，"知情圈"每轮翻倍**——3 轮 = log₂8。而且双方通完话**各自都记下合并结果**，所以不用再广播，人人手里都是全量。

代价：每通电话都要**把手里全部内容说一遍**——信息量一大（比如要对齐的是一份 500 页报告），电话费就爆了。另外人 数得是 2 的幂，不然配不齐。

::: details 小测 1：RD 为什么大消息吃亏？
每轮交换的是"全量部分和"：每 rank 总流量 S·log₂N。N=8 时 = 3S，而 Ring 只要约 1.75S——报告越厚，电话费差距越大。
:::

### 2. 层层转达：Tree（树）

另一个办法是**建组织树**：组员报给组长，组长汇总报给经理，经理报到总监（**上行归约**，每轮层级减半，log₂N 轮到顶）；总监拿到全量后沿原路发回（**下行广播**，又是 log₂N 轮）。

- 优点：**几轮就完事**（N=1024 只要约 20 轮，Ring 要 2046 轮）；**人数不是 2 的幂也优雅**；组织树天然匹配"组→经理→总监"的层级（预告：下一课的分层通信）。
- 缺点：**总监和经理的电话被打爆**（根节点链路热点），而且总监是单点。

::: details 小测 2：RD 和 Tree 都只有 log 轮，本质区别是什么？
RD 全员对称、双向交换（无需广播阶段，但需 2 的幂）；Tree 有中心（上行+下行两段、根部热点，但任意 N 都行、层级友好）。
:::

### 3. 怎么选：起步价 vs 运费

把上一章的记账本借来（α = 起步价/轮，β = 运费/字节）：

| | Ring（流水传抄） | RD（配对通话） | Tree（层层转达） |
| --- | --- | --- | --- |
| 轮次 | 2(N−1)，人多恐怖 | log₂N | 2·log₂N |
| 每 rank 流量 | ~2S **最少** | S·log₂N | 根部重 |
| 适合 | **大部头** | **小道消息** | 小道消息 + 层级场景 |

**分界点是算出来的**：两个公式相等解 S*。同一组参数（α=20µs、BW=25GB/s）下，N=8 时约 4.4 MB，N=64 时约 15 MB——**集群越大，"小消息"的定义越宽**。

真实通信库（HCCL/NCCL）内部就有个**自动选型器**：查表 + 公式动态比价；你也可以用环境变量（`HCCL_ALGO`/`NCCL_ALGO`）强制指定，再用基准测试从 8B 扫到 1GB 画条曲线，看它选得对不对。

::: details 小测 3：N=64 的集群同步 1 MB 梯度，选谁？
N=64 时分界点约 15 MB，1 MB < 15 MB → α 主导 → 选 Tree/RD 这类 log 轮次算法。若同步 512 MB 梯度则远超分界点 → Ring。
:::

### 第 3 章 · 3 句话带走

1. **RD = 配对通话**：距离翻倍、知情圈翻倍，log₂N 轮人人有全量——但每轮说全量、要 2 的幂；
2. **Tree = 层层转达**：上行+下行各 log₂N 轮，任意 N 优雅、层级友好，代价是根部热点；
3. **选型 = 算账**：小消息看轮次（Tree/RD）、大消息看流量（Ring），分界点随 N 和硬件移动，实测说了算。

## 第 4 章｜AllGather、ReduceScatter 与 AlltoAll

完整正文 → [第 4 章｜AllGather、ReduceScatter 与 AlltoAll](04-gather-scatter-alltoall.md)

> 适用：时间紧，或完整版跟不动时。这页用"办公室分发动作"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 复印发全员：AllGather

每人手里有一章稿子（合起来是一份完整报告）。**AllGather = 每人复印自己那章、发给所有人**——结束后人手一册完整报告。

- 形状变化：每人 `[1/4 本]` → 人人 `[完整 4 章]`；
- 报告被复制了 4 份（4 = 人数）；
- 谁在用：TP 前向（各卡算出激活的不同切片，拼全才能算下一步）、FSDP（参数平时分片存，用时拼全）。

::: details 小测 1：AllGather 和 AllReduce 的关系？
AllReduce = ReduceScatter + AllGather（黄金恒等式）。Ring AllReduce 的下半场舞步，单独跳就是一次完整的 AllGather——账本也正好是 AllReduce 的一半。
:::

### 2. 汇总后各撕一章：ReduceScatter

每人手里都有一份**带批注的全稿**（内容不同、要合并）。**ReduceScatter = 全员逐段求和，然后每人撕走自己负责的那一章**——你拿到"数学章的全组批注之和"，他拿到"语文章的"。

- 形状变化：每人 `[全稿]` → 每人 `[自己那章的合并版]`；
- 只规约、不复制全量；
- 谁在用：TP 反向（梯度求和后各拿自己参数段）、FSDP 反向（比 AllReduce **省一半**——别人的梯度段对我没用）。

::: details 小测 2：FSDP 反向为什么用 RS 不用 AllReduce？
参数本来就分片存：我只需要"我这段参数"的梯度。AllReduce 给每人全长（2S），RS 只给各段（S）——**语义上够用的最小原语**，通信直接省一半。
:::

### 3. 各部门互寄快递：AlltoAll

前两个都是"汇总/复制"，第三个是**搬家**：每个部门把自己手里的包裹按**收件地址**分好，同时寄出——寄给谁的、寄多少，**出发前就查好路由**。

- 形状变化：每人总量**不变**，但内部按"目的地"重排了（近似一次转置）；
- 和 AG 的本质区别：**总量守恒、人人拿到的都不一样**（AG 是总量翻倍、人人拿到一样的）；
- 谁在用：MoE 的 dispatch/combine（token 按路由结果寄往专家所在的卡）。

### 4. MoE 的快递为什么总堵：动态失衡

MoE 的"收件地址"是**路由器实时决定**的——今天上午热点在专家 3（他所在的部门爆仓），下午热点换到专家 7。而集合通信是**全员到齐才散场**：7 个方向都寄完了，也得陪最慢的那个等——**木桶效应，最慢方向 = 全体耗时**。

两条缓解路线：

- **模型侧**：辅助损失/均衡约束（让路由别扎堆）、容量因子限流（每个专家设收件上限，超了就丢——通信均匀了，牺牲一点计算）；
- **通信侧**：等大小块 + padding（凑成通信库喜欢的规整形状）、多小块流水（压缩等待空泡——下一课的 chunk/channel 就是钥匙）。

::: details 小测 3：为什么说"同步性放大了失衡的伤害"？
集合通信是同步协议：所有 rank 的 A2A 要一起结束。任何方向慢了，全体都在等它——失衡不是"局部慢"，而是"全体被最慢方向拖死"。
:::

### 第 4 章 · 3 句话带走

1. **AG 复制拼全**（`[S/N]→[S]`）、**RS 规约分持**（`[S]→[S/N]`）——TP/SP/FSDP 的日常动词；
2. **A2A 是定向搬运不是复制**——总量守恒、按目的地重排，MoE 的骨架；
3. **MoE 之难在动态失衡**——同步集合通信木桶效应；模型侧调流量、通信侧抗失衡。

## 第 5 章｜拓扑、分层通信与通信计算重叠

完整正文 → [第 5 章｜拓扑、分层通信与通信计算重叠](05-topology-hierarchical-overlap.md)

> 适用：时间紧，或完整版跟不动时。这页用"物流网络"讲完整章，读完抓住 80% 的主干。任何一节想深入，拉到文末点对应单元。

### 1. 两层世界：同城骑手 vs 跨省干线

一家电商的配送网络：**同城**有海量骑手专线（快、便宜、随便跑）；**跨省**只有几家干线卡车（慢、贵、大家挤着用）。算力集群一模一样：

- **机内**（一台服务器 8 张卡之间）：HCCS/NVLink 专线，百 GB/s；
- **机间**（跨服务器）：网卡走交换网络，几十 GB/s——**差近一个量级**。

第 2 章的"环"只是**送货顺序**（逻辑编排）。如果排顺序时不看地图——送一票要在两省之间来回蹿——干线就全是冤枉流量。**排布必须贴着地图**：同城的 8 个站点连着送，跨省只送"汇总件"。

::: details 小测 1：为什么"逻辑环 ≠ 物理连线"会造成灾难？
环上相邻的 rank 若大多在不同机器，几乎每一跳都挤机间"共用公路"——每卡约 2S 字节过网；而按节点分段排布后，只有少数跳跨机，过网流量降到"每节点一份"。
:::

### 2. 分层：各城市先集货，干线只跑汇总件

8 个城市、每城 8 个仓库要统一库存。聪明的做法分三步：

```text
① 各城市内部先对账（同城骑手跑） → 每城得到一份汇总
② 8 个城市各派代表互相同步汇总（干线只运 8 份）
③ 代表回城广播给其余 7 仓（又是同城骑手）
```

数字感受一下（512 MB 梯度）：乱序直送约 40 ms 走干线；分层后干线只运"每城一份"、8 张网卡分担，约 **4.5 ms**——**快了一个量级**，原因只有一条：**贵链路少搬字节**。

两个细节：① 城市代表如果只有一张网卡，896 MB 串行过一张卡会把优势吃光——要**多张网卡分担**（第 3 节的伏笔）；② 干线上的 8 人小组怎么同步（环/树/配对）、城内怎么收发，可以**各自选型**——每层挑最合适的算法。

::: details 小测 2：分层的本质一句话是什么？
让贵链路少搬字节：机间流量从"每卡一份 2S"降到"每节点一份 2S"。拓扑感知排布的 flat ring 能达到同量级——分层只是它的显式形式，不是魔法咒语。
:::

### 3. 兑现三板斧：拆包裹、多卡车、边装边发

算法对了、路线贴了，实测带宽还是上不去？差距在**兑现率**：

- **Chunk（拆包裹）**：512 MB 一整包直运，装车、核对、卸货的间隙全是空泡；拆成 1 MB 小包流水发运——第 k 包在路上时第 k+1 包在装车。代价：包太小则"每包手续费"占比上升，有甜点区间。
- **Channel（多卡车）**：一条路一辆车跑再满也有限；多辆车各走一条路（多网卡、多 lane、多队列），吞吐 ≈ 单路 × 车数。代价：每辆车要独立装卸区和调度（缓冲与同步开销）。
- **重叠（边装边发）**：仓库这边还在打包后面的货，前面打好的包已经在路上——通信藏进计算。要三个条件：**车道分开**（网卡/通信引擎 vs 计算核心）、**货等得起**（数据就绪、后面计算不依赖没到的货）、**有人排班**（显式编排 + 同步点，如 FSDP 的分桶）。

有的货藏不住：**TP 每层的输出必须拼全才能算下一层**——通信卡在关键路径上。此时只剩两招：**压缩包裹**（量化，字节砍半）或**改流程**（TP→TP+SP，把一次大通信拆成前后向两半）。

::: details 小测 3：MoE 的 A2A 堵了，三板斧里先用哪个？
先看是"单路利用率"还是"总吞吐"问题：链路没打满 → 拆小流水（chunk）+ 多路并行（channel）压缩空泡；若通信量本身在关键路径 → 回到模型侧（均衡路由/限流）或压缩（量化）。三把钥匙常常一起拧。
:::

### 第 5 章 · 3 句话带走

1. **两层世界**：机内专线 vs 机间公路，差一个量级——rank 排布必须贴地图；
2. **分层 = 贵链路少搬字节**：先城内集货、干线只运汇总件，每层还能各自选算法；
3. **兑现三板斧**：拆包裹（chunk）铺流水、多卡车（channel）铺并行、边装边发（重叠）藏通信——藏不住的就压缩或改流程。
